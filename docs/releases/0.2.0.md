# tscache 0.2.0

The release of change events: a view can now follow its cache, in every tab,
instead of reading again on a timer or being told by the application.

```sh
npm install @anishbenji/tscache@~0.2.0
```

## Highlights

- **Change events.** `cacheChanged` reports, once per call that changed a
  cache, where a read's result may have changed. It carries ranges, never
  data: `written` lists what a put, a fetch or a hydrate wrote, the forming
  bar included; `removed` the coverage an `invalidate` or a watermark moved
  back withdrew; `cleared` a clear, a `clearAll` or a new dataset version;
  `requestId` the call that caused it. With a SharedWorker every listening
  tab hears every tab's change, the writer's own included, before the writing
  call resolves. Listen with `client.on('cacheChanged', fn)` for every cache
  or `cache.on('cacheChanged', fn)` for one; the first listener subscribes the
  client in the worker, so a page that does not listen costs the worker
  nothing
  ([Change events](https://anishbenji.github.io/tscache/concepts/events#change-events)).
- **A read rule that cannot loop.** After an event that wrote something, read
  the range you show again with `{ cacheOnly: true }`; after one that wrote
  nothing but cleared the cache or withdrew coverage over that range, read it
  with a fetching `get`; otherwise do nothing. No event a fetch caused starts
  a fetch, so two tabs following a live tail do not fetch forever
  ([Reading after an event](https://anishbenji.github.io/tscache/concepts/events#reading-after-an-event)).
- **`client.features`.** The worker's hello now lists the optional features it
  offers, exposed as `client.features`, a `ReadonlySet<WorkerFeature>`. A
  client facing a worker script from before change events (a stale cached
  script during a deploy) sees no `'cacheChanged'` there, its listeners are
  never called, and a development build warns once
  ([Hostings and older workers](https://anishbenji.github.io/tscache/concepts/events#hostings-and-older-workers)).
- **Integrations and reference clients.** The framework integrations in the
  repository's `integrations/` follow their cache from `cacheChanged`, with at
  most one read per animation frame, and the reference clients redraw from
  it in the SharedWorker hosting instead of from a `BroadcastChannel`
  message.
- **Deploy-skew guidance.** The guides now describe a deploy that changes only
  the fetcher: with Vite's hashed names the worker keeps its URL, so a new
  tab joins the old SharedWorker and `createClient` rejects with a
  `ConfigError` whose message starts with `this worker already runs fetcher`.
  A page of the current deploy can create its client again with
  `mode: 'dedicated'` until the old tabs close
  ([Stale scripts after a deploy](https://anishbenji.github.io/tscache/guides/workers#stale-scripts-after-a-deploy)).

## Compatibility

- The protocol stays at version 1: the new operations and the hello's
  `features` are additive, so an older page and a newer worker, or the
  reverse, still connect. A newer page on an older worker hears no change
  events.
- `TscacheClient` gains the readonly `features` member, `ClientEvents` and
  `CacheEvent` gain `cacheChanged`, and the type `WorkerFeature` is exported.
  Code that implements `TscacheClient` itself, such as a test double, must
  add `features`.
- `hydrate` now sends `cacheChanged` for the parts it applied and for the
  coverage its first watermark withdrew; it still sends no other event.

## Entries and sizes

Each entry bundled on its own with the chunks it loads, minified and
compressed with brotli, as measured by `bun scripts/size.ts` on the release
build. A row marked _lazy_ is code the entry loads with `import()` only on the
path that needs it: the page's fallback to a worker-less engine, and the
worker's persistence. The 0.1.0 column repeats that release's notes; since
then the measurement replaces the content hash in the name of a chunk an
entry leaves out with a constant, which moves a row by a few bytes at most.

| ↳ lazy: in-process hosting      | loaded only when neither worker hosting starts            | 12.16 kB | 12.72 kB |

| `@anishbenji/tscache/fetcher`   | the fetcher module: its types and `AuthInvalidError`      | 0.17 kB  | 0.17 kB  |
| `@anishbenji/tscache/engine`    | the engine without a worker, for Node and tests           | 9.86 kB  | 10.11 kB |

The package is still ESM-only with no runtime dependencies, and Vite 8 is
still an optional peer dependency, needed only for `@anishbenji/tscache/vite`.
A local `npm pack --dry-run` of this release reports a tarball of 27 files,
81.6 kB packed and 271.4 kB unpacked; npm counts 1,000 bytes to the kB, while
the table above counts 1,024.

## Known limits

The limits of 0.2.0 that an application has to design around, each with its
workaround in the guides:

- **Memory is still neither bounded nor reported.** A cache keeps everything
  it was asked for until its worker ends
  ([Memory](https://anishbenji.github.io/tscache/guides/patterns#memory)). A
  memory budget is proposed but not built.
- **A deploy can still leave tabs on two versions.** Old and new tabs may run
  separate SharedWorkers, or `createClient` may reject with
  `ProtocolMismatchError` or `ConfigError` until the old tabs close
  ([Stale scripts after a deploy](https://anishbenji.github.io/tscache/guides/workers#stale-scripts-after-a-deploy)).
  A recovery path is proposed but not built.
- **Change events reach other tabs only through a SharedWorker.** With a
  dedicated worker or in-process, each tab has a cache of its own and hears
  only its own changes; another tab's data must still be sent to it
  ([Redrawing when the cache changes](https://anishbenji.github.io/tscache/guides/live-feeds#redrawing-when-the-cache-changes)).
- **Other tabs may show misses after a new dataset version.** After a fetch
  brings a new version, other tabs show misses outside the range that fetch
  wrote until their next ordinary read: the price of a read rule that cannot
  loop.

## Stability

tscache follows semantic versioning within 0.x: a minor release may break the
API, a patch release never does. Pin a minor range (`~0.2.0`) to take fixes
without breaking changes.
