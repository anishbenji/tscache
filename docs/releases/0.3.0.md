# tscache 0.3.0 (in preparation)

Not released yet: these notes collect what the next release adds, step by
step, until it is cut.

```sh
npm install @anishbenji/tscache@~0.3.0
```

## Highlights

- **Memory budgets.** `createClient({ memoryBudget })` and
  `new Engine({ memoryBudget })` bound, in bytes, what a worker's caches hold:
  in a SharedWorker every tab's caches together. Above the budget the worker
  evicts the least recently used pages of any cache, with their coverage, so
  a later read fetches an evicted range again and never mistakes it for a
  confirmed gap. Reads and writes in any tab keep a page recent; the pages a
  pending `get` is reading and those holding a provisional bar are never
  evicted, so the budget may be exceeded while they are held. Without a
  budget nothing changes: nothing is counted or evicted
  ([Memory](https://anishbenji.github.io/tscache/guides/patterns#memory)).
- **`memoryStats()`.** `client.memoryStats()` and `engine.memoryStats()`
  report the budget in force, the bytes the cached points hold, the pinned
  part, the pages evicted so far and one row per cache.
- **Eviction in change events.** `cacheChanged` gains an optional `evicted`
  list: coverage the budget evicted, which a view does not need to read again.
  With a budget, a later `invalidate` or watermark moved back over an evicted
  range still lists it in `removed`, so a view showing it hears the change
  ([Change events](https://anishbenji.github.io/tscache/concepts/events#change-events)).
- **Persistence follows memory.** With a budget, an evicted page's record is
  deleted at the next write-behind flush, so the disk and the next session's
  load stay within what the budget let the worker hold; an evicted range is
  fetched again in the next session too.
- **Deploys no longer collide.** The SharedWorker is named by its generation:
  the tscache version and the fetcher module URL. A deploy that changes
  either, or the worker bundle, starts a worker of its own, where 0.2.0
  refused every new tab with `ConfigError` after a fetcher-only deploy, or ran
  new tabs against the old worker's code at a fixed worker URL. Tabs that
  agree on all three share one worker, as before
  ([Stale scripts after a deploy](https://anishbenji.github.io/tscache/guides/workers#stale-scripts-after-a-deploy)).
- **`superseded`.** The SharedWorkers of an origin find each other. Of two
  generations the lower-ranked one (the lower tscache version, else the one
  that started earlier) stops persisting, so the database has one writer
  again, and its tabs hear a `superseded` event; `client.superseded` holds
  its payload for code that runs later. Each persisted cache reports
  `persistStopped` with the new reason `'superseded'`, and nothing is deleted.
  The tab keeps working from memory and its fetcher; a reload joins the newer
  worker. The library never reloads a page.
- **`clearAll` reaches every worker.** A logout's `clearAll`, from a client of
  any hosting, is relayed to every SharedWorker of the origin: each clears its
  memory and the disk, so an older deploy's worker no longer writes the data
  back.
- **`ConfigError.code`.** The refusal of a second fetcher module carries
  `code: 'fetcher-conflict'` (type `ConfigErrorCode`); recognise it by the
  code, not by its message, which is unchanged.

## Compatibility

- The protocol stays at version 1: the `memoryBudget` and `memoryStats` ops
  are additive, and the worker lists `'memoryBudget'` in its hello's
  `features` (architecture N101). A client facing a worker script from before
  them sends no budget, warns once in a development build, and its
  `memoryStats()` rejects with `TscacheError`.
- In a SharedWorker the first budget the worker receives holds until it
  restarts, and a budget that reaches a worker already holding a cache is not
  applied (N88, N103); a development build warns in both cases.
- `TscacheClient` gains `memoryStats()`, `ClientOptions` gains `memoryBudget`,
  `WorkerFeature` gains `'memoryBudget'`, and `cacheChanged` gains the optional
  `evicted`. Code that implements `TscacheClient` itself, such as a test
  double, must add `memoryStats`. `./engine` exports `EngineOptions` and both
  entries export `MemoryStats`.
- The deploy-skew changes keep the protocol at version 1 too: the port
  carries one more client-scoped event name, one more name in the hello's
  `features` (`'superseded'`), one more `persistStopped` reason and the
  refusal's `code`; an older client or worker ignores each (architecture
  §3.2).
- `TscacheClient` gains the `superseded` property, `ClientEvents` gains
  `superseded`, `WorkerFeature` gains `'superseded'`, `ConfigError` gains the
  optional `code`, and both entries export `ConfigErrorCode`. Code that
  implements `TscacheClient` itself must add `superseded`. `persistStopped`'s
  `reason` gains `'superseded'`: an exhaustive `switch` over the reason stops
  compiling until it handles it.
- Behaviour that changes with named workers: a page without a fetcher no
  longer shares the worker of pages that pass one, and pages that name one
  fetcher module by two different strings get a worker each; pass the same
  `fetcher.module` on every page. A fetcher served under a fixed name needs a
  URL that changes with its contents (a query or a versioned path), or a
  running worker keeps the module it loaded.
- The first upgrade from 0.2.0 behaves as 0.2.0 did: a 0.2.0 worker has no
  name and does not listen, so a newer tab runs a worker beside it, the old
  worker keeps writing the database until its tabs close, a `clearAll` does
  not reach it, and its tabs are told nothing.
- A `clearAll` is now heard in the tabs of every SharedWorker of the origin,
  as `cacheCleared` and, where subscribed, `cacheChanged` without a
  `requestId`, possibly more than once for one call.
- Brotli sizes grow: `index` 5.00 to 5.77 kB, the in-process hosting 12.72 to
  14.77 kB, `worker` 13.98 to 17.00 kB, `engine` 10.11 to 11.58 kB (memory
  budgets took them to 5.31, 14.25, 15.50 and 11.57 kB).

## Known limits

- The budget counts the bytes the cached points' arrays have allocated, not
  the worker's whole footprint: object overhead and transient copies (a read's
  result on its way to the page, a load's records while they are applied) are
  not counted.
- Evicted history is fetched again from the backend rather than reloaded from
  the disk; loading evicted pages from IndexedDB on demand needs lazy loading,
  a later design step.
- A tab of an older deploy without the option that opened a cache first keeps
  the SharedWorker unbudgeted until it restarts (finding M5).
- Pages that hold coverage but no bar (confirmed gaps) are not counted and
  never evicted.
- A fetcher whose contents change behind an unchanged URL is not seen as a
  new generation: new tabs join the running worker, which keeps the module it
  loaded.
- A dedicated worker and an in-process client are never superseded and never
  told of a newer deploy.
- A stale worker script (an old HTTP cache entry) still rejects `createClient`
  with `ProtocolMismatchError`; reload with the cache revalidated.
- A `clearAll` that fails, or reaches its five-second deadline, leaves the
  records it could not delete, which a worker started later can load, as
  before.
