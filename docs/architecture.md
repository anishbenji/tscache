# tscache — Consolidated Architecture

Status: **draft for review** (starter-prompt §12 deliverable). All decisions from the starter's §3 Decision Register are locked and reflected here unchanged. Section 7 records the resolved open decisions; section 8 registers the _new_ decision points that surfaced while concretizing the API — all resolved with the user on 2026-06-11.

---

## 1. Overview

`tscache` caches timestamp-aligned time-series data in the browser. One engine class runs in a SharedWorker, a dedicated Worker, or in-process (fallback chain, pinnable). Coverage (what is _known_) is tracked separately from data (what _exists_), so confirmed real gaps are first-class. The worker orchestrates fetches via a consumer-supplied fetcher module, deduplicating in-flight requests across tabs.

```
┌─ tab A ─────────┐  ┌─ tab B ─────────┐
│ client (RPC)    │  │ client (RPC)    │
└───────┬─────────┘  └────────┬────────┘
        └────── MessagePort ──┘
        ┌───────────▼────────────┐
        │ SharedWorker           │
        │  rpc server            │
        │  orchestrator ── fetcher (dynamic import)
        │  engine                │
        │   ├ coverage index     │
        │   └ segments (dense)   │
        └────────────────────────┘
```

Out of scope for v1 (roadmap): aggregation/resampling, ColumnarSegment, subscriptions, eviction, SharedArrayBuffer, per-field presence masks, irregular timestamps, elected auth handler, Node `worker_threads`. IndexedDB persistence, once on that list, is specified in §4.10 (step 38).

## 2. Public API surface

All types below are exact proposals; names and shapes are the review surface.

### 2.1 Client creation and fallback chain

```ts
type HostingMode = "shared" | "dedicated" | "in-process";

interface ClientOptions {
  /**
   * Worker script URL as your setup serves the `@anishbenji/tscache/worker` entry
   * (docs/guides/worker-setup.md: Vite `?worker&url`; webpack and
   * no-bundler setups serve a copy of the whole dist/ directory, since a
   * bare `new URL()` would emit the entry without its chunks). Omit only
   * when pinning 'in-process'.
   */
  workerUrl?: string | URL;
  /**
   * Pin the starting hosting mode; fallback continues down-chain from
   * the pin (shared → dedicated → in-process). Default: 'shared'.
   */
  mode?: HostingMode;
  /**
   * How long a hosting may take to say hello before the chain steps down
   * (N25). Default 5000 ms. The timeout bounds only the wait for hello:
   * what the worker does after hello, such as loading the `fetcher` module,
   * is not bounded by it. A fetcher module that fails to load rejects
   * `createClient` with a `TscacheError` (`init-err`) instead of falling
   * back. A protocol mismatch never falls back either.
   */
  handshakeTimeoutMs?: number;
  /** Worker-side fetch orchestration (§2.5). Omit for pure pull-model use. */
  fetcher?: {
    /** Module specifier/URL the worker will dynamic-import(). */
    module: string | URL;
    /** Structured-cloneable config/auth material passed to the fetcher. */
    context?: unknown;
  };
}

/** Resolves after transport is established and the protocol handshake passed. */
declare function createClient(options?: ClientOptions): Promise<TscacheClient>;

interface TscacheClient {
  /**
   * Get-or-create. Identical config returns the existing cache (multi-tab:
   * every tab calls this with the same values). Structural mismatch with the
   * live config (interval/fields/offset/...) rejects with ConfigError (N4).
   */
  cache(config: CacheConfig): Promise<CacheHandle>;
  /** Which hosting mode actually won the fallback chain. */
  readonly mode: HostingMode;
  clearAll(): Promise<void>;
  /** Deliver new auth material to the fetcher; the next get fetches again
      (nothing is paused or retried, §4.9). */
  updateAuth(context: unknown): Promise<void>;
  on<E extends keyof ClientEvents>(
    event: E,
    fn: (e: ClientEvents[E]) => void,
  ): () => void;
  off<E extends keyof ClientEvents>(
    event: E,
    fn: (e: ClientEvents[E]) => void,
  ): void;
  /** Release the port / terminate owned worker. Idempotent. */
  dispose(): Promise<void>;
}
```

The in-process engine has zero DOM/worker imports at module top level (lazy construction), so `'in-process'` is SSR/Node-safe and is the mode used by the SSR examples. The `'.'` entry loads the in-process hosting, with the engine, by `import()` only when the chain reaches it or the client is pinned to it, so a page served by a worker never downloads the engine; `createClient` resolves after that load and the handshake, as before.

### 2.2 Cache configuration

```ts
type Dtype = "f64" | "f32" | "i32" | "u32" | "i16" | "u16" | "i8" | "u8"; // N7: final for v1

interface CacheConfig {
  id: string;
  /** Interval in ms. REQUIRED — no default (resolved decision #2). */
  interval: number;
  /** Timestamps satisfy (t - alignmentOffset) % interval === 0. Default 0. */
  alignmentOffset?: number;
  /** Field name → dtype. Every field names its dtype; 'f64' is the usual choice. */
  fields: Record<string, Dtype>;
  /** Dense segment splits where more than K consecutive slots hold no point
   *  (N14). Default 4. */
  gapSplitK?: number;
  /** Max slots per segment. Default 32_768; at most 2^31 − 1 (N12). */
  segmentSlotCap?: number;
  /** Opt-in dataset version; mismatch on put → auto-clear + cacheCleared event. */
  version?: string;
  /** Initial finalized-watermark; points at t >= watermark are provisional. */
  finalizedUntil?: number;
  /** Opt-in differs-on-overlap warning (O(overlap) cost). Default false. */
  warnOnOverlapDiff?: boolean;
  /** Keep the cache in IndexedDB across sessions; structural (N20). Default
   *  false. Acts in the SharedWorker hosting only (N52); elsewhere a no-op.
   *  Additive (§4.10.1, N45). */
  persist?: boolean;
}
```

Timestamps are Float64 ms epoch, exact integers to 2^53, aligned to `interval` (modulo `alignmentOffset`). Presence is point-level (1 bit per point); `NaN` is a legal field value; integer fields cannot represent per-field missingness (documented limitation; the self-describing payload format leaves room for per-field masks later).

### 2.3 Read path

```ts
/**
 * Inclusive on BOTH ends (N1) — matches charting-library visible ranges
 * (Lightweight Charts setVisibleRange from/to, uPlot setScale min/max), so
 * chart.getVisibleRange() feeds get() directly. get/invalidate accept
 * arbitrary ms values and snap OUTWARD to the alignment grid (floor(start),
 * ceil(end)); put timestamps must be exactly aligned (locked). Internally
 * all range math runs on integer slot indices ((t - offset) / interval) —
 * the ms↔slot conversion is the single place fencepost logic lives.
 */
interface Range { start: number; end: number }

type MissReason = 'uncached' | 'fetch-failed' | 'auth-pending';

interface Miss {
  range: Range;
  reason: MissReason;
  /** Present for 'fetch-failed': structured-cloneable error detail. */
  error?: { name: string; message: string };
}

interface GetResult {
  /** Present points only — equal lengths, no holes, no mask. */
  timestamps: Float64Array;
  fields: Record<string, Float64Array | Float32Array | Int32Array | Uint32Array
                        | Int16Array | Uint16Array | Int8Array | Uint8Array>;
  /** Authoritative sub-ranges of the request. Absence of points inside = real gap. */
  coverage: Range[];
  /** Always present (possibly empty) — cannot be overlooked. */
  misses: Miss[];
  /** Present when `GetOptions.snapshot` was set (§2.8). */
  snapshot?: Snapshot;
}

interface GetOptions {
  /** Skip orchestration, return current cache state immediately. Default false (N2). */
  cacheOnly?: boolean;
  /** Also return a snapshot of the request, from the same read (§2.8, N36). Default false. */
  snapshot?: boolean;
}

// CacheHandle
get(range: Range, options?: GetOptions): Promise<GetResult>;
```

**Partial-result policy (locked):** `get` never rejects for data-availability reasons. With a fetcher configured, `get` awaits the (deduplicated) fetches for its miss ranges and returns the merged result; fetch failures and auth-pending ranges degrade to misses with reasons. Rejection is reserved for programmer errors (invalid range, unknown cache, disposed client). Auth-pending never blocks: affected ranges come back promptly as misses (design "y"), and the consumer re-`get`s after `updateAuth`.

Returned typed arrays are copies — never views into cache-owned memory.

### 2.4 Write path and invalidation

```ts
interface PutBatch {
  /** Sorted ascending, aligned, no duplicates — else the whole batch is rejected. */
  timestamps: Float64Array | number[];
  fields: Record<string, ArrayBufferView | number[]>;
  meta?: {
    /** Dataset version; mismatch with stored version → auto-clear + event. */
    version?: string;
    /** Advance the finalized watermark. */
    finalizedUntil?: number;
  };
}

interface PutOptions {
  /**
   * The range this data is authoritative for. Must contain all batch
   * timestamps (else PutError 'range-mismatch'). Coverage is recorded for
   * the whole range minus the volatile region — flanks without points become
   * CONFIRMED real gaps, never re-fetched; only invalidate() undoes a wrong
   * claim. Default: the batch's own span [t₀, tₙ] — safe for streaming
   * appends, claims nothing the points don't prove (N3). The orchestrated
   * path always passes the fetch's requested range automatically. A range
   * that is not on the grid snaps INWARD: it covers the grid points inside it
   * and no others (N13).
   */
  range?: Range;
}

interface MergeWarning { range: Range; fields: string[] }

interface PutResult {
  /** Non-empty only when warnOnOverlapDiff is on and overlapping values differed. */
  warnings: MergeWarning[];
}

// CacheHandle
put(batch: PutBatch, options?: PutOptions): Promise<PutResult>;
invalidate(range: Range): Promise<void>;   // coverage subtraction
clear(): Promise<void>;                    // NOTE: SharedWorker mode — affects ALL tabs
setFinalizedUntil(t: number): Promise<void>;
```

**Atomic reject (locked):** misaligned, unsorted, or duplicate timestamps reject the entire batch with a descriptive error naming the first offender and the expected alignment (`PutError`, §2.6). Merge policy is new-data-wins; the volatile region (`t >= finalizedUntil`) is excluded from coverage authority, so the live tail is always re-fetched and merged new-wins.

**Field values (N68).** Every field value of a batch, from `put` and from every fetcher response alike (they share the path), must be a value its field can hold; otherwise the whole batch is rejected, atomically, with `PutError` `'field-mismatch'` naming the first offender (its field, index, timestamp and value, and what was expected). A value that is not of type `number` is never accepted and never coerced: `null`, `undefined`, a hole in a sparse array, a string, a boolean, a bigint or an object rejects the batch. A float field (`f64`, `f32`) accepts every number, `NaN`, `Infinity` and `-Infinity` included: `NaN` stays the way to mark a missing value in a present point. An integer field accepts only an integer inside its dtype's range, stored as given (`-0` and an integral float such as `2.0` included); a fraction (`1.5` for an `i32` field, decision 38), `NaN`, `±Infinity` and an out-of-range value (`300` for a `u8` field, `-1` for a `u32` field) reject the batch. A typed array of the field's own dtype is accepted as it is. The rules and their order are in §4.3.

**What a put removes (N11):** a write that states its range — every orchestrated fetch, and a `put` with `options.range` — replaces that range: afterwards the points inside it are exactly the batch's, so a point the backend no longer returns disappears. A `put` without `range` only adds or overwrites the points it carries and never removes one.

**Restatements without a version signal are undetectable.** If the backend revises a point that the cache already holds as covered and reports no `version` change, no library mechanism can notice: the cache keeps returning the old value until the consumer calls `invalidate` over the range or `clear`. The `version` machinery only helps when the backend reports a version. (Documentation debt from starter §8, committed.)

TTL is deliberately not in core: call `invalidate`/`clear` on your own clock (a documented consumer pattern).

### 2.5 Fetcher module contract

The consumer provides a self-contained ES module (no closure over main-thread state); the worker `import()`s it. Config/auth arrives only via structured-cloneable `context`. The fetcher module must load or fail: an `import()` that never settles (a module server that accepts the request and never answers, a top-level `await` that never resolves) leaves `createClient` pending, and no timeout bounds it in 0.1.0 (user decision 2026-11-10, decision 25).

```ts
// What the fetcher module must export (default export):
interface Fetcher {
  fetch(req: FetchRequest): Promise<FetchResponse>;
  /** Optional: observe auth updates (e.g. swap a token held in module state). */
  updateAuth?(context: unknown): void | Promise<void>;
}

interface FetchRequest {
  cacheId: string;
  range: Range; // already miss-coalesced (flank-extended by one interval)
  interval: number;
  alignmentOffset: number;
  context: unknown; // latest auth/config material
}

interface FetchResponse {
  timestamps: Float64Array | number[];
  fields: Record<string, ArrayBufferView | number[]>;
  meta?: { version?: string; finalizedUntil?: number };
}

/**
 * Distinguished auth-failure signal: THROW it from fetch() (N8). Exported
 * from the '@anishbenji/tscache/fetcher' subpath (N6) — a ~20-line module (this class +
 * the types above, zero other imports) so fetcher bundles stay lean and pull
 * no DOM-touching client code into the worker. Detection in the orchestrator
 * is marker-based (error.code === 'tscache:auth-invalid'), NOT instanceof:
 * fetcher and worker are separate bundles and may each hold their own copy
 * of the class.
 */
declare class AuthInvalidError extends Error {
  readonly code: "tscache:auth-invalid";
}
```

Worker-side orchestration (locked behaviors): in-flight dedup in the worker — one fetch serves all tabs, and a `get` whose misses overlap fetches already in flight for the cache awaits them for the overlap and fetches only the rest (§4.9.1, N31; until step 44 the dedup was keyed per `(cacheId, range)`, so only identical ranges shared a fetch); miss coalescing extends computed miss ranges by one interval on flanks abutting existing coverage; an `AuthInvalidError` flips the auth state, broadcasts `authInvalid` to all tabs (design "b"), and while auth is invalid no fetch is issued (the misses come back `'auth-pending'` at once, design "y"); `updateAuth(context)` from any tab delivers new material and restores auth, and the next `get` fetches again. Nothing is paused or retried on behalf of a `get` that already returned (§4.9, step ⑪). The examples ship a copy-pasteable Web Locks snippet for refresh-token rotation safety.

Cookie-based auth needs none of this machinery — cookies flow in worker fetches natively.

**What a fetcher must deliver (consequences of N11, N17, N19; documentation debt from step ⑤, committed here).** A response is authoritative for the whole requested range: every point the backend has in `[range.start, range.end]` must be in it, so a fetcher against a paginated API loops until it has all pages before returning; a partial response would record the missing points as confirmed gaps that are never refetched. A backend that publishes late or revises recent points must report `meta.finalizedUntil` (the first timestamp that is not yet final): points at or after it are stored but stay provisional and are refetched, and the response is authoritative only below it. A backend that restates history without reporting a `version` cannot be detected (§2.4); report `meta.version` when the dataset has one. Throw `AuthInvalidError` for an authentication failure (N8); any other thrown error marks the range `'fetch-failed'` for every `get` that awaited that fetch (§4.9.1 rule 7, built at step 44) and is retried by the next `get` that needs it. A fetcher must not close its worker (`self.close()`): a dedicated worker that closes itself fires no `error`, so the calls of its tab hang (N44). A fetcher should bound how long a request may take (for example with `AbortSignal.timeout()` on its `fetch`) and throw when the bound passes: the orchestrator never cancels a fetch, and a fetch that never settles holds every `get` that needs one of its slots, from every tab (§4.9.1, N65). The thrown error is an ordinary failure, `'fetch-failed'` for those gets.

### 2.7 Events — three scopes (N5)

One wire channel, three scopes. Subscribe via `client.on(...)` (hears everything of that type) or `cache.on(...)` (cacheId-filtered sugar for cache/request-scoped events).

```ts
/** '<clientId>:<seq>' — clientId is per-connection, so ids are unique across
    tabs; tab B can trace which tab/request originated a broadcast event. */
type RequestId = string;

interface ClientEvents {
  // ── client-scoped ──
  /** Fetcher signaled auth failure. Broadcast to ALL tabs (design "b").
      `context` is the fetcher context the refused fetch was issued with
      (N33), so a tab refreshes only when its credential is the refused one. */
  authInvalid: { error: { name: string; message: string }; context: unknown };
  /** Fallback chain stepped down (e.g. no SharedWorker in Samsung Internet,
      or in Chrome for Android before 148). */
  modeFallback: { from: HostingMode; to: HostingMode; reason: string };
  /** The worker behind this client is gone (N32). Every pending and later
      call rejects with TscacheError; create a new client to go on (it starts
      a new worker). At most once per client; never after dispose(). */
  workerLost: { reason: string };

  // ── cache-scoped ──
  /** Cache was cleared. In SharedWorker mode one tab's clear affects all tabs. */
  cacheCleared: {
    cacheId: string;
    reason: "manual" | "clear-all" | "version-mismatch";
  };
  /** Persistence of the cache stopped; it goes on in memory. Additive
      (§4.10.1, N47). */
  persistStopped: {
    cacheId: string;
    reason: "quota-exceeded" | "unavailable" | "error";
    error?: { name: string; message: string };
  };

  // ── request-scoped (carries originating request's id) ──
  /** Opt-in (warnOnOverlapDiff): overlapping put differed outside volatile region.
      Also console.warn in dev builds (resolved decision #8), by the
      requesting tab only (below). */
  mergeWarning: {
    cacheId: string;
    requestId: RequestId;
    range: Range;
    fields: string[];
  };
}
```

The initiating call additionally receives request-scoped results directly — `put()` resolves with its own `warnings` (§2.4) — so the common case needs no event wiring; the event channel serves telemetry and cross-tab observability.

**Where the development warning prints (decision #8, clarified at fix 35).** In the page that made the write, so it appears once, in the console of the tab that caused it. A client's `put()` prints its result's warnings in one `console.warn` naming the cache and every range with its fields. A client whose `get` started an orchestrated fetch prints that fetch's warnings from the request-scoped events carrying its own request ids, one line per warned range, since a `get` result carries no warnings. Other tabs hear the events and print nothing, the worker never prints, and an `Engine` called directly (server rendering, tests) only returns the warnings. A development build is one where `process.env.NODE_ENV` is not `'production'`, as the application's bundler replaces it (Vite, webpack, Bun); the package's own build leaves the expression in place for that. A page that no bundler prepared, where `process` does not exist, counts as production. Roadmap events slot into existing scopes: dirty-notifications → cache-scoped, fetch lifecycle → request-scoped.

`modeFallback` is an addition beyond the starter's event list — observability for the documented Chrome-Android path (accepted under N5). `workerLost` is another such addition (N32).

### 2.8 Snapshots (N34–N39, approved 2026-10-23)

A snapshot is what a cache knows about a range: the §3.4 payloads of its present points, clipped to the range, in an envelope that names the grid and schema they belong to, the dataset version and watermark in force, and the covered sub-ranges. It is the server-rendering hydration payload the one-format invariant promised (starter §3.7) and the cache record of the persistence sketch (`docs/roadmap.md`). It is applied in one engine call, so a seed can neither outlive a restatement nor overwrite what another tab fetched (step ⑭ R2-2).

```ts
/** What a cache knows about a range (N34): §3.4 payloads in an envelope. */
interface Snapshot {
  /** The envelope's schema version; each payload carries its own `format`. */
  format: 1;
  /** The grid and schema of the cache it was taken from; hydrate refuses any other. */
  interval: number;
  alignmentOffset: number;
  fields: Record<string, Dtype>;
  /** The request it answers, snapped outward (N1), in ms. */
  range: Range;
  /** The dataset version in force when it was taken, if any. */
  version?: string;
  /** The finalized watermark in force when it was taken, if any. */
  finalizedUntil?: number;
  /** Authoritative sub-ranges of `range`, ascending; equals GetResult.coverage. */
  coverage: Range[];
  /**
   * The present points inside `range`, covered or not (N16): one payload per
   * segment of the cache with a point inside the range, holding exactly those
   * points; ascending and disjoint; fresh buffers.
   */
  segments: DenseSegmentPayload[];
}

interface GetOptions {
  cacheOnly?: boolean;                 // §2.3
  /** Also return `snapshot`, from the same state as the result (N36). Default false. */
  snapshot?: boolean;
}

interface GetResult {
  // …as §2.3, plus:
  /** Present when `GetOptions.snapshot` was set. */
  snapshot?: Snapshot;
}

interface HydrateResult {
  /** The ranges written, in ms, ascending and disjoint: the snapshot's coverage
   *  minus what the cache already covered or holds as provisional. */
  applied: Range[];
  /** Set when nothing was applied because the two versions differ. */
  skipped?: 'version-mismatch';
}

// CacheHandle
hydrate(snapshot: Snapshot): Promise<HydrateResult>;

/** A Snapshot with its binary parts as base64 text: a plain JSON value (N38). */
interface EncodedSnapshot extends Omit<Snapshot, 'segments'> {
  segments: EncodedSegmentPayload[];
}
interface EncodedSegmentPayload extends Omit<DenseSegmentPayload, 'mask' | 'fields'> {
  mask: string;
  fields: { name: string; dtype: Dtype; data: string }[];
}
// Exported from '.' and './engine'; no DOM, no engine code.
function encodeSnapshot(snapshot: Snapshot): EncodedSnapshot;
function decodeSnapshot(encoded: EncodedSnapshot): Snapshot;
```

**Taking a snapshot.** `get(range, { snapshot: true })` resolves with the result and its `snapshot`, both from the one engine read whose result the call returns (§4.9): with a fetcher, the read after the fetches the call awaited; with `cacheOnly` or without a fetcher, the only read. They cannot disagree: `snapshot.coverage` equals `result.coverage`, and the payloads hold the result's points. The buffers are fresh copies, never cache-owned memory (§3.3), and are transferred to the page. Equal cache state yields equal snapshots (the layout rule N15 and the tight extent of §4.2), so a snapshot can be compared and stored. `Engine.snapshot(cacheId, range)` gives the same snapshot without a read, for persistence and tests.

**Applying a snapshot: `hydrate`.** One engine call, and between two messages no other write runs (§4.7), so another tab's fetch cannot land between the check and the write. Its rules:

- _Checked first, in full._ The envelope must describe this cache: `format` 1, `interval` and `alignmentOffset` equal to the grid, `fields` the schema's names and dtypes (key order irrelevant); then every range and every payload (by the §4.2 decoding rules). Any failure throws `TscacheError` before anything changes, as an invalid payload does (N10); an unknown cache throws `UnknownCacheError`. A snapshot with no segment, a confirmed gap, is therefore checked too (step ⑭ R6-1). A snapshot that carries a `finalizedUntil` must keep its coverage below it (N69): coverage of a slot at or after the snapshot's own watermark, which the snapshot itself calls provisional, is a malformation and throws like the others, while its points there, outside its coverage, stay legal. Taking a snapshot never produces one, since a cache never covers a volatile slot (§4.5). A malformed snapshot is rejected, never snapped or repaired: snapshots are made by the library, so a malformation is corruption.
- _Version precondition._ When the snapshot and the cache both have a version and they differ, nothing is applied, not even the watermark, and the result is `{ applied: [], skipped: 'version-mismatch' }`. A versioned `put` clears and adopts (§2.4); a seed never does, since a stale page would wipe a newer cache. A cache without a version adopts the snapshot's without clearing, as N18 does for the first versioned put; a snapshot without a version leaves the cache's alone.
- _Watermark._ The snapshot's `finalizedUntil` advances the cache's watermark as a put's `meta.finalizedUntil` does: forwards only (N17), never back.
- _Fill only where nothing is known._ The parts written are each covered range of the snapshot minus the slots the cache already covers and minus the cache's volatile region (after the advance). Inside a part the points end up exactly the snapshot's (a replace, N11: what was there had been invalidated or was provisional, never authoritative), and the part is recorded as coverage. Covered slots are never touched, so a later fetch by another tab survives; volatile slots are never touched, so a seed neither covers nor replaces a slot the browser calls provisional; and the snapshot's own provisional tail, its points outside its coverage, is not applied: the browser fetches it, as its first live `get` does anyway.
- _No events, no warnings._ `hydrate` never clears, so it emits no `cacheCleared`; it reports no `mergeWarning`, since the points it replaces were never authoritative and may differ.
- _Result._ `applied` lists the parts written, in ms: empty when the cache already covered everything, or when the snapshot covered nothing.
- _Ownership._ The snapshot is cloned to the worker, not transferred: it stays usable, so a page can hydrate a replacement client from the same object. A `get` result's snapshot is transferred the other way, as the result's arrays are: the page owns it.

**Old workers (N37).** The op is additive and `PROTOCOL_VERSION` stays 1. A worker from before it (a stale cached script, §3.1) answers `unknown op`, so `hydrate` rejects with `TscacheError` and the cache is as it was; a `get` with `snapshot: true` from such a worker returns no `snapshot`. An app treats a failed `hydrate` as "not seeded" and lets the cache fetch: hydration is an optimisation, never a requirement for correctness.

**Encoding for HTML (N38).** A snapshot holds `ArrayBuffer`s and a `Uint8Array`; a page carries text. `encodeSnapshot` returns the snapshot with each payload's mask and field data as base64 strings: a plain JSON value the app serialises with `JSON.stringify` next to its own data (the columns it renders, say), and `decodeSnapshot` restores it. The byte form survives what JSON loses: `NaN`, a legal field value, becomes `null` in JSON. `decodeSnapshot` checks the shape only: an object with the envelope's fields of the right JavaScript types (`format` 1, numbers, strings, arrays, `fields` an object of strings, and in each payload a `mask` and every `data` as a base64 string that `atob` accepts), and throws `TscacheError` for anything else, leaving its input unchanged. It restores the buffers and checks nothing more: lengths, ordering, alignment and the schema are `hydrate`'s to check against the cache. Escaping for a `<script>` element (every `<` as `<`) stays with the app, since it depends on how the page is built. Both functions use the native `Uint8Array.prototype.toBase64` and `Uint8Array.fromBase64` where the runtime has both (detected once, at load) and `btoa`/`atob`, which browsers and Node provide, otherwise; the text is the same either way, and `fromBase64` accepts what `atob` accepts. Neither uses the DOM. Persistence needs neither: IndexedDB stores the buffers.

**Server rendering.** The server reads with an in-process client, `get(range, { snapshot: true })`. The page carries two forms of the answer: the result's columns, so the server's render and the browser's hydration render agree before any client exists, and the encoded snapshot, for the cache. The browser decodes the snapshot and calls `hydrate` before its first live read; that read then fetches only what the snapshot did not cover, typically the provisional tail. A page's snapshot is as old as the page. With a versioned dataset a stale snapshot is refused; a cache created without a version adopts the snapshot's, and the first response reporting a newer version clears it and is applied, with fetches then in flight re-issued once (N29). Without a version a seed is no staler than the server's render was. The helpers of the examples and integrations (`putSeeds`, `putCovered` and their encodings) are replaced by this API in the step that adds it (N39). A public reader that derives `GetResult` columns from a snapshot can be added later without changing the format (N38).

## 3. RPC protocol

### 3.1 Handshake (locked)

On connect, the worker immediately reports its protocol version; the client refuses on mismatch with `ProtocolMismatchError`. Protects against package skew and stale cached worker scripts.

```ts
const PROTOCOL_VERSION = 1;

// worker → client, unprompted on connect. clientId is assigned by the
// worker per connection (N23) and prefixes the client's request ids (§2.7).
// lock names the Web Lock a SharedWorker holds for its lifetime (N32);
// absent where there is none:
{ t: 'hello', protocol: 1, lib: '0.1.0', clientId: 'c1', lock?: 'tscache-worker:<uuid>' }
// client → worker (also carries fetcher config so the worker can import it):
{ t: 'init', protocol: 1, fetcher?: { module: string, context?: unknown } }
// worker → client:
{ t: 'init-ok' } | { t: 'init-err', error: WireError }
```

### 3.2 Message envelopes

```ts
type WireError = { name: string; message: string; code?: string; data?: unknown };

// request/response (client → worker → client), id correlates; the wire id is
// the <seq> half of the public RequestId ('<clientId>:<seq>', §2.7):
{ t: 'req', id: number, op: Op, params: unknown }
{ t: 'res', id: number, ok: true,  result: unknown }
{ t: 'res', id: number, ok: false, error: WireError }

// broadcast (worker → every connected port), scope-discriminated (N5):
{ t: 'evt', scope: 'client',  event: string, payload: unknown }
{ t: 'evt', scope: 'cache',   cacheId: string, event: string, payload: unknown }
{ t: 'evt', scope: 'request', cacheId: string, requestId: string, event: string, payload: unknown }

// controlled detach (worker → one port): the server is dropping this port,
// so the client treats it as closure, during the handshake or after (step ⑨ R5-1;
// a browser MessagePort fires no close event)
{ t: 'bye' }

type Op = 'cache' | 'get' | 'put' | 'invalidate' | 'clear' | 'clearAll'
        | 'setFinalizedUntil' | 'updateAuth' | 'dispose'
        | 'hydrate';   // §2.8 (N36); additive, so the protocol stays 1 (N37)
```

SharedWorker: one RPC server, N ports; `evt` fans out to all ports. Dedicated worker / in-process: same protocol over one port (in-process uses a direct in-memory port pair — the RPC layer is exercised even without a worker, and unit tests run against the engine beneath it).

### 3.3 Transfer semantics (locked)

`get` results: the worker copies requested slices out of cache-owned buffers, then **transfers** the copies (zero-copy move of the copy; cache-owned memory is never transferred). `put`/`FetchResponse` typed arrays are transferred into the worker where possible and are consumed — documented. No SharedArrayBuffer in v1. A `get` result's snapshot (§2.8) is made of fresh payloads and is transferred with the result; a `hydrate` request's snapshot is cloned, so the caller keeps it.

### 3.4 Segment transfer payload — one format, three uses (locked invariant)

The same self-describing structure is the RPC wire format, the future IndexedDB persistence value, and the SSR hydration payload serialized into HTML. As built, all three carry it inside a snapshot (§2.8): a `get` result's snapshot and a `hydrate` request cross a port with it, while ordinary `get` and `put` carry plain columns (§3.3); each persisted page record holds one (§4.10.2, shipped with persistence); and the SSR payload is an encoded snapshot. Every design change must keep all three viable.

```ts
interface DenseSegmentPayload {
  format: 1; // payload schema version (persistence requirement)
  layout: "dense"; // future: 'columnar', ...
  start: number; // aligned first-slot timestamp
  count: number; // slot count; t_i = start + i * interval
  interval: number;
  alignmentOffset: number;
  mask: Uint8Array; // ceil(count/8) bytes, 1 bit per slot
  fields: { name: string; dtype: Dtype; data: ArrayBuffer }[];
}
```

A `Snapshot` (§2.8, N34) is a set of these payloads, clipped to a request, in an envelope naming the grid, the schema, the dataset version, the watermark and the coverage: the SSR hydration payload of this invariant, and the cache record of the persistence sketch in `docs/roadmap.md`.

Settled persistence notes (roadmap §3.7): write-behind only (dirty-segment set, debounce + `pagehide` flush), volatile region excluded, coverage reconciled against actual segment presence on hydrate, `format` field mandatory. Specified in §4.10: the dirty set is kept per page, the stable container of segments (N15); a page record is a `Snapshot` of its page's covered ranges, so its coverage is stored with exactly the points a load applies (N55).

### 4.1 Internal contracts — `grid.ts` and `coverage.ts` (N9, approved 2026-10-03)

Internal modules: not exported from any package entry. Contract tests (step ③) pin this surface.

**Supported domain: safe integers.** Timestamps and slot indices are safe integers (|x| ≤ 2^53 − 1), so every `± 1` on a slot and every ms↔slot conversion is exact. Values outside the domain are rejected at the boundary as described below (user-confirmed 2026-10-03).

```ts
// grid.ts — every ms↔slot conversion in the codebase goes through here (N1).
/** Built from ResolvedCacheConfig: interval a positive safe integer,
 *  alignmentOffset in [0, interval). */
interface Grid {
  interval: number;
  alignmentOffset: number;
}
/** Inclusive on both ends; safe-integer slot indices; start <= end. Slots
 *  may be negative (timestamps before the grid origin). */
interface SlotRange {
  start: number;
  end: number;
}

/** True when t is a safe integer lying exactly on the grid:
 *  (t - alignmentOffset) % interval === 0 in exact integer arithmetic, for
 *  every safe-integer t (the literal floating-point expression is not the
 *  definition: its subtraction can round near ±2^53). False for anything
 *  else, including fractions, NaN and |t| >= 2^53. */
function isAligned(t: number, g: Grid): boolean;
/** Slot of an aligned timestamp. Throws RangeError if t is not aligned —
 *  callers validate first (put validation reports PutError 'misaligned'). */
function slotOf(t: number, g: Grid): number;
/** Timestamp of a slot: alignmentOffset + slot * interval. */
function msOf(slot: number, g: Grid): number;
/** get/invalidate input → slots, snapped OUTWARD: start floors to the slot at
 *  or before it, end ceils to the slot at or after it. Never narrower than the
 *  input. Throws InvalidRangeError if either endpoint is not a finite number
 *  within ±(2^53 − 1), if start > end, or if the outward snap lands on a grid
 *  point beyond ±(2^53 − 1). start === end is legal (one slot if aligned,
 *  else two). */
function snapOut(r: Range, g: Grid): SlotRange;
/** put's options.range → slots, snapped INWARD (N13): the grid points lying
 *  inside r, or undefined when there is none. Never wider than the input,
 *  so unlike snapOut it cannot land beyond ±(2^53 − 1). Throws
 *  InvalidRangeError if either endpoint is not a finite number within
 *  ±(2^53 − 1) or if start > end. */
function snapIn(r: Range, g: Grid): SlotRange | undefined;
/** Slot range → inclusive ms Range (GetResult.coverage and misses). */
function toMs(r: SlotRange, g: Grid): Range;
/** First slot whose timestamp is at or after t (the watermark's slot: points
 *  at t >= finalizedUntil are provisional, §2.4). Throws InvalidRangeError
 *  if t is not a finite number within ±(2^53 − 1), or if that slot's
 *  timestamp would not be a safe integer. */
function slotAtOrAfter(t: number, g: Grid): number;

// coverage.ts — one index per cache; slot ranges only, no ms arithmetic.
class CoverageIndex {
  /** Record r as authoritative. Overlapping AND adjacent ranges merge
   *  (a.end + 1 === b.start: no slot lies between them). */
  add(r: SlotRange): void;
  /** Forget r (invalidate). May split one range into two; subtracting an
   *  uncovered range is a no-op. */
  subtract(r: SlotRange): void;
  /** Covered sub-ranges of r, ascending, each clipped to r. */
  covered(r: SlotRange): SlotRange[];
  /** Uncovered sub-ranges of r, ascending, each clipped to r. covered(r) and
   *  gaps(r) are disjoint and together tile r exactly. */
  gaps(r: SlotRange): SlotRange[];
  /** Copy of the index: sorted, disjoint, no two adjacent. Mutating the
   *  result does not affect the index. */
  ranges(): SlotRange[];
  clear(): void;
}
```

Ownership: `CoverageIndex` never shares range objects with its callers. It does not keep an object passed to it, and `covered()`, `gaps()` and `ranges()` return fresh objects, so callers may mutate or keep results freely.

`CoverageIndex` methods throw `RangeError` for a malformed `SlotRange` (endpoints that are not safe integers, or start > end): a programming error, never reachable from consumer input, which `snapOut`/`slotOf` validate. Out of step ③ by design: excluding the volatile region (`t >= finalizedUntil`) from coverage is the engine's job (step ⑦); flank coalescing of misses is the orchestrator's (step ⑪).

### 4.2 Internal contracts — `segment/` (N10, N11, approved 2026-10-04)

Internal modules: not exported from any package entry. Contract tests (step ④) pin this surface; `countIn` and `sliceInto` were added for the read path in step 33 (2026-10-30), with their own tests. Code outside `segment/` depends only on the `Segment` interface. Segments work in slot terms and do no ms arithmetic of their own; the payload's `start` goes through `grid.ts`.

```ts
// segment/types.ts
/** Present points only, in slot terms: every field array has slots.length
 *  elements; slots are strictly ascending safe integers. */
interface Columns {
  slots: Float64Array;
  fields: Record<string, FieldArray>;
}

interface Segment {
  /** First to last PRESENT slot (tight); undefined when no point is present. */
  readonly extent: SlotRange | undefined;
  /** Number of present points. */
  readonly size: number;

  /** The point at slot as a fresh { field name → value } object holding
   *  exactly the schema's fields, or undefined if no point is present there
   *  (including outside the extent). A present point whose value is NaN is
   *  returned: presence is per point, not per value. */
  lookup(slot: number): Record<string, number> | undefined;

  /** The present points inside range, as fresh arrays (never views into the
   *  segment): one array per schema field, of that field's dtype. The range
   *  may reach beyond the extent; an empty result has zero-length arrays. */
  slice(range: SlotRange): Columns;

  /** How many points slice(range) would return, without copying any. */
  countIn(range: SlotRange): number;

  /** Writes the points slice(range) would return into `out` from index
   *  `at`, ascending, and returns how many. `out` holds the schema's fields,
   *  of their dtypes; nothing outside those indices is written. Lets a read
   *  across segments (§4.4) count first, allocate each result array once,
   *  and copy every point once, straight into it. */
  sliceInto(range: SlotRange, out: Columns, at: number): number;

  /** Write points in; new values win over old ones at the same slot.
   *  - Without authority (upsert): each point becomes present with its
   *    values; nothing else changes.
   *  - With authority (replace): afterwards the present points inside
   *    authority are exactly `points`; points outside it are unchanged.
   *    Empty `points` with an authority clears that range.
   *  Values are stored by typed-array assignment into the field's dtype.
   *  The input arrays are copied, not kept. */
  mergeFrom(points: Columns, authority?: SlotRange): void;

  /** A self-describing copy of the whole segment (§3.4), in fresh buffers
   *  that share nothing with the segment, so it is safe to transfer. */
  transferPayload(): DenseSegmentPayload;
}

// segment/dense.ts
class DenseSegment implements Segment {
  /** Empty at construction. fields and slotCap come from ResolvedCacheConfig. */
  constructor(options: {
    grid: Grid;
    fields: Readonly<Record<string, Dtype>>;
    slotCap: number;
  });
}

// segment/payload.ts
/** Rebuilds a segment from a payload, copying its buffers. */
function segmentFromPayload(
  payload: DenseSegmentPayload,
  options: {
    grid: Grid;
    fields: Readonly<Record<string, Dtype>>;
    slotCap: number;
  },
): Segment;
```

Rules:

- **Slot cap.** `slotCap` is a positive integer up to 2^31 − 1 (N12); the constructor throws `RangeError` otherwise. `mergeFrom` throws `RangeError` if the extent after the merge would span more than `slotCap` slots. Where to split (gap-split K, segment selection) is merge-path policy (step ⑤); the segment only refuses to exceed its own limit. A segment grows in either direction.
- **Atomic.** `mergeFrom` validates, and allocates any buffers it needs, before it mutates; when it throws, including on an allocation failure, the segment is unchanged.
- **Programming errors** throw `RangeError`: a slot or range that is not made of safe integers or has start > end; a `sliceInto` offset that is not a non-negative safe integer, or an `out` too short to hold the points from it (checked before anything is written); `points` whose slots are not strictly ascending safe integers, whose field names are not exactly the schema's, or whose field arrays differ in length from `slots`; a point outside `authority`; `transferPayload()` on an empty segment. None is reachable from consumer input, which put validation rejects first.
- **Payload layout.** `start` is the timestamp of `extent.start`; `count` is the extent's slot count; `mask` is a `Uint8Array` of exactly `ceil(count / 8)` bytes in which slot `i` of the extent is bit `i & 7` of byte `i >> 3`, with unused trailing bits zero; `fields` follows the schema's declaration order, each `data` an `ArrayBuffer` of exactly `count × bytes-per-element`, with the values of absent slots zero. Equal segments therefore produce equal payloads. Field data is little-endian, which is the native order of every supported platform; no byte swapping is done. The payload is a plain structured-cloneable object.
- **Decoding.** `segmentFromPayload` throws `TscacheError` with a descriptive message for an invalid payload: `format` other than 1, `layout` other than `'dense'`, `interval` or `alignmentOffset` differing from the grid, `start` not aligned, `count` not a positive safe integer or greater than `slotCap`, a mask of the wrong type or length or with trailing bits set, fields that do not match the schema's names and dtypes with correctly sized buffers, or a `start` and `count` whose last slot has no safe-integer timestamp. Field entries may come in any order (a schema declared in a different key order names the same fields); re-encoding restores schema order. Values stored under absent mask bits are ignored, since presence is decided by the mask alone; re-encoding writes zeros. The decoded segment's extent is the tight bounds of the present points, and `segmentFromPayload(s.transferPayload(), …)` is equal to `s` in every observable way.

Out of step ④ by design: gap-split K and segment selection (step ⑤), the overlap-difference warning (step ⑤ builds it from `slice`, so it costs nothing when off), ms conversion of results and concatenation across segments (step ⑥).

### 4.3 Internal contracts — put path (N13–N15, approved 2026-10-05)

Internal modules: not exported from any package entry. Contract tests (step ⑤) pin this surface. Both work in slot terms; the only ms arithmetic is the calls into `grid.ts`.

```ts
// engine/batch.ts
/** Validates a consumer batch against the cache's config and converts it to
 *  slot terms. Rejects the whole batch (§2.4) by throwing; never mutates or
 *  keeps its input. `authority` is the inward snap of `range` (N13), and
 *  undefined when no range was given or the range holds no grid point. */
function validateBatch(
  batch: PutBatch,
  config: ResolvedCacheConfig,
  range?: Range,
): { points: Columns; authority: SlotRange | undefined };

// engine/merge.ts
/** A merge warning in slot terms; the engine converts it to a MergeWarning. */
interface SlotWarning {
  range: SlotRange;
  fields: string[];
}

/** All the segments of one cache. */
class SegmentStore {
  constructor(config: ResolvedCacheConfig);
  /** Ascending by extent, disjoint, none empty, in the layout defined below. */
  readonly segments: readonly Segment[];
  /** Merges validated points in; new values win. Without authority it only
   *  adds or overwrites; with authority the present points inside it end up
   *  exactly `points` (N11). Returns the overlap warnings, always empty when
   *  `warnOnOverlapDiff` is off. */
  put(points: Columns, authority?: SlotRange): SlotWarning[];
  /** Drops every segment. */
  clear(): void;
}
```

Rules for `validateBatch`:

- **Order of checks.** (1) The batch is an object whose `timestamps` is a `number[]` or a `Float64Array`, and whose `fields` is an object with exactly the schema's field names, each a `number[]` or a typed array other than a BigInt one (a `DataView` is not accepted; arrays made in another realm, such as an iframe, are recognized): otherwise `PutError` `'field-mismatch'`. (2) Every field array has as many elements as `timestamps`: otherwise `'length-mismatch'`. (3) Timestamps are scanned once in order, and the first offender is reported with its index and value: a timestamp that is not on the grid is `'misaligned'` (with `expected`, e.g. `"t ≡ 0 (mod 60000)"`); otherwise one equal to its predecessor is `'duplicate'` and one below it is `'unsorted'`. Anything that is not an aligned safe integer, including `NaN` and a non-number, is `'misaligned'`; a non-number offender is reported by index only, without `offenderTimestamp`. (4) With a `range`: a malformed range throws `InvalidRangeError` (as `snapOut`), and the first timestamp outside it is `'range-mismatch'`. (5) Field values, by the rule below (N68): the first offender is `'field-mismatch'`. Structural rejects (1) and (2) have no offending timestamp and carry `offenderIndex: -1`. Error messages never call a value's own string conversion, so a hostile value (a symbol, a null-prototype object) still produces the documented error.
- **Values (N68).** Checked as step (5), after (1)–(4) have passed, so a batch whose structure, timestamps or range fail reports that failure, and every value offender has a valid timestamp. Fields are checked one after another in schema order (the key order of the cache's `fields`), each array scanned once in index order; the first offender found this way rejects the batch, so an offender in an earlier field is reported before one at a lower index in a later field. For a field `name` of dtype `d` and its array `a`:
  - _Own dtype, no check._ When `a` is a typed array whose element type is `d`'s (`Float64Array` for `f64`, `Float32Array` for `f32`, `Int32Array`, `Uint32Array`, `Int16Array`, `Uint16Array`, `Int8Array` and `Uint8Array` for `i32` to `u8`; recognised across realms as in (1)), no value is checked: it cannot hold a value this rule rejects. `Uint8ClampedArray` is not `u8`'s element type and is checked like any other array (it always passes).
  - _Not a number._ Every other array is checked element by element. An element `v` with `typeof v !== "number"` rejects the batch with `expected: "a number"`, in any field: `null`, `undefined` (a hole in a sparse array reads as `undefined`), a string (`"1"` included), a boolean, a bigint, a symbol, an object, a function. Nothing is coerced. Only a `number[]` can hold such an element.
  - _Float fields_ (`f64`, `f32`): every number is accepted, `NaN`, `Infinity`, `-Infinity` and `-0` included. `f64` stores it exactly. `f32` stores the nearest float32, as `Math.fround` gives it (so a finite value beyond the float32 range is stored as `±Infinity`). A typed array of another element type is accepted and converted the same way: a `Float32Array` or any integer typed array into an `f64` field exactly, a `Float64Array` or an `Int32Array`/`Uint32Array` into an `f32` field rounded to the nearest float32.
  - _Integer fields:_ `v` is accepted when it is an integer (`Math.trunc(v) === v`) inside the dtype's range, both ends included: `i32` [−2 147 483 648, 2 147 483 647], `u32` [0, 4 294 967 295], `i16` [−32 768, 32 767], `u16` [0, 65 535], `i8` [−128, 127], `u8` [0, 255]. It is stored as given; `-0` is accepted (stored as `0`), and so is an integral float such as `2.0`. A fraction (`1.5`, `-1.5`, `0.5` and `255.9` for `u8`), `NaN`, `Infinity`, `-Infinity`, and a value outside the range (`256` or `-1` for `u8`, `2 ** 31` for `i32`) reject the batch with `expected` set to `` `an integer in [${min}, ${max}]` `` (for `u8`, `"an integer in [0, 255]"`). Fractions are rejected rather than truncated by user decision 38 (option B, 2026-11-10; see N68). Typed arrays of another element type are checked by the same rule: a `Float64Array` holding `NaN` or `300` for a `u8` field, a `Float32Array` holding `1.5` for an `i32` field, an `Int32Array` holding `300` for a `u8` field and a `Uint32Array` holding `2 ** 31` for an `i32` field all reject, while a `Float64Array` of integers in range is accepted. An implementation may skip the scan when every value of the source element type is in range (an `Int8Array` for an `i16` field); the outcome is the same.
  - _The error._ `PutError` with `code: 'field-mismatch'`, `offenderIndex` the element's index, `offenderTimestamp` the batch timestamp at that index, `offenderField` the field's name, and `expected` as above. The message names the field in double quotes and its dtype, the value as `show()` prints it (`errors.ts`; it never calls the value's own conversion, so a symbol or a null-prototype object still yields this error), the value's `typeof` in parentheses when it is neither a number nor `null` (so the string `"1"` is not mistaken for the number), the index, the timestamp and `expected`, for example `field "close" (f64) value null at index 1, t = 60000: expected a number`, `field "close" (f64) value 1 (string) at index 0, t = 0: expected a number` and `field "flags" (u8) value 300 at index 2, t = 120000: expected an integer in [0, 255]`. Tests match the named parts, not the whole text.
  - This replaces the former rule that an element which cannot be converted to a number (a symbol, an object whose conversion throws) rejects with `offenderIndex: -1`: such an element is now a non-number and is reported with its index. A whole field that is not an array, or is a BigInt typed array or a `DataView`, is still a structural reject (1) with `offenderIndex: -1`.
  - After the checks, each field is copied into a fresh array of the schema's dtype, as before; for every accepted value the copy stores exactly the value stated above. Timestamps are unaffected by this rule (they follow (3)).
- **Cost of the value check.** At most one pass over each checked field array, with no allocation beyond the copy the batch already makes; a typed array of the field's own dtype costs nothing extra, so a caller that already holds typed arrays stays on the fast path. The performance budgets (`docs/benchmarking.md`: the exact budgets and the put cases `put-page`, `put-live-bar`, `append-bars`, `fill-month`) and the entry size budgets (`scripts/size.ts`) must hold; a budget that has to move is changed as `docs/benchmarking.md` describes, with the reason.
- **Empty batch.** Zero timestamps is legal. With a range it states that the range holds no points; without one it does nothing.
- **Not here.** `meta` (`version`, `finalizedUntil`) is validated and applied in step ⑦.

Rules for `SegmentStore`:

- **Layout (N14, N15).** With `K = gapSplitK` and `cap = segmentSlotCap`, the page of slot `s` is `floor(s / cap)`. Two present points with no present point between them share a segment exactly when they are on the same page and at most `K` slots between them hold no point. The layout is therefore a function of which points are present, whatever order they arrived in, and it holds after every `put`: a replace that opens a gap wider than `K` splits a segment, and a point that closes one joins two. No segment spans more than `cap` slots. Each segment is built with `slotCap = cap`.
- **Overlap warning.** When `warnOnOverlapDiff` is on, a batch point _differs_ if a point was already present at its slot and at least one field's stored value changes; values are compared after conversion to the field's dtype, and two values are equal when `a === b` or both are `NaN`. Each maximal run of batch points that are consecutive in the batch and all differ yields one warning: `range` from the first to the last slot of the run, `fields` the names that differed anywhere in the run, in schema order. A point that a replace removes is not a difference. When the option is off no comparison is made. Excluding the volatile region from warnings is step ⑦.
- **Programming errors** throw `RangeError` before anything changes: the same malformed `points` and `authority` that `Segment.mergeFrom` rejects (§4.2). None is reachable through `validateBatch`.
- **Allocation failure.** Segments are updated in place, so a `put` that fails because memory cannot be allocated may be left half done. It works in steps, each of which either completes or changes nothing: first, for a replace, the old points inside the authority are removed; then the batch goes in one run of points at a time (a run is a stretch of the batch that shares a segment). After a failure the store is therefore still well formed (ascending, disjoint, no empty segment) and in the layout above — the one exception is a replace that cleared the middle of a segment and then could not allocate the split — and no slot outside the put's range has changed. The engine records coverage only after `put` returns, and when `put` throws it must also withdraw any coverage it already held for the put's range (step ⑦), so a half-written range is refetched and never trusted. Rejected: copying every touched segment first, which would cost a full segment copy on each live-tail append.

Out of step ⑤ by design: coverage recording, the watermark and version handling (step ⑦); converting warnings to ms and emitting `mergeWarning` (step ⑧).

### 4.4 Internal contracts — read path (N16, approved 2026-10-06)

Internal module: not exported from any package entry. Contract tests (step ⑥) pin this surface. Input is in slot terms; the result is the consumer's `GetResult` (§2.3), so this is where slots become milliseconds again, through `grid.ts`.

```ts
// engine/read.ts
/** The present points of `segments` inside `range`, concatenated ascending,
 *  as fresh arrays (never views): one per field of `fields` (the cache's
 *  schema), of that field's dtype, so the result has the schema's shape
 *  even when there is no segment. Segments are the store's: ascending and
 *  disjoint. */
function collect(
  segments: readonly Segment[],
  range: SlotRange,
  fields: Readonly<Record<string, Dtype>>,
): Columns;

/** Assembles a GetResult for a request already snapped to slots. */
function read(
  request: SlotRange,
  segments: readonly Segment[],
  coverage: CoverageIndex,
  grid: Grid,
  fields: Readonly<Record<string, Dtype>>,
): GetResult;
```

Rules:

- **What is returned (N16).** Every present point inside the request, whether or not its slot is covered: `timestamps` are their slots in ms (`msOf`), ascending; `fields` holds one array per schema field, same length. The live tail (volatile region, never covered) and points whose coverage was invalidated but not yet refetched are therefore returned too; `coverage` says which parts are authoritative.
- **Coverage and misses.** `coverage` is `coverage.covered(request)` in ms (`toMs`), ascending; `misses` is `coverage.gaps(request)` in ms, ascending, each with `reason: 'uncached'` and no `error`. They tile the request exactly: every slot of the request is in exactly one of them, and both are independent of which points are present: a covered stretch without points is still coverage (a confirmed gap), and a request with no points and no coverage yields zero-length arrays, `coverage: []` and `misses: [request in ms]`.
- **Fresh results.** Arrays and range objects in the result share nothing with the segments or the index; mutating a result changes nothing.
- **Programming errors** throw `RangeError` for a malformed `request` (not safe integers, start > end), as the store does. None is reachable from consumer input: `snapOut` validates first.
- **Not here.** Snapping the consumer's ms range outward is the engine's job (step ⑧); excluding the volatile region from the coverage passed in is the engine's job (step ⑦), as is the version check; miss reasons other than `'uncached'` are set by the orchestrator (step ⑪), which rewrites the misses of a request after fetching.

### 4.5 Internal contracts — per-cache state (N17, N18, approved 2026-10-06; N34–N36 approved 2026-10-23)

Internal module: not exported from any package entry. Contract tests (step ⑦) pin this surface. `CacheState` is one cache: its resolved config, a `SegmentStore`, a `CoverageIndex`, the finalized watermark and the dataset version. It speaks milliseconds to its callers and slots to the modules beneath it; every conversion goes through `grid.ts`. Step ⑧'s `Engine` is a map of these plus events.

```ts
// engine/cache.ts
interface CachePutResult {
  /** In ms, outside the volatile region only. */
  warnings: MergeWarning[];
  /** True when a version mismatch cleared the cache before this put. */
  cleared: boolean;
}

interface CacheStateHooks {
  /** Called once when a put's version mismatch has cleared the cache: after
   *  the put was applied, or, if its write then failed, before the error
   *  propagates. */
  onVersionClear?: () => void;
}

class CacheState {
  constructor(config: ResolvedCacheConfig, hooks?: CacheStateHooks);
  readonly config: ResolvedCacheConfig;
  /** The dataset version in force: config.version, then whatever puts report. */
  readonly version: string | undefined;
  /** Points at t >= finalizedUntil are provisional; undefined: nothing is. */
  readonly finalizedUntil: number | undefined;

  put(batch: PutBatch, options?: PutOptions): CachePutResult;
  /** `snapshot: true` adds a Snapshot taken from the same state, in the same call. */
  get(range: Range, options?: { snapshot?: boolean }): GetResult;
  /** §2.8: what this cache knows about the range (snapped outward). */
  snapshot(range: Range): Snapshot;
  /** §2.8: applies a snapshot where nothing is known; one synchronous call. */
  hydrate(snapshot: Snapshot): HydrateResult;
  /** Covered sub-ranges of the range (snapped outward), in ms, without
   *  reading points; the orchestrator's flank check uses it. */
  coverage(range: Range): Range[];
  invalidate(range: Range): void;
  clear(): void;
  setFinalizedUntil(t: number): void;
}
```

Rules:

- **Volatile region (§2.4, starter §3.3).** `volatileFrom = slotAtOrAfter(finalizedUntil)`; with no watermark there is no volatile region. Coverage is excluded **when it is recorded**: a put records `[claim.start, min(claim.end, volatileFrom − 1)]`, where `claim` is the put's authority (N13) or, without a range, the batch's span (N3); nothing is recorded if that is empty. Slots that were provisional when fetched are therefore never covered, and when the watermark later moves forward they are fetched once more, which is the point: provisional data may have changed. Rejected: excluding the volatile region when coverage is read, which would promote stale provisional points to authoritative the moment the watermark passes them.
- **Moving the watermark.** `setFinalizedUntil(t)` sets it exactly. Moving it **backwards** subtracts coverage from the new `volatileFrom` onward (those points are provisional again); moving it forwards subtracts nothing. `t` is validated as `slotAtOrAfter` does, throwing `InvalidRangeError`. `put` with `meta.finalizedUntil` only ever **advances** the watermark (N17): a value at or below the current one is ignored, so fetch responses that arrive out of order cannot pull it back.
- **Version (starter §3.3).** `version` starts as `config.version`. A put whose `meta.version` differs from a **set** `version` first clears the cache (segments and coverage, as `clear()` does), then adopts the new version and applies the put; the result's `cleared` is true and the engine emits `cacheCleared` with `reason: 'version-mismatch'` (step ⑧). When `version` is unset, the first `meta.version` seen is adopted without clearing (N18). A put without `meta.version` never triggers any of this; in particular a restatement from a backend that reports no version is undetectable (§2.4), and only `invalidate` or `clear` recovers from it. `meta` must be an object when present, `meta.version` a non-empty string and `meta.finalizedUntil` a timestamp `slotAtOrAfter` accepts; otherwise `PutError` `'field-mismatch'` with `offenderIndex: -1`, raised after the batch's own checks and before anything changes.
- **A response's own watermark bounds its authority (N19).** When a put carries `meta.finalizedUntil`, it is authoritative only for slots below `slotAtOrAfter(meta.finalizedUntil)`: its replace authority (N11) and its coverage claim are clipped there, and its points at or beyond that slot are merged new-wins but neither replace anything nor record coverage. A response that arrives late with an older watermark therefore cannot delete, or confirm as a gap, a point it itself called provisional. A put without `meta.finalizedUntil` keeps its full authority.
- **Order inside `put`.** Validate the batch (so a rejected batch never clears anything) → version check and clear → `store.put` → advance the watermark → record coverage. If `store.put` throws (an allocation failure, §4.3), nothing is recorded, the coverage the put would have recorded is subtracted so a half-written range is refetched, and the error is rethrown.
- **Warnings** come back in ms, dropping any inside the volatile region (§2.4), judged against the watermark **after** this put's `meta.finalizedUntil` has been applied: a response that declares points final also vouches for the differences it found there. A warning range that straddles `volatileFrom` is clipped to end at `volatileFrom − 1`; its `fields` are kept as reported for the whole run.
- **`get`** snaps the range outward (N1) and returns `read()` over the store and the index; since the index never holds volatile slots, no further filtering is needed. **`invalidate`** snaps outward and subtracts; the points stay (N16). **`clear`** drops segments and coverage and keeps config, version and watermark, which describe the dataset rather than its contents.
- **Errors.** `get`/`invalidate` throw `InvalidRangeError` for a malformed range (as `snapOut`), `setFinalizedUntil` as `slotAtOrAfter` does; `put` throws as `validateBatch` does; a `config.finalizedUntil` that `slotAtOrAfter` rejects makes the constructor throw `ConfigError`. Nothing is changed by a call that throws, except the recorded coverage withdrawal above.

- **Snapshot (N34, N36).** `snapshot(range)` builds, from the current state in one synchronous call: `range` = `toMs(snapOut(range))`; `coverage` = `covered(request)` in ms, ascending; `version` and `finalizedUntil` as the getters report them (omitted when undefined); `fields`, a copy of the schema; `segments`: for each segment of the store, ascending, that has at least one present point inside the request, the payload (§4.2 layout) of a segment holding exactly the present points of that segment inside the request, so `start` is the first of them and `count` their tight span. An implementation may build each from `slice()` into a fresh `DenseSegment`. Payloads are fresh buffers; `coverage` and `range` are fresh objects. Because the store's layout is a function of the present points (N15) and the extent is tight, the snapshot is a function of the state and the request. `get(range, { snapshot: true })` adds this snapshot to the result from the same state: its `coverage` equals the result's, and the payloads' present points, concatenated, are the result's `timestamps` and `fields`. Errors: `InvalidRangeError` as `get`.
- **Hydrate: validation (N35).** Before anything changes, in this order, each failure throwing `TscacheError` whose message starts with `invalid snapshot:` (a payload keeps `segmentFromPayload`'s own message): (1) the snapshot is an object with `format === 1`, `interval` and `alignmentOffset` equal to the grid's, and `fields` an object naming exactly the schema's fields with equal dtypes; (2) `range` is an object whose `start` and `end` are aligned safe-integer timestamps (`isAligned`) with `start <= end`; its slots are the request, and an unaligned endpoint is a malformation (§2.8: a snapshot is never snapped), unlike a call argument; (3) `version`, when present, is a non-empty string, and `finalizedUntil`, when present, is accepted by `slotAtOrAfter` (as `put` validates `meta`); (4) `coverage` is an array of ranges with aligned safe-integer endpoints and `start <= end`, each inside the request, ascending, disjoint and not adjacent (as `CoverageIndex.ranges()` yields them), and, when `finalizedUntil` is present, each ending below `w = slotAtOrAfter(finalizedUntil)`, the snapshot's own `volatileFrom` (N69): a coverage range whose last slot is `w` or later fails with a message naming it and the watermark (for example `invalid snapshot: coverage[0] reaches past finalizedUntil 30`), checked in the same pass, so a coverage range that breaks an earlier rule reports that rule; a snapshot without `finalizedUntil` is not bound by it; (5) `segments` is an array of payloads, each accepted by `segmentFromPayload` with this cache's options and with its extent inside the request, their extents ascending and disjoint. Anything else, including a missing field or a value of the wrong type, fails. A failure inside the snapshot is a `TscacheError` even where the same value as a call argument would be an `InvalidRangeError`. Field values are not otherwise checked: a payload's data are arrays of the field's own dtype, which cannot hold a value N68 rejects (as a typed array of the field's dtype passes `put` unchecked), and `NaN` is legal in a float field, as in `put`. Rule (4)'s watermark bound (N69) is the snapshot analogue of N19: a put is clipped to its own watermark, while a snapshot is made by the library and crosses a trust boundary (a server's HTML), so a snapshot that claims authority over slots it calls provisional is corrupt and is refused whole, never clipped. A snapshot it rejects fails `hydrate` as any malformed snapshot does: it throws before anything changes, the version and watermark included, and nothing is applied. A snapshot whose points (not coverage) lie at or after its watermark is legal: those are the provisional tail §2.8 leaves unapplied. Stored records (§4.10.5 step 5) reuse this validation, and a page snapshot never carries `finalizedUntil`, so the rule binds no page record and changes no load: coverage of a page at or after the cache record's watermark is already clipped there, with `rewrite: true` (§4.10.5 step 6).
- **Hydrate: application (N35).** (1) Version precondition: both set and different → return `{ applied: [], skipped: 'version-mismatch' }` with nothing changed; cache unversioned and snapshot versioned → adopt it, no clear, no hook; snapshot unversioned → the cache's version is untouched. (2) Watermark: `finalizedUntil`, when present, advances the watermark exactly as a put's `meta.finalizedUntil` does (N17: a value at or below the current one is ignored). (3) Parts: for each coverage range, in order, subtract the cache's covered slots and, when the cache has a volatile region after step 2, the slots at or after `volatileFrom`; the pieces, ascending, are the parts. (4) For each part, ascending: the decoded present points inside it are written with the part as authority (`store.put(points, part)`, a replace, N11), then the part is recorded as coverage (`#cover`, which cannot clip it further). Points outside every part are not written. Warnings from `store.put` are dropped. (5) Result: `applied` = the parts in ms (`toMs`), ascending and disjoint; two parts are never adjacent, since covered or volatile slots separate them.
- **Hydrate: failure part-way.** A write that fails (an allocation failure, §4.3) withdraws coverage for its part, as a put does, and rethrows; parts already applied stay, as do the version and watermark steps; the store is then as §4.3 describes after a failed put.
- **Properties the contract tests pin.** (a) Round trip: for any state `S` and request `R`, hydrating `S.snapshot(R)` into an empty cache `E` of the same structural config, created without a version or watermark, gives `E.get(R)` whose `coverage` equals `S.get(R).coverage` and whose points are `S`'s points inside that coverage; `E.version` is `S.version` when set, and `E.finalizedUntil` is `S.finalizedUntil`. (b) Idempotence: hydrating the same snapshot again applies nothing. (c) Never overwrites: for a cache `C` that covers part of `R` with other values, `C.hydrate(S.snapshot(R))` leaves `C`'s covered points unchanged, and `applied` is exactly `S`'s coverage of `R` minus `C`'s coverage and `C`'s volatile region. (d) `get(R, { snapshot: true }).snapshot` deep-equals `snapshot(R)`. (e) `decodeSnapshot(JSON.parse(JSON.stringify(encodeSnapshot(s))))` deep-equals `s`, `NaN` included.

Out of step ⑦ by design: the caches map, `clearAll`, config conflicts (N4) and event emission (step ⑧); orchestration (step ⑪).

### 4.6 Internal contracts — engine assembly (N20–N22, approved 2026-10-07; N34–N36 approved 2026-10-23)

`Engine` is the `./engine` export surface (SSR/Node, tests) and what the RPC server (step ⑨) drives. Contract tests (step ⑧) pin this surface. It is a map of `CacheState` (§4.5) keyed by cache id, with the cache-scoped events; it speaks milliseconds and consumer types only. Zero DOM/worker imports at module top level (locked, §2.1).

```ts
// engine/emitter.ts
/** Minimal typed emitter: on() returns the unsubscribe; listeners added or
 *  removed during emit do not affect that emit; a throwing listener does
 *  not stop the others (the first error is rethrown after all ran). */
class Emitter<Events extends object> {
  on<E extends keyof Events>(
    event: E,
    fn: (payload: Events[E]) => void,
  ): () => void;
  off<E extends keyof Events>(event: E, fn: (payload: Events[E]) => void): void;
  emit<E extends keyof Events>(event: E, payload: Events[E]): void;
}

// engine/engine.ts
interface EngineEvents {
  /** Cache-scoped (N5). */
  cacheCleared: {
    cacheId: string;
    reason: "manual" | "clear-all" | "version-mismatch";
  };
}

class Engine {
  /** Get-or-create (N4, N20). Returns the resolved config in force. */
  cache(config: CacheConfig): ResolvedCacheConfig;
  has(cacheId: string): boolean;
  /** Current state only: no orchestration (that is step ⑪). */
  get(
    cacheId: string,
    range: Range,
    options?: { snapshot?: boolean },
  ): GetResult;
  /** §2.8. */
  snapshot(cacheId: string, range: Range): Snapshot;
  hydrate(cacheId: string, snapshot: Snapshot): HydrateResult;
  coverage(cacheId: string, range: Range): Range[];
  configOf(cacheId: string): ResolvedCacheConfig;
  put(cacheId: string, batch: PutBatch, options?: PutOptions): PutResult;
  invalidate(cacheId: string, range: Range): void;
  clear(cacheId: string): void;
  clearAll(): void;
  setFinalizedUntil(cacheId: string, t: number): void;
  on<E extends keyof EngineEvents>(
    event: E,
    fn: (e: EngineEvents[E]) => void,
  ): () => void;
  off<E extends keyof EngineEvents>(
    event: E,
    fn: (e: EngineEvents[E]) => void,
  ): void;
}
```

Rules:

- **Get-or-create (N20).** `cache(config)` first resolves the config (`resolveCacheConfig`, so a bad config throws `ConfigError` before the map is touched). With no cache under that id, a `CacheState` is created from it. With one, the resolved **structural** fields must equal the live ones: `interval`, `alignmentOffset`, `fields` (same names and dtypes; key order irrelevant), `gapSplitK`, `segmentSlotCap`, `warnOnOverlapDiff`, and since persistence `persist` (N45, §4.10); any difference throws `ConfigError` naming the field, and the live cache is untouched. `version` and `finalizedUntil` describe the dataset, not the structure: they apply only when the cache is created and are **ignored** when joining an existing cache, so a tab from an older deploy can neither clear nor rewind the live cache. The return value is the resolved config the cache was **created** with (`CacheState.config`): it carries the creation-time `version` and `finalizedUntil`, while the current ones are observable through behaviour (and, for the RPC layer, through `CacheState` — the engine exposes no getters for them in step ⑧).
- **Unknown id.** Every method that takes a `cacheId`, except `has`, throws `UnknownCacheError` for an id without a cache, before validating anything else; `has` answers `false`.
- **Delegation.** `get`, `put`, `invalidate`, `setFinalizedUntil` delegate to the `CacheState` and keep its errors and results; `put` returns `{ warnings }` (§2.4); the engine registers `onVersionClear` on each state, so a version-mismatch clear emits `cacheCleared` with `reason: 'version-mismatch'` **after** the put has been applied — or, when the write fails after the clear, before the error propagates (the cache is empty either way, and a retry emits nothing more). In that failure path the write error is the one the caller sees; an error thrown by a listener is dropped. `clear(id)` clears that cache and emits `'manual'`.
- **`clearAll` (N22).** Clears every cache's data and coverage and emits `cacheCleared` with `reason: 'clear-all'` for each, in creation order; the caches themselves, their configs, versions and watermarks stay, so handles in every tab remain valid. An engine with no caches emits nothing.
- **Events (N21).** The engine emits only cache-scoped events. Request-scoped `mergeWarning` (requestId `clientId:seq`, §2.7) is emitted by the RPC server from `put`'s return value (step ⑨); the engine never carries request identity. Listeners run synchronously inside the emitting call, after the state change they describe.
- **Snapshots (N34–N36).** `get` passes `options.snapshot` through; `snapshot` and `hydrate` delegate to the `CacheState` and keep its errors and results, after the id check (`UnknownCacheError`). `hydrate` emits nothing: it never clears. All three are synchronous, so under the RPC server's one-call-per-message dispatch a `hydrate` cannot interleave with another tab's write (step ⑭ R2-2): the atomicity the public API lacked. `encodeSnapshot`, `decodeSnapshot` and the types `Snapshot`, `EncodedSnapshot`, `EncodedSegmentPayload`, `HydrateResult` and `DenseSegmentPayload` are exported from `./engine` as from `.`.
- **No DOM, no worker, no timers** at module top level or in any method: the module is importable and usable in Node.

Out of step ⑧ by design: orchestration and `cacheOnly` (step ⑪ — until then every `get` is cache-only), RPC envelopes and request ids (step ⑨), `updateAuth`/`dispose` (client and worker layers).

### 4.7 Internal contracts — RPC layer (N23, N24, approved 2026-10-07)

Not an engine step: tests are written with the code (hybrid TDD, AGENTS.md). The wire format is §3; this section fixes the module shapes.

```ts
// rpc/protocol.ts — wire types (§3.1–§3.2) and helpers; no DOM references.
const PROTOCOL_VERSION = 1;
/** Error → WireError: name, message, code (PutError, AuthInvalidError) and,

 *  side that does not know it leaves it unset). */

/** WireError → the §2.6 class with that name, fields restored; an unknown
 *  name becomes a TscacheError carrying the original name in its message. */

/** The buffers of a result's arrays, for the postMessage transfer list. */

// rpc/server.ts — worker-side shell around Engine.
class RpcServer {
  /** `lock`: the worker's lifetime Web Lock, reported in hello (N32).
   *  `persistence`: the SharedWorker's persister, when it has one (§4.10). */
  constructor(
    engine: Engine,
    lib: string,
    lock?: string,
    persistence?: Persistence,
  );
  /** Sends hello with a fresh clientId, awaits init (protocol check),
   *  then dispatches req → engine and fans out evt to every attached port. */
  attach(port: MessagePortLike): void;
  detach(port: MessagePortLike): void;
}

// rpc/port-client.ts — client-side port wrapper.
class PortClient {
  /**
   * Completes the handshake; rejects with ProtocolMismatchError. `signal`
   * aborts it (handshake timeout, worker error); `afterHello` runs once a
   * hello with this protocol arrives, with `hello.lock` (N25, N32).
   */
  static connect(
    port: MessagePortLike,
    init?: { fetcher?: FetcherConfig },
    signal?: AbortSignal,
    afterHello?: (lock: string | undefined) => void,
  ): Promise<PortClient>;
  readonly clientId: string;
  /** hello.lock, when the worker holds a lifetime lock (N32). */
  readonly lock: string | undefined;
  request(op: Op, params: unknown, transfer?: ArrayBuffer[]): Promise<unknown>;
  on(fn: (evt: Evt) => void): () => void;
  /** Called once when the transport fails underneath; never after dispose(). */
  onLost(fn: (error: TscacheError) => void): () => void;
  dispose(): void;
}
```

Rules:

- **`MessagePortLike`** is the structural subset both `MessagePort` (browser, Node) and a dedicated worker's global/`Worker` object satisfy: `postMessage(message, transfer?)`, `addEventListener('message' | 'close', …)`, `start?()`, `close?()`. In-process mode builds a `MessageChannel` and attaches the server to one port and the client to the other (§3.2, locked), so the RPC layer has one code path and its tests run under Node.
- **Handshake.** On `attach`, the server posts `hello` with `PROTOCOL_VERSION`, `lib` and the new `clientId` (`'c' + counter`, N23). The client answers `init`; a `protocol` other than the server's gets `init-err` with a `ProtocolMismatchError` wire error and the port is detached; the client likewise rejects `connect()` with `ProtocolMismatchError` when `hello.protocol` differs. A `req` before `init-ok` is answered with an error.
- **Dispatch.** `op` maps one-to-one onto `Engine` (`cache`, `get`, `put`, `invalidate`, `clear`, `clearAll`, `setFinalizedUntil`, `hydrate` with `params.snapshot`, §2.8) plus `updateAuth` (accepted and ignored until step ⑪) and `dispose` (detaches the port). Params are passed through to the engine, which validates them; any thrown error travels back as `res ok:false` with `toWireError`, so `PutError` fields and `code` survive the wire and the client rethrows the same class.
- **Transfer (§3.3).** The server transfers the buffers of a `get` result (already copies) and the client transfers the batch's typed arrays on `put` where it owns them; the sender's arrays are detached afterwards (documented in `put`). A `get` result's `snapshot` payloads are fresh too and go in the same transfer list (`transferablesOf` lists each payload's mask buffer and field data); a `hydrate` request carries no transfer list, so the snapshot is cloned and stays usable (§2.8).
- **Events.** `Engine` `cacheCleared` → `evt scope:'cache'` to every attached port. `mergeWarning` (N21) is sent by the server from `put`'s warnings as `evt scope:'request'` with `requestId = clientId + ':' + req.id`, to every port (cross-tab observability, §2.7). The client re-emits `evt` to its `on` listeners as received.
- **Browser coverage (N24).** Step ⑨ is tested under Node over `MessageChannel`. A real dedicated `Worker` and transfer across a real port are covered at step ⑩ with Playwright (already a dependency; needs `bunx playwright install chromium` locally and a browser-install step in CI, on a chore branch), and the multi-tab suite at step ⑫.
- **Entries.** `entries/worker.ts` gains the dedicated-worker path: when the module runs inside a dedicated worker (a worker global without `onconnect`), it attaches the worker global as a port at load; messages the worker posts before the page listens are buffered by the browser. SharedWorker `onconnect` arrives at step ⑩. The entry imports `Engine` and `RpcServer` only, and is the package's one side-effecting module (`sideEffects` in `package.json`).

### 4.8 Internal contracts — client and hosting (N25–N27, approved 2026-10-08; N32, 2026-10-11; N43–N44, 2026-10-23)

Not an engine step: tests are written with the code. The public surface is §2.1 and §2.3–§2.4; this section fixes the module shapes and the fallback rules.

```ts
// client/client.ts
/** §2.1. Resolves once a hosting completed the handshake. */
function createClient(options?: ClientOptions): Promise<TscacheClient>;

// client/hosting.ts — one function per hosting, each yielding a Hosting (a
// connected PortClient, its mode, and a terminate() that releases what the
// client owns) or throwing a HostingError the chain treats as "step down".
// `fetcher` is sent in init (N30).
interface Hosting {
  mode: HostingMode;
  client: PortClient;
  terminate(): void;
}
function openShared(
  url: string | URL,
  fetcher: FetcherConfig | undefined,
  timeoutMs: number,
): Promise<Hosting>;
function openDedicated(
  url: string | URL,
  fetcher: FetcherConfig | undefined,
  timeoutMs: number,
): Promise<Hosting>;
/**
 * MessageChannel pair with RpcServer(new Engine()) in this realm (N27).
 * Loads client/in-process.ts with import(), its own chunk (step 48); a load
 * that fails is a HostingError like any other failed hosting.
 */
function openInProcess(fetcher: FetcherConfig | undefined): Promise<Hosting>;

// client/cache.ts — CacheHandle facade over PortClient.request.
// client/events.ts — ClientEvents emitter fed by evt messages (reuses engine/emitter).
```

Rules:

- **Chain (§3.4, locked).** From the pin (`mode`, default `'shared'`): shared → dedicated → in-process. A hosting **fails** (N25) when its constructor throws (no `SharedWorker`, as in Samsung Internet or Chrome for Android before 148), the worker fires `error` before the handshake completed (script failed to load or threw at top level), or no `hello` arrives within `handshakeTimeoutMs` (default 5000). The timeout bounds only the wait for `hello`: the client stops its timer when `hello` arrives, so what follows (the worker loading the fetcher module, N30, then `init-ok` or `init-err`) is not bounded by it, and a fetcher load failure rejects `createClient` with a `TscacheError` from `init-err` without stepping down. A worker `error` before `init-ok` still fails the hosting, and so does a SharedWorker whose lifetime lock (N32) is granted before `init-ok`: the client queues on `hello.lock` as soon as `hello` arrives, and the same request goes on watching the connected client. Until step 68 (2026-11-09) the timer ran until `init-ok`, so a fetcher load slower than the timeout stepped the chain down; that was an implementation defect against N25, fixed to match it. Each failure emits `modeFallback { from, to, reason }` (§2.7) and the next hosting is tried; when the last one fails, `createClient` rejects with that error. A `ProtocolMismatchError` is **not** a failure to step down from: it is a real incompatibility and rejects `createClient` at once (stale cached script, package skew — §3.1).
- **`workerUrl`** is required for `'shared'` and `'dedicated'`; omitting it with the default pin throws `ConfigError` before anything is created (the doc says: omit only when pinning `'in-process'`). Workers are created as module workers (`{ type: 'module' }`); the SharedWorker also with `extendedLifetime: true` (§4.10.8).
- **In-process (N27).** Every `createClient` with the in-process hosting builds its own `Engine` behind a `MessageChannel` pair in the page (no module-level singleton); two in-process clients in one page do not share data — sharing in a page is what the workers are for. The server side is the same `RpcServer`, so the RPC layer is exercised (§3.2).
- **Handles.** `client.cache(config)` sends `cache` and returns a `CacheHandle` whose methods map one-to-one onto the ops with `cacheId` filled in. `put` transfers the batch's typed-array buffers (§3.3); the TSDoc says the arrays are consumed. `hydrate(snapshot)` sends `hydrate` with the snapshot cloned, so it stays usable (§2.8). `cache.on(event, fn)` filters `client.on` by `cacheId` for cache- and request-scoped events.
- **Events.** `evt` messages re-emit as `ClientEvents`: `cacheCleared` (cache scope), `mergeWarning` (request scope, with `requestId`), `authInvalid` (client scope, step ⑪), `persistStopped` (cache scope, §4.10.8), and the client-made `modeFallback` and `workerLost`. Listeners run on the page; a throwing listener does not break the port (the emitter's rule).
- **Dispose.** `client.dispose()` sends `dispose`, releases the port, terminates an owned dedicated worker, and rejects later calls with `TscacheError`; idempotent. A SharedWorker is never terminated by a client (other tabs may use it). The client also disposes itself on the page's `pagehide` event when the page is not being persisted (best effort), because browsers fire no port-close event a SharedWorker could use to notice a closed tab; a page entering the back/forward cache (`persisted: true`) keeps its client, since it may be restored with its objects intact. A tab whose renderer dies abruptly fires no `pagehide` either; its connection then stays registered in the worker until the worker is torn down with the last tab — a bounded leak accepted by N28. A handshake that times out or sees a worker `error` is aborted: its listeners go and this side's port closes, so a late `hello` completes nothing. A dedicated worker's `error` after the handshake aborts the client's pending requests (a `Worker` has no port closure to observe).
- **Worker loss (N32).** A client is lost when its transport fails underneath it after the handshake: its SharedWorker's lifetime lock is granted to it (below), a dedicated worker fires `error` (which already aborts pending requests), or the port closes or the server sends `bye`. On loss, pending and later calls reject with `TscacheError(reason)`. The client releases what it owns, as `dispose()` would: an owned dedicated worker is terminated and the `pagehide` listener removed, but no `dispose` message is sent. Then it emits `workerLost { reason }` once. `dispose()` withdraws the queued lock request and never emits it. Chromium runs a SharedWorker in the renderer of the tab that created it. A crash of that renderer kills the worker, and the other tabs get no `error` and no port `close`. In a SharedWorker scope with Web Locks, the worker entry requests an exclusive lock `tscache-worker:<random UUID>` at startup and holds it for its lifetime. Ports that connect before the grant wait, then get `hello` with `lock`. From `hello`, a shared-mode client requests that lock in `'shared'` mode with an `AbortSignal`. The browser grants it only once the worker is gone, so a grant means worker loss; a grant before `init-ok` fails the hosting instead, under the chain rule above (step 68; confirmed by the user 2026-11-10, decision 24), and the same request goes on watching the connected client. Without Web Locks (a non-secure context) or without `hello.lock` (an older worker script), nothing is watched and a host crash hangs as before. Dedicated and in-process hostings hold no lock: a dedicated worker shares its page's renderer and dies with it. Both protocol changes of N32 and N33 are additive and optional (an old client ignores `lock` and `context`; a new client facing an old worker sees no `lock` and skips the watch, and gets `authInvalid` without `context`, which the refresh snippet treats as a refusal of the stored token), so `PROTOCOL_VERSION` stays 1.
- **What loss detection assumes (N43, N44).** Same-origin scripts are inside the trust boundary: one can already connect to the worker and call `clearAll`, or terminate a dedicated worker. A script that reads the lock's name with `navigator.locks.query()` and requests it with `steal: true` is granted it ahead of the clients' queued requests; when it releases the lock, every queued client is granted it and reports `workerLost` while the worker runs on. The worker never requests its lock again, so every client that connects later is granted it at once and reports loss too, and a recovery loop that creates a client on `workerLost` reconnects until the last tab closes the worker, whose cache stays intact throughout. This is deliberate misuse and is not detected. Second, a fetcher must not close its worker (§2.5). Only code inside the worker can call `self.close()`; a dedicated worker that does fires no `error`, and dedicated and in-process hostings hold no lock by design, so the calls of its tab hang.
- **Browser coverage (N26).** A Playwright suite in Chromium runs: a real dedicated `Worker`; a real `SharedWorker` with two pages of one `BrowserContext` sharing one engine (a put in one page is read in the other); the in-process pin; and the no-`SharedWorker` fallback (the API deleted from `window` before `createClient`, expecting `modeFallback` to `'dedicated'`). CI installs Chromium with `bunx playwright install --with-deps chromium` and `scripts/ci.sh` runs the suite (chore branch). Node tests over `MessageChannel` cover the facade and the chain logic with fake hostings.

### 4.9 Internal contracts — orchestration (N29–N31, approved 2026-10-08; N33, 2026-10-11; N31 built with N62–N65, 2026-10-30; N29 amended, 2026-10-31)

Not an engine step: tests are written with the code (in-flight subtraction, §4.9.1, is the exception: its contract tests come first). The orchestrator lives in the worker (and in the in-process server) in front of `Engine`; the RPC server routes `get`, `updateAuth`, `invalidate` (§4.9.1 rule 9) and `init.fetcher` to it. Without a fetcher configured, `get` stays cache-only and `updateAuth` is a no-op.

```ts
// orchestrator/orchestrator.ts
class Orchestrator {
  constructor(engine: Engine, broadcast: (evt: Evt) => void);
  /** import()s the module once; a failure rejects (N30). */
  load(config: FetcherConfig): Promise<void>;
  /** `requestId` names the get on the request-scoped mergeWarning events
   *  of the fetches it issues (step ⑪). */
  get(
    cacheId: string,
    range: Range,
    options?: GetOptions,
    requestId?: string,
  ): Promise<GetResult>;
  updateAuth(context: unknown): Promise<void>;
  /** engine.invalidate, then fences the fetches in flight over the range (§4.9.1, N64). */
  invalidate(cacheId: string, range: Range): void;
}
// orchestrator/auth.ts — AuthState: 'valid' | 'invalid'; see rules.
// entries/fetcher.ts — exports Fetcher, FetchRequest, FetchResponse (§2.5).
```

Rules:

- **Loading (N30).** `init.fetcher` makes the server call `load()` before answering: `import(module)` once per worker (the first connection loads it; later connections reuse it; a different module on a later connection is a `ConfigError` in `init-err`). An import failure, or a module whose default export has no `fetch` function, answers `init-err` with a `TscacheError` naming the module, so `createClient` rejects at startup. The fetcher module must load or fail: an `import()` that never settles (a module server that accepts the request and never answers, a top-level `await` that never resolves) leaves `createClient` pending, and no timeout bounds it in 0.1.0 (user decision 2026-11-10, decision 25). `context` is stored and sent with every request; `updateAuth` replaces it. A tab that joins with a context that is not the identical value takes the `updateAuth` path once the module is loaded (structured-cloneable values have no cheap, cycle-safe equality, so anything else is treated as new material).
- **Orchestrated get (N2).** With `cacheOnly` or no fetcher, `get` reads the engine and returns that. Otherwise it plans from `engine.coverage`: the request's uncovered slots, which a read would report as `'uncached'` misses, are **coalesced**: adjacent misses merge, and a miss abutting existing coverage is extended by one interval into it (locked: the one-point overlap aids range merge). What is already in flight for the cache is subtracted first, and the `get` awaits those fetches for the overlap (§4.9.1); each coalesced range of the rest becomes one `FetchRequest`; the response is applied with `engine.put(cacheId, response, { range })`, so the fetched range is authoritative (N3, clipped by the response's own watermark, N19). The engine is then read once, after the fetches the `get` awaited, its own and those of other gets (at once when it awaits none), and the result returned; `options.snapshot` is applied to that read, so the result's columns and its `snapshot` come from one state (N36). One read per `get` is an exact budget (`test/perf/counters.test.ts`). A range whose fetch threw comes back as a miss with `reason: 'fetch-failed'` and `error: { name, message }`; a range not fetched because auth is invalid comes back `'auth-pending'`; `'uncached'` is reserved for slots nobody asked to fetch (only after the fence, below).
- **Dedup (N31).** _Replaced at step 44 by in-flight subtraction (§4.9.1)._ Until then, in-flight fetches were keyed by `(cacheId, range.start, range.end)` of the coalesced range, a second `get` from any tab that produced the same key awaited the same promise, and overlapping but different ranges fetched separately. A `get` that joins a fetch still applies nothing itself.
- **Version fence (N29, amended 2026-10-31; companion to N19).** The orchestrator counts `cacheCleared` events per cache: the cache's generation. A response whose fetch started before the latest clear is **not applied**. A `get` whose fetches end under another generation than the one it planned them under (the cache was cleared while it waited, whether the clear dropped a response it awaited or wiped one already applied) asks for what is still missing **once** more; that second answer is final, and whatever is still missing after it, because a second clear dropped or wiped it, is returned as `'uncached'`. A fetch's `put` may itself trigger a version-mismatch clear (its `meta.version` is newer): that clear happens inside the put and does not fence the response that caused it, but the fetch then ends under a new generation, so the get asks once more for what the clear wiped. With fetches shared between gets, the fence reads as §4.9.1 rule 5 says. As first written, only a dropped response led to the second request, so a get whose awaited responses were all applied, the clearing one among them, returned the wiped slots `'uncached'` (amended by user decision #10, option B; DC-1 in `docs/reviews/step-44.md`).
- **Auth (design b/y, locked).** `AuthInvalidError` (detected by `code === 'tscache:auth-invalid'`, never `instanceof`) from a fetch flips the state to `'invalid'` and broadcasts `authInvalid { error, context }` to every port once per flip, where `context` is the context the refused fetch was issued with (N33). Only a failure under the current auth generation flips the state, so this is the context in place when the event is sent. Every tab of the origin receives it; those tabs supplied it. That is the SharedWorker hosting: a dedicated worker serves one tab, and the in-process hosting has no worker but one engine per client (N27); in both, `authInvalid` reaches only that tab and `updateAuth` restores only that tab's worker or that client's engine. The failed range comes back `'auth-pending'`, and while invalid no fetch is issued (every miss resolves `'auth-pending'` at once). `updateAuth(context)` from any tab is applied in call order, one at a time: the fetcher's `updateAuth` hook runs, then the context and the auth generation switch together and the state flips to `'valid'`; the next `get` fetches again. While the fetcher's hook is running (a credential transition, machine-speed), no fetch starts: the module's own state and the orchestrator's stamp could disagree, so uncached ranges come back `'auth-pending'` at once and the consumer re-gets after the switch. A fetch that was already out carries the generation it started under, and an auth failure from a superseded generation is ignored. A `get` waiting on several fetches is released the moment one of them invalidates auth: the ranges still out come back `'auth-pending'` while their fetches finish in the background. The fetcher receives a copy of the range; the orchestrator's own range object decides the authoritative write. Likewise the fetcher and its `updateAuth` hook receive copies of the context, so what later fetches carry and what `authInvalid` names cannot be changed by fetcher code. Nothing is retried on behalf of a `get` that already returned: a `get` never waits for a human.
- **Failure of the fetcher itself.** A fetch that rejects with anything else is `'fetch-failed'` for the gets that awaited it (§4.9.1 rule 7) and for no later one; nothing is cached about the failure and the next `get` tries again. A response that fails engine validation (`PutError`) is likewise `'fetch-failed'` with the error's name and message.
- **Events.** `authInvalid` is client-scoped (§2.7). Fetch lifecycle events are roadmap.

#### 4.9.1 In-flight subtraction (N31, N62–N65, 2026-10-30; rule 5 amended, 2026-10-31)

Additive to §4.9. The rules marked _replaces_ name the §4.9 text they supersede; every other rule of §4.9 stands. Unlike the rest of §4.9 this is strict test-first: Codex writes the contract tests from this subsection (`docs/reviews/step-44.md` lists them), and the implementation follows.

Before a `get` fetches its misses, it subtracts the fetches already in flight for the cache, whichever tab's `get` issued them, awaits those fetches for the overlap, and fetches only the rest. A chart that scrolls faster than the backend answers then asks the backend for each bar once, where the exact-range dedup fetched every read's whole miss again (up to three times the bars on a fast scroll; N31). An identical range is the case where nothing is left to fetch, so the locked guarantee (starter §3.5: dedup in the worker, one fetch serves all tabs) holds and now covers overlapping ranges too.

```ts
// orchestrator/orchestrator.ts — internal, exported for tests only
/** How a fetch ended, as every get awaiting it sees it (§4.9). */
type Outcome =
  | { kind: "applied"; warnings: MergeWarning[] }
  | { kind: "dropped" } // fenced by a clear (N29)
  | { kind: "auth" } // refused; a get released by an auth flip counts its fetches still out so
  | { kind: "failed"; error: { name: string; message: string } };

/** A fetch in flight; replaces the entry keyed by (cacheId, start, end). */
interface Inflight {
  /** The coalesced slot range sent to the fetcher, and its put's authority (N3). */
  readonly range: SlotRange;
  /** The cache's clear count when the fetch was issued (N29). */
  readonly generation: number;
  /** The auth generation when the fetch was issued (§4.9 Auth). */
  readonly authGeneration: number;
  /** Set once, by an invalidate that meets `range` (N64). */
  fenced: boolean;
  readonly outcome: Promise<Outcome>;
}

/** What one round of a get does (rule 2). */
interface RoundPlan {
  /** The ranges to fetch, ascending: coalesced, flanks included. */
  fetch: SlotRange[];
  /** Indices into `inflight`, ascending: the fetches to await. */
  join: number[];
}

/**
 * Rule 2 (d); pure, in slots. `around`: the coverage of the request and of
 * one slot beyond each end, ascending, disjoint, not adjacent. `inflight`:
 * the ranges of the cache's joinable fetches, ascending by start, possibly
 * overlapping. `blocked`: ascending, disjoint.
 */
function planRound(
  request: SlotRange,
  around: readonly SlotRange[],
  inflight: readonly SlotRange[],
  blocked: readonly SlotRange[],
  grid: Grid,
): RoundPlan;
```

`planFetches` (§4.9, step 36) stays as the case without fetches in flight: `planRound(r, a, [], b, g).fetch` equals `planFetches(r, a, b, g)`.

Rules:

1. **The in-flight list (N62).** Per cache id, the orchestrator keeps its fetches in flight as an array of `Inflight`, ascending by `range.start`, equal starts in issue order.
   - _Membership._ An entry is added when its fetch is issued, in the synchronous step of the round that plans it (rule 2). It is removed in the synchronous step that decides its outcome (after the fence check and the put, or once the fetcher's rejection is classified), before `outcome` settles. So no plan sees a fetch whose outcome is decided, and every get awaiting a fetch resumes after its entry is gone.
   - _Stamps._ `generation` and `authGeneration` are those in force when the fetch was issued and never change; `fenced` only ever goes from false to true.
   - _Joinable._ An entry is joinable while its `generation` equals the cache's current one, its `authGeneration` equals the current auth generation, and it is not `fenced`. An entry that stops being joinable stays in the list until its outcome is decided, since its fetch runs on and is applied or dropped as §4.9 says. Gets that already await it go on awaiting it; no later plan subtracts it or awaits it.
   - _No slot fetched twice._ A plan never sends the fetcher a slot that was uncovered when it ran and lies inside a joinable entry, or inside `blocked`. Every slot a fetch shares with a joinable entry was covered when the later of the two was planned, and was reached by its flank or bridge (rule 3), so two joinable entries share at most two slots, both covered at that time.

2. **A round** (_replaces_ "each coalesced range becomes one `FetchRequest`", §4.9 Orchestrated get). A `get` runs one round, or two when the cache was cleared while its first round waited (rule 5). A round runs as one synchronous step from the coverage read to the registration of its fetches, so two rounds never interleave, whichever tabs they serve:
   1. `request` is the range snapped outward (N1); `around` is the coverage of the request and of one slot beyond each end, read as §4.9 reads it.
   2. `need` is `request` minus `around` minus `blocked`; `blocked` is empty in the first round.
   3. _Auth gate._ While auth is invalid, or an `updateAuth` hook is running (§4.9 Auth), the round awaits nothing and issues nothing: every slot of `need` that the read reports missing comes back `'auth-pending'`, at once, as before this rule.
   4. Otherwise `planRound` runs over the ranges of the cache's joinable entries: `join` is the entries whose range meets `need`; `fetch` is the pieces of `need` outside every joinable range, coalesced (rule 3).
   5. Each range of `fetch` is issued as one `FetchRequest`, and its entry added (rule 1).
   6. The round awaits the joined entries and its own fetches together (rule 4).

   A fetch in flight that meets the request only on covered slots is not awaited. A get whose `need` lies wholly inside fetches in flight issues nothing.

3. **Flanks and bridges (N63).** Subtraction comes before coalescing, and coalescing extends into coverage only, as locked (starter §3.5). This is `coalesce` (§4.9) unchanged: a piece abutting a covered slot is extended one slot into it, and extended pieces that then touch or overlap merge. Two pieces one or two covered slots apart therefore merge into one fetch across the gap (each extends one slot into it), and pieces three or more covered slots apart stay separate. This holds when the covered slots lie inside a joinable entry too, which is the overlap of at most two slots rule 1 allows. A covered slot inside `blocked` is extended into in the same way; only uncovered blocked slots are never fetched. A piece abutting an in-flight range is not extended into it: the two fetches meet edge to edge, and once both have landed the coverage index merges the adjacent ranges (§4.1). Pieces separated by in-flight slots are separate fetches, so a round can issue more, smaller requests than `planFetches` would for the same request, coverage and `blocked` with nothing in flight: at most one more for each maximal range of the joinable ranges' union that meets `need`, so at most `join.length` more.

4. **Awaiting, the read and the miss annotation.** A round's fetches, joined and its own, are awaited as one set. Any auth flip releases the get at once (§4.9 Auth), and the fetches still out count as `'auth'`. The one engine read follows the get's last round with no await between them, and `options.snapshot` applies to it (N36); one engine read per `get` remains an exact budget. The annotation of §4.9 takes every fetch the get awaited, in every round, with its range and outcome: a `'failed'` fetch labels the missing slots of its range `'fetch-failed'` with its error, an `'auth'` fetch labels them `'auth-pending'`, `'applied'` and `'dropped'` label nothing, and missing slots left unlabelled are `'uncached'`. Where two labelled ranges meet one missing slot, the one that starts first labels it; on equal starts, the one from the earlier round, then the one issued first.

5. **Version fence** (N29 as amended 2026-10-31, read with shared fetches). Every clear of the cache (`cacheCleared`: a version mismatch inside a put, `clear` or `clearAll`) advances its generation, makes every entry issued before it not joinable, and each such fetch's response is dropped on arrival, except that the fetch whose own put caused a version clear is applied (§4.9). Every get awaiting a dropped fetch sees `'dropped'`, whether it issued that fetch or joined it.
   - _Who re-plans._ A get plans a second round when its first round ends under another generation than the one it was planned under. A round is planned under the generation in force in its synchronous step (rule 2). It ends when the get stops awaiting, because every fetch it awaited has settled or an auth flip released it (rule 4), and the generation is compared in the continuation of that await, the same synchronous step in which the get then either reads (rule 4) or plans its second round. Every fetch a round awaits was issued under the generation the round planned under (its own fetches, and the joined ones, which are joinable, rule 1), so a `'dropped'` outcome implies a clear, and the trigger as first written is one case of this one. The others are a clear that wiped fetches the get awaited after they were applied, its own or joined ones, by whichever put or call caused it, the put of the get's own response included. Its `blocked` is then the ranges of the fetches it awaited in the first round that came back `'failed'` or `'auth'`. The second round is an ordinary round (rule 2): it subtracts and joins among the entries issued after the clear, so the gets that re-plan after one clear share the refetch: the first to re-plan issues it, the others join it. While auth is invalid or a hook is running, the second round is gated like any other (rule 2, step 3), and the slots it would fetch come back `'auth-pending'`. A get never plans a third round, and its second round's result is final: when a fetch it awaited in its second round is dropped, or a clear during its second round wipes what that round fetched, its missing slots come back `'uncached'`, even if the get that issued that fetch is still in its first round and fetches once more.
   - _What is refetched._ Every slot still missing inside the get's request when it re-plans, outside `blocked`: what was in flight at the clear and what the clear wiped, whether the get fetched it itself or joined it. Each such slot is fetched once across the gets that re-plan after the clear (rule 1). When nothing in the request is missing by then (the clear wiped only slots outside it, or the clearing response covered what it wiped), the second round issues nothing and joins nothing, and the get reads at once: one more coverage read and plan, no request.
   - _What each get sees._ The cache after its last round: points put after the clear, never a response fetched before it.
   - _As first written_ (until 2026-10-31): a get planned its second round only when a fetch it awaited in its first came back `'dropped'`, so a get whose awaited fetches were all applied, the clearing one among them, planned no second round and reported the slots the clear wiped `'uncached'`. User decision #10, option B (DC-1 in `docs/reviews/step-44.md`), replaced that trigger with the generation comparison above; `docs/reviews/step-47.md` records the change.

6. **Auth** (§4.9 unchanged, read with shared fetches).
   - A get never joins a fetch issued under an earlier auth generation (rule 1). After `updateAuth` switches the generation, a get fetches those slots again with the new context, while the old fetch runs on and is applied if it succeeds.
   - While auth is invalid or a hook is running, a get joins nothing and fetches nothing (rule 2, step 3): it never waits, not even on fetches in flight that may still succeed.
   - Any auth flip releases every waiting get. The fetches each still awaits, its own and joined ones, come back `'auth'`, their missing slots `'auth-pending'`, and they finish in the background. A get released in its first round after the cache was cleared still plans its second round, under the gate, so the slots the clear wiped come back `'auth-pending'` too (rule 5). Auth stays invalid until the next `updateAuth`, which also switches the generation, so no get joins them again.
   - A joined fetch refused with `tscache:auth-invalid` under the current generation flips the state and broadcasts `authInvalid` with that fetch's context (N33), whichever get issued it. If the get's own fetch had already been applied, its slots come back present and the joined fetch's slots `'auth-pending'`. If the get's own fetch is still out at the flip, its slots come back `'auth-pending'` too, and its later success is applied for the next get.
   - A joined fetch issued under a generation that `updateAuth` has since replaced, refused with the marker, flips nothing and comes back `'auth'` (§4.9). Its slots are `'auth-pending'` although auth is valid, and the consumer's next `get` fetches them with the new context, as for a get's own fetch before this rule.

7. **Errors** (_replaces_ "`'fetch-failed'` for that `get` only", §4.9). A joined fetch that rejects, or whose response the put rejects (`PutError`), comes back `'failed'` to every get awaiting it; each reports the missing slots of its range `'fetch-failed'` with that error. Nothing is cached about the failure, and the entry has left the list before any of those gets resumes (rule 1), so the next get plans those slots afresh. In a second round a get neither refetches nor joins a fetch for the uncovered slots it saw fail in its first (`need` excludes `blocked`); a blocked slot that has since been covered can still be the flank or bridge of a new fetch, as `planFetches` extends into it today (rule 3).

8. **Abort, dispose, and fetches that never settle (N65).** There is no abort: `GetOptions` and `FetchRequest` carry no signal, and the orchestrator never cancels a fetch, before this rule or after it. A fetch belongs to the worker, not to the get or the connection that issued it. When a client disposes, or its tab goes away, its pending gets go unanswered, but the fetches they issued stay in the list, joinable, and are applied when they land; the gets of other tabs awaiting them resolve as usual. Their `mergeWarning` events carry the request id of the get that issued the fetch (§2.7): when that tab has gone, no console prints them, and a get that joined prints nothing, as for an identical range before. A fetch that never settles holds every get awaiting it, which is now every get that needs one of its slots rather than every get of the identical range. The orchestrator adds no timeout (N32, N44); a fetcher bounds its own requests (§2.5).

9. **Invalidate fences joins (N64).** `Orchestrator.invalidate` calls `engine.invalidate(cacheId, range)`, whose errors propagate before anything is fenced, then sets `fenced` on every entry of the cache whose range meets the range snapped outward. A get issued after an invalidate therefore fetches the invalidated slots anew rather than await a fetch issued before it. Fencing is per entry: a fetch meeting the range in one slot is no longer joinable for any of its slots, which over-fetches as `invalidate` over-invalidates (N1). The fenced fetch is still applied when it lands, as before this rule, so a fetch in flight across an invalidate can cover the range again with what it fetched before (decision concern DC-2). `put`, `hydrate` and `setFinalizedUntil` fence nothing; `clear` and `clearAll` act through the generation (rule 5).

10. **`cacheOnly` and no fetcher** (unchanged). Such a get reads at once: it plans nothing, awaits nothing and adds no entry, and fetches in flight neither delay it nor see it.

11. **Several tabs.** One orchestrator serves every connection of its worker, so a cache's list spans tabs: a get from one tab awaits fetches issued for another, and its own fetches serve theirs. A dedicated worker or an in-process client serves one page, where subtraction applies between that page's concurrent gets, as in a fast scroll. Separate workers share nothing.

12. **Bounds (N62).** A round reads each coverage range around the request, each entry of the cache's list and each range of `blocked` a bounded number of times. One pass over the list in start order keeps the joinable entries and the running union of their ranges; one two-pointer pass over those and the pieces of `need` finds `join`; `fetch` comes from the sweeps of `planFetches`, with the union and `blocked` as the cuts. A round is therefore linear in those counts plus its pieces, as step 36 made the coverage sweep. Its fetches are merged into the list in one pass, and an entry is removed by identity in one pass. Binary search over the list does not work: ends are not ordered by start (an entry of one or two slots can sit inside one that bridged over it, and entries that are no longer joinable overlap anything), and the list holds only the fetches outstanding for one cache. There is no cap on the fetches a get awaits: each costs one promise reaction, and a cap would need a fallback that fetches in-flight slots again, the duplicate traffic this rule removes. A round awaits at most the joinable entries of the cache plus its own fetches.

13. **Budgets.** Exact, in `test/perf/counters.test.ts`: a fast scroll, each read issued before the earlier fetches resolve, fetches what its reads need plus the one-interval flank and nothing more, with one fetch and one engine read per read; and a round over thousands of in-flight entries and coverage fragments reads each of them a few times. The end-to-end scenario `fast-scroll` counts the bars the backend serves for the same scroll in Chromium, checked; its timing is report-only. The numbers and setups are in `docs/reviews/step-44.md`.

### 4.10 Internal contracts — IndexedDB persistence (N45–N61, 2026-10-30; redesigned after review round 2; narrowed to the SharedWorker hosting 2026-10-31)

Persistence keeps a cache's authoritative data in IndexedDB, so a reload or a new tab starts from what earlier sessions fetched: immutable history, the primary use (N11), is fetched once per device instead of once per session. It realises the settled notes of starter §3.7 (write-behind, volatile region excluded, coverage reconciled against what is stored, a schema version on every record) and the sketch in `docs/roadmap.md`, through decisions N45–N61. **Only the SharedWorker hosting persists** (user decision of 2026-10-31, N52): one engine then owns the database of its origin and is its only writer. In the dedicated-worker and in-process hostings, where each tab has an engine of its own, `persist: true` does nothing (§4.10.1, §4.10.7); their `clearAll` still empties the database, with a clear-only call (N66, user decision #11 of 2026-11-02). It was built in two slices (`docs/reviews/step-38.md`): (a) records, loading and write-behind in the SharedWorker hosting; (c) the quota stop and the SharedWorker's extended lifetime (step 57, `docs/reviews/step-57.md`). Slice (b), which let several engines share the database, was retired on 2026-10-31 (N52).

Two rules carry the design, and every later paragraph follows from them. **Memory is canonical:** the disk is never merged with live memory slot by slot. A load applies records only into a cache that knows nothing yet, and a cache that changed while its load was pending starts without the records and rewrites them from memory (§4.10.5); a flush writes what memory holds and never reads the disk (§4.10.6). **One deadline:** every write transaction is a job of one writer per persister, due at a known time and failed for good `timeoutMs` later, whatever it was waiting for: the queue, a store call or a retry (§4.10.6). A call that waits for a removal therefore waits for at most two deadlines.

Strict test-first applies to `CacheState.restore`, the `Persister` and the store contract (§4.10.3–§4.10.6): their contract tests are written from this section before the code. The hosting wiring (§4.10.8) is tested with the code.

Dependency rule, extended: `persist/` imports `engine/`, `grid`, `coverage`, `segment/` and `types`; nothing under `engine/`, `grid`, `coverage` or `segment/` imports `persist/`, and none of them gains a DOM, worker or timer reference (§4.6). Timers and IndexedDB live in `persist/` and in the hostings. Nothing an application loads without a persisted cache carries the persistence code (§4.10.8): `engine/restore.ts` is imported only by the persister, and the persister, the record builder, the IndexedDB adapter and the clear-only call are a chunk loaded on demand: by the SharedWorker at its first persisted cache or `clearAll`, by the other hostings at their first `clearAll`.

#### 4.10.1 Public surface (all additive)

```ts
interface CacheConfig {
  // …§2.2, plus:
  /**
   * Keep this cache in IndexedDB across sessions (§4.10). Structural (N20):
   * every tab must pass the same value. Default false. Acts only when the
   * client's mode is 'shared' (N52); elsewhere accepted and ignored (N45).
   */
  persist?: boolean;
}

interface ResolvedCacheConfig {
  // …plus:
  persist: boolean;
}

interface ClientEvents {
  // ── cache-scoped ──, plus:
  /**
   * Persistence of this cache stopped (N47). The cache goes on in memory;
   * nothing more is written for it while its worker (or page) lives.
   */
  persistStopped: {
    cacheId: string;
    reason: "quota-exceeded" | "unavailable" | "error";
    /** The underlying failure, when there is one. */

// client/cache.ts
type CacheEvent = "cacheCleared" | "mergeWarning" | "persistStopped";
```

Rules:

- **Validation.** `persist` resolves to `false` when omitted; a value that is not a boolean throws `ConfigError` (`persist must be a boolean when set, got …`). It is structural under N20's rule (every resolved field except `version` and `finalizedUntil`): joining a live cache with another value throws `ConfigError` naming `persist`, and the live cache is untouched. There is no new error class or code: a persistence failure never rejects a call (below).
- **Where it acts.** A persisted cache is loaded and written by the SharedWorker's persister, the only hosting that has one (N52). Everywhere else `persist: true` is accepted, validated and kept structural, and does nothing, without an event (N45): in the dedicated-worker and in-process hostings (on a browser without `SharedWorker`, after a fallback, or when `ClientOptions.mode` pins them), where the realm has no IndexedDB (Node, so every server render), and for an `Engine` used directly through `./engine`. A consumer tells the cases apart by `client.mode` (§2.1): a persisted cache persists when it is `'shared'` and the browser has IndexedDB. Where it does not, `cache()` does not wait for a load and nothing is written. `clearAll` still empties the disk from a dedicated-worker or in-process client whose realm has IndexedDB (N66, §4.10.7); without IndexedDB (Node) it clears memory only. No event is emitted, as in Node: the configuration is not a failure, and an event at every open in every such tab would only be noise.
- **What persists.** The covered ranges below the watermark and the points inside them (§4.10.2). The volatile region never reaches the disk (starter §3.7); after a reload the provisional tail is fetched again, as in a running session. A cache opened with `persist: true` starts from the stored records, unless something changed it before they were applied (§4.10.5). A range the stored records do not cover, including one whose record the browser evicted, reads as uncached, never as a confirmed gap.
- **When calls wait for the disk.** `cache()` of a persisted cache resolves after its records are loaded and applied, after the load gave up (5000 ms, §4.10.6), or after the load was abandoned because the cache changed meanwhile, so the first `get` through its handle sees the records. A call that removes coverage of a persisted cache resolves only once the removal is durable (N58): `invalidate`, `clear`, `clearAll`, a `setFinalizedUntil` that moves the watermark back or sets the first one, and also a `put`, `hydrate` or orchestrated `get` whose data cleared the cache for a newer version or set its first watermark. Durable means written with strict durability, or else persistence of the cache has stopped and the deletion of its records has settled. The wait is bounded by one deadline (§4.10.6): the write has `timeoutMs` (5000 ms) from the removal to land, retries included; then the cache stops, and the deletion that follows is bounded the same way. A `clearAll` pending at the removal, or called after it, settles the removal itself within the same bound (§4.10.6, `clearAll`). On a failing disk such a call therefore takes at most about 10 s, and it never rejects. Nothing else waits: additions are written behind (§4.10.6), and a persistence failure emits `persistStopped` instead of rejecting. A stop during `cache()` is emitted before the handle exists: subscribe with `client.on('persistStopped', …)` to hear it.
- **What can outlive a removal.** Only a disk that refuses every write: when the removal's write has not landed by its deadline and the deletion that follows the stop fails or times out too, the records written before the removal stay, and a later session that can read them loads them. The same holds for a `clearAll` whose job fails at its deadline: every record stays. `persistStopped` reports the stop; nothing in a later session can tell. The worker that failed to clear loads nothing more for the rest of its life (§4.10.6), so the data a failed logout left on disk comes back only in a later worker. A failed clear-only call of a dedicated-worker or in-process client leaves every record too; that hosting never reads the disk, so here also the records come back only in a SharedWorker started later (N66).
- **Version honesty across sessions** (§2.4). A restatement without a version signal is undetectable, and persistence carries that across reloads: a stored range is served without asking the backend in every later session. Set `CacheConfig.version` when the dataset has one, and stored records of another version are never loaded (N56). TTL stays a consumer pattern: `invalidate` or `clear` on your own clock removes stored ranges too.
- **One writer.** Every tab of a deploy reaches one SharedWorker, so one engine writes the database, and a `clearAll` from any of those tabs clears that engine's memory and the disk together. A `clearAll` from a dedicated-worker or in-process page empties the disk but cannot reach the SharedWorker's memory: that engine writes back what it holds at its next flushes (§4.10.7). Two SharedWorkers write it only for a moment: during a deploy skew (two worker URLs), or while a worker that lost its last tab is still closing as a new tab starts the next. Each writes from its own memory, and page records are self-contained, so the overlap costs coverage, never a wrong point; what one engine removed, the other may still hold and write back once (§4.10.7).
- **Durable storage is the app's call (N48).** Browsers evict best-effort storage under pressure, an origin at a time, and the load rule absorbs it. An app that wants its cache kept calls `navigator.storage.persist()` itself; the library never does, since some browsers prompt the user.
- **Sensitive data.** Stored records are readable by every script of the origin and outlive the session until `clearAll`. Keep per-user or sensitive caches in memory; that is why `persist` is per cache (N45).
- **Protocol.** No new op. `persistStopped` travels as `{ t: 'evt', scope: 'cache', cacheId, event: 'persistStopped', payload }`. `PROTOCOL_VERSION` stays 1 (as N37): an older worker ignores `persist` (config validation keeps only the fields it knows, `engine/validate.ts`) and never emits the event; an older client ignores the unknown event name (`ClientEmitter.receive`, `client/events.ts`).

#### 4.10.2 Database and records (N51, N53, N55)

One database per origin, named `tscache`, at IndexedDB version 1. Its upgrade from version 0 creates two object stores without indexes: `caches`, key path `'cacheId'`, and `pages`, key path `['cacheId', 'page']`. Keys sort by cache id, then numerically by page, so one key range reads or deletes every page of a cache, or a run of its pages (lazy loading, later, §4.10.10).

```ts
// persist/records.ts
/** Store 'caches': one per persisted cache. */
interface CacheRecord {
  cacheId: string;
  /** Schema version of the persisted records. */
  format: 1;
  /** The structural config (N20) the records were written under. */
  config: {
    interval: number;
    alignmentOffset: number;
    fields: Record<string, Dtype>;
    gapSplitK: number;
    segmentSlotCap: number;
    warnOnOverlapDiff: boolean;
  };
  /** The dataset version and the watermark when written; each omitted when unset. */
  version?: string;
  finalizedUntil?: number;
}

/** Store 'pages': one per page that holds coverage. */
interface PageRecord {
  cacheId: string;
  /** floor(slot / segmentSlotCap) of every slot of `snapshot` (N15); may be negative. */
  page: number;
  /** The page's covered slots and the points inside them (§2.8). */
  snapshot: Snapshot;
}
```

**Canonical records.** `recordsOf(S)`, for the state `S` of a persisted cache, is what a flush writes and, with a single writer, what the disk holds after it (§4.10.6); it has the shape of a `StoredCache` (§4.10.3), pages ascending. When `S` covers nothing, it is empty (`{ cache: undefined, pages: [] }`), so a cleared cache leaves nothing on disk. Otherwise:

- One cache record: `cacheId`; `format: 1`; `config`, the six fields of `S.config` (`fields` a fresh object in schema order); `version` and `finalizedUntil` as `S` reports them, each omitted when undefined.
- One page record for each page `p` that holds coverage. Page `p` spans slots `[p · cap, p · cap + cap − 1]` with `cap = segmentSlotCap`: the pages of the segment store (§4.3, N15). Let `cov_p` be `S`'s covered slot ranges clipped to page `p`. When it is not empty, its _hull_ runs from its first slot to its last, and the record's `snapshot` is the _page snapshot_: the envelope of `S.snapshot(toMs(hull))` (§4.5) without its `finalizedUntil`, whose `segments` are the payloads of `S.snapshot(toMs(r))` for each range `r` of `cov_p`, in order. Its `range` is therefore the hull in ms, its `coverage` is `cov_p` in ms, its `segments` hold exactly the present points inside `cov_p` (one payload per store segment per covered range; a segment never crosses a page edge, N15), and its `version` is `S`'s.
- Nothing else: a page without coverage has no record.

Consequences the tests rely on:

- **A record holds exactly what a load applies.** No point outside coverage is stored: not a point whose coverage was invalidated, not one that was provisional when fetched, not one at or after the watermark (coverage never reaches the volatile region, §4.5, so no hull does). Restoring `recordsOf(S)` into a cache that knows nothing (§4.10.5) therefore gives a cache whose records are `recordsOf(S)` again.
- A covered page without points, a confirmed gap, is a record with `segments: []`, so the gap survives a reload.
- Equal states have equal records (§2.8: a snapshot is a function of the state and the range).
- The buffers are fresh copies and IndexedDB clones them on write; cache-owned memory never leaves (§3.3).
- A page record is self-contained: it names its grid, schema, version, range and coverage, so it is checked and applied on its own, whoever wrote it (§4.10.5). This is why coverage is stored per page rather than in the cache record (N55).

The page snapshot omits `finalizedUntil` so that a watermark change rewrites the cache record only; a load applies the cache record's watermark.

**Format and versioning.** Each layer carries its own version, and each mismatch has one outcome:

| Layer                 | Version                                                                                                  | On a mismatch at load                                                                                                                                                          |
| --------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Database layout       | IndexedDB version 1                                                                                      | A database at a higher version (a newer deploy) cannot be opened: persistence is `'unavailable'` for this engine. A later layout bumps the version and migrates in its upgrade |
| Records               | `CacheRecord.format: 1`                                                                                  | The cache's records are not applied; the cache rewrites them at its next flush                                                                                                 |
| Structure             | `CacheRecord.config` against the cache's N20 fields (`fields` by names and dtypes, key order irrelevant) | Not applied; rewritten                                                                                                                                                         |
| Dataset               | `CacheRecord.version` against the cache's version (N56)                                                  | Not applied; rewritten                                                                                                                                                         |
| Snapshot and payloads | `Snapshot.format: 1` and each payload's `format: 1` (§2.8, §3.4)                                         | That page is skipped; the cache is rewritten                                                                                                                                   |

A mismatch clears nothing in memory and emits nothing: the cache starts without the stored records, and its own records replace them at its next flush, a full rewrite (§4.10.6).

#### 4.10.3 Store interface and test seam (N60)

Persistence reaches IndexedDB through one narrow interface. The logic above it is tested against an in-memory fake; the IndexedDB adapter is held to the same contract by a conformance suite.

```ts
// persist/store.ts
/** Inclusive range of page indices; ±Infinity allowed. */
interface PageRange {
  start: number;
  end: number;
}

/** The stored records of one cache. */
interface StoredCache {
  cache: CacheRecord | undefined;
  /** Ascending by page. */
  pages: PageRecord[];
}

/** One atomic write: deletions, then page puts, then the cache record. */
interface WritePlan {
  /** Every page record of the cache whose page lies in one of these ranges goes. */
  deletePages: PageRange[];
  /** Each replaces the record under its key; every cacheId is the write's. */
  putPages: PageRecord[];
  /** The cache record to put, or null to delete it. */
  putCache: CacheRecord | null;
  /** Strict durability: set when the plan carries a removal (N49, N58). */
  strict: boolean;
}

interface PersistStore {
  /** One read-only transaction: the cache record and its page records, all of them or those in `pages`. */
  read(cacheId: string, pages?: PageRange[]): Promise<StoredCache>;
  /**
   * One read-write transaction, with strict durability when `plan.strict`
   * and relaxed otherwise (N49): all of the plan or none of it. Resolves when
   * the transaction completed. Rejects with the transaction's error, whose
   * `name` is 'QuotaExceededError' when the origin's quota is exceeded.
   */
  write(cacheId: string, plan: WritePlan): Promise<void>;
  /** One read-write transaction with strict durability: every record of every cache goes. */
  clearAll(): Promise<void>;
  /** Releases the connection; every later call rejects with an error named 'InvalidStateError'. */
  close(): void;
}

// persist/idb-store.ts
/**
 * Opens the database through `factory`, creating or upgrading it (§4.10.2).
 * With `ifExists`, resolves undefined and creates nothing when
 * `factory.databases()` does not list it. Rejects when it cannot be opened.
 */
function openIdbStore(
  factory: IDBFactory,
  options?: { name?: string; ifExists?: boolean },
): Promise<PersistStore | undefined>;
```

The store takes no signal and no timeout: a call the persister has given up on (§4.10.6) is left to settle on its own, and its result is ignored. The store contract, which the conformance suite checks against `MemoryStore` and against `openIdbStore` over `fake-indexeddb`:

- **Copies.** Records are structured-cloned in and out: changing a record after `write`, or a result of `read`, changes nothing stored. `ArrayBuffer`, `Uint8Array` and `NaN` survive with their types and bytes.
- **Read.** An unknown cache reads `{ cache: undefined, pages: [] }`. Pages come ascending by page number, negative ones first. With `pages`, only records whose page lies in one of the inclusive ranges, ascending, each once even where ranges overlap.
- **Write.** Deletions, then page puts, then the cache record; records of other caches are never touched. Atomic: when any part fails (a record that cannot be cloned, say), nothing of the plan is stored and the promise rejects with an error whose `name` is the failure's (`DataCloneError` in that example).
- **Clear all.** Afterwards every cache reads empty.
- **Close.** Later calls reject with an error named `'InvalidStateError'`. The IndexedDB store also closes itself on its database's `versionchange` event, so a newer deploy's upgrade is not blocked.
- **`openIdbStore` alone.** The database it creates has the name, version, stores and key paths of §4.10.2. With `ifExists`, against a factory without the database, it resolves `undefined` and the factory still lists no such database.

`MemoryStore` (`packages/tscache/test/persist-memory-store.ts`, a test helper) implements the interface over maps, cloning with `structuredClone`, and adds what the tests need: a log of every `read`, `write` (with its plan, `strict` included, since durability itself cannot be observed) and `clearAll`; failure injection (the next `n` calls of a kind reject with an error of a given `name`, or every call does); gates that hold a call pending until the test releases it; and direct access to the stored records, to inspect them or to plant foreign, corrupt or other-version records.

Why this seam: the logic under test (the load and its abandon rule, scheduling, the writer's deadlines, failure handling) needs what a real or emulated IndexedDB does not give: failing a chosen transaction with a chosen error (`fake-indexeddb` has no quota to exceed), holding a transaction open while engine calls run, and counting transactions, all deterministic under Vitest's fake timers, which would also capture the `setImmediate` that `fake-indexeddb` schedules its work with. `fake-indexeddb` (a dev dependency, first imported in slice (a)) tests the adapter only: compound keys, key ranges with ±Infinity bounds, atomic abort and clone semantics. Playwright covers Chromium's own IndexedDB (`docs/reviews/step-38.md`).

#### 4.10.4 What a change marks (N57, N58)

`CacheStateHooks` (§4.5) gains `onChange`, called synchronously after each change to what persistence stores, in slot terms. It reports; it never alters the operation.

```ts
// engine/cache.ts
type CacheChange =
  /** Points or coverage below the watermark may have changed in these slots. */
  | { kind: "write"; slots: SlotRange }
  /** Coverage was subtracted over these slots. */
  | { kind: "remove"; slots: SlotRange }
  /** Every point and all coverage went. */
  | { kind: "clear" }
  | { kind: "version" }
  | { kind: "watermark" };

interface CacheStateHooks {
  onVersionClear?: () => void;
  onChange?: (change: CacheChange) => void;
  /**
   * Called once at the end of every mutating call (put, hydrate, invalidate,
   * clear, setFinalizedUntil) that passed validation, after that call's
   * onChange calls and before it returns or rethrows; never by get, snapshot,
   * coverage or restore. The load's abandon signal (§4.10.5), independent of
   * whether the call changed anything the disk holds.
   */
  onMutate?: () => void;
}
```

`onMutate` is independent of the table: it fires for every mutating call that passed validation, including one that reports no change (a put wholly inside the volatile region, with or without a range; an empty put; a `setFinalizedUntil` to the current value; a `hydrate` that applies nothing, skipped for its version or not). It exists so that a pending load observes every mutation of its cache, not only those the disk cares about (round 3, R3-2); for a running cache the persister ignores it.

The persister maps slots to pages (`floor(slot / segmentSlotCap)`, computed exactly as the segment store does) and keeps, per cache: whether it is _loading_, _running_ or _stopped_; the dirty pages; a `rewrite` flag; and the number of removals (`remove` and `clear` changes) recorded and the number of them durable (§4.10.6). A `write` or `watermark` change makes the cache's flush due after a quiet spell; a `remove` or `clear` at once (N58); a `clear` or `version` change also sets `rewrite`, since every page record names the version (§4.10.2) and a cleared cache leaves nothing on disk. The first `onChange` or `onMutate` of a cache whose load is pending abandons the load (§4.10.5). A put wholly inside the volatile region marks nothing, so a live tail costs no disk write.

The persister reaches a cache's `CacheState` and its change hook through an internal accessor of `engine/engine.ts` that no package entry exports; the surface of `./engine` does not change.

#### 4.10.5 Loading: memory is canonical (N56, N57)

A load reads a cache's records in one read-only transaction (every page, at open: N46) and applies them in one synchronous call, `CacheState.restore`, into a cache that knows nothing yet. The disk is never merged with live memory:

1. **Handles wait.** `cache()` of a persisted cache resolves only after its load has settled (§4.10.8), so no call through a handle reaches the cache while its load is pending; a second tab opening the same cache waits for the same load.
2. **A mutating call abandons the load.** Any mutating call on the cache while its load is pending, `put`, `hydrate`, `invalidate`, `clear` or `setFinalizedUntil`, whatever it changed and whether or not the disk would care (a put wholly inside the volatile region included; round 3, R3-2), abandons it: the persister hears the call through `onChange` or `onMutate` (§4.10.4), nothing stored is applied, the read's result is ignored when it comes, and the cache is marked for a full rewrite, so its next flush replaces the stored records with its own (§4.10.6). What reaches a loading cache this way is a `clearAll` from another tab, whose `clear` reaches every cache; a raw request by cache id without a handle; or anything an `Engine` driven directly does. Memory is canonical; the cost is a cold start, in a case that handles make unreachable in ordinary use.
3. **A load never starts during a `clearAll` barrier.** From a `clearAll()` call until its job settles, through every retry, the writer holds every flush and the disk is not read for a load: the barrier (§4.10.6, N54). A cache opened in that time reads nothing: its `open` resolves at once, it starts cold, and it is marked for a full rewrite, which the barrier holds until the clear has settled. Otherwise its read transaction, created before the clear's write transaction, would see the records the clear is about to delete, and the cache would serve and later persist data the `clearAll` removed (round 5, R5-1). A load already pending at the call is abandoned by the engine's `clear` (rule 2). When the clear succeeds, the rewrite then writes the cache's own records; when it fails, the cache stops with every other tracked cache, and no later open of this persister loads (§4.10.6). Either way the cold cache holds nothing from before the call.
4. **`restore` applies records only into a cache that knows nothing**: one that covers nothing and holds no point. It throws `TscacheError` before anything changes when the cache holds either, a programming error: every mutation abandons the load first (rule 2), so the persister calls it in no other state, and treats a throw as a stop with `'error'` (§4.10.6). No path therefore exists on which stored and live data of one slot are reconciled.

```ts
// engine/cache.ts
interface RestoreResult {
  /** The ranges covered by the load, in ms: ascending, disjoint, adjacent ones merged. */
  applied: Range[];
  /** The stored records are not what the cache now holds (a record invalid,
   *  skipped, of another version or clipped, or an orphan page): the next
   *  flush rewrites the cache. */
  rewrite: boolean;
}

class CacheState {
  // …§4.5, plus:
  /** Applies stored (untrusted) records into a cache that knows nothing; one synchronous call. */
  restore(stored: { cache: unknown; pages: readonly unknown[] }): RestoreResult;
}
```

`restore` takes the records as `unknown`, since they come from disk, and `engine/` imports no type from `persist/`. Its implementation is `engine/restore.ts`, which reaches the cache's store, coverage, version and watermark through an internal seam of `engine/cache.ts` (`cacheInternals`, exported by no entry) and which the persister installs when it is built (`installRestore`), so `index`, `engine` and the worker's initial load do not carry it (§4.10.8). Called before that, `restore` throws `TscacheError`. Its steps, in order:

1. **Precondition.** The cache covers nothing and holds no point (provisional or not); otherwise `TscacheError` whose message starts with `restore:`, and nothing changes.
2. **Cache record.** Absent (`undefined`) → nothing is applied, and `rewrite` is true when `pages` is not empty (orphans). Otherwise it must be an object with `format === 1`; a `config` whose six fields equal the cache's (`fields` naming exactly the schema's fields with equal dtypes, key order irrelevant); `version` absent or a non-empty string; `finalizedUntil` absent or accepted by `slotAtOrAfter`. Any failure → nothing is applied; `rewrite: true`.
3. **Version (N56).** With `C` the cache's version now and `R` the record's: when `C` is set and `R !== C` (an unversioned record included) → nothing is applied; `rewrite: true`. When `C` is unset and `R` is set, the cache adopts `R` without clearing (as N18). This is stricter than `hydrate`, which applies an unversioned snapshot to a versioned cache (N35): a record written without a version may hold any version's data, while a server's snapshot is as fresh as its page.
4. **Watermark.** The record's `finalizedUntil` advances the watermark as a put's `meta.finalizedUntil` does (N17: forwards only; a value at or below the cache's is ignored). The cache covers nothing, so the advance subtracts nothing. When the watermark after this step differs from the record's (`finalizedUntil` absent counting as a value of its own), `restore` reports a `watermark` change through `onChange` (§4.10.4), so the next flush writes the cache record; it reports nothing else.
5. **Pages,** ascending. A page record is valid when it is an object whose `cacheId` is the cache's, whose `page` is a safe integer, and whose `snapshot` passes `hydrate`'s validation (§4.5, steps (1)–(5)) against this cache, with every slot of its `range` in page `page`, `snapshot.version` equal to `R` (both absent counts as equal), and no `snapshot.finalizedUntil` (a page snapshot never carries one, §4.10.2). An invalid page is skipped and sets `rewrite: true`; the others are still applied. Only the cache record moves the watermark (step 4): nothing a page record holds can.
6. **Parts.** For each valid page, ascending: its coverage ranges in slots, minus the slots at or after `volatileFrom` (after step 4) when the cache has a watermark, are the parts. Each part is written with the page's decoded points inside it as authority (`store.put(points, part)`, a replace, N11) and then covered, exactly as `hydrate` applies a part (§4.5, application steps (3)–(4)); since the cache covers nothing and pages are disjoint, nothing else is subtracted. A part clipped by the volatile region (a record written by a session without a watermark, under a config that sets one) sets `rewrite: true`: memory refuses coverage the record claims. Points outside every part are not written; warnings are dropped.
7. **Result.** `applied` lists every part in ms, ascending, with adjacent ones (on neighbouring pages) merged. `rewrite` is false exactly when every record was applied in full, and then `recordsOf(S)` (§4.10.2) equals `stored`, apart from the cache record's `finalizedUntil` where step 4 reported a change.

A write that fails part-way (an allocation failure, §4.3) withdraws its part's coverage and rethrows, as in `hydrate` (§4.5); the persister then stops the cache with `'error'`.

**Atomicity.** The read is asynchronous; the apply is one synchronous call, so under the RPC server's one-call-per-message dispatch (§4.7) no other write runs inside it, and rule 2 covers everything that happened between the read and the apply: whatever changed the cache meanwhile, by whatever path, made the load moot. `hydrate` from a page runs after `cache()` resolved, so after the load, and fills only what the load left unknown (N35).

Properties the contract tests pin:

- (a) **Round trip.** For any state `S` of a persisted cache that covers something, and records `recordsOf(S)`, restoring them into a fresh cache `E` of the same structural config, created without a version or watermark: for every range `R`, `E.coverage(R)` equals `S.coverage(R)` and `E`'s points inside it are `S`'s; `E.version` is `S.version`; `E.finalizedUntil` is `S.finalizedUntil`; `rewrite` is false; no change is reported; and `recordsOf(E)` deep-equals `recordsOf(S)`.
- (b) **Knows nothing, or throws.** `restore` into a cache with a covered slot, or with a point, covered or not, provisional or not, throws `TscacheError` and changes nothing. That includes the state of review round 1 (R1-1): watermark 100, a provisional point at 150 with value 20, stored records with watermark 200 covering 150 with value 10: afterwards the point is 20, slot 150 is uncovered, and the watermark is 100.
- (c) **Versions.** The cases of step 3: equal; both unset; cache unset (adopts); cache set and record unset or different (nothing applied, `rewrite`).
- (d) **Robustness.** A cache record failing any check of step 2, a differing structural field included, applies nothing; a page record failing any check of step 5 (a snapshot carrying `finalizedUntil` included: with the cache record at watermark 100 and a page snapshot saying 200 over coverage of 150, slot 150 stays uncovered and the watermark stays 100) is skipped, the others are applied, and `rewrite` is true; orphan pages without a cache record give `rewrite` with nothing applied.
- (e) **Gaps.** A page whose snapshot has coverage and no segments restores a confirmed gap: `get` over it returns coverage, no point and no miss.
- (f) **Watermarks.** A cache created with `finalizedUntil` above the record's keeps its own, and `restore` reports `watermark`; one created below the record's advances to the record's and reports nothing; a record without a watermark restored into a cache with one applies no coverage at or after it, and `rewrite` is true.
- (g) **Convergence** (with the persister, §4.10.6): after `open` and one flush, the store holds `recordsOf(S)` in every case above.

#### 4.10.6 The persister: open, the writer, write-behind and flush (N46, N49, N50, N54, N58, N59, N61)

```ts
// persist/persister.ts
interface PersisterOptions {
  /** Quiet time before a flush is due, and the delay before a retry. Default 1000 ms. */
  debounceMs?: number;
  /** Longest a change waits before its flush is due. Default 5000 ms. */
  maxDelayMs?: number;
  /**
   * The one deadline (N61): how long a load may take from open(), and how
   * long a job of the writer (a flush, a clearAll, a cleanup) has from the
   * moment it is due, whatever it waits for. Default 5000 ms.
   */
  timeoutMs?: number;
  /** Called once for each cache whose persistence stops. */
  onStopped?: (event: ClientEvents["persistStopped"]) => void;
}

class Persister {
  /**
   * `openStore` is called lazily: by the first open(), or by a clearAll()
   * before any open(), which passes { ifExists: true }. A store it returns is
   * kept for the persister's life; an `undefined` result (no database yet)
   * lets a later open() call it again.
   */
  constructor(
    engine: Engine,
    openStore: (options?: {
      ifExists?: boolean;
    }) => Promise<PersistStore | undefined>,
    options?: PersisterOptions,
  );
  /**
   * Starts persisting a cache: loads and applies its records. Idempotent.
   * `startedAt` (a `performance.now()` time, default now) starts the load's
   * deadline earlier: the hosting's lazy loading of the persister counts
   * against it (§4.10.8).
   */
  open(cacheId: string, startedAt?: number): Promise<void>;
  /** Makes the flush of one cache, or of every running cache with dirty state, due now; resolves when those jobs settled. */
  flush(cacheId?: string): Promise<void>;
  /** How many removals (`remove` and `clear` changes) have been recorded for the cache; 0 when untracked. */
  removals(cacheId: string): number;
  /**
   * Resolves once every removal recorded for the cache so far is durable, or
   * once its persistence has stopped and its cleanup has settled (N58).
   */
  durable(cacheId: string): Promise<void>;
  /**
   * Empties the disk (N54), holding every flush and load until its job
   * settles; resolves once the disk is empty, or once every tracked cache
   * has stopped.
   */
  clearAll(): Promise<void>;
  /** Flushes, then closes the store. */
  close(): Promise<void>;
}
```

None of these rejects for a persistence failure; failures stop the cache (below). `open` rejects with `UnknownCacheError` for an id the engine has no cache under, a programming error.

**Open.**

- For a cache whose `persist` is false, `open` resolves at once and does nothing.
- The first call for a cache starts tracking it: the cache is _loading_, and from then on its changes (§4.10.4) are observed. The hosting calls `open` in the same synchronous step that creates the cache (§4.10.8), so no change precedes it.
- During a `clearAll` barrier (below), a new cache reads nothing (§4.10.5, rule 3): it is _running_ at once with `rewrite` set, and `open` resolves. It starts no store opening of its own, and its first flush, due after the quiet spell like any change, is held until the barrier settles. After a `clearAll` that failed, a new cache stops at once with that job's reason, reads nothing and has no cleanup (below).
- Otherwise the store is opened, once per persister (concurrent opens share the attempt; `open` never passes `ifExists`). When `openStore` rejects, or resolves `undefined`, this cache and every persisted cache opened later stop with `'unavailable'`.
- Then one `store.read(id)` for every page; a rejection stops the cache with `'error'`. On success, if the cache is still loading, `restore(stored)` in one synchronous step: the cache is _running_; `rewrite: true` sets the cache's `rewrite` flag and makes its flush due at once; a `watermark` change it reports is dirty state as any other. An error thrown by `restore` (an allocation failure, §4.3, or its precondition) stops the cache with `'error'`.
- **A mutating call abandons the load.** The first `onChange` or `onMutate` of a loading cache (§4.10.5, rule 2) makes it _running_ at once with `rewrite` set, cancels its load timer, and resolves `open`; the changes of that call and of later ones are recorded as for a running cache. The abandonment itself makes the cache's flush due as a `write` change would, after the quiet spell; a `remove` or `clear` among the call's changes makes it due at once, strict. A read not yet issued is not issued; a pending store opening or read goes on, and its result for this cache is ignored.
- `open` resolves after the restore, or when `timeoutMs` passes first (the store's opening and the read counted together): the cache then stops with `'unavailable'` and the read's result, should it come, is ignored.
- A later call for the same id returns the first call's promise, so a cache is read once per persister. For a stopped cache it resolves at once.

**The writer (N61).** One per persister. It runs the persister's write transactions one at a time: flushes, `clearAll`, and the cleanup that follows a stop. Each is a _job_ with a due time and a deadline `timeoutMs` after it. Jobs run in order of due time, except that a job carrying a removal (a flush whose dirty state holds a removal not yet durable, a `clearAll`, a cleanup) runs before any queued job that carries none. A pending `clearAll` job is also a barrier: from its call until it settles, no flush job starts, and the job running at the call makes a final attempt, with no retry and no stop (`clearAll`, below); the rules that follow hold apart from that. The writer takes no lock: it is the database's only writer (§4.10.7). An attempt waits for the store's opening, counted against its deadline; when the persister has no store and none is opening, which happens only after a `clearAll` found no database, a flush's attempt opens it as `open` does (Open, above). An attempt whose store call rejects puts its dirty state back and schedules a retry: a request for the same cache due `debounceMs` later, coalesced into the cache's one queued job like any other request (Scheduling, below) and keeping the failed job's deadline; when that retry would be due after the deadline, the job fails at the deadline instead. A store call still pending at the deadline is abandoned: its result is ignored, and a transaction that completes later is harmless, since the cleanup queued after it runs after it (IndexedDB runs overlapping read-write transactions in creation order). At the deadline the job fails for good: a flush or a cleanup job stops its cache, with `'error'` and the last rejection's name and message when an attempt was rejected, else `'unavailable'`; a `clearAll` job stops every tracked cache the same way. Queue wait, store calls and retries all count against the one deadline, so every job settles within `timeoutMs` of being due, and no call waits for the disk longer than two deadlines: a job, and the cleanup after its stop.

**Scheduling.**

- A `write`, `version` or `watermark` change of a running cache makes its flush due `debounceMs` after the latest such change, and no later than `maxDelayMs` after the first change not yet flushed: a feed pushing every 500 ms is still written every 5 s.
- A `remove` or `clear` makes it due at once (a zero-delay timer, so the operation's own call completes first; N58), and the job carries a removal.
- A loading cache has nothing dirty, since a change abandons its load; no flush runs during a load.
- During a `clearAll` barrier every request (from a change, `flush` or `close`) is held. When the barrier settles, a held request becomes due at the later of its own due time and the settling, and its deadline is `timeoutMs` after that, so time spent behind the barrier never counts against it (`clearAll`, below).
- At most one queued flush job per cache: a request while one is queued joins it (the earlier due time, the earlier deadline, and the removal when either had one); a request while the cache's job is running queues the next, which runs after it. One flush per cache at a time. A retry is such a request (The writer, above), so a failed job and a removal that arrived meanwhile become one job, bounded by the earlier of the two deadlines.
- `flush(id)` makes the cache's flush due now and resolves when that job settled, success or failure at its deadline, and at once when nothing is dirty, the cache is stopped, or it was never opened; `flush()` does so for every running cache with dirty state. A resolved `flush` acknowledges nothing: acknowledging a removal is `durable`'s job (below).

**Durability of removals (N58).** Each `remove` or `clear` change increments the cache's removal count. A flush job takes the count when it builds its plan, and a successful write makes every removal up to that count durable; a failed attempt makes none durable, and its retry carries them on. `durable(id)` resolves when the durable count reaches the count recorded at the call, or when the cache's persistence has stopped and its cleanup (below) has settled, whichever comes first; at once when the cache is not tracked, or nothing is pending. It never rejects. The removal's flush is due at once and settles within `timeoutMs`; a stop's cleanup settles within another; so a call waits at most about 10 s with the defaults, through any number of retries or queued jobs.

A `clearAll` settles removals too, and keeps that bound (`clearAll`, below). On success it makes every removal recorded until its job settled durable, those recorded during the barrier included; on failure its stops release them, since the failed clear was their deletion. A removal recorded during the barrier is therefore answered when the job settles, under one deadline after the removal, since the job's deadline is `timeoutMs` after its call. A removal whose flush job is queued or running at the call is answered when that job's attempt succeeds or when the `clearAll` job settles; the call came before that flush job's deadline, so this is within two deadlines of the removal. A removal of a cache stopped before the call waits for its cleanup, which keeps its place ahead of the `clearAll` job.

**Flush.** In the synchronous step that starts the job's attempt, before the attempt waits for anything (the store's opening included), the dirty state is taken (and reset) and the plan built from the cache's state `S` at that instant. The transaction therefore writes one state, and the attempt running at a `clearAll()` call writes only state that predates the call (round 9, R9-1). The plan:

- `rewrite` → `deletePages: [{ start: -Infinity, end: Infinity }]` and `putPages`: every page record of `recordsOf(S)`.
- Otherwise → `deletePages`: the dirty page ranges, merged and ascending; `putPages`: the page records of `recordsOf(S)` whose page lies in one of them.
- `putCache`: the cache record of `recordsOf(S)`, or `null` when there is none (`S` covers nothing).
- `strict`: true when the removal count taken exceeds the durable count; false otherwise.

Then one `store.write(id, plan)`. The plan comes from memory alone: a flush never reads the disk, so nothing stored can reach the next write. With nothing dirty there is no job. Changes made during the transaction are dirty for the next flush. A failed attempt puts the taken dirty state back, merged with what changed meanwhile, so that the retry writes the union; the one exception is the attempt running when a `clearAll` is called, which is final (`clearAll`, below).

**Failures (N59).**

- A `write` that rejects with `name === 'QuotaExceededError'` stops the cache at once with `'quota-exceeded'` and that error, without a retry: a retry would meet the same full disk. The stop follows the rule below, and its cleanup is a deletion, which needs no quota. Two writes keep their own rules: a cleanup's failure is ignored, a quota error included, and the attempt running at a `clearAll()` call is final (`clearAll`, below). A `store.clearAll()` rejected with a quota error is retried like any other rejection of the `clearAll` job.
- Any other rejection is retried after `debounceMs`, until the job's deadline (the writer, above).
- **Stopping** a cache, for any reason: its dirty state is dropped and its timers cancelled, its queued or running job is abandoned, and the persister never writes for it again (later changes are ignored, `flush` resolves at once); `onStopped` is called once with `{ cacheId, reason, error? }`; and, when a store is open, one _cleanup_ job follows: a `write` of `{ deletePages: [{ start: -Infinity, end: Infinity }], putPages: [], putCache: null, strict: true }`, due at once, with its own deadline and no retry. Its failure is ignored, and its settling releases the cache's pending `durable` calls. The disk may still cover what memory has withdrawn (a removal that never landed), and a later session must not load that; a deletion needs no quota. When it fails too, the records stay: the one way a removal can outlive its call (§4.10.1).

**`clearAll` (N54): a barrier.** The caller runs `Engine.clearAll()` and calls `clearAll()` in the same synchronous step, so the engine's `clear` changes have marked every tracked cache and abandoned any pending load (§4.10.5 rule 2). From the call until its job settles, through every retry, the `clearAll` job is a _barrier_: no flush is written and no load reads the disk, for any cache. Nothing the clear deletes can then be loaded before it (round 5, R5-1), and nothing written after the call can be deleted by it (round 6, R6-1).

- **The job.** `clearAll()` queues one `clearAll` job, due now, carrying a removal. It opens the store if no `open` did, with `{ ifExists: true }`: an origin without the database has nothing to clear and is given none, and the job then succeeds at once. Then it runs `store.clearAll()`: every record of every cache goes, those of caches this engine never opened included, with strict durability. A failed attempt is retried after `debounceMs`, until the job's deadline; a store that fails to open fails the job at once, with `'unavailable'`.
- **At the call.** `clearAll()` takes over the dirty state of every tracked cache (its dirty pages, its `rewrite` flag and its removal count at that instant), so no cache has anything dirty. Every queued flush job is absorbed: it never runs, a scheduled retry included, and a `flush` waiting for it resolves when the `clearAll` job settles. The job running at the call, whose plan predates the call, finishes its attempt first, and that attempt is final: when it is rejected, for any reason (a quota error included), or is still pending at its deadline, the job ends without a retry and without a stop, and its taken state is not put back, since the clear holds it. Cleanup jobs queued before the call keep their place ahead of the `clearAll` job, as their earlier due time and their removal give them: a cleanup only deletes the records of a stopped cache, which writes nothing again, so it cannot put back what the clear removes. The queue then holds those cleanups and the `clearAll` job, and nothing else.
- **During the barrier.** The writer starts no flush. A request made meanwhile is held, and becomes due when the barrier settles (Scheduling, above). A cache opened meanwhile reads nothing (§4.10.5 rule 3): it is _running_ at once with `rewrite` set, its `open` resolves, and its flush request is held like any other. A second `clearAll()` joins the pending job: it takes over the dirty state again, and its call resolves when the job settles; the job keeps its attempts, its retry time and its deadline. Nothing has been written since the first call, so the attempt that empties the disk serves both calls, and later calls cannot extend the barrier. No cache stops during the barrier except through a store that fails to open (Open, above) or through the job's own failure; neither leaves a store to clean, so no cleanup job is created.
- **Success.** The dirty state taken over is dropped. Every removal recorded for a tracked cache until the job settled is durable: the clear left the disk empty with strict durability, and nothing has been written since its transaction was created. The held requests become due, and loads read the disk again. The flushes that follow write `recordsOf(S)` from memory as always, and carry no removal recorded before the settling.
- **Failure,** at the job's deadline, or at once when the store fails to open: every tracked cache stops (`'error'` with the last rejection's name and message, or `'unavailable'` when no attempt settled), those opened during the barrier included, without a cleanup of its own. The failed `clearAll` was the cleanup, and a disk that refused it for a deadline would refuse per-cache deletions too. Held requests go with their caches, and the `flush` calls waiting for them resolve. The persister then persists nothing for the rest of its life: every persisted cache opened later stops at once with the same reason, reads nothing and has no cleanup, since the disk still holds what the clear was to delete and a load would serve it back; the failed clear was its cleanup too. A later `clearAll()` still runs a job, which may empty the disk, and stops nothing more. A store call still pending at the deadline is abandoned; should it commit later, it empties the disk then, and nothing this persister writes follows it.
- `clearAll()` resolves when the job settles: on success, or once the failure's stops are done, when the records of every cache stay. Every call answers within `timeoutMs` of the first call of its barrier. It never rejects.

**Close.** `close()` makes every running cache's flush due, waits for the writer's queue to drain, then closes the store; later calls resolve at once.

Properties the contract tests pin (one engine per store):

- (a) After `await flush()`, `store.read(id)` deep-equals `recordsOf(S)` for every running persisted cache, over random sequences of `put` (with and without a range, with `meta`), `hydrate`, `invalidate`, `clear`, `clearAll` and `setFinalizedUntil` both ways. The test derives `recordsOf(S)` from public calls: `Engine.coverage` for the covered ranges, and `Engine.snapshot` for each covered range of each page.
- (b) **Reload.** A second `Engine` and `Persister` over the same store, the cache created with the same structural config: after `await open(id)`, every range reads the coverage and the covered points the first engine had at its last flush, and `recordsOf` the second engine's state equals the store.
- (c) **Incremental.** A flush puts only the page records of the pages that changed: a put inside one page puts that page's record and the cache record; a put wholly inside the volatile region writes nothing.
- (d) **Removals are acknowledged only when durable** (round 1, R1-3). With the store failing the next `k` writes, `k` small enough for a retry to fit before the deadline: `durable(id)` after an `invalidate` stays pending through the failures and resolves after the successful write, which is `strict`, holds the removal, and leaves the store not covering the range. With every write failing, it resolves only after the deadline stop and the cleanup settled, and the store then holds no record of the cache. With the write held past the deadline, after the `'unavailable'` stop and the cleanup. With the cleanup failing too, it still resolves, and the records stay. The same holds for `clearAll()`, except that no cleanup follows its stop.
- (e) **Strict when it matters.** A plan is `strict` exactly when it carries a removal or a clear; a flush of additions alone is relaxed.
- (f) **One deadline** (round 2, R2-2). Under fake timers, a removal's `durable` resolves within `2 × timeoutMs` of the removal whatever the store does: writes rejected, a write held forever, ten addition flushes of other caches due ahead of it, one of them held forever; a `clearAll` pending at the removal, or called after it, its attempts rejected or held (round 6). A removal-carrying job runs before queued jobs that carry none.
- (g) **Convergence.** After `open` and one `flush`, the store holds `recordsOf(S)`, for every load outcome of §4.10.5: records applied in full, a skipped page, a cache record of another version or config, orphan pages, a clipped part, a watermark above or below the record's.
- (h2) **No load during the barrier** (round 5, R5-1; changed at round 6). With the `clearAll` write held by a gate and the store holding records of caches B and C, which this engine has not opened: `open(B)` resolves at once without a `store.read` and without a store opening of its own, B starts cold, and a `get` through B's handle never returns a stored point. When the gate is released and the clear succeeds, B's first flush, which runs only after that, writes `recordsOf(S)` with a full rewrite, and a later `open(C)` loads as usual. When the clear fails until its deadline instead, B stops with every other tracked cache, nothing of B is ever written, and a later `open(C)` stops at once with the same reason and issues no `store.read`.
- (h) **Abandon.** With the read held by a gate, any mutating call on the cache (a `put` below the watermark, a `put` wholly inside the volatile region with and without a range, an empty `put`, a `hydrate` that applies something and one that applies nothing, an `invalidate`, a `setFinalizedUntil` forwards, backwards and to the current value, a `clear`, a `clearAll`) resolves `open` at once, applies nothing from the read when it is released, and the next flush writes `recordsOf(S)` with a full rewrite (for a cache holding only a provisional point: every stored record deleted, so the round 3 state R3-2 leaves no stored authority behind); a removal among those changes makes that flush due at once and strict, is durable only after it, and its call waits for it; a mutation that reports no change makes it due after the quiet spell. For a `clearAll`, its job takes that flush's place: once it succeeds the store holds `recordsOf(S)`, which is nothing, and the removal is durable then (property (j)). The same mutating calls on a running cache that reports no change write nothing (property (c)).
- (i) **The barrier** (round 6, R6-1). R6-1's interleaving, under fake timers with the defaults: the store fails the first `clearAll` call, so the job's retry is due at 1000 ms and its deadline is 5000 ms; at 100 ms an open cache A takes a `put` covering slot 0 and then an `invalidate` of slot 1. The store's log holds no `write` between the `clearAll()` call and the retry's successful `clearAll`; the `invalidate`'s `durable` resolves when the retry succeeds, before any write for A; after `await flush()` the store holds `recordsOf(S)` of A, which covers slot 0, and a reload (property (b)) reads slot 0. With every attempt failing instead, the log holds no `write` for any cache after the call, A stops at 5000 ms with every tracked cache and no cleanup, and the `invalidate` answers then. Over random sequences of operations, `flush`, `clearAll`, failure injection and gates, the log never holds a `write` started between a `clearAll()` call and its job's settling, other than the attempt running at the call and cleanups queued before it, nor a `read` started in that time.
- (j) **Jobs at the call.** A flush attempt running at the call finishes and is final: when it is rejected, or held past its deadline, its cache does not stop on its account, and no second write of its taken state follows; when it succeeds, its removals are durable as usual. Queued flush jobs, a scheduled retry included, never run, and a `flush(id)` waiting for one resolves when the `clearAll` job settles. A cleanup queued before the call runs before the job's first attempt. Every removal recorded before the call, queued or running, is durable once the clear succeeds.
- (k) **Deadlines across the barrier.** With the clear held for `timeoutMs − 1` ms and then succeeding, a `put` made 10 ms after the call has its flush due at the settling and its deadline `timeoutMs` after that: with that flush's write then held for 2000 ms and released, the cache does not stop. With `maxDelayMs: 2000`, a put every 500 ms from 10 ms after the call, through a clear held for 4999 ms, makes its flush due at the settling, not at its cap.
- (l) **Removals during the barrier.** A removal recorded during the barrier (`invalidate`, `clear`, `setFinalizedUntil` back, a version-mismatch clear) is durable when the job settles: on success with no write of its own, the next write for its cache being relaxed, and on failure through the stop; in both cases within `timeoutMs` of the `clearAll()` call.
- (m) **A second `clearAll()`.** Called while the job is queued, between attempts or during an attempt, it joins the job: one sequence of `store.clearAll` attempts, both calls resolve when the job settles, the job's deadline is the first call's, and on success every removal recorded before the settling is durable.
- (n) **After a failed `clearAll`.** Every tracked cache has stopped, those opened during the barrier included, each with one `onStopped` call and no cleanup write; every persisted cache opened later stops at once with the same reason and issues no `read` and no cleanup write; a later `clearAll()` calls `store.clearAll()` again and resolves when its job settles.

#### 4.10.7 One writer per origin (N52)

Every tab of a deploy that reaches the SharedWorker hosting shares one worker, one engine and one persister, so one writer owns the database: what it writes is what its memory holds (§4.10.6), and no rule here reads the disk to combine it with another engine's state. That is why persistence is confined to this hosting (user decision of 2026-10-31). The dedicated-worker and in-process hostings give each tab an engine of its own; were they to persist, each flush would replace page records another tab had written, and combining them correctly means reading, merging and writing across engines, which four design rounds did not settle (`docs/reviews/step-38.md`). They have no persister: they neither load nor write the database, and `persist: true` does nothing there (§4.10.1). They clear it, though, below.

Two SharedWorkers can still write the database for a short while:

- **Deploy skew.** Tabs of two deploys load different worker URLs, so each deploy has its own SharedWorker until the older tabs are gone. Where an app serves the worker at a fixed URL (no content hash), the two deploys share one URL instead: tabs of a release from before slice (c) created the SharedWorker without `extendedLifetime`, and the HTML standard makes a `SharedWorker` whose `extendedLifetime` differs from the running worker's fire `error` rather than connect, so on the first upgrade to slice (c) a new tab steps down to the dedicated worker (`modeFallback`) until the old tabs are closed; later releases pass the same options and join as before. With the same database layout both write; a newer layout's upgrade closes the older worker's connection (§4.10.3), whose persistence then stops.
- **A worker that is closing.** When a worker's last tab goes, the browser may close it while a new tab of the same deploy already starts the next one, and the closing worker's final flush can land after its successor's load.

In both cases each writer writes plainly from its own memory, and the rules above keep the result correct: every page record is self-contained and checked on its own at load (N55, §4.10.5), only the cache record moves the watermark (§4.10.5 step 4), and a record of another version or config is never applied (§4.10.2). What the overlap can cost is coverage: a full rewrite by one engine deletes the other's pages. At worst it also brings back a range one engine removed, when the other engine still covers it in memory and flushes that page before it goes; its own tabs are served that range from memory meanwhile anyway. A dataset whose restatements carry a `version` loses nothing this way, since a record of another version is never applied (N56). Nothing is locked for this: a lock would only order two writes that each stand on their own.

Persistence for the dedicated-worker and in-process hostings is later work (§4.10.10).

**The clear-only call (N66; user decision #11 (1), option (b), 2026-11-02).** A logout from a page pinned to a dedicated worker, or served in-process, must not leave behind what a SharedWorker session of the same origin stored. So the `clearAll` of those hostings, after emptying its engine (N22), empties the database too, with one call that writes nothing else, `clearDisk` (`persist/clear-disk.ts`, in the lazy chunk, §4.10.8):

- It opens the database only if it exists (`openIdbStore(indexedDB, { ifExists: true })`): a browser that never persisted gets no database. The check needs `IDBFactory.databases()`; a browser without it (Firefox before 126) cannot tell, so the database is opened, and created empty when there was none, as the persister's clear job does there (§4.10.6). The clear is kept on those browsers, since they have SharedWorker and so can hold persisted records. Then one `store.clearAll()`, every record of every cache with strict durability (N49), and the connection is closed: a hosting that never reads or writes the disk keeps no connection open.
- It is bounded as the persister's `clearAll` job is (N61): a rejected clear is tried again after `debounceMs` (1000 ms) while the retry is due before the deadline, `timeoutMs` (5000 ms) from the call, the chunk's import included; a database that fails to open, or a realm whose `indexedDB` throws, fails it at once. A call still pending at the deadline is abandoned and its connection closed then (IndexedDB lets the pending transaction finish: should it commit later, it empties the disk then, as the persister's would, §4.10.6). No disk call starts at or after the deadline: the clock is checked before the database is opened and before each attempt, not left to the deadline's timer, which can run after a late continuation, so a chunk imported after the deadline opens nothing and a database that opens at or after it is closed unused. Every connection that opens is closed exactly once.
- The `clearAll` call answers once the disk is empty or the clear has failed, at most `timeoutMs` after the call, and never rejects for it (N59). The deadline has one owner at a time: a timer while the chunk is loading, which answers with no connection yet open, and `clearDisk` once the chunk has arrived (the timer is then cancelled), whose end closes the connection before it resolves; so the call never answers while a connection it opened is still open. A chunk that arrives after the timer fired is dropped. Two calls each run their own clear; nothing in this hosting writes between them, so neither needs the other.
- A realm without IndexedDB (Node, so every server render) has nothing to clear: no call is made and the chunk is never loaded.

**What "off" means after a failed clear.** In the SharedWorker hosting a failed clear turns persistence off for the worker's life (§4.10.6, D27 of step 38): its tracked caches stop, and no later open loads, so that worker never serves back what the logout was to delete; a later `clearAll` still tries again; a later worker can load the records (§4.10.1). Mapped to a hosting that does not persist, each part is already the case or carries over unchanged, so a failed clear-only call changes nothing else: there is no tracked cache to stop and no event to emit (as in a SharedWorker that tracks none; `persist: true` is inert here, N45), the hosting never loads, so it never serves the records back, and the next `clearAll` tries again. A SharedWorker started later can load what the failed clear left, the same limit as for the SharedWorker path. A marker that would make a later SharedWorker distrust the store was rejected: it needs a durable write to the storage that has just refused one, and a record kind or layout version of its own (N51).

A SharedWorker alive at the call is another engine, out of the call's reach: its memory still holds its caches, and its next flushes write back the pages it changes, each with its cache record, as during a deploy skew (above). Its records stay self-contained, so this costs nothing but the data the call could not reach; a `clearAll` from one of its own tabs clears both. A load of that worker pending at the call reads before or after the clear, as IndexedDB orders the two transactions.

#### 4.10.8 Hosting wiring

| Hosting          | Persister                                                                                                                           | Final flush                                                                                                                                                                                  |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SharedWorker     | One per worker, when `indexedDB` exists                                                                                             | When the last connection goes (its `dispose`, or its port closing). The worker is created with `extendedLifetime: true`, which keeps it about 30 s after its last tab so that flush can land |
| Dedicated worker | None: `persist: true` does nothing; `clearAll` empties the database with the clear-only call when `indexedDB` exists (§4.10.7, N66) | —                                                                                                                                                                                            |
| In-process       | None: `persist: true` does nothing; `clearAll` empties the database with the clear-only call when `indexedDB` exists (§4.10.7, N66) | —                                                                                                                                                                                            |
| `./engine`, Node | None                                                                                                                                | —                                                                                                                                                                                            |

A flush that never ran loses the last debounce window: the disk still holds an earlier consistent state, and what was not written is not covered on disk either. Removals are not exposed to this: their calls answer only once they are durable (N58).

`RpcServer` (§4.7) takes an optional persistence, `new RpcServer(engine, lib, lock?, persistence?)`, through a narrow interface of four calls, `open`, `durably`, `clearAll` and `flush`, which the SharedWorker hosting implements around its persister (`HostedPersistence`, below) and the other two hostings with the clear-only call (`ClearOnlyPersistence`, `persist/clear-only.ts`: `open`, `durably` and `flush` do nothing; `clearAll` is `engine.clearAll()`, then `clearDisk`, §4.10.7); the rules each call follows are these:

- `cache`: `engine.cache(config)`; when the resolved config has `persist` and there is a persister, it awaits `persister.open(id)` before answering. No call through a handle therefore reaches a cache whose load is pending (§4.10.5).
- Every op that names a cache (`put`, `get`, `hydrate`, `invalidate`, `clear`, `setFinalizedUntil`): the server reads `persister.removals(cacheId)` before it, and when the count has grown by the time the op is done, success or failure, it awaits `persister.durable(cacheId)` before answering (N58). So an `invalidate`, a `clear` and a `setFinalizedUntil` that moved the watermark back answer after their removal is durable, as do a `put`, a `hydrate` or an orchestrated `get` whose data cleared the cache for a new version or set its first watermark; any other op answers as before. A removal another op made meanwhile is waited for too; removals are rare. `clearAll`: `engine.clearAll()`, then `await persister.clearAll()`.
- A connection dropped (its `dispose`, its port closing, a detach) that leaves none: `void persister.flush()`.
- `onStopped` broadcasts `{ t: 'evt', scope: 'cache', cacheId, event: 'persistStopped', payload }` to every ready port, as `cacheCleared` is.

Client side: `ClientEmitter.receive` re-emits a cache-scoped `persistStopped`, and `CacheHandle.on` filters it by cache id like the other cache-scoped events. `openShared` passes `{ type: 'module', extendedLifetime: true }`. A browser without the option ignores the unknown dictionary member, and every tab of a deploy passes the same options, so they reach one worker. Tabs of a release from before slice (c) passed no `extendedLifetime`; at a fixed worker URL their worker and a new tab's options differ, so the new tab falls back until those tabs close (see Deploy skew, §4.10.7). In Chromium the worker now lingers about 30 s after its last tab, so after closing old tabs a reload joins the old worker until that has passed.

Entries: the SharedWorker path of `entries/worker.ts` builds a `HostedPersistence` when `indexedDB` exists (a presence check: the factory is read when the store first opens) and passes it to its `RpcServer`. Its dedicated path and `connectInProcess` (`client/in-process.ts`) build a `ClearOnlyPersistence` under the same check (N66), and none without IndexedDB, so a server render behaves exactly as before persistence.

**Lazy loading** (clarified 2026-10-31, step 38: the persistence code is paid for only by an application that persists). The persister, `restore`, the record builder and the IndexedDB adapter are `persist/lazy.ts`, which `entries/worker.ts` imports with `import()`, so the build emits them as a chunk of their own. `HostedPersistence` (`persist/hosted.ts`, in the worker's initial load) imports it once, at the first `open` of a persisted cache or the first `clearAll` (which must empty the disk of earlier sessions even when this one persists nothing), then builds `new Persister(engine, (o) => openIdbStore(indexedDB, o))` and forwards every call to it. Until the chunk has loaded:

- `open` waits for it, and passes its own call time to `Persister.open(cacheId, startedAt)`: the import and the load share the load's deadline (N61), so `cache()` of a persisted cache still answers within `timeoutMs`.
- An op on a cache whose open waits for the chunk is held, and so, once one op is held, is every later op and `clearAll`; they reach the persister in arrival order once it exists, so it sees each where it would have seen it had it been loaded all along (a held mutation abandons the pending load, §4.10.5 rule 2). Ops on other caches run at once: no persisted cache is tracked yet, so they concern nothing on disk.
- `clearAll` clears memory at once and holds its disk part; `flush` is held.
- A chunk that fails to load, or has not loaded `timeoutMs` after its import started, turns persistence off for the worker's life, as a store that fails to open does (§4.10.6): every waiting and later open stops with `'unavailable'` (with the import's error when it failed), held ops run as they come, and `clearAll` clears memory only.

The clear-only call of the other hostings is in the same chunk: `ClearOnlyPersistence` imports it at each `clearAll` (the module system keeps it once loaded) and nowhere else, so a page that never calls `clearAll` never loads it. The import counts against the clear's deadline, and a chunk that fails to load, or has not loaded `timeoutMs` after the call, fails that clear only: memory is cleared, the call answers, and the next `clearAll` imports again (N66). In the in-process hosting, itself a chunk of `index` (§4.8), the persistence chunk is an import of that chunk, measured on the `index (lazy, nested)` row of `scripts/size.ts`.

With a bundler that inlines dynamic imports (Vite's default worker format, `'iife'`), the chunk is part of the worker file and only its evaluation waits; with `worker.format: 'es'`, or `dist/` served as it is, it is a file of its own, loaded only by a worker that persists (`docs/guides/worker-setup.md`).

| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

#### 4.10.10 Later

Not in these slices: persistence in the dedicated-worker and in-process hostings, which needs several engines to share one database (designed as slice (b) and retired on 2026-10-31 after four review rounds without converging, N52 and `docs/reviews/step-38.md`; Chrome for Android before version 148 and pinned dedicated modes are the hostings it would serve); lazy loading of pages on first read (needed by eviction; `read(id, pages)` and the page keys already serve it, but an asynchronous step inside `get` needs its own atomicity design, and the abandon rule of §4.10.5 does not carry over to a cache that already holds data); a byte budget for the eager load; compression; and encryption at rest.
