## 1. The gap

A deploy reaches open tabs in one of three ways today, and none of them has a recovery path:

1. **Rejected.** A tab whose worker speaks another protocol version cannot create a client: `createClient` rejects with `ProtocolMismatchError`, and the guide's advice is "close the old tabs and reload" (`site/troubleshooting.md:17-25`; since step 101 it adds a retry with `mode: 'dedicated'` for a page that is the newer side). An application cannot close a user's other tabs.
2. **Rejected, and more common than (1).** A tab whose fetcher module URL differs from the one the running SharedWorker loaded cannot create a client either: `createClient` rejects with `ConfigError` ("this worker already runs fetcher …"). §2.3 shows that with Vite's `?worker&url` and `?fetcher` (the setup every example uses), a deploy that changes the fetcher but not tscache keeps the worker's URL and changes the fetcher's, so this is what such a deploy does to every new tab until the old ones close.
3. **Silent.** A deploy that changes the worker script's URL (a tscache upgrade under a hashed URL) starts a second SharedWorker. Tabs of the two deploys stop sharing memory, in-flight fetches, `clear`, `clearAll` and `authInvalid`; nothing reports it; and both workers write the one IndexedDB database of the origin, which N52 accepts on the premise that the overlap is brief (`docs/architecture.md:1855-1860`). A tab left open keeps the old worker alive for days.

The finding also notes that `hello.lib` is never read. That still holds on `main`: every server writes the field (`rpc/server.ts:194`), the wire type declares it (`rpc/protocol.ts:69`), and the client's handshake takes `protocol`, `clientId`, `lock` and, since step 114, `features` from the hello, and nothing else (`rpc/port-client.ts:180-197`); no other module of `client/` or `rpc/` reads it. §4.7 says what reads it once this design is built. Step 82 documented the limit, and step 101 corrected what it said of a fetcher-only deploy (`site/guides/workers.md:135-206`, `site/guides/persistence.md:91-93`, `docs/guides/patterns.md:167-177`).

This design makes every deploy that changes what the worker runs start a worker of its own (case 3), never cases 1 or 2 against a running worker; lets the workers of different deploys find each other; has the older ones stop writing the database and tell their tabs; and lets a logout reach every deploy's worker. It adds no message and no field to the handshake, one name to `hello.features`, and keeps `PROTOCOL_VERSION` at 1 (§4.12).

## 3. The failure shapes

### 3.1 Rejected at connect

- **Protocol mismatch.** Possible only when a page and the worker it reaches come from different tscache versions with different `PROTOCOL_VERSION`: a fixed worker URL whose running worker is older (old tabs keep it alive), or a script served stale. The page rejects (`rpc/port-client.ts:181-184`) or the worker refuses `init` (`rpc/server.ts:294-305`); under N25 neither falls back. `PROTOCOL_VERSION` has never changed, and N37, N79 and N101 kept every additive change so far at 1, so this shape has not yet occurred in a release.
- **Fetcher conflict.** A page whose fetcher URL differs from the running worker's (`orchestrator/orchestrator.ts:311-316`). With hashed fetcher URLs it follows every deploy that changes the fetcher, at either kind of worker URL (§2.3). Like the protocol mismatch it rejects without falling back, since `ConfigError` is not a `HostingError` (`client/client.ts:177`).

Neither shape touches the database: the tab never gets a client.

### 3.2 Silent: two workers side by side

Two SharedWorkers of one origin, each with its own engine, orchestrator, fetcher and persister. Their tabs share nothing: a `clear`, a `clearAll`, an `authInvalid` or an in-flight fetch in one worker does not reach the other's tabs (`rpc/server.ts:554-558`), and both fetch the ranges both views show.

Both write the database `tscache`, each plainly from its own memory (§4.10.7). What happens to the records depends on what differs between the two deploys:

| What differs                                                                                                         | What the two writers do to each other                                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Nothing a record names (same structure and version)                                                                  | Records interoperate: each page record is self-contained and checked on its own (N55). The cost is coverage: a full rewrite by one deletes every page of the cache first (`persist/persister.ts:961-963`), including pages only the other had written; and one can write back a range the other removed while it still covers it in memory (N52's accepted cost)                                                                                               |
| The cache's structure (N20: fields, dtypes, interval, alignment, `gapSplitK`, `segmentSlotCap`, `warnOnOverlapDiff`) | Every flush puts the writer's own cache record (`persist/persister.ts:965`), so the cache record flips to whichever wrote last. A load then rejects the record of the other structure and applies nothing of the cache (`engine/restore.ts:114-121`, `:191-198`), and that cache is rewritten at its next flush, a full rewrite that deletes the other's pages. While both run, a reload in either deploy starts that cache cold whenever the other wrote last |
| The dataset `version` (N56)                                                                                          | As for structure: a record of another version applies nothing (`engine/restore.ts:117-121`), and the two rewrite each other. No wrong point is ever loaded                                                                                                                                                                                                                                                                                                     |
| The database layout (a later IndexedDB version)                                                                      | The newer worker's upgrade fires `versionchange` at the older connection, which closes itself (`persist/idb-store.ts:113-114`); the older worker's later writes fail, and its caches stop at their deadlines (`persistStopped`). An older worker that opens after the upgrade cannot open at all: persistence is `'unavailable'` for it (§4.10.2). Only one writer remains                                                                                     |
| The record `format` or `Snapshot.format`                                                                             | As for structure: applies nothing, or skips that page, and rewrites (§4.10.2 table)                                                                                                                                                                                                                                                                                                                                                                            |

Two further costs do not depend on what differs. A logout's `clearAll` in a tab of one deploy empties its engine and the disk, but the other worker keeps its memory and writes back the pages it changes (`docs/architecture.md:1873`); a logout from an old tab leaves the new worker's memory alike. And each worker has a memory budget of its own, since a budget belongs to one engine (architecture §2.9, N87): while two workers run, the origin may hold the sum of the two. A third cost came with M7: `cacheChanged` reaches only the subscribed connections of the worker whose cache changed (`rpc/server.ts:504-530`), so a view in a tab of one deploy is not told of a write, an `invalidate` or a `clear` made through a tab of the other.

### 3.3 Silent: one worker, two deploys

At a fixed worker URL, or at a hashed one when only the application changed, new tabs join the old worker. When the deploys agree on tscache and the fetcher, the worker runs exactly what the new tabs would have run, so nothing is skewed: that is the case where sharing is right. When they agree on the protocol but not the library, new tabs run the old library's worker code, and `hello.lib` tells them nothing because nobody reads it. Since step 114 `hello.features` tells such a tab which optional features the old worker lacks (`client.features`, N79, N80), feature by feature; it does not say that the worker is of another library.

### 4.2 Worker identity: one SharedWorker per generation (F1, F2)

The shared hosting passes a name: `new SharedWorker(url, { type: "module", extendedLifetime: true, name })`, where `name` is the page's **generation key**:

```ts
// client/hosting.ts (sketch). LIB_VERSION: rpc/protocol.ts. fetcher: the
// string the page passes (client/client.ts:116-123), as the worker compares it.
const name = `tscache:${LIB_VERSION}:${fetcher?.module ?? ""}`;
```

A SharedWorker is found by its URL and its name together, so the worker URL and the key between them decide what a worker runs: the URL its build (the worker bundle; at a hashed URL its content hash), the key the library (the worker script's version, which `packages/tscache/test/version.test.ts` keeps equal to the package's) and the fetcher module's URL string (the fetcher is the only application code inside the worker, N44). The key sees the fetcher's URL, not its contents: it names a changed fetcher only when the URL string changes with it, as a hashed `?fetcher` URL, a versioned path or a query such as `fetcher.js?v=3` does; a fetcher rebuilt behind a fixed name is not seen (§4.9). Two pages with the same URL and key run the same code in the worker and share one; two pages that differ in either never share one. The key alone does not name a build: two deploys with one tscache version and one fetcher but different worker bundles (a change of `worker.format`, which tscache's own build warning prompts, or a Vite upgrade) differ only in the URL, so §4.3 compares the URL too. Consequences:

- **A fetcher change whose URL string changes starts a new worker** (a hashed `?fetcher` URL, a versioned path, a query such as `?v=3`) instead of a `ConfigError` against the old one. A fetcher whose contents change behind an unchanged URL is not detected: the new tab joins the old worker, which keeps the module it loaded (§4.9). The guard in `orchestrator/orchestrator.ts:311-316` stays, and pages of this release no longer reach it in the shared hosting: the name carries the very string the worker compares, so two pages that pass different strings never meet in one worker (§4.9). It stays reachable for connections that arrive without the name: pages of an earlier release that load this release's worker script at a fixed URL, and any caller of the server or the orchestrator itself. (The proposal said here that two strings for one module still reach it; §4.9 gives them different workers.)
- **The refusal gets a code (user decision 71).** The decision gives the `this worker already runs fetcher` refusal "a dedicated error class or code in M5; the prefix stays until then", and leaves the choice between the two open. This spec takes a code: `ConfigError` gains an optional, read-only `code`, of the new exported type `ConfigErrorCode = 'fetcher-conflict'`, set on this refusal and unset on every other `ConfigError`. The error stays a `ConfigError` with the same `name`, and its message is unchanged, so it still starts with `this worker already runs fetcher` and names both modules; an application recognises it by `error.code === 'fetcher-conflict'`, and the documentation stops telling it to match the message. The reasons for a code over a class are skew and the module's own pattern. On the wire the error keeps the name `ConfigError` and travels with `WireError.code`, a field that exists and that the server already fills from any error's string `code` (`rpc/protocol.ts:57`, `:206-207`); only the client's rebuilder changes, to restore it (`rpc/protocol.ts:256`). A client from before the code therefore rebuilds the same `ConfigError` with the same message, and its documented prefix check goes on working, whereas a new class name would reach such a client as a plain `TscacheError` with the name put in front of the message (`rpc/protocol.ts:268-278`), in exactly the stale-page case that still reaches the guard. And `errors.ts` already tells the variants of one class apart by a `code` (`PutError.code`, `errors.ts:55-67`), while its classes each stand for a failure of their own. The throw is in `orchestrator/`, which is strict test-first, so its test is Codex's (test 35, §6).
- **A tscache upgrade at a fixed URL starts a new worker** instead of running the old code (same protocol) or rejecting with `ProtocolMismatchError` (new protocol). A protocol mismatch then needs a stale _script_, not a running old worker (§4.8).
- **At a hashed URL**, a tscache upgrade already starts a new worker; the name adds the fetcher, which the URL does not see (§2.3).
- **Nothing changes for a deploy that changes neither** the library nor the fetcher: its tabs join the running worker, as now. Application code, cache configs and budgets are not in the key; a changed cache structure is still refused by N20 within the worker, and a changed budget waits for the worker to restart (N88; §4.10).
- **Tabs of an earlier release** (0.1.0, 0.2.0, and any other that ships before this design) pass no name, so a release with this design never joins such a worker, even at a fixed URL: a SharedWorker created without a name has the empty name, which no generation key equals.
- **A cost within one deploy.** Today a page that passes no fetcher shares the worker of pages that pass one (`rpc/server.ts:308` loads a fetcher only when one is given). With the fetcher in the key, the two get workers of their own, both writing the database, until the application passes the same fetcher on every page. §4.3 keeps such workers from superseding each other, and F16 records the choice.

The dedicated-worker and in-process hostings are per tab and take no name.

### 4.3 Finding the other generations (F3, F4)

Each SharedWorker subscribes to a `BroadcastChannel` named `tscache-workers` before it answers any `init-ok`, so before any cache of it is opened or loaded: a channel delivers a message only to the subscribers it has when the message is posted, and a `clearAll` posted later must reach a worker before that worker reads the disk (§4.6). Once its first connection has completed `init` (it then knows its fetcher), it posts one message:

```ts
// Worker ↔ worker, on BroadcastChannel "tscache-workers". A channel message
// may come from any release: unknown `t` or `v` values are ignored.
type Announce = {
  t: "announce" | "present";
  v: 1;
  id: string; // this worker's lifetime lock name (N32), or a random id
  lib: string; // LIB_VERSION
  url: string; // self.location.href: the worker script, so its build
  fetcher?: string; // the module it loaded, resolved against `url`; absent when none
  startedAt: number; // performance.timeOrigin of the worker
};
type ClearAll = { t: "clearAll"; v: 1; id: string; clear: string }; // F11 (a) omits `clear`
```

- A worker that receives an `announce` from another `id` answers with one `present`, so a newcomer learns of the workers already running.
- **Same generation.** Two workers are of one generation when their `url` and `lib` are equal and their `fetcher`s are equal or one of them is absent. Neither acts on a worker of its own generation. That covers a closing worker and its successor (same URL and name, §4.10.7), and the two cases within one deploy where pages pass different keys (§4.9, F16): a page with no fetcher beside pages with one, and two strings that resolve to one module. In both of those, a development build of each worker prints one warning naming the two keys, since a reload cannot join them.
- **Different generations** are compared by **rank**: the higher `lib` (by semantic version) ranks higher; for equal `lib`, the later `startedAt`; for equal `startedAt`, the greater `id`. Both sides compute the same answer from the same two messages. So two worker builds with one key (equal `lib` and `fetcher`, different `url`) are ranked like any other skew.
- A worker that finds a higher-ranked worker of another generation is **superseded** (§4.4, §4.5). It never becomes current again (F6).

The channel is the origin's (more exactly, the storage key's, the same partition as the database), so it reaches exactly the workers that write that database. Workers of an earlier release (0.1.0, 0.2.0, and any other that ships before this design) neither announce nor listen: a release with this design neither sees them nor reaches them (F3 records the lock-query alternative that could see them).

### 4.4 The superseded worker stops writing the database (F5, F6, F7)

When a worker is superseded, its persister stops persisting for the rest of its life, by the path a failed `clearAll` already takes (`persist/persister.ts:166`, `:228-230`):

- Every tracked cache stops with `persistStopped { reason: 'superseded' }`, **without** the cleanup deletion (`#stop(…, cleanup = false)`, `persist/persister.ts:593-613`): the records belong to the current generation now. Dirty state and queued jobs are dropped; an attempt already running is abandoned as by any stop, and IndexedDB may still commit it.
- A cache opened later stops at once with the same reason, reading nothing. Once set, `'superseded'` is kept: a `clearAll` that fails afterwards stops what it stops with its own reason, as today, but does not replace the reason later opens stop with (today `#clearFailed` overwrites `#failure`, `persist/persister.ts:694`). After `supersede()` no tracked cache is left running, so such a clear has none to stop and reports nothing more (test 4).
- Waiters for a removal's durability (N58) are released by the stop, as for any stop, so an `invalidate` or `clear` answers at once. Such a removal does not reach the disk; the current generation's engine never held the old engine's memory anyway, so the disk is no worse than the current generation's own state.
- `clearAll` still empties the disk, as the clear-only call does (N66): a logout from an old tab must not leave records behind.
- **Nothing in the engine changes.** Superseding is not a mutating call: no cache loses a point or coverage, so it sends no `cacheCleared` and no `cacheChanged` (N73), and the engine's memory budget, use order and pins stay as they were (§4.10). The tabs hear `superseded` (§4.5) and then one `persistStopped` for each tracked cache, which goes to every ready connection whatever it subscribed to (`rpc/server.ts:206-214`).
- **Evictions after the stop write nothing.** With a memory budget the superseded worker goes on evicting. The persister marks an evicted page only for a cache whose persistence is live (`persist/persister.ts:398-403`, `:411-415`), so an eviction after the stop deletes no record, and the relaxed deletion that a page evicted before the stop was waiting for (N95) is dropped with the rest of the dirty state. Those records belong to the current generation, which keeps or evicts them under its own budget.
- **A persister that had already failed.** Where a store that failed to open or a failed `clearAll` came first, every tracked cache has already stopped with that reason and is not reported again (one `persistStopped` per cache, N59); `supersede()` still makes `'superseded'` the reason later opens stop with.

The current generation's worker changes nothing: it loads and writes as before. From the moment a worker is superseded, the database has one writer again. Before it, during the time between the new worker's start and its first `init`, both write, as during a closing worker's final flush.

### 4.5 What the application is told (F8, F9, F10)

The superseded worker tells every ready connection, and every connection that completes `init` later, with a client-scoped event:

```ts
// types.ts, ClientEvents (additive)
/**
 * A worker of a newer generation of this application (another tscache
 * version, fetcher module or worker build) is running in the origin. This tab's
 * worker no longer persists; the tab keeps working from memory and its
 * fetcher. Reload the tab to join the newer worker. Fires at most once.
 */
superseded: { lib: string };

// TscacheClient (additive): set when the event arrives, for a listener
// attached later (the lesson of modeFallback, client/client.ts:210-228).
readonly superseded: { lib: string } | undefined;
```

- **Only the superseded side is told.** The current generation's tabs need to do nothing.
- **The library never reloads a page.** The guide recommends showing the user a prompt to reload. An automatic reload is the application's choice; the guide warns that a page served stale (an HTTP cache, a service worker's old shell) can rank as newer by start time and make the current worker's tabs reload into the stale build (F4's con).
- **In development**, the client prints one `console.info` naming both library versions: the payload's `lib`, which is the newer worker's, and `hello.lib`, which is this tab's worker's (§4.7).
- **The payload's `lib` comes from the channel**, from the `lib` of the higher-ranked worker's `announce` or `present` (§4.3), never from a hello: the newer worker and this tab share no port.
- **The event is client-scoped and needs no subscription.** It goes to every ready connection, as `authInvalid` does (`rpc/server.ts:554-558`); the `subscribe` op gates `cacheChanged` only (N74). The server sends `superseded` before the `persistStopped` events of the same stop (§4.4), so a `persistStopped` listener that sees `'superseded'` finds `client.superseded` set.
- **A connection that completes `init` later** is sent the event right after its `init-ok`. That is before its `memoryBudget` op can be answered, and so, for a client created with a budget, before the client object exists and before anything listens on the port (`rpc/port-client.ts:313-314`, `client/client.ts:386-396`): as the code stands, the event would reach nobody. So the port client keeps the first `superseded` payload it receives, as it keeps `features`, whoever listens. When `createClient` resolves, `client.superseded` already holds a payload that arrived earlier, and the event for it is delivered on the macrotask after `createClient` resolves, after the `modeFallback` steps (`client/client.ts:210-228`). A listener attached in the same turn as `await createClient()` therefore hears the event whether or not a budget was set, and a listener attached later reads the property. The approved rows do not settle this timing; §8 lists it (DC4).
- **`client.features.has('superseded')`** says whether this tab's worker can send the event at all (§4.7): a worker that cannot (a dedicated or in-process hosting under F14 (a), a realm without `BroadcastChannel`, a worker script from before this design) leaves `client.superseded` undefined for good, which then means "not known", not "current".

### 4.6 `clearAll` reaches every generation (F11)

The decided protocol is the relay, F11 (b) (user decision 71); §4.6.3 describes the alternative the user did not take, F11 (a), and the gap it leaves.

#### 4.6.1 The relay (F11 (b))

Every `clearAll` carries a clear id, chosen by the worker or hosting where the call was made: `{ t: "clearAll", v: 1, id, clear }`.

- **The originator** posts the message twice: once after it has started its own clear, and once when its own disk clear has settled, whether it succeeded, failed or reached its deadline (N59, N61, N66). "Started" is the synchronous step that clears its memory: a `clearAll` that the SharedWorker's persistence holds behind its loading chunk, in arrival order with the ops held before it (`persist/hosted.ts:125-128`, §4.10.8), posts when it runs, not at the call.
- **A receiver**, a SharedWorker that gets a message from another `id`, runs `clearAll` exactly as if one of its own tabs had called it: its engine clears (its tabs get `cacheCleared { reason: 'clear-all' }`) and, when it persists, its disk clear runs. It does so for each message it receives, the originator's second as well as its first. Since M7 each such clear also sends `cacheChanged { cleared: true }` to the subscribers of every cache, an empty cache included (N78), after that cache's `cacheCleared` (N73). The event carries no `requestId`: the clear has no request on this worker, and a request id of another worker's connection (`'c1:7'`) would name the wrong tab here. The server therefore gets an entry of its own for a channel clear, beside `persistStopped` (`rpc/server.ts:206-214`); it hands its memory clear to the persistence as the `clearAll` op does (`rpc/server.ts:451-458`), under no cause.
- **The relay:** a worker that runs a clear for a `clear` id it did not originate posts once, with that id, when its own first disk clear for that id settles (success, failure or deadline), and never again for that id. It keeps a small set of the ids it has seen, which also keeps two workers from echoing each other.
- The posts are made by the hosting's persistence (`persist/hosted.ts`, `persist/clear-only.ts`) through a callback the entry injects, so they are tested with the persistence (§6). The posting call does not wait for other workers: their number is unknown and any of them may be closing. It answers as now, once its own disk clear is done or failed (N54, N66).
- A dedicated or in-process hosting opens the channel at the call and keeps it until its second post, then closes it.

#### 4.6.2 Why it closes the logout gap, and on what premises

Three cases need a worker to hear of a clear after the first post:

- **A worker that starts while the clear is pending.** The first post never reached it, and it may load records the clear has not yet deleted: the disk clear starts only after the persistence chunk has loaded (`persist/clear-only.ts:88-108`), and a persisted cache loads eagerly at open (`persist/persister.ts:244`, `:498-527`). It subscribed before it opened anything (§4.3), so the originator's second post reaches it and clears what it loaded.
- **A lagging writer.** A running worker R writes from its own memory on a timer (`persist/persister.ts:1060-1079`, `:915-941`), a task separate from the channel's messages, so R can flush pre-logout pages after the originator's disk clear has committed and before R has handled either post. A worker N that subscribes after the originator's second post then loads R's record. N read R's record before R's clear deleted it, so N had subscribed before R's clear settled; R's relay post, sent when R's clear settles, reaches N, and N clears. This is the case the two posts of F11 (a) miss (§4.6.3, finding R2-1 of step 100).
- **A chain of late workers.** Each worker that loads pre-logout data from a lagging writer hears that writer's settle post, by the same argument, so a chain is covered link by link.

The argument rests on three premises, each a contract the later step pins:

1. A worker subscribes to the channel before it answers any `init-ok`, so before it opens or loads anything (§4.3).
2. Within one persister, a flush already running finishes before the clear job, and no flush starts while the clear is pending (the `clearAll` barrier, N54). A worker's settle post therefore follows every write it made before the clear.
3. A `BroadcastChannel` delivers a message to every subscriber it has when the message is posted.

Its soundness is proven by Codex-first test 10 (§6): with delivery to a running worker held, a late worker that loads that worker's flush must end with an empty engine, and the store empty, which the two-post design of F11 (a) fails.

**What remains under the relay:** a clear that failed or reached its deadline leaves the records it did not delete, which a worker started later can load, as after any failed clear (§4.10.7, "What 'off' means after a failed clear"); every worker that heard a message has cleared its memory and tried its own disk clear, and the next `clearAll` tries again. Workers of an earlier release (0.1.0, 0.2.0, and any other that ships before this design) neither listen nor post, a realm without `BroadcastChannel` takes no part, and a hosting in a realm without IndexedDB has no persistence (`entries/worker.ts:49`, `client/in-process.ts:31-39`), so it posts nothing; a SharedWorker there still clears its memory when it hears a message. Within those limits the relay closes the logout gap §4.10.7 records for a SharedWorker of another deploy, and the one for a pinned dedicated or in-process tab whose origin also runs a SharedWorker (`docs/guides/patterns.md:149-156`).

**Its cost:** with k other workers running, each clears about k + 1 times per logout (the originator's two posts and one relay post from each other worker, so with n workers in all each clears n times), and its tabs get as many `cacheCleared` events unless the step coalesces them; each worker keeps a set of seen clear ids. With M7 its subscribed tabs get as many `cacheChanged { cleared: true }` events per cache, and the read rule (N84) answers each with a fetching read of what the view shows. What a tab fetched and wrote between two of those clears is cleared again, and a `get` pending at one of them is planned once more (N29). So one `clearAll` can cost a subscribed view about k + 1 fetching reads, where N84 counts at most one for each application call that writes nothing. The count is bounded, since each worker relays a clear id once, and k is 0 unless workers of two generations or two keys run side by side; but the approved F11 row did not weigh it, so §8 lists it (DC1).

#### 4.6.3 The alternative: two posts without a relay (F11 (a))

As the relay, without the clear id and the relay posts: the originator posts twice, and a clear started by a channel message posts nothing. It covers a worker that starts while the clear is pending, but not a lagging writer: R's flush after the originator's clear lands, N loads it after the second post, R then clears but posts nothing, and N keeps and serves the pre-logout data until it ends or the next `clearAll`, writing back the pages it changes. Every clear in that sequence succeeds. It needs three parties (an originator, a worker running when the clear starts, and one that starts after it settles), a running worker with unwritten changes whose flush timer fires in the window between the originator's clear and its own handling of the posts, and the late worker's load landing after that flush. Superseding does not prevent it: within one generation (§4.3, F16) nobody is superseded, and N announces only after its first `init`. So F11 (a) narrows the logout gap but does not close it, and leaves the failed-clear case as the relay does. It costs two clears per other worker per logout and keeps no ids.

Any script of the origin can post on the channel and so clear every worker. It gains nothing it lacks today: it can create a client and call `clearAll`, or delete the database.

### 4.7 `hello.lib` and `hello.features` (F12)

With §4.2, a page reaches a worker of another library only when the script at the worker URL is not the page's (a fixed URL whose script was replaced under an old page, or a script served stale). The client compares `hello.lib` with its own `LIB_VERSION` and, in a development build, warns once naming both. Nothing else changes: the protocol check stays the gate.

**Nothing reads `hello.lib` today.** Every server sends it (`rpc/server.ts:194`, from the `LIB_VERSION` its entry passes: `entries/worker.ts:49-64`, `client/in-process.ts:32-34`), and the client's handshake drops it: `onHello` takes `protocol`, `clientId`, `lock` and `features` (`rpc/port-client.ts:180-197`), and `PortClient` has no member for it (`rpc/port-client.ts:110-134`). So the reader is new code, and the step that builds this design adds exactly these three uses:

1. **The handshake keeps it.** `PortClient.connect` stores `hello.lib` when it is a string, and `undefined` otherwise, as a read-only `PortClient.lib`, beside `clientId`, `lock` and `features`. The handshake does not act on it: no value of `lib` fails a connection, steps the chain down or changes what is sent.
2. **The client compares it (F12 (a)).** When the client is built, it compares `PortClient.lib` with its own `LIB_VERSION` (`rpc/protocol.ts:27`). When they differ, in either direction, or the worker sent none, a development build prints one `console.warn` for that client naming both versions (in `client/dev.ts`, with the other development warnings); a production build prints nothing. This runs in every hosting. A dedicated worker loads the script at the same URL, so a stale script reaches it too; the in-process server is part of the page's own bundle, so there the two are always equal.
3. **The `superseded` note names it.** The development `console.info` of §4.5 names `hello.lib` as the library of this tab's worker, beside the payload's `lib`.

Nothing else reads it. It is not public (F12 (d), `client.workerVersion`, was not taken), and no production code path depends on it.

**What `hello.lib` is not used for.** The generation key is built from the page's own `LIB_VERSION` before any worker exists (§4.2). The rank compares the `lib` each worker announces on the channel, which is that worker's own constant (§4.3). And no capability is derived from it: the client never compares versions to decide what a worker can do.

**Beside `hello.features`.** The two fields answer different questions, and the design keeps them apart, as N79's rule has it (a client learns of a worker's optional features from `hello.features`, not from a version and not from a failing request):

|                    | `hello.lib`                                                                    | `hello.features`                                                                                                                            |
| ------------------ | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Says               | Which library the worker script is                                             | Which optional features this worker offers                                                                                                  |
| Kept by            | `PortClient.lib` (new)                                                         | `PortClient.features`, the names the client knows (`rpc/port-client.ts:58-63`)                                                              |
| Decides behaviour  | Never                                                                          | Whether `subscribe` is sent (N80), whether the budget op is sent and `memoryStats` answers (N101), and whether `superseded` can ever arrive |
| Public             | No                                                                             | `client.features`                                                                                                                           |
| Development output | One warning at connect when it differs from the page's `LIB_VERSION` (F12 (a)) | One warning for each feature a client asks for and the worker lacks (N80, N101); none for `'superseded'`, below                             |

**The feature name.** `WorkerFeature` gains `'superseded'`, and a worker lists it in `hello.features` when it takes part in the detection of §4.3: the SharedWorker hosting, in a realm that has `BroadcastChannel`. A dedicated worker and the in-process hosting do not list it, since under F14 (a) they never report a newer generation, and neither does a SharedWorker without `BroadcastChannel`. A page can then tell the two cases the proposal named: a worker that has nothing to report (`'superseded'` listed, `client.superseded` undefined) from one that cannot report (not listed). Today the list is one constant that every hosting's server sends (`rpc/protocol.ts:48-52`, `rpc/server.ts:196`), so the server takes the names it lists from its entry. A `superseded` listener on a client whose worker does not list the name is never called, and no development warning is printed for it, unlike N80's for `cacheChanged`: in a dedicated or in-process hosting the absence is by design, and for a worker script of another library the warning of use 2 has already been printed at connect. Which hostings list the name is not settled by the approved rows; §8 lists it (DC2), and this section takes its recommended option.

**A stale worker script, in development.** Each warning is keyed on its own field: the library warning on `lib`, at connect; N80's on a missing `'cacheChanged'`, at the first listener; N101's on a missing `'memoryBudget'`, when a budget was set. A worker script from before this design also lacks `'superseded'`, which prints nothing more.

### 4.8 A protocol mismatch (F13)

With §4.2, a running worker of an older deploy can no longer cause a `ProtocolMismatchError`, since a newer page creates its own worker. What remains is a script served stale, for which a dedicated worker loads the same stale script and does not help. F13 (a) keeps N25 as it is: the mismatch rejects. The guide's advice to retry with `mode: 'dedicated'` when the page is the newer side (`site/guides/workers.md:184-206`, `site/troubleshooting.md:17-35`, as step 101 left them) is replaced by: reload with the HTTP cache revalidated, and serve the worker script with revalidation. The retry it describes for a second fetcher module goes too, since that conflict no longer follows a deploy (§4.2); where a page still names that refusal, it names its code, `'fetcher-conflict'`, in place of the message prefix.

### 4.9 Edge cases

- **Two strings for one fetcher module.** A page passing `./fetcher.js` and another passing `/fetcher.js` get different keys and so different workers; today the second gets a `ConfigError` (the comparison is by string either way). Their `fetcher`s resolve to one URL, so they are one generation (§4.3): neither is superseded, both write the database, and each warns in development. A reload cannot join them, so no event is sent. The guide states that every page of a deploy must pass the same string; the `?fetcher` import always does.
- **A page without a fetcher in an application that uses one** (§4.2): one generation with the fetcher's worker, likewise with no event and a development warning; the guide says to pass the fetcher on every page. **Pull-model use** throughout (no page passes a fetcher): one worker per library version and worker URL, as today.
- **Strings that differ and resolve to different modules within one deploy** cannot be told from a fetcher-only deploy; they are ranked, and the lower one's tabs are told to reload, which brings them back to the same worker. The prompt recurs; the data stays correct. This is the case today's `ConfigError` reports; under this design nothing tells it from a deploy.
- **A fetcher changed behind an unchanged URL** (the fixed-name fetcher of `docs/guides/worker-setup.md` and `site/guides/vite.md`, served with revalidation): the key is equal, so a new tab joins the running worker, which keeps the module it imported (`orchestrator/orchestrator.ts:311-316`), and runs the old fetcher with no `superseded`, until that worker stops. Revalidation updates the file, not a module already loaded. There is one writer and no data damage; it is today's behaviour, not a regression. A versioned or content-addressed fetcher URL avoids it, and F2 (d) would cover it too.
- **A rollback.** A library rollback (0.3.0 to 0.2.0 while 0.3.0 tabs are open) ranks the rolled-back worker lower, so it is superseded and its tabs are told to reload into the same build until the 0.3.0 tabs close; F4 (b) would rank it current instead. A fetcher rollback (deploy B, then back to A while A's worker still runs) brings new tabs back to A's worker, which B already superseded: they persist nothing and are told to reload until A's worker ends, since a superseded worker never becomes current again (F6). The data stays correct in both; persistence and the prompt are what a rollback costs.
- **A third generation:** each worker yields to any higher-ranked worker it hears of; the highest remains current.
- **A current worker that ends first** (its tabs closed, the old ones kept): the old worker stays superseded and persists nothing until it ends (F6).
- **No `BroadcastChannel`** in the realm: no detection; the worker behaves as today and lists no `'superseded'` feature (§4.7). Every browser with SharedWorker has it.
- **The first upgrade from an earlier release** (0.1.0, 0.2.0, and any other that ships before this design): the old worker keeps writing the database beside the new one until its tabs close, as today, a `clearAll` does not reach it, and its tabs are told nothing.

### 4.10 Interactions with M7 and M3

Both designs are built and on `main` (M7 in step 114, decisions N71–N84; M3 in step 121, decisions N86–N105). This section says how this design meets each; it was rewritten in step 127.

**M7 (change events).**

- **The compatibility rule (N79):** adopted. A change that a peer from the other side of a skew can ignore or detect is additive and keeps `PROTOCOL_VERSION`. Everything this design puts on the port is of that kind: one client-scoped event name, which an older client ignores (`client/events.ts:11-49`); one feature name, of which a client keeps only those it knows (`rpc/port-client.ts:58-63`); one more value of `persistStopped`'s `reason`, a string an older client passes on unread; and no op. The worker-to-worker messages are on a channel of their own with their own `v`, never on the port.
- **`hello.features` (D9 (a), N79):** used. The proposal avoided the handshake, because §3.1 is locked and D9 was open; the user approved D9 (a) on the day M5 was decided, and decision 71 asked this design to build on the field. A worker that can report a newer generation lists `'superseded'` (§4.7). The rest of the design does not depend on the list: the worker never reads it, and a page of this release normally meets a worker of its own library (§4.2).
- **`cacheChanged` stays within one worker.** A generation's change never reaches the other's tabs, which hold other memory; `superseded` tells those tabs to reload, and the guide says that a view in a superseded tab is no longer told of changes made through the newer deploy's tabs.
- **Superseding sends no `cacheChanged`.** It changes no cache (§4.4). The `superseded` event and the `persistStopped` events of the stop go to every ready connection, subscribed or not.
- **A clear that arrives by the channel** sends, for each cache, `cacheCleared { reason: 'clear-all' }` and then `cacheChanged { cleared: true }` to its subscribers, with no `requestId` (§4.6.1), once for each message the worker acts on. The read rule (N84) turns each into a fetching read by every subscribed view; §4.6.2 states the cost and §8 raises it (DC1).

**M3 (memory budget). What a budget belongs to.** One engine (N87), so one worker. Under F1 (a) "one worker" is the tabs that pass the same worker URL and the same generation key, where N87 and architecture §2.9 say "every tab of the origin that reaches the same worker URL": the step that builds this design corrects that sentence, and §8 asks for the dated note on N87 (DC3).

**E3 (N88): the first budget an engine receives holds for its life.** For two generations of workers that means:

- Each generation's worker has an engine of its own, so each takes the first budget its own tabs send. A deploy that changes the library or the fetcher's URL gets a fresh worker, and its budget is in force for its tabs from their first connection. N88 and N103 each note that a new deploy's budget waits for the worker to restart, and point at finding M5; under this design a deploy that changes the library or the fetcher's URL no longer waits.
- The superseded worker keeps its own budget, or its lack of one, until it ends. Superseding touches nothing in the engine: the budget, the use order, the pins and the eviction counter stay, and the worker goes on evicting under it. No channel message carries a budget, and neither worker's budget changes when the other starts or ends.
- The two budgets are not shared and do not add up to one bound: while both workers run, the origin may hold the sum of the two, each worker at or below its own (pins aside, N97). A worker without a budget stays unbounded beside a budgeted one.
- A deploy that changes only the budget, or only adds one, changes neither the library nor the fetcher, so its tabs join the running worker (§4.2): N88 and N103 apply there unchanged. The value is ignored, a development build warns naming both, and `memoryStats()` reports the budget in force. The budget is not in the generation key (F2 (a)); F2 (d), an application build id, would cover it.
- Tabs that rejoin a superseded worker (the fetcher rollback of §4.9) meet that worker's first budget, by the same rule.
- Two workers of one generation (F16: a page without a fetcher beside pages with one, or two strings for one module) have a budget each, so an application that mixes the two kinds of page holds up to twice its budget. Both write the database: a page one of them evicts loses its record at that worker's next flush (N95) while the other may still hold it in memory, which costs a refetch after a reload and never a wrong point (the coverage cost N52 accepts).
- The current generation loads the records the older one wrote, and a load is a write under its budget (architecture §2.9): a smaller budget keeps the newest part of each load and deletes the rest from the disk at its next flush. Only the current generation writes by then (§4.4).

**E18 (N101): the two additive ops, `memoryBudget` and `memoryStats`.**

- **Neither changes with `superseded`.** A superseded worker answers both as before. Neither crosses the channel, and the relay carries no budget and no stats. `memoryStats()` reports the one engine behind the client (N98): in a superseded tab the old worker's caches, in a current tab the new worker's; nothing sums them, and an application that watches memory during a skew sees its own worker only.
- **Neither waits for the persistence.** The server hands both straight to the engine (`rpc/server.ts:419-425`), not through `durably` and not behind a loading chunk, so a pending `clearAll`, a relayed clear and a superseded persister delay neither.
- **The order at connect to a superseded worker** is fixed: `hello` (with `'superseded'` and `'memoryBudget'` among its features), `init`, `init-ok`, the `superseded` event, and only then the answer to the `memoryBudget` op, which the client sends when it has seen `init-ok`. For a connection that was ready when its worker was superseded, the event and a budget answer in flight can arrive in either order. In both cases the port client keeps the event until the client exists (§4.5); without that rule a client created with a budget would lose it.
- **A clear that arrives by the channel** runs `Engine.clearAll()`, which drops every page from the use order and the byte count and empties each cache's index of evicted coverage (architecture §2.9, Interactions; N104). `memoryStats()` then reports no bytes; the budget and `evictedPages` stay. The caches and their configs stay too (`engine/engine.ts:327-344`), so a cleared engine still holds caches and takes no new budget (N103).
- **`memoryStats` is not a mutating call**, so it sends no event in either generation (architecture §2.7).

**E20 (N103): a budget reaches a worker's engine by op, after `init-ok`.** When a superseded worker receives one, nothing is special about it:

- The engine applies N88 and N103 as any engine does (`engine/engine.ts:213-218`): it takes the budget when it has none and holds no cache, and otherwise answers the budget in force, or none. The answer is honest, and the client's development warning is N101's.
- A superseded worker usually holds caches, since old tabs keep it alive, so a late tab's other value is usually ignored. It can still be taken: a worker superseded before any tab opened a cache (it announced at its first `init` and a higher-ranked worker answered at once) holds none, so the budget of its first tab is in force for its life.
- Being superseded does not make `createClient` fail or wait: it resolves once the budget op is answered, as always, with `client.superseded` already set (§4.5).
- The reverse order holds too. A worker subscribes to the channel before its first `init-ok` (§4.3), so a `clearAll` message can reach it before any budget op. That clear finds no cache and changes nothing in the engine, so the budget that follows is still the first one and is taken.

**Eviction and the superseded stop.** §4.4: an eviction after the stop writes nothing. An eviction is not a removal (N95), so no call was waiting for it, and the stop releases nothing on its account.

**Eviction and the relay's proof.** Premise 2 of §4.6.2 holds with a budget. An eviction marks its page through the same quiet-spell request a write makes (`persist/persister.ts:398-403`, `:453-459`), which the `clearAll` barrier holds like any other, and a load's own evictions happen inside `restore`, which the barrier does not let start (§4.10.5 rule 3). A late worker that loads a lagging writer's pages may evict some of them at once under its budget; its clear for the relay post then empties what is left, and its index of evicted coverage with it.

### 4.11 Cost

- **Nothing skewed:** zero per operation and per message on the port. Per SharedWorker: one `BroadcastChannel` and one `announce` at its first `init`, with no answer when it is alone. Per tab: one string concatenation at `createClient`. Per `clearAll`, with k other workers running: the originator's two channel messages and one relay message from each other worker, so each worker clears about k + 1 times and its tabs get as many `cacheCleared` events unless coalesced; each worker keeps a set of seen clear ids; the dedicated and in-process hostings keep one channel open from the call until their second message (§4.6.1).
- **Skewed:** one `present` per running worker for each newcomer, the event to each tab of the superseded worker, and the persister's stop.
- **On the port:** each hello of a detecting worker carries one more feature name; the client makes one string comparison of `hello.lib` when it is built. With M7, a clear that arrives by the channel sends one `cacheChanged` per cache to each subscribed connection, for each message acted on (§4.6.2).
- **Bundle:** the worker entry grows by the channel handling and the rank comparison, the client by the name and the property; `scripts/size.ts` measures both, and the later step states the figures.

### 4.12 Public API, protocol and version

- **Public API, all additive:** `ClientEvents.superseded`, `TscacheClient.superseded`, `'superseded'` in `persistStopped`'s `reason` union (F7), `'superseded'` in the `WorkerFeature` union, so in `client.features` (§4.7), and `ConfigError.code` with its type `ConfigErrorCode` (§4.2, decision 71). A union member is additive at runtime but can fail an application's exhaustive `switch` at compile time; the release notes say so.
- **Behaviour:** the SharedWorker is named (F1), so pages of different library versions or fetchers stop sharing a worker; `clearAll` reaches other workers (F11).
- **Protocol:** `PROTOCOL_VERSION` stays 1. The port carries one new client-scoped event name, one new name in `hello.features`, one new value of `persistStopped`'s `reason`, and the refusal's code in the existing `WireError.code` of an `init-err`; no op, no message and no field is added, and nothing existing changes its meaning. The proposal's additive argument still holds, by the rule N79 set for this design (a change that a peer from the other side of a skew can ignore or detect keeps the version): an older client ignores an event name it does not know (`client/events.ts:11-49`) and a feature name it does not know (`rpc/port-client.ts:58-63`; a client from before N79 ignores the whole field), passes an unknown `reason` on as a string, and rebuilds a `ConfigError` from its name and message without looking at a code; a newer client that meets an older worker sees no `'superseded'` in `client.features`, so it knows that no report can come. Nothing here is a change an old peer would misread, which is the only case N79 and N37 reserve a new version for, and a bump would make every tab of the other deploy reject `createClient` (N25), the failure this design removes.
- **What changes in §3.1 (locked).** Not the handshake: `hello`, `init`, `init-ok` and `init-err` keep their fields. The list N79 added gains a name, so §3.1's example and its comment gain `'superseded'`, as step 121 added `'memoryBudget'` under N101, which records that the locked handshake is untouched by it. User decision 71 asked for this use of the field. `hello.lib`, which §3.1 has carried since the first release, gets its first reader (§4.7); its wire shape does not change.
- **Version:** a minor release under 0.x semver, its own once its contract tests pass (F15 (a)). M7 shipped in 0.2.0, and M3 is in the notes of 0.3.0, which is in preparation (`docs/releases/0.3.0.md`); which number this design's release takes is the user's call when it is cut.

**Codex first: `persist/`.** At the level of the `Persister` over the in-memory store of the existing persistence tests (`packages/tscache/test/persist-memory-store.ts`) under fake timers, of `HostedPersistence` and of `ClearOnlyPersistence`. The seams as they stand on `main`: `new Persister(engine, openStore, options)` with `options.onStopped` (`persist/persister.ts:38`, `:190-209`); `new HostedPersistence(engine, load, openStore, options)` (`persist/hosted.ts:79-90`); `new ClearOnlyPersistence(engine, load, openStore, options)` (`persist/clear-only.ts:42-53`); and `clearAll(clearMemory?)`, to which the server passes its own memory clear (`rpc/server.ts:116`, `:451-458`). The names of what this design adds are for the tests to fix: below they are `supersede()` on the persister and on `HostedPersistence`, an injected `post` that takes a clear id, an injected source of clear ids (so that a test can name them), and a way to say that a `clearAll` runs on behalf of a channel message with a given id.

1. **Superseding stops persisting.** After `supersede()`, every tracked cache reports `persistStopped { reason: 'superseded' }` once; no cleanup job runs and the store keeps every record; dirty state and queued jobs are dropped; the store sees no further write for those caches.
2. **Later opens.** A persisted cache opened after `supersede()` stops at once with `'superseded'` and reads nothing from the store, also after a `clearAll` that failed since: the reason stays `'superseded'`.
3. **Removals are released.** A removal waiting for durability when `supersede()` runs is released at once, and its call answers; nothing is written for it.
4. **`clearAll` still clears.** After `supersede()`, `clearAll()` empties the store with strict durability and answers as before. A failed one answers when its job settles and reports no cache again: every tracked cache has already stopped, and a cache is reported once (N59; `persist/persister.ts:594`). It leaves the reason later opens stop with at `'superseded'` (test 2), where today a failed clear replaces it (`persist/persister.ts:694`). (The proposal's wording, "stops the caches it tracks … with that failure's reason", described caches that cannot exist: after `supersede()` none is left running.)
5. **A running attempt.** A flush attempt running at `supersede()` is abandoned: its result changes no state, and nothing is retried.
6. **Idempotent.** A second `supersede()` changes nothing and emits nothing.
7. **Before the persistence chunk.** `supersede()` on a `HostedPersistence` whose chunk has not loaded: a persisted cache opened later stops with `'superseded'` and nothing is read; a later `clearAll` still loads the chunk and empties the store. With the chunk loading at `supersede()` and an open waiting for it (`persist/hosted.ts:104-110`): when the chunk arrives, that open stops with `'superseded'` and reads nothing, and the ops held behind it run in arrival order. With the chunk failed or timed out before `supersede()`: a cache already reported `'unavailable'` is not reported again, and a cache opened afterwards stops with `'superseded'`.
8. **`clearAll` is posted twice, and relayed.** `HostedPersistence.clearAll()` and `ClearOnlyPersistence.clearAll()` call the injected post, with the call's clear id, once in the synchronous step that clears their memory and once when their disk clear has settled, on each path: success, a rejected clear, a failed chunk import and the deadline; they answer without waiting for anything the posts cause. A `HostedPersistence.clearAll()` held behind the loading chunk (`persist/hosted.ts:125-128`) posts nothing while it is held and makes its first post when it runs. The memory clear the caller passes (`clearMemory`) is still the one that runs, exactly once per call. A clear started on behalf of a channel message posts once, with the message's clear id, when its disk clear settles, on each of those paths, and never again for that id: a second message with an id already seen clears again and posts nothing. Without an injected post nothing changes from today.
9. **A worker that starts during a clear (deterministic, fake timers).** Two `HostedPersistence` instances, each with its engine, over one store that holds records of a persisted cache, joined by a fake channel. The first calls `clearAll()` with its chunk import (or its `store.clearAll()`) held; after the first post, the second subscribes, opens the cache and loads the records. When the hold is released and the first clear settles, the second receives the settle post: its engine holds no point of the cache and the store holds no record. A design with only the first post fails this test.
10. **A lagging writer (deterministic, fake timers).** Three `HostedPersistence` instances, each with its engine, over one store, joined by a fake channel whose delivery to the second, R, can be held: S, which calls `clearAll()`; R, running with unwritten changes to a persisted cache; and N, which subscribes after S's settle post. With R's delivery held, S's clear settles and posts twice; R's flush timer fires and writes its pages; N subscribes, opens the cache and loads them; then R's delivery is released and R clears. Expected, under F11 (b) as decided: R's relay post reaches N, and N's engine and the store end empty. The two-post design of F11 (a), which the user did not take, fails this expectation: there N keeps the cache's points.

### DC1. A relayed `clearAll` and M7's read rule (F11 (b), N78, N84)

**Question.** Under F11 (b) one `clearAll` makes every worker clear about k + 1 times, k being the number of other workers (§4.6.2). M7 was a proposal when that cost was written down. As built, every clear sends `cacheChanged { cleared: true }` for every cache, an empty one included (N78), and the read rule answers such an event with a fetching read by every subscribed view (N84). So one `clearAll` costs a subscribed view up to k + 1 fetching reads. What a tab fetched between two of the clears is dropped and fetched again; a `get` pending across two of them can come back `uncached` (N29's second round), until the read after the last event fills the view. N84, which is locked, states the bound this exceeds: the application's calls that write nothing lead "to at most one fetching read per subscribed view" each. Nothing loops: each worker relays a clear id once, so the count is fixed by k, and k is 0 unless two generations or two keys run side by side.

| Option                                                                                                                                                                                                             | Pros                                                                                                                               | Cons                                                                                                                                                                                             |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| (a) As decided: every message a worker acts on clears its memory and sends both events. A dated note on N84 and a sentence in the guide say that a `clearAll` relayed across k other workers counts as k + 1 calls | Nothing to design; the proof of §4.6.2 and test 10 stand as approved; the cost is bounded and falls only on a logout during a skew | Up to k + 1 fetching reads per subscribed view, with misses shown between them; a note on a locked decision                                                                                      |
| (b) A clear from the channel sends no event for a cache it found empty                                                                                                                                             | A view that has not read again yet is not told twice                                                                               | Amends N78 (locked) for channel clears; a view that already fetched again is still cleared and told, so the saving is small                                                                      |
| (c) A repeat message for a clear id clears memory only when the worker loaded from the disk since its first clear for that id                                                                                      | One event per view in the common case                                                                                              | Changes the receiver rule of the approved F11 (b); the disk clear without a memory clear needs a rewrite rule (N57) and a new proof; tests 8 and 10 change, so the Codex round would wait for it |
| (d) The integrations drop `cleared` events without a `requestId` that follow one another closely                                                                                                                   | No protocol change                                                                                                                 | Needs a time window, which the library's events avoid (N73); applications with their own views get nothing                                                                                       |

**Recommendation: (a).** The repeated clears are what closes the logout gap, the cost is small and bounded, and a note records it.
