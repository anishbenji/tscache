# M5: deploy skew — design proposal

Status: **proposal for the user's decision** (step 100, 2026-11-14). Nothing here is built or approved. It answers finding M5 of the review of 2026-11-10 (`docs/reviews/2026-11-review.md`, M5 and §3d) under user decision 46 A: after 0.1.0, three design steps in the order M7, M3, M5, each a spec first, then the user's decision rows, then contract tests. The open choices are the decision rows F1–F15 in §5; §4 describes the design with each row's recommended option taken, and says where a row changes it.

**Why a proposal file, not a section of `docs/architecture.md`.** The architecture document records approved contracts, and each of its sections was written after its decisions were taken. This design has fifteen open rows, and four would amend approved text: the persistence rules for two engines writing one database (§4.10.7, N52; F5), the reach of `clearAll` (§4.10.7, N54, N66; F11), the SharedWorker creation options (§4.8 and §4.10.8; F1), and the review checklist's persistence item (§12, a protected path). The handshake of §3.1, which is locked, is left as it is by every recommended option; the options that would change it are marked. Once the user has decided the rows, the contract-test step moves the approved text into architecture §2.1 and §2.7 (the event and the property), §3.2 (the event name), §4.8 (hosting), §4.10.6–§4.10.8 (persistence), adds the decision files under `docs/decisions/`, and this file stays as the record of the alternatives. M7 (`docs/design/m7-change-events.md`, step 92) and M3 (`docs/design/m3-memory.md`, step 98) are proposed the same way.

## 1. The gap

A deploy reaches open tabs in one of three ways today, and none of them has a recovery path:

1. **Rejected.** A tab whose worker speaks another protocol version cannot create a client: `createClient` rejects with `ProtocolMismatchError`, and the guide's advice is "close the old tabs and reload" (`site/troubleshooting.md:17-25`). An application cannot close a user's other tabs.
2. **Rejected, and more common than (1).** A tab whose fetcher module URL differs from the one the running SharedWorker loaded cannot create a client either: `createClient` rejects with `ConfigError` ("this worker already runs fetcher …"). §2.3 shows that with Vite's `?worker&url` and `?fetcher` (the setup every example uses), a deploy that changes the fetcher but not tscache keeps the worker's URL and changes the fetcher's, so this is what such a deploy does to every new tab until the old ones close.
3. **Silent.** A deploy that changes the worker script's URL (a tscache upgrade under a hashed URL) starts a second SharedWorker. Tabs of the two deploys stop sharing memory, in-flight fetches, `clear`, `clearAll` and `authInvalid`; nothing reports it; and both workers write the one IndexedDB database of the origin, which N52 accepts on the premise that the overlap is brief (`docs/architecture.md:1705-1710`). A tab left open keeps the old worker alive for days.

The finding also notes that `hello.lib` is never read. Step 82 documented the limit (`site/guides/workers.md:132-178`, `site/guides/persistence.md:84-86`, `docs/guides/patterns.md:167-171`).

This proposal makes every deploy that changes what the worker runs start a worker of its own (case 3), never cases 1 or 2 against a running worker; lets the workers of different deploys find each other; has the older ones stop writing the database and tell their tabs; and lets a logout reach every deploy's worker. It adds no message to the handshake and keeps `PROTOCOL_VERSION` at 1.

### 2.3 A probe: what a hashed worker URL depends on

The guides say a hashed worker URL "gives each deploy a SharedWorker of its own" (`site/guides/workers.md:146-147`; architecture §4.10.7, `docs/architecture.md:1707`). That holds only for deploys that change the worker bundle. Vite builds the `?worker&url` entry on its own, and the fetcher is a chunk the worker loads with `import()` at runtime, so the worker's content hash does not see the application or its fetcher. A probe on 2026-11-14 (Vite 8.3, `examples/react-lwcharts`, built twice into a scratch directory, the second time with one exported constant added to `examples/mock-backend/src/fetcher.ts`; both edits reverted) gave:

| Worker format           | Worker file, first build | Worker file, second build | Fetcher file, first → second                  |
| ----------------------- | ------------------------ | ------------------------- | --------------------------------------------- |
| `es` (the example's)    | `worker-_aG70VYQ.js`     | `worker-_aG70VYQ.js`      | `fetcher-DfwwfM5A.js` → `fetcher-BNLmUWkn.js` |
| `iife` (Vite's default) | `worker-oS7chE_R.js`     | `worker-oS7chE_R.js`      | `fetcher-DfwwfM5A.js` → `fetcher-BNLmUWkn.js` |

So a deploy that changes the fetcher keeps the worker's URL and changes the fetcher's: the second row of §2.2, a rejected `createClient` in every new tab. The guides' statement and the §4.10.7 bullet should be corrected whatever is decided here (§7).

## 3. The failure shapes

### 3.1 Rejected at connect

- **Protocol mismatch.** Possible only when a page and the worker it reaches come from different tscache versions with different `PROTOCOL_VERSION`: a fixed worker URL whose running worker is older (old tabs keep it alive), or a script served stale. The page rejects (`rpc/port-client.ts:162-166`) or the worker refuses `init` (`rpc/server.ts:247-258`); under N25 neither falls back. `PROTOCOL_VERSION` has never changed, and N37 keeps additive changes at 1, so this shape has not yet occurred in a release.
- **Fetcher conflict.** A page whose fetcher URL differs from the running worker's (`orchestrator/orchestrator.ts:298-303`). With hashed fetcher URLs it follows every deploy that changes the fetcher, at either kind of worker URL (§2.3). Like the protocol mismatch it rejects without falling back, since `ConfigError` is not a `HostingError` (`client/client.ts:143-144`).

Neither shape touches the database: the tab never gets a client.

### 3.2 Silent: two workers side by side

Two SharedWorkers of one origin, each with its own engine, orchestrator, fetcher and persister. Their tabs share nothing: a `clear`, a `clearAll`, an `authInvalid` or an in-flight fetch in one worker does not reach the other's tabs (`rpc/server.ts:408-412`), and both fetch the ranges both views show.

Both write the database `tscache`, each plainly from its own memory (§4.10.7). What happens to the records depends on what differs between the two deploys:

| What differs                                                                                                         | What the two writers do to each other                                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Nothing a record names (same structure and version)                                                                  | Records interoperate: each page record is self-contained and checked on its own (N55). The cost is coverage: a full rewrite by one deletes every page of the cache first (`persist/persister.ts:946-948`), including pages only the other had written; and one can write back a range the other removed while it still covers it in memory (N52's accepted cost)                                                                                               |
| The cache's structure (N20: fields, dtypes, interval, alignment, `gapSplitK`, `segmentSlotCap`, `warnOnOverlapDiff`) | Every flush puts the writer's own cache record (`persist/persister.ts:950`), so the cache record flips to whichever wrote last. A load then rejects the record of the other structure and applies nothing of the cache (`engine/restore.ts:115-121`, `:191-199`), and that cache is rewritten at its next flush, a full rewrite that deletes the other's pages. While both run, a reload in either deploy starts that cache cold whenever the other wrote last |
| The dataset `version` (N56)                                                                                          | As for structure: a record of another version applies nothing (`engine/restore.ts:117-121`), and the two rewrite each other. No wrong point is ever loaded                                                                                                                                                                                                                                                                                                     |
| The database layout (a later IndexedDB version)                                                                      | The newer worker's upgrade fires `versionchange` at the older connection, which closes itself (`persist/idb-store.ts:113-114`); the older worker's later writes fail, and its caches stop at their deadlines (`persistStopped`). An older worker that opens after the upgrade cannot open at all: persistence is `'unavailable'` for it (§4.10.2). Only one writer remains                                                                                     |
| The record `format` or `Snapshot.format`                                                                             | As for structure: applies nothing, or skips that page, and rewrites (§4.10.2 table)                                                                                                                                                                                                                                                                                                                                                                            |

Two further costs do not depend on what differs. A logout's `clearAll` in a tab of one deploy empties its engine and the disk, but the other worker keeps its memory and writes back the pages it changes (`docs/architecture.md:1723`); a logout from an old tab leaves the new worker's memory alike. And under M3, each worker has a budget of its own (`docs/design/m3-memory.md` §3.2).

### 3.3 Silent: one worker, two deploys

At a fixed worker URL, or at a hashed one when only the application changed, new tabs join the old worker. When the deploys agree on tscache and the fetcher, the worker runs exactly what the new tabs would have run, so nothing is skewed: that is the case where sharing is right. When they agree on the protocol but not the library, new tabs run the old library's worker code, and `hello.lib` tells them nothing because nobody reads it.

### 4.2 Worker identity: one SharedWorker per generation (F1, F2)

The shared hosting passes a name: `new SharedWorker(url, { type: "module", extendedLifetime: true, name })`, where `name` is the page's **generation key**:

```ts
// client/hosting.ts (sketch). LIB_VERSION: rpc/protocol.ts. fetcher: the
// string the page passes (client/client.ts:97-103), as the worker compares it.
const name = `tscache:${LIB_VERSION}:${fetcher?.module ?? ""}`;
```

The key holds everything that decides what the worker runs: the library (the worker script's version, which `test/version.test.ts` keeps equal to the package's) and the fetcher module (the only application code inside the worker, N44). Two pages with the same key would run the same code in the worker, so they share one, at a fixed or a hashed URL alike; two pages with different keys never share one. Consequences:

- **A fetcher change starts a new worker** instead of a `ConfigError` against the old one. The guard in `orchestrator/orchestrator.ts:298-303` stays, now reachable only when two pages pass the same library and different strings for one module (§4.9).
- **A tscache upgrade at a fixed URL starts a new worker** instead of running the old code (same protocol) or rejecting with `ProtocolMismatchError` (new protocol). A protocol mismatch then needs a stale _script_, not a running old worker (§4.8).
- **At a hashed URL**, a tscache upgrade already starts a new worker; the name adds the fetcher, which the URL does not see (§2.3).
- **Nothing changes for a deploy that changes neither** the library nor the fetcher: its tabs join the running worker, as now. Application code, cache configs and budgets are not in the key; a changed cache structure is still refused by N20 within the worker, and a changed budget waits for the worker to restart (M3 E3).
- **Tabs of 0.1.0** pass no name, so a release with this design never joins a 0.1.0 worker, even at a fixed URL.

The dedicated-worker and in-process hostings are per tab and take no name.

### 4.3 Finding the other generations (F3, F4)

Each SharedWorker opens a `BroadcastChannel` named `tscache-workers` once its first connection has completed `init` (it then knows its fetcher), and posts one message:

```ts
// Worker ↔ worker, on BroadcastChannel "tscache-workers". A channel message
// may come from any release: unknown `t` or `v` values are ignored.
type Announce = {
  t: "announce" | "present";
  v: 1;
  id: string; // this worker's lifetime lock name (N32), or a random id
  lib: string; // LIB_VERSION
  key: string; // the generation key of §4.2
  startedAt: number; // performance.timeOrigin of the worker
};
type ClearAll = { t: "clearAll"; v: 1; id: string };
```

- A worker that receives an `announce` from another `id` answers with one `present`, so a newcomer learns of the workers already running.
- Each side compares the two by **rank**: the higher `lib` (by semantic version) ranks higher; for equal `lib`, the later `startedAt`; for equal `startedAt`, the greater `id`. Both sides compute the same answer from the same two messages.
- A message with the worker's own `key` is not skew: it is a closing worker and its successor of the same generation (§4.10.7), and neither acts on it.
- A worker that finds a higher-ranked worker of another key is **superseded** (§4.4, §4.5). It never becomes current again (F6).

The channel is the origin's (more exactly, the storage key's, the same partition as the database), so it reaches exactly the workers that write that database. Workers of 0.1.0 neither announce nor listen: a release with this design neither sees them nor reaches them (F3 records the lock-query alternative that could see them).

### 4.4 The superseded worker stops writing the database (F5, F6, F7)

When a worker is superseded, its persister stops persisting for the rest of its life, by the path a failed `clearAll` already takes (`persist/persister.ts:166`, `:227-229`):

- Every tracked cache stops with `persistStopped { reason: 'superseded' }`, **without** the cleanup deletion (`#stop(…, cleanup = false)`, `persist/persister.ts:578-597`): the records belong to the current generation now. Dirty state and queued jobs are dropped; an attempt already running is abandoned as by any stop, and IndexedDB may still commit it.
- A cache opened later stops at once with the same reason, reading nothing.
- Waiters for a removal's durability (N58) are released by the stop, as for any stop, so an `invalidate` or `clear` answers at once. Such a removal does not reach the disk; the current generation's engine never held the old engine's memory anyway, so the disk is no worse than the current generation's own state.
- `clearAll` still empties the disk, as the clear-only call does (N66): a logout from an old tab must not leave records behind.

The current generation's worker changes nothing: it loads and writes as before. From the moment a worker is superseded, the database has one writer again. Before it, during the time between the new worker's start and its first `init`, both write, as during a closing worker's final flush.

### 4.5 What the application is told (F8, F9, F10)

The superseded worker tells every ready connection, and every connection that completes `init` later, with a client-scoped event:

```ts
// types.ts, ClientEvents (additive)
/**
 * A worker of a newer generation of this application (another tscache
 * version or another fetcher module) is running in the origin. This tab's
 * worker no longer persists; the tab keeps working from memory and its
 * fetcher. Reload the tab to join the newer worker. Fires at most once.
 */
superseded: { lib: string };

// TscacheClient (additive): set when the event arrives, for a listener
// attached later (the lesson of modeFallback, client/client.ts:172-186).
readonly superseded: { lib: string } | undefined;
```

- **Only the superseded side is told.** The current generation's tabs need to do nothing.
- **The library never reloads a page.** The guide recommends showing the user a prompt to reload. An automatic reload is the application's choice; the guide warns that a page served stale (an HTTP cache, a service worker's old shell) can rank as newer by start time and make the current worker's tabs reload into the stale build (F4's con).
- **In development**, the client prints one `console.info` naming both library versions.

### 4.6 `clearAll` reaches every generation (F11)

A `clearAll` from any hosting, after it has started its own clear, posts `{ t: "clearAll", v: 1, id }` on the channel. Every SharedWorker that receives it from another `id` runs `clearAll` exactly as if one of its own tabs had called it: its engine clears (its tabs get `cacheCleared { reason: 'clear-all' }`) and, when it persists, its disk clear runs. The posting call does not wait for other workers: their number is unknown and any of them may be closing. It answers as now, once its own disk clear is done or failed (N54, N66). A `clearAll` run because of a channel message posts nothing, so two workers never echo each other's clear.

This closes the logout gap §4.10.7 records for a SharedWorker of another deploy, and the one for a pinned dedicated or in-process tab whose origin also runs a SharedWorker (`docs/guides/patterns.md:149-156`). A dedicated or in-process hosting opens the channel only for that one post and closes it at once.

Any script of the origin can post on the channel and so clear every worker. It gains nothing it lacks today: it can create a client and call `clearAll`, or delete the database.

### 4.7 `hello.lib` (F12)

With §4.2, a page reaches a worker of another library only when the script at the worker URL is not the page's (a fixed URL whose script was replaced under an old page, or a script served stale). The client compares `hello.lib` with its own `LIB_VERSION` and, in a development build, warns once naming both. Nothing else changes: the protocol check stays the gate.

### 4.8 A protocol mismatch (F13)

With §4.2, a running worker of an older deploy can no longer cause a `ProtocolMismatchError`, since a newer page creates its own worker. What remains is a script served stale, for which a dedicated worker loads the same stale script and does not help. The recommendation keeps N25 as it is: the mismatch rejects. The guide's advice to retry with `mode: 'dedicated'` (`site/guides/workers.md:169-178`) is replaced by: reload with the HTTP cache revalidated, and serve the worker script with revalidation.

### 4.9 Edge cases

- **Two strings for one fetcher module.** A page passing `./fetcher.js` and another passing `/fetcher.js` get different keys and so different workers; today the second gets a `ConfigError` (the comparison is by string either way). The one that ranks lower is superseded, so the data stays correct, but the tabs no longer share. The guide states that every page of a deploy must pass the same string; the `?fetcher` import always does.
- **Pull-model use** (no fetcher): the key ends in an empty module; one worker per library version.
- **A third generation:** each worker yields to any higher-ranked worker it hears of; the highest remains current.
- **A current worker that ends first** (its tabs closed, the old ones kept): the old worker stays superseded and persists nothing until it ends (F6).
- **No `BroadcastChannel`** in the realm: no detection; the worker behaves as today. Every browser with SharedWorker has it.
- **The first upgrade from 0.1.0:** a 0.1.0 worker keeps writing the database beside the new one until its tabs close, as today, and a `clearAll` does not reach it.

### 4.10 Interactions with M7 and M3

- **M7, the compatibility rule** (`docs/design/m7-change-events.md:156`): adopted. Everything here is additive on the port: one event name, which an older client ignores (`client/events.ts:12-43`), and no op. The worker-to-worker messages are on a channel of their own with their own `v`, never on the port.
- **M7, D9 (`hello.features` or a `features` op):** not needed by this design, and not duplicated. If D9 (a) or (d) is adopted, the worker lists `'superseded'`, so a page can tell a worker that cannot report skew from one that has nothing to report. If neither is, a page of this release always meets a worker of its own library (§4.2), so the event's presence is known.
- **M7, `cacheChanged`:** stays within one worker. A generation's change never reaches the other's tabs, which hold other memory; the superseded event tells those tabs to reload.
- **M3, the budget op after the handshake (E18, E20):** not used here; this design adds no op. A connection to a superseded worker gets `superseded` after `init-ok`, in any order with the budget answer.
- **M3, first value wins (E3, E20):** the generation key gives a new library or fetcher a fresh worker, so its budget takes effect at once for its tabs. A deploy that changes only the budget keeps the running worker and its first value, as M3 states.
- **M3, two budgets during a skew** (`docs/design/m3-memory.md` §3.2): unchanged. A superseded worker keeps its memory until its tabs go; its budget still bounds it.

### 4.11 Cost

- **Nothing skewed:** zero per operation and per message on the port. Per SharedWorker: one `BroadcastChannel` and one `announce` at its first `init`, with no answer when it is alone. Per tab: one string concatenation at `createClient`. Per `clearAll`: one channel message (and, in the dedicated and in-process hostings, one channel opened and closed).
- **Skewed:** one `present` per running worker for each newcomer, the event to each tab of the superseded worker, and the persister's stop.
- **Bundle:** the worker entry grows by the channel handling and the rank comparison, the client by the name and the property; `scripts/size.ts` measures both, and the later step states the figures.

### 4.12 Public API, protocol and version

- **Public API, all additive:** `ClientEvents.superseded`, `TscacheClient.superseded`, and `'superseded'` in `persistStopped`'s `reason` union (F7). A union member is additive at runtime but can fail an application's exhaustive `switch` at compile time; the release notes say so.
- **Behaviour:** the SharedWorker is named (F1), so pages of different library versions or fetchers stop sharing a worker; `clearAll` reaches other workers (F11).
- **Protocol:** `PROTOCOL_VERSION` stays 1 (N37). The port carries one new client-scoped event name; the handshake (§3.1, locked) is unchanged.
- **Version:** a minor release under 0.x semver, on its own or with M7 and M3 (F15).

## 6. Contract tests for the later step

Contract tests that Codex writes first, from the approved text (strict test-first for `persist/`, AGENTS.md), at the level of the `Persister` over `MemoryStore` under fake timers and of `HostedPersistence`. Nothing under `engine/`, `orchestrator/`, `segment/`, `grid` or `coverage` changes.

1. **Superseding stops persisting.** After `supersede()`, every tracked cache reports `persistStopped { reason: 'superseded' }` once; no cleanup job runs and the store keeps every record; dirty state and queued jobs are dropped; the store sees no further write for those caches.
2. **Later opens.** A persisted cache opened after `supersede()` stops at once with `'superseded'` and reads nothing from the store.
3. **Removals are released.** A removal waiting for durability when `supersede()` runs is released at once, and its call answers; nothing is written for it.
4. **`clearAll` still clears.** After `supersede()`, `clearAll()` empties the store with strict durability and answers as before; a failed one behaves as a failed `clearAll` does today.
5. **A running attempt.** A flush attempt running at `supersede()` is abandoned: its result changes no state, and nothing is retried.
6. **Idempotent.** A second `supersede()` changes nothing and emits nothing.
7. **Before the persistence chunk.** `supersede()` on a `HostedPersistence` whose chunk has not loaded: a persisted cache opened later stops with `'superseded'` and nothing is read; a later `clearAll` still loads the chunk and empties the store.

RPC, hosting and client tests (written with the code, hybrid TDD). The rank is a pure function in the new worker-side module, so its tests can be properties:

8. **Rank.** For pairs of announcements: a higher `lib` ranks higher whatever the start times (`0.10.0` above `0.9.0`; a prerelease below its release); for equal `lib`, the later `startedAt`; for equal both, the greater `id`. The order is antisymmetric and transitive, and both sides of every pair agree. Two announcements with one key supersede neither, whatever their ranks.
9. **Name.** The shared hosting passes `name: "tscache:<LIB_VERSION>:<module>"` (empty module without a fetcher) with `type` and `extendedLifetime`; the dedicated and in-process hostings pass none.
10. **Announce.** A worker posts one `announce` after its first `init-ok` and none after later ones; it answers another `id`'s `announce` with one `present`; it ignores its own messages and any with an unknown `t` or `v`; with no `BroadcastChannel` in the realm it posts nothing and behaves as today.
11. **Superseded event.** A worker that hears a higher-ranked worker of another key sends `superseded { lib }` to every ready connection, and once to each connection that completes `init` later; `client.superseded` holds the payload; an older client ignores the event name.
12. **`clearAll` across workers.** A `clearAll` posts one `clearAll` channel message after starting its own clear and answers without waiting for other workers; a worker hearing another's `clearAll` clears its engine (its tabs get `cacheCleared { reason: 'clear-all' }`) and its disk; it ignores its own message, and a clear it runs because of a channel message posts nothing. The dedicated and in-process hostings post it too and close their channel.
13. **`hello.lib`.** A client whose `LIB_VERSION` differs from `hello.lib` warns once in a development build and connects; a production build prints nothing.

Browser (Playwright, one context, several pages). Two generations can be made without a second build, since the fetcher is part of the key: the end-to-end server serves the fetcher under two URLs, `/fetcher.js` and `/fetcher-b.js`.

14. **No more fetcher conflict.** Tab A connects with `/fetcher.js` and tab B with `/fetcher-b.js` at the same worker URL: both clients resolve, each `get` is answered by its own worker, and tab A's client reports `superseded` (B started later, same library).
15. **One writer.** A persisted cache in both tabs: after A is superseded, A's puts reach no record; after B's flush and a reload with `/fetcher-b.js`, the reload loads B's records without a fetch.
16. **Logout.** `clearAll` in tab B: tab A gets `cacheCleared { reason: 'clear-all' }`, A's next `get` fetches again, and a reload of either loads nothing from the disk.
17. **Same generation shares.** Two tabs with the same fetcher reach one worker (one `announce`, no `superseded`), as today; the messages-per-read budget is unchanged.
18. **Library skew** (a second build, or the end-to-end server serving a copy of the worker with another `LIB_VERSION` at another URL): the higher library's tabs stay current whatever the start order.

Bench: none new. The messages-per-read and memory budgets must be unchanged, since nothing is added per operation.
