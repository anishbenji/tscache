## 1. The gap

The grid is `alignmentOffset + k × interval` in fixed milliseconds (§4.1, N9). Two common shapes of OHLC data do not fit it:

- **Daily bars stamped at a session open in a daylight-saving zone.** A session that opens at 09:30 New York time opens at 14:30 UTC in winter and 13:30 UTC in summer. No `alignmentOffset` fits both, so a batch stamped at the open is rejected whole as `'misaligned'` for half the year.
- **Weekly, monthly, quarterly and yearly bars.** Weekly bars fit a fixed 604,800,000 ms step only in UTC; a week that starts at local midnight moves by an hour twice a year. Months, quarters and years have no fixed length at all.

Step 71 published recipes for both (§2.3): stamp a daily bar at 00:00 UTC of its trading date, stamp weekly bars on a fixed UTC weekday, and map months to a synthetic ordinal grid of interval 1 in the fetcher. They work, at a price the application pays: a daily cache holds dates rather than instants, and a monthly cache holds no times at all, so every range, watermark, result and event of it is an ordinal the fetcher and the chart must convert. The checkpoint of November 2026 (`~/code/tscache-reports/proposals/checkpoint-2026-11.md`, part 1, rank 8) calls this a real user-facing gap for an OHLC chart cache, and it touches a locked area.

### 2.4 What follows

Everything inside the engine except `grid.ts` runs on integer slot indices. Coverage, segments, pages, the gap rule, the slot cap, the in-flight subtraction and the persisted page keys never see a millisecond. A grid whose slots have different lengths is therefore, inside the engine, a change to the two primitives of `grid.ts` and nothing else, as the review's §3b noted. The cost lies at the edges where the grid is _named_ rather than _used_: the config and its N20 comparison, the payload and snapshot envelope and their JSON form, the cache record, the fetch request, the domain checks that assume every safe-integer slot has a timestamp, and the code outside the package that does grid arithmetic in milliseconds.

## 4. The options

The brief names four options. For each: the public API, what it costs every engine path that assumes fixed slots today, its bundle size against the budgets, and how it behaves with snapshots and persistence when records written under one grid are read under another.

### 4.1 (a) Recipes only, unchanged

- **API:** none. The four recipes of §2.3 stay; the docs keep the limit.
- **Engine cost:** none.
- **Bundle:** none.
- **Snapshots and persistence:** unchanged; a recipe cache is an ordinary fixed-grid cache, and its records are what the fetcher stamped. A change of recipe (for example from dates to ordinals) is a change of meaning the engine cannot see: the grid may be the same (`interval: 1` holds day ordinals and month ordinals alike), so records written under one mapping load silently under the other unless the application changes the cache's id or `version`.
- **Who pays:** every application with daily bars in a DST zone or with monthly bars, in conversions at the fetcher and at the chart, and the risk above.

### 4.2 (b) A pluggable grid in the config

The application supplies the two primitives: `slotOf(t)` (the slot at or before `t`) and `startOf(k)` (the timestamp of slot `k`), and the engine derives `isAligned`, the snaps and the watermark slot from them. Next and previous slots are `k ± 1` and need no function of their own.

- **API:** a config cannot carry a function across the port (`client/client.ts:208-215`, a structured clone), so the grid must be code the worker loads. The only application code a worker loads is the fetcher module (`rpc/server.ts:260-269`, N44); the fetcher module would export named grids, and the config would name one: `interval: { grid: "xnys-daily" }`. An application without a fetcher module (one that only hydrates and puts) needs a second way to load code into the worker, and the page needs the same functions for its own range arithmetic (§5.8).
- **Engine cost:** every path of §2.1 calls the grid through an interface instead of doing arithmetic, one call per point on the put and read loops (`engine/batch.ts:133`, `:297`; `engine/read.ts:83`); the domain checks (`grid.ts:107-116`, `:153-157`, `orchestrator/orchestrator.ts:75-77`, `segment/payload.ts:54`) ask the grid for its bounds. Correctness becomes the application's: a function that is not strictly increasing, not deterministic, or that differs between the page, the worker and the server corrupts coverage silently (a slot that maps to the wrong time is a confirmed gap or a misplaced bar). The engine can sample-check monotonicity at `cache()`, not prove it.
- **Bundle:** small in the package: the dispatch and the loading path, an estimated few hundred bytes on the worker and engine entries. The calendar code is the application's.
- **Snapshots and persistence:** the grid's identity is its name, which the application must change whenever the function's results change; records and snapshots written under an old function with the same name load as if nothing changed. N20 compares the name.

### 4.3 (c) Built-in calendar grids keyed by IANA zone and session

A small closed set of calendar units, described by data: `{ unit: "day" | "week" | "month" | "quarter" | "year", zone?, at?, weekStart? }`. The descriptor is structured-cloneable and comparable by value, so it crosses the port, serialises into snapshots and records, and takes part in N20 like any other field.

- **API:** the descriptor in `CacheConfig.interval` (G4), mirrored in the fetch request (G10) and the snapshot envelope (G9); a helper entry for the page (G11). §5 has the details.
- **Engine cost:** the same paths as (b), but with code the library owns and tests. In UTC the conversions are integer calendar arithmetic (days from a civil date and back), a few operations per call. In another zone each slot's start needs the zone's UTC offset at that local time, which the runtime's `Intl.DateTimeFormat` gives through `formatToParts`; that is far slower than a multiplication, so the engine keeps computed slot starts in tables shared by every cache of one descriptor (G19, §5.7). The slot at or before an arbitrary `t` needs only slot starts: the UTC date of `t` gives a candidate slot within two slots of the answer (§5.2).
- **Zone data:** the runtime's own (`Intl`), so nothing is bundled. Bundling a zone database was considered and rejected (G3): even a packed subset of the IANA database is many kilobytes, comparable to or larger than the worker entry's whole 13,728 B budget, and it ages with every IANA release. `Temporal` would do the zone arithmetic natively, but the package targets ES2023 (`tsconfig.json:4`) and cannot assume it in every supported browser; a polyfill also costs more than the worker's budget.
- **`Intl` limits:** a zone name the runtime does not know throws `RangeError` (reported as `ConfigError`); `Intl` converts an instant to local fields but not local fields to an instant, so the inverse is a guess-and-correct step of two or three calls; a local time that does not exist (the spring-forward gap) or exists twice (the fall-back overlap) needs a rule (G6), and so does a whole local date a zone skipped when it moved across the date line (G18); the zone rules are the runtime's ICU data, which differ between browser versions, and between a server's Node and a browser (G8); a runtime built without time-zone data cannot resolve any zone but UTC.
- **Bundle:** estimated 1–2 KB brotli on the `worker` and `engine` entries (calendar arithmetic, the `Intl` offset lookup, the shared tables of slot starts (G19) and the descriptor's validation), measured by `scripts/size.ts` in the build step. That exceeds the 3 % headroom of both budgets, so the build step raises them in a reviewed edit with the reason. The `index` entry grows by the client's feature check (G14) and by `decodeSnapshot`'s format 2 branch, since the root entry exports the JSON form (`entries/index.ts:26`); the page helpers live in their own entry (G11).
- **Snapshots and persistence:** the descriptor names the grid in the envelope, payload and cache record, and in their JSON form for server rendering (N38), compared by value; a cache of another grid refuses a snapshot and does not apply records, as today. Within one descriptor, a change of the runtime's zone rules can move a slot's start; §5.6 and G8 say what happens then.

### 4.4 (d) An ordinal grid the user maps

The monthly recipe made a library feature: the engine stores ordinals on a grid of interval 1, and a mapping layer in the page converts between milliseconds and ordinals at every call: ranges, timestamps and watermarks going in; timestamps, coverage, misses and event ranges coming out. The mapping is two functions given to `client.cache()` and kept in the page, never sent to the worker.

- **API:** an option of `client.cache()` that the page-side handle applies (`ordinal: { toOrdinal(t), toTime(n) }`); the worker sees an ordinary `interval: 1` cache.
- **Engine cost:** none; N9 and every engine path are untouched. The cost moves to the page: an extra pass over every result's timestamps on the main thread, a conversion of every event range, and a fetcher that still receives ordinals, because the fetcher runs in the worker, where the mapping is not (the fetcher module must carry the same functions, as in today's recipe).
- **Bundle:** small, on the `index` entry (the mapping layer), which every application loads; an estimated few hundred bytes.
- **Snapshots and persistence:** they hold ordinals. The mapping is invisible to the engine, so two mappings over `interval: 1` look identical to N20, to `hydrate` and to a load: a changed mapping silently re-labels every stored record unless the application changes the id or `version`. A server-rendered snapshot is correct only when the server maps as the page does.

## 5. The design (recommended options taken)

### 5.1 The descriptor

```ts
/** A calendar grid: one slot per calendar unit in a time zone (G1 c). */
interface CalendarInterval {
  /** G2 (a). */
  unit: "day" | "week" | "month" | "quarter" | "year";
  /** An IANA time zone, compared as written (G7). Default "UTC". */
  zone?: string;
  /** Local wall-clock time each slot starts at, "HH:MM" (24-hour). Default "00:00". */
  at?: string;
  /** For unit "week" only: the first day, 1 = Monday … 7 = Sunday (ISO 8601). Default 1. */
  weekStart?: 1 | 2 | 3 | 4 | 5 | 6 | 7;
}

interface CacheConfig {
  /** A fixed interval in ms, or a calendar interval (G4 a). Required, no default (decision 2). */
  interval: number | CalendarInterval;
  /** Fixed intervals only; must be absent or 0 with a calendar interval (G4). */
  alignmentOffset?: number;
  // … unchanged
}
```

Examples:

```ts
// Daily bars of a New York session, stamped at the open, all year.
{ id: "candles/ACME/1d", interval: { unit: "day", zone: "America/New_York", at: "09:30" }, fields }
// Weekly bars starting Monday at local midnight in London.
{ id: "candles/ACME/1w", interval: { unit: "week", zone: "Europe/London" }, fields }
// Monthly bars at 00:00 UTC of the first day.
{ id: "candles/BTC/1mo", interval: { unit: "month" }, fields }
```

The resolved config holds the descriptor with its defaults applied, frozen, `weekStart` present only for weeks. A fixed config resolves exactly as today.

### 5.2 Slots and the two primitives

- **Slot numbering.** Slot 0 is the unit that contains the local date 1970-01-01 in the grid's zone: for days, the local day number since that date; for weeks, the week containing it (a Thursday), so with `weekStart: 1` slot 0 starts on Monday 1969-12-29; for months, `(year − 1970) × 12 + (month − 1)`; for quarters, `(year − 1970) × 4 + ⌊(month − 1) / 3⌋`; for years, `year − 1970`. Slots before 1970 are negative, as today. The numbering depends only on the descriptor, never on the data or on the zone's rules, so page keys (N15) are stable across rule changes.
- **`startOf(k)`**, the generalised `msOf`: the instant at which the local date that begins unit `k` reads `at` on the wall clock of the zone. In UTC it is calendar arithmetic. Elsewhere it resolves the local time through the zone's offset, with the rule of G6 for a local time that does not exist or exists twice. `startOf` must be strictly increasing in `k`, since coverage and `toMs` rely on distinct slots having distinct starts. Daylight-saving shifts never break that, but a zone that moved across the date line skipped a whole local date: Pacific/Apia has no 2011-12-30 (its clock went from 2011-12-29 23:59 at UTC−10 to 2011-12-31 00:00 at UTC+14, at 2011-12-30 10:00 UTC), and Pacific/Kwajalein has no 1993-08-21 (from UTC−12 to UTC+12 at 1993-08-21 12:00 UTC); both are in the runtime's zone data. G6 (a) alone would give the skipped date's day slot the start of the next day, so two slots would share one start: coverage ending at the skipped slot would convert to milliseconds that read back as the next slot, a confirmed gap over a day never fetched. G18 decides that slot's start; with G18 (b) it starts one millisecond before the next slot, so `startOf` stays strictly increasing and the slot, which no bar is stamped at, stays empty, provided records written under zone data from before the skip are refused: G8 (c) refuses them, while under G8 (a) such a record can put a bar there (§5.6). A skipped date affects only day slots: a week, month, quarter or year whose first local date was skipped starts at G6's next existing instant, still before the next unit. A local date that exists twice (a zone that moved the other way) makes its slot about 48 hours long, which breaks nothing.
- **`floorSlot(t)`**, the slot at or before `t`: start from the candidate slot of `t`'s UTC date and step until `startOf(k) <= t < startOf(k + 1)`. A day slot's start lies from about 14 hours before to about 36 hours after the UTC midnight of its date with today's offsets (`at` up to 23:59, offsets from UTC−12 to UTC+14), and within a day before to two days after with any offset under a day, historical local mean time included (about −16 hours in Asia/Manila before 1845), so the answer is at most one slot above the candidate and two below it: with `{ unit: "day", zone: "America/Los_Angeles", at: "18:00" }` in winter, local date D starts at D+1 02:00 UTC, so for `t` at D+1 00:30 UTC the candidate D+1 and the slot D both start after `t`, and the answer is D−1. For longer units one step suffices. The build asserts the bound in its tests (test 2) rather than looping without one.
- **Everything else as today, in terms of the two:** `isAligned(t)` is `Number.isSafeInteger(t) && startOf(floorSlot(t)) === t`, and false when `floorSlot` throws `InvalidRangeError` for a `t` outside the domain (below); `snapOut`, `snapIn`, `slotAtOrAfter` and `toMs` keep their code. N1 (outward snap of reads), N13 (inward snap of a put's range) and the watermark (`slotAtOrAfter`, §2.4) keep their meaning, with "the grid point at or before" read on the calendar.
- **Supported domain (G12), checked once, inside the two primitives.** The domain is the slots `kMin` to `kMax` whose local date lies in the years 1–9999; both bounds follow from the descriptor by calendar arithmetic, with no `Intl` call. `floorSlot(t)` first checks `t` against an arithmetic outer bound (UTC 0001-01-01 minus two days to 10000-01-01 plus two days, wider than any zone offset and far inside `Date`'s range of ±8.64 × 10^15 ms), throwing `InvalidRangeError` before any `Intl` call, then steps to its slot and throws `InvalidRangeError` if that slot lies outside `kMin`–`kMax`. `startOf(k)` throws `InvalidRangeError` for a `k` more than two slots outside `kMin`–`kMax` (its neighbours are needed by `floorSlot`'s steps at the edges; their local dates lie within two units of the years 1–9999, from year −1 to year 10001 at most, as for a yearly grid's `kMin − 2` and `kMax + 2`, all inside `Date`'s range and valid for `Intl`). No caller checks the domain itself; every one inherits the primitives' error. `snapOut`, `snapIn`, `slotAtOrAfter` and `toMs` reject with `InvalidRangeError`, as §4.1 says they reject slots beyond the safe integers today; `isAligned` turns it into false, so a put reports `PutError` `'misaligned'`; `get`, `invalidate`, `coverage` and `setFinalizedUntil` reject with `InvalidRangeError` (`engine/cache.ts:345`, `:453`, `:459`, `:481`); a load's stored watermark is set aside as not applied (`storedWatermark`, `engine/restore.ts:201-209`, catches `InvalidRangeError` only); and `hydrate` rejects a snapshot's watermark with `TscacheError` (`checkMeta`, `engine/snapshot.ts:194-199`, which also catches `InvalidRangeError` only). Without the check inside the primitives, every one of those paths would meet `Intl`'s own `RangeError` ("Invalid time value", thrown for any instant beyond ±8.64 × 10^15 ms, such as 9 × 10^15, a safe integer) and rethrow it, so a malformed stored watermark would fail the whole load. A `RangeError` out of `Intl` can then only be a bug. The other checks that assume a safe-integer slot has a timestamp (`grid.ts:107-116`, `:153-157`; `orchestrator/orchestrator.ts:75-77`; `segment/payload.ts:54`) ask the grid for `kMin` and `kMax` instead.

`grid.ts` stays the one place where milliseconds become slots (G13 a): the calendar arithmetic, the `Intl` lookup and the tables of slot starts are in it, and the fixed-grid functions keep their current arithmetic unchanged.

### 5.3 What stays in slots, unchanged

Coverage, segments, the gap rule (N14: "more than K consecutive slots"), the slot cap (N12), pages (N15), the in-flight subtraction (§4.9.1), the persisted page keys and the IndexedDB layout (one database at version 1, keys `['cacheId', 'page']`, N51). A calendar slot is a session, a week or a month, so their sizes read in those units: with the default `segmentSlotCap` of 32,768, one page of a daily cache spans about 89 years, and of a monthly cache about 2,730. That is also true of a fixed daily cache today.

### 5.4 Trading days, weekends and holidays

Every calendar day is a slot (G5 a). A day without a session is an empty slot: the fetcher's response covers it (its `range` is the request) and holds no bar for it, so the engine records a confirmed gap and never fetches it again, exactly as it does today for a weekend on a fixed daily grid. A weekend is two empty slots and a long weekend three or four, within the default K = 4, so they stay inside one segment; a closure of more than four days splits it (N14), as on a fixed daily grid today: a week-long national holiday such as the Shanghai exchange's in October, the Lunar New Year closures, or the New York Stock Exchange's closure from 11 to 16 September 2001 (six empty slots with the weekend). The empty slots inside a segment cost their capacity (weekends alone are about 2/7 of a daily cache's slots). No holiday list is part of the grid, so the numbering never changes when an exchange adds a holiday.

### 5.5 Where the grid is named

- **Config and N20.** `interval` is compared by value: two numbers with `===` as today, two descriptors by their resolved fields, and a number never equals a descriptor. `alignmentOffset` is 0 for a calendar cache. The structural list of N20 (`engine/engine.ts:31-40`) is unchanged; the cache record's list (`engine/restore.ts:26-32`) is compared with the same value equality.
- **Errors.** An unknown unit, a zone the runtime does not resolve, an `at` that is not `HH:MM` from `00:00` to `23:59`, a `weekStart` on a unit other than week, or a non-zero `alignmentOffset` with a calendar interval reject `cache()` with `ConfigError` naming the field. A misaligned put names the calendar ("not the start of a day in America/New_York at 09:30") instead of `t ≡ offset (mod interval)`.
- **Payload, snapshot and cache record (G9 a).** A calendar cache writes `format: 2` envelopes, payloads and cache records, in which one field, `grid`, replaces `interval` and `alignmentOffset`: `grid` is the resolved descriptor. With G8 (c), format 2 also stores, beside each instant that names a slot, the slot index it had under the zone rules it was written with: `startSlot` beside each payload's `start`, and `rangeSlots` and `coverageSlots` beside the envelope's `range` and `coverage` (the cache record's watermark needs none, since `slotAtOrAfter` accepts any instant); the JSON form carries them as numbers, and every reader refuses the record or snapshot when `slotOf` of a stored instant differs from its stored index (§5.6). The payload's rule becomes "slot i is the i-th slot after the slot of `start`", which is what the decoder already computes (`segment/payload.ts:51-57`). A fixed cache keeps writing `format: 1` with the same bytes as today, so no stored record or rendered snapshot of a fixed cache changes. Readers accept both formats; a fixed cache refuses a format 2 snapshot and a calendar cache a format 1 one (the grid differs), and 0.1.0 engines refuse format 2 as an unsupported format (`engine/snapshot.ts:135`, `segment/payload.ts:27`), never misreading it.
- **The JSON form for server rendering (G9 a, N38).** `encodeSnapshot` and `decodeSnapshot` carry both formats: a format 2 envelope and its payloads keep their `grid` (the descriptor is plain JSON) and the base64 of masks and field data, and `decodeSnapshot` checks a format 2 envelope's `grid` for shape (an object with a string `unit`) and leaves its meaning to `hydrate`, as it does for everything else today (`snapshot.ts:122-127`). `decodePayload` rebuilds each payload in its own format instead of always `format: 1` (`snapshot.ts:107-119`). `EncodedSnapshot` and `EncodedSegmentPayload` become unions of the two formats, as `Snapshot` and `DenseSegmentPayload` do. A 0.1.0 `decodeSnapshot` refuses a format 2 value ("format must be 1"), so a page on the old library given a new server's snapshot fails at decoding, before `hydrate`.
- **Fetch request (G10 a).** `FetchRequest.interval` mirrors the config: `number | CalendarInterval`; `alignmentOffset` is 0 for a calendar cache. The range is in milliseconds, aligned to slot starts, coalesced as today: a miss that abuts covered slots is extended one slot into them (a month on a monthly cache), and a flank with no coverage next to it is not (`orchestrator/orchestrator.ts:126-157`). The comment at `types.ts:333` changes from "flanks extended by one interval" to say that.
- **Results and events.** Unchanged in shape: `timestamps`, `coverage`, `misses`, snapshot ranges, watermarks and M7's `cacheChanged` ranges are milliseconds on the grid, converted by `toMs` as today.

### 5.6 Zone rules that change

A slot's start in a zone is computed from the runtime's zone rules. These change when a browser or Node release ships a new IANA database, which happens when a country changes its daylight-saving rules. The descriptor stays the same, so N20, `hydrate` and a load all accept the other runtime's data. What then happens, with G8 (c), recommended, and with its cheaper alternative G8 (a):

- A snapshot or page record is self-describing in slots: its payloads hold `start` and slot-relative entries, and its range and coverage endpoints must be aligned (`engine/snapshot.ts:156-174`). If the change moved neither the record's endpoints nor its `start`, the record applies, and each point keeps its slot, its session, and reads at the instant the new rules give. That is the right reading for bars whose identity is their session.
- If the change moved an endpoint or a `start` off the grid, the alignment checks refuse that record: the page is skipped and the cache rewrites it at its next flush (§4.10.2, "Snapshot and payloads"), and a `hydrate` rejects. That covers every change of a fraction of a slot: a daylight-saving rule moved by an hour, a zone's standard offset changed, and on a week, month, quarter or year grid any change at all, since no zone moves its clock by a whole week.
- **A whole-day change on a day grid, the reason G8 (c) is recommended.** A rule change of exactly one day, as when a zone moves across the date line, moves each later slot start by exactly one slot, so a stored instant stays aligned and alignment alone cannot see the change: the decoder checks only `isAligned(p.start)` and then takes `slotOf(p.start)` (`segment/payload.ts:42`, `:51`), and the snapshot check is the same (`engine/snapshot.ts:156-174`). Pacific/Apia is the case: under zone data from before its December 2011 change (UTC−10), 2011-12-31 00:00 local is 2011-12-31 10:00 UTC; under current data that instant is 2012-01-01 00:00 local. Under G8 (a), a record written under the old data and read under the new passes every check, with three effects. A one-point snapshot's bar moves silently from slot 15,339 (2011-12-31) to slot 15,340 (2012-01-01), both on page 0; in general every point of a payload that starts after the change shifts one slot. A payload that starts before the change keeps its points' slots, since they are relative to a start that both rule sets agree on: in a record covering 2011-12-01 to 2012-01-05, whose payload starts at slot 15,309, the old 2011-12-30 bar stays in slot 15,338, the date the current rules skip, and is returned at G18 (b)'s synthetic instant, 2011-12-30 09:59:59.999 UTC, an instant G18 (b) assumes no bar uses. And that record's range end reads one slot later, 2012-01-06 (slot 15,345), a covered slot with no point, which the engine treats as a confirmed gap and never fetches. G8 (c) closes all three with one exact check: the stored slot indices (§5.5) are compared with `slotOf` of their instants, so the one-point record's start reads 15,340 against a stored 15,339, and the spanning record's range end 15,345 against a stored 15,344; each record is refused (its page skipped and rewritten at the next flush, a `hydrate` rejected with `TscacheError`), and the data is fetched again under the current rules. G8 (a) remains the cheaper alternative, with this exception documented: it needs a record about dates after a date-line move written under zone data that predates the move.
- In practice rule changes concern future dates, so cached history is rarely touched, and an OHLC cache holds no bars for dates that have not happened; the whole-day exception therefore needs data written after the change under zone data that predates it. The server-rendering case is the visible one: a Node server and a browser with different zone data render and hydrate the same descriptor; the docs tell server-rendering applications to keep Node's ICU data current, and `hydrate`'s rejection is the signal.

### 5.7 Performance

The fixed grid's hot loops are untouched: `isAligned` and `slotOf` on put (`engine/batch.ts:133`, `:297`) and `msOf` on read (`engine/read.ts:83`) keep their arithmetic, and the grid kind is decided once per call, not per point, so the bench gate (`docs/benchmarking.md`) holds for fixed caches with no budget change. A calendar grid in a non-UTC zone needs `formatToParts` to compute a slot's start, two or three calls of about 1.4 µs each (measured in Node 26.13), and every conversion asks for starts, not only stored data: `snapOut` of each read's and invalidation's endpoints, `toMs` of coverage and misses, `slotAtOrAfter` of each watermark, and `floorSlot`'s neighbours. With G19 (c), the engine keeps **tables of slot starts per resolved descriptor**: a table holds the starts of 512 consecutive slots (a block, `⌊k / 512⌋`), computed whole on first touch, except at the two edges of the domain: a block that reaches past `kMin − 2` or `kMax + 2`, the margin `startOf` accepts (§5.2), holds only the slots within it, and the rest are never computed (for a yearly grid, year 9999 is slot 8,029 in the block of slots 7,680–8,191, whose table holds 7,680–8,031), and all tables of the engine share one least-recently-used order with a fixed capacity (256 tables, about 1 MB, in the sketch). The tables are a pure function of the descriptor and the runtime's zone rules, so every cache with the same descriptor shares them: a thousand daily caches of New York sessions use the same tables, and `clear`, `clearAll` and eviction have nothing to drop. Costs: a cold block costs about 1.5–2 ms; a 35-year daily chart touches 25 blocks, about 50 ms once, then one array lookup per point on every redraw; the capacity covers about 350 years of daily slots or 10,000 years of monthly slots before a single read can make tables evict one another. A UTC calendar needs no table: its conversions are arithmetic. The build step adds calendar rows to the bench (put and read of a year and of 35 years of daily bars in `America/New_York`, cold and warm tables, and a read of more blocks than the capacity) with budgets set from their first measurement. M3 counts segment bytes only and leaves object overhead out (E5 a); the tables' fixed capacity, engine-wide, limits their memory.

### 5.8 The page side

The page needs grid arithmetic too: M7's integrations decide whether a change touches a view by snapping the view's range outward (`integrations/shared/changes.ts:40-49`), and the reference clients compare ranges against half an interval (`reference/shared/src/chart/view.ts:43-53`), look one interval past the visible end (`reference/shared/src/session.ts:301`, `:408`) and floor `now` to the forming bar (`reference/shared/src/market.ts:42-47`). All of them assume a fixed step. A new entry, `@anishbenji/tscache/grid` (G11 a), exports the outward snap and the slot start and length in milliseconds for both kinds of interval, built from the same `grid.ts`:

```ts
// @anishbenji/tscache/grid (sketch)
export function snapRange(
  range: Range,
  interval: number | CalendarInterval,
  alignmentOffset?: number,
): Range;
export function slotStart(
  t: number,
  interval: number | CalendarInterval,
  alignmentOffset?: number,
): number;
export function nextSlotStart(
  t: number,
  interval: number | CalendarInterval,
  alignmentOffset?: number,
): number;
```

An application that never imports it pays nothing; the integrations import it and replace `snappedOut`, and the reference clients replace `interval / 2` with half the length of the slot at the range's edge, `+ market.interval` with `nextSlotStart`, and `formingBar` with `slotStart`.

### 5.9 Old workers and the handshake

A page with calendar support can meet a worker without it: a 0.1.0 SharedWorker at a fixed URL, until M5's generation key (F1 a) gives each library version its own worker. Such a worker rejects a calendar config with `ConfigError` ("interval must be a positive integer, got [object Object]"), loudly but confusingly, because the descriptor sits in `interval` (G4 a) and `resolveCacheConfig` rejects a non-number there (`engine/validate.ts:17-21`, `:118`). With G14 (a), a worker that supports calendars lists `'calendar-grid'` in `hello.features` (N79, from M7), and the client refuses a calendar config itself with a clear `ConfigError` when the worker does not list it. `PROTOCOL_VERSION` stays 1 (N37): no op is added, and the `cache` op's parameters widen.

## 6. Interactions

### 6.1 M3, memory bounds (`docs/design/m3-memory.md`, decided as decision 67)

- **What is counted** is segment bytes at capacity (E5 a), not slots, so a calendar cache is counted like any other. Its empty weekend slots cost capacity and are counted, as on a fixed daily grid.
- **The eviction unit** is the page (E6 a), `segmentSlotCap` slots. For a daily or longer calendar cache one page spans decades (§5.3), so eviction can drop such a cache only whole unless the application lowers `segmentSlotCap`. That is already true of a fixed daily cache; the M3 guide's figures ("17 pages per year at one minute") gain a sentence for calendar caches.
- **The tables of slot starts** are object overhead, outside the count (E5 a). Their engine-wide capacity bounds them whatever the queries and however many caches share a descriptor (G19, §5.7); they hold no points, so neither an eviction nor a `clear` touches them.
- Nothing in M3's eviction, pinning or persistence rules depends on the length of a slot.

### 6.2 M7, change notifications (`docs/design/m7-change-events.md`, decided as decision 65; built on step 114, `feat/114-m7-change-events`)

- **Event ranges** are milliseconds on the grid, produced by `toMs` in the engine, so they are correct on a calendar grid with no M7 change.
- **The integrations' outward snap** (`integrations/shared/changes.ts:40-49`, `snappedOut`) computes `floor` and `ceil` with fixed-step arithmetic from `{ interval, alignmentOffset }`. On a calendar grid it is wrong at every view edge, so a change at the edge of a view would be missed or a change outside it would wake the view. The calendar build step replaces it with `snapRange` from the grid entry (§5.8) and widens the integrations' `Grid` type to the config's `interval`.
- **N84** (reading after a change) is unaffected: it decides between a cache-only and a fetching read from the event's lists, not from slot lengths.
- **`hello.features`** (N79) carries the calendar capability (G14).

### 6.3 M5, deploy skew (`docs/design/m5-deploy-skew.md`, decided as decision 71)

- **A deploy that changes a cache's grid** (a fixed interval to a calendar one, or one descriptor to another) is a structural change. M5's generation key holds the library version and the fetcher URL, not cache configs (§4.2 of that proposal), so while a worker of the same generation runs, a new tab's `cache()` meets N20 and rejects with `ConfigError`, as it does today for any structural change. The application's remedies are today's: a new cache id for the new grid, or a fetcher URL that changes with the deploy (a new generation).
- **Persisted records under the old grid** are not applied by a cache of the new grid (structure mismatch, §4.10.2) and are rewritten at its next flush. A rolled-back deploy (a 0.1.0 engine) refuses the format 2 records as an unsupported format and rewrites its own.
- **A library upgrade that brings calendar support** starts a new worker under F1 (a), so an old worker never receives a calendar config from a new page once M5 is built. Before M5, G14 catches it (§5.9).
- **A change of zone rules** is not a deploy: the browser updates under a running application. §5.6 covers it.

### 6.4 Versioning and release

All additive at runtime: a widened `interval` type in the config, a new entry (`./grid`), new snapshot and record formats written only by calendar caches (with their JSON form), and a new feature name. Compile-time breaks for TypeScript code that reads the grid back, fixed-grid applications included, because the types widen whatever grid a cache uses: `CacheConfig.interval` (a config the application reads back, as `reference/shared/src/market.ts:44-46` destructures and divides it), `ResolvedCacheConfig.interval` (returned by `Engine.cache()` and `configOf()` and exported from `./engine`, `engine/engine.ts:117`, `:140`; `entries/engine.ts:39`) and `FetchRequest.interval` become `number | CalendarInterval`, so arithmetic on them must narrow first; and the four public types that carry a grid, `Snapshot`, `DenseSegmentPayload`, `EncodedSnapshot` and `EncodedSegmentPayload` (`entries/index.ts:31-34`), become unions of their format 1 and format 2 shapes, so code that reads their `interval` or `alignmentOffset` narrows on `format` first. The compiler does not catch every use: `String(request.interval)`, as the documented fetchers build their query (`site/snippets/fetcher.ts:50`, `site/snippets/fetcher-columns.ts:44`), compiles for both kinds and sends `interval=[object Object]` for a calendar cache; those snippets and the fetcher guide gain a calendar branch in the build step. Under 0.x semver that is a minor release (`packages/tscache/README.md`, "Stability"); the release notes name all seven types and the `String(interval)` pattern. G17 places it in its own minor release, after M3 and before M5, in the order of decision 62.

## 7. Migration

- **Fixed-grid users:** nothing changes at runtime. Their configs resolve as today, their records and snapshots keep `format: 1` byte for byte, their fetch requests carry the same numbers, and their hot paths keep their arithmetic (§5.7). At compile time, TypeScript code that does arithmetic on `interval` read from a `CacheConfig`, a `ResolvedCacheConfig` or a `FetchRequest`, or reads it from one of the four snapshot and payload types, narrows it first (§6.4); this repository's reference client is such code (`reference/shared/src/market.ts:44-46`, `session.ts:301`, `:408`).
- **Users of the daily-by-date recipe** who move to `{ unit: "day", zone, at }`: the timestamps change meaning, from dates at 00:00 UTC to session opens. Use a new cache id. The structural change already keeps the old records from loading into the new cache; a new id also keeps tabs of the old deploy, which still pass the old config, from rejecting each other under N20. The fetcher stops restamping bars.
- **Users of the monthly ordinal recipe** who move to `{ unit: "month" }`: timestamps change from ordinals to milliseconds. Use a new cache id; the fetcher and the chart drop their conversions.
- **Users of the weekly recipe in UTC** need not move: a fixed week with an offset is the same set of grid points. A calendar week is a different config (and numbers its slots from another week, §5.2), so moving means a new id for no gain. Weekly bars that start in a local zone move to `{ unit: "week", zone }`.
- **Records under an abandoned id** stay on disk until the application clears them with `clearAll`, as for any cache id an application stops using.
- **The docs** (G16 b): `site/concepts/grid.md` replaces the daily-DST and monthly recipes with the calendar grid, keeps the weekly recipe for UTC weeks and the jitter recipe, and keeps the ordinal technique as a note for calendars the built-in units do not cover; the snippet regions and their `docs:run` checks follow.

## 9. Contract tests for the later step

Engine-logic tests (Codex writes them first, from the approved text), at the level of `grid.ts`, the config, the put and read paths, snapshots and records. Zone tests use instants whose rules are settled (New York in 2026: daylight saving from 8 March to 1 November) and never the current date (`docs/testing.md`), and the property tests run against an injected offset function as well as the real `Intl`, so they do not depend on one runtime's ICU data.

1. **Fixed grids unchanged.** Every existing `grid.ts` contract test passes as it is; a fixed cache's payloads, snapshots and records are equal, field for field, to those of 0.1.0 (`format: 1`, `interval`, `alignmentOffset`).
2. **Calendar primitives, per unit.** For random slots and instants over the domain, in UTC and in the zones of tests 3, 4 and 6: `startOf` strictly increasing; `floorSlot(startOf(k)) === k`; `floorSlot(t) === k` exactly when `startOf(k) <= t < startOf(k + 1)`; leap years, month lengths, year ends and negative slots (before 1970) included. Slot 0 of each unit is the unit containing 1970-01-01 (§5.2), with `weekStart` 1 and 7. `floorSlot` never steps more than once above or twice below its candidate (a spy on the step count), with the extreme case `{ unit: "day", zone: "America/Los_Angeles", at: "18:00" }` at 00:30 UTC in winter, whose answer is two slots below the candidate (§5.2).
3. **A zone's daily session.** `{ unit: "day", zone: "America/New_York", at: "09:30" }`: 2026-03-06 starts at 14:30 UTC and 2026-03-09 at 13:30 UTC, both aligned; 14:30 UTC on 2026-03-09 is not.
4. **Transitions (G6, G18).** `at: "02:30"` on 2026-03-08 in New York starts at 03:30 local (07:30 UTC); `at: "01:30"` on 2026-11-01 starts at the earlier instant (05:30 UTC). A zone with a 30-minute shift (`Australia/Lord_Howe`), a zone with a 45-minute offset (`Asia/Kathmandu`) and a southern-hemisphere zone keep the properties of test 2. Skipped dates: in `Pacific/Apia`, the day slots of 2011-12-29, 2011-12-30 and 2011-12-31 have three distinct, increasing starts, the skipped 2011-12-30 starting as G18 decides (with G18 (b), one millisecond before 2011-12-31's); the same for `Pacific/Kwajalein` over 1993-08-20 to 1993-08-22. Coverage that ends at the skipped slot converts with `toMs` and snaps back to that slot, not the next; a fetch over it records the slot as a gap; and a put of a bar stamped at the next day's start lands in the next day's slot.
5. **Domain guard, in the primitives.** For safe integers outside the domain (the first instant after the year 9999, 8.64 × 10^15 + 1 and 9 × 10^15, beyond `Date`'s range), with a spy on the offset seam that must not be called: `floorSlot` and `startOf` throw `InvalidRangeError`; a put with such a timestamp rejects with `PutError` `'misaligned'`; `get` and `invalidate` over a range ending there and `setFinalizedUntil` at it reject with `InvalidRangeError`; `hydrate` of a snapshot whose `finalizedUntil` is there rejects with `TscacheError`; and a load whose stored cache record holds that `finalizedUntil` neither rejects nor applies the watermark, and the cache rewrites its records at the next flush (§4.10.5).
6. **Weeks and months in a zone.** A London week starts on Monday at local midnight in both seasons; a month in a zone starts at `at` on its first local day; quarters and years likewise.
7. **Snaps and watermark.** `snapOut`, `snapIn`, `slotAtOrAfter` and `toMs` on calendar grids keep §4.1's contracts: outward never narrower, inward never wider, `start === end` one slot when aligned and two otherwise, a watermark mid-month making the next month's start the volatile boundary.
8. **Domain (G12).** Ranges and watermarks beyond the years 1–9999 reject with `InvalidRangeError`. For each unit, in UTC and in a non-UTC zone (`America/New_York`) with the tables of G19: the first and last slot of the domain, `kMin` and `kMax` (year 9999 is slot 8,029 of a yearly grid), convert exactly both ways; `startOf(kMax + 3)` and `startOf(kMin − 3)` throw `InvalidRangeError`; and a spy on the offset seam sees no call for a slot outside `kMin − 2` to `kMax + 2`, although the edge blocks extend past it (§5.7).
9. **Config.** Each invalid descriptor of §5.5 rejects with `ConfigError` naming its field; a calendar `interval` with a non-zero `alignmentOffset` rejects; the resolved descriptor is frozen with its defaults; N20: equal descriptors join one cache, a differing unit, zone, `at` or `weekStart` rejects, two aliases of one zone reject (G7), and a number never equals a descriptor.
10. **Put.** A misaligned timestamp rejects the batch with `'misaligned'`, its index and value, and a message naming the calendar; aligned batches store their points at the right slots.
11. **Read.** Timestamps come back as slot starts; coverage and misses are milliseconds on the calendar; a read's ranges equal `toMs` of the snapped slots.
12. **Segments.** On a daily calendar, a weekend (2 empty slots) and a 4-day gap stay inside one segment and a 5-day gap splits it (N14); pages are `segmentSlotCap` calendar slots (N15).
13. **Snapshots (G9).** A calendar cache's snapshot has `format: 2` and its `grid`; it round-trips through `hydrate`; a fixed cache refuses it and a calendar cache refuses a fixed one; a differing descriptor is refused; a snapshot whose endpoint no longer aligns (an injected offset change) is refused. With an injected 24-hour rule change on a day grid (the Apia case of §5.6: an offset function that moves every instant after a date by one day), a one-point snapshot and a snapshot spanning the change, taken under the old rules and hydrated, and the same as page records loaded, behave as G8 decides. With G8 (c), recommended: both are refused, `hydrate` with `TscacheError` and a load by skipping the pages, which are rewritten at the next flush; slot 15,338, the date the current rules skip, holds no point. With G8 (a): both apply; the one-point bar reads in the next slot; the spanning record's old 2011-12-30 bar is in slot 15,338 and reads at 2011-12-30 09:59:59.999 UTC; and its range end is one slot later, as §5.6 documents.
14. **The JSON form (N38).** For a calendar cache in a zone and a fixed cache: `hydrate(decodeSnapshot(JSON.parse(JSON.stringify(encodeSnapshot(s)))))` into an empty cache of the same config gives the same read as the source, with `NaN` field values preserved; a decoded format 2 snapshot keeps `format: 2` and `grid` in its envelope and every payload, and with G8 (c) its slot indices; a fixed cache's encoded value is equal, field for field, to 0.1.0's; `decodeSnapshot` refuses an unknown format and a format 2 value whose `grid` is not an object with a string `unit`, with `TscacheError`.
15. **Records.** A calendar cache's records restore into an empty cache whose records are equal again (§4.10.2's convergence, for calendar caches); a record under another descriptor is not applied and is rewritten; an unknown format is refused.
16. **Fetch request.** It carries the descriptor in `interval` and `alignmentOffset` 0; its range is aligned to slot starts; a miss that abuts covered slots is extended one slot into them (a month on a monthly cache), and a flank with no coverage next to it is not extended.
17. **Tables of slot starts (G19).** A block's starts are computed once per resolved descriptor (a spy on the offset seam): two caches with equal descriptors share a table, two with different ones do not; after reads over more blocks than the capacity, no more tables are held than the capacity; a warm read computes nothing; `clear` and eviction leave the tables; a fixed grid and a UTC calendar never call the seam.

RPC, client and entry tests (written with the code, hybrid TDD):

18. **The grid entry.** `snapRange`, `slotStart` and `nextSlotStart` equal the engine's `snapOut` and `toMs` for random ranges, on fixed and calendar grids (a property test).
19. **Features (G14).** A worker lists `'calendar-grid'`; against a hello without it, `cache()` with a calendar config rejects with `ConfigError` before posting anything.
20. **Integrations.** M7's `reaction` with a calendar grid: a change at a view's calendar edge wakes it, a change one slot outside does not.

Browser (Playwright, one context, several pages):

21. Two tabs on a SharedWorker share a New York daily cache; a put in one is read in the other at the session-open instants of both seasons.
22. A snapshot rendered by the Node engine for a zone grid, carried in the page through `encodeSnapshot` and `decodeSnapshot` (test 14), hydrates in the browser, and a persisted calendar cache reloads with no fetch.
