## 1. The gap

A reader gets no event when the data it read changes ("tscache has no subscriptions", `site/guides/live-feeds.md:3`; the known-limit box at `site/guides/live-feeds.md:61-69`, written in step 82). A `put` from another tab, a fetch started by another tab's `get`, an `invalidate` and a moved watermark all change a cache silently. The only events about a cache's contents are `cacheCleared` and the opt-in `mergeWarning` (§2.7). The reference clients work around it: one tab, elected with a Web Lock, holds the live feed, puts each bar and tells the other tabs on a `BroadcastChannel`, and they re-read with `cacheOnly` (`reference/shared/src/live.ts:1-12`, `:109`).

The roadmap sketch (`docs/roadmap.md`, "Design sketch: subscriptions (dirty notifications)") proposes a notify-only, cache-scoped `cacheChanged { cacheId, range }`, emitted after any merge, invalidation or clear, coalesced per cache and macrotask, with consumers calling `get` again and the in-flight dedup keeping the fan-out to one fetch. This proposal keeps the notify-only, cache-scoped core and changes three things, each with its reason: the delivery is per mutating call, not per macrotask (D3); the payload separates written from withdrawn ranges (D2); and the consumer re-reads with `cacheOnly` after a write, because a fetching re-read on every event loops wherever a cache has a volatile region (§3.5).

## 3. The design (recommended options taken)

### 3.1 The event

```ts
interface ClientEvents {
  // …§2.7, plus, cache-scoped:
  /**
   * What a reader of this cache sees may have changed. Notify-only: it
   * carries no data (D1). Sent once per mutating call that changed the
   * cache (D3), to every client that subscribed (D4), the writer's included
   * (D5). Ranges are in ms on the grid, ascending, disjoint and not adjacent.
   */
  cacheChanged: {
    cacheId: string;
    /** Points or coverage were written here: a put, a fetch, a hydrate. */
    written: Range[];
    /** Coverage was withdrawn here; the points may still be present. */
    removed: Range[];
    /** Every point and all coverage went (clear, clearAll, version mismatch). */
    cleared: boolean;
    /** The call that made the change, when there is one (§3.3). */
    requestId?: RequestId;
  };
}
```

- **Notify-only (D1).** The event names ranges, never values. Each subscribed tab that shows an overlapping range reads it (§3.5). Data in the event would be copied once per tab per change (a buffer can be transferred to one port only), would be stale by the time a slow tab handled it, and would duplicate what a `cacheOnly` read returns from the one state.
- **Written and removed (D2).** The two lists answer the reader's one question, "must I fetch, or only re-read?": a written range is already in the cache, so a `cacheOnly` read shows it; a removed range has lost its coverage, so a reader that shows it needs a fetching read to fill it again, unless the same event also wrote (§3.5). A range may appear in both lists when one call did both (a put that sets the first watermark withdraws coverage from it onward and writes provisional points there).
- **Cleared.** `cleared: true` says everything the cache held before the call went; `removed` is then empty, and `written` lists what the same call wrote after the clear (a version-mismatch put), or nothing (`clear`, `clearAll`). `cacheCleared` stays as it is (N5): it carries the reason, and `cacheChanged` is the one event a view needs to stay current (D8).
- **What a range means.** Written ranges are the slots the call _touched_ (a put's authority, N13, or without one its batch's span, N3; a hydrate's applied parts), provisional slots included (D6), not the slots whose values differed: finding those costs a comparison of the overlap, which only `warnOnOverlapDiff` pays for. Removed ranges are the coverage actually withdrawn, never slots that were not covered (D12).

### 3.3 Delivery, ordering and hostings

- **Per call (D3).** The engine collects a cache's changes while one mutating call runs and reports them once when the call ends, returned or thrown. The RPC server turns that report into one `evt scope:'cache'` per subscribed connection (§3.2 of the architecture) and posts it at once: after any `cacheCleared` of the call, and before the call's `mergeWarning` events and its response. No timer is involved. The sketch's per-macrotask window would rarely merge anything in a worker, where each message and each fetch completion already runs in its own task, and it would put a timer between a change and its event; bursts are the consumer's to coalesce, per animation frame (§3.7).
- **Order for one call.** `cacheCleared` (a version mismatch, emitted inside the put; a manual clear, emitted after the state call) → `cacheChanged` → the request-scoped `mergeWarning` events → the response. A call through `durably` (N58) whose answer waits for the disk still sends its `cacheChanged` when memory changed: the event reports the cache readers see, not the disk.
- **Order across calls.** Messages on one port arrive in order (`docs/testing.md`, Waiting), and the event is posted after the change it reports was applied, so a read a tab sends after hearing the event sees that change or a later state. That is the guarantee readers rely on: **no lost wake-up**. Subscribe first, then read: the subscription is a message on the same port, so the worker handles it before the read, and every change after the read is reported. A change applied between the subscription and the read is both shown by the read and reported; the extra re-read is harmless.
- **The writer's own tab (D5).** It hears the event like every subscriber. A `put`'s event arrives before the `put` resolves; an orchestrated fetch's event arrives before the `get` that issued it resolves. `requestId` names the call: the client's own put, invalidate, clear, hydrate or setFinalizedUntil, or, for a fetch, the `get` that issued it (as `mergeWarning` does, N21; joined gets are not named). A tab can recognise its own requests by their `clientId` prefix (N23). `requestId` is absent only when no request caused the change; the server must carry the id with an op that `durably` or `clearAll` defers (`persist/hosted.ts:113-128`), so today every change has one.
- **SharedWorker.** One engine, so a change by any tab reaches every subscribed tab of the origin.
- **Dedicated worker and in-process.** One engine per tab, so the event reaches the tab whose cache changed, which is the only tab that reads that cache. Other tabs have caches of their own and hear nothing, as with `authInvalid` there (finding M6). A page that needs another tab's data in these hostings must still send it, as the reference clients do with a `BroadcastChannel` (`site/guides/live-feeds.md:71-81`).
- **Disposal and loss.** A connection's subscriptions go with it (dispose, `pagehide`, `bye`). After `workerLost` no event arrives (N32).

### 3.4 Interactions

- **`cacheOnly` reads** change nothing and send nothing. They are what a listener uses to re-read after a write (§3.5).
- **Orchestrated `get`s** send one event per fetch they apply, not one per `get`; a `get` that awaits a fetch another tab started sends none of its own.
- **`mergeWarning`** keeps its scope, payload and printing rule (decision #8). It follows the `cacheChanged` of the same call.
- **`cacheCleared`** is unchanged and still sent to every ready port (it predates subscriptions; D4 leaves it alone). A clear sends both.
- **Auth pending** writes nothing, so it sends nothing. After `updateAuth` the consumer re-reads, as today (§2.5); `updateAuth` itself changes no cache.
- **Persistence.** The persister's hook and its semantics (§4.10.4) are untouched: the reader report is separate, so a live tail still costs no disk write, and an event costs no disk work. `persistStopped` is unchanged.
- **`hydrate`** sends an event for what it applied (D7). This amends the "No events" bullet of §2.8 for `cacheChanged` only; `hydrate` still never clears and reports no `mergeWarning`.

### 3.5 Reading after an event

The sketch's rule, "a consumer whose shown range overlaps calls `get` again", loops whenever the cache has a volatile region. A fetching `get` over the forming bar always fetches it (the volatile region is never covered, §4.5), the fetch's put writes it, the write sends `cacheChanged`, and the listener's fetching `get` starts the next fetch. Two tabs showing the tail ping-pong the same way even if each ignores its own events. The rule this design documents, and every integration follows:

- **The event wrote something** (`written` is not empty), whatever else it says: read what the view shows with `get(range, { cacheOnly: true })`, if the written or removed ranges overlap it, or `cleared` is set.
- **The event wrote nothing**, and `cleared` is set or a `removed` range overlaps what the view shows: read the shown range with a fetching `get`.
- Otherwise: do nothing.

**Why this cannot loop.** Every event an orchestrated fetch causes has a non-empty `written`: a fetch's put always carries its requested range as its authority (`orchestrator/orchestrator.ts:677`), so it touches that range even when its response holds no point, when its version clears the cache first, or when its write fails part-way (§3.2). Under the rule, such an event leads only to `cacheOnly` reads, which fetch nothing. So no event caused by a fetch causes a fetch, and the fetches events cause are bounded by the application's own calls that write nothing: `invalidate`, `clear`, `clearAll`, `setFinalizedUntil`, and a `put` of an empty batch whose `meta` withdraws or clears. Each such call leads to at most one fetching read per subscribed view, and tabs reacting to the same call issue overlapping `get`s that the in-flight dedup (§4.9.1) fetches once.

The cost of the rule: when a fetch's response clears the cache (a new dataset version), other tabs re-read without fetching and show misses outside the range that fetch wrote, until their next ordinary read fills them. That is the price of the guarantee. Without it, a deployment whose backends alternate between two versions during a rolling deploy would clear the cache on every fetch, and every clear would make every tab fetch again: an unbounded loop driven only by events. Without events, N29 bounds each `get` to two rounds (`orchestrator/orchestrator.ts:438`), and the rule keeps the same bound.

### 3.6 Cost

- **Nobody subscribed: zero.** No message is posted, nothing is allocated, and the removed coverage is not computed. The engine's report is gated on a subscriber count kept by the server; with none, a change costs one counter check besides the persistence hook it already calls.
- **Someone subscribed, per mutating call that changed a subscribed cache:** collecting at most a few slot ranges the call already computes; for `invalidate` and a watermark withdrawal, one `CoverageIndex.covered` over the withdrawn slots before the subtraction (`coverage.ts:85`; a binary search plus the ranges it returns); converting the ranges to ms; and one `postMessage` of a small object per subscribed connection, structured-cloned, with no transfer list. No point data moves.
- **The re-read is the consumer's,** and is what it would do anyway: a `cacheOnly` read copies the visible slice (§3.3 of the architecture); a fetching read after a removal fetches only what is missing.
- **Bench gate.** The messages-per-read budget (`docs/benchmarking.md`) is unaffected while nobody subscribes; the contract-test step adds a budget for messages per put with one subscriber.

### 3.7 Public API

```ts
// client.on hears every cache's changes; cache.on only its own (N5 sugar).
client.on('cacheChanged', fn): () => void;
cache.on('cacheChanged', fn): () => void;   // CacheEvent gains 'cacheChanged'
client.off('cacheChanged', fn);

/** Which optional worker features this client's worker offers (D9, D10). */
readonly features: ReadonlySet<'cacheChanged'>;
```

- **Subscription.** The first `cacheChanged` listener for a cache on a client sends `subscribe { cacheId }`; a `client.on` listener sends `subscribe { all: true }`. The last listener's unsubscribe sends `unsubscribe` with the same parameters. Both are ordinary requests, fire-and-forget from `on`'s point of view: `on` stays synchronous and returns the unsubscribe. A listener removed while an event is in flight does not hear it (the emitter's rule, `engine/emitter.ts:26-30`).
- **Listener errors.** As for every wire event today: a throwing listener does not stop the others, and the first error is rethrown from the port's message handler, where the page reports it as uncaught (`engine/emitter.ts:31-43`, `client/client.ts:163-166`).
- **No library helper (D13).** The library ships the event and the read rule (§3.5); the integrations and reference clients own the view logic, as framework-native code (the reference clients decision of 2026-10-22: tested source to copy, not packages). Each integration's series subscribes on mount, keeps its shown range, and on an overlapping event schedules one read per animation frame (fetching if an overlapping event of that frame wrote nothing and removed or cleared, `cacheOnly` otherwise, per §3.5), then unsubscribes on unmount. The reference clients keep the Web Lock election for the feed and replace their `BroadcastChannel` redraw message with `cacheChanged` in the SharedWorker hosting; in the dedicated and in-process hostings the channel still carries the bars (§3.3).

### 3.8 Protocol and versioning

- **Additive, `PROTOCOL_VERSION` stays 1 (D9),** as for `hydrate` (N37): two new ops, `subscribe` and `unsubscribe`; one new cache-scoped event name; and an optional `hello.features: string[]` listing `'cacheChanged'`. N37 covers additive ops, not the handshake's shape: the hello is part of architecture §3.1, which is marked locked, so the `features` field needs the user's explicit approval (D9 a); option (d) of D9 carries the same list in an op instead and leaves §3.1 untouched.
- **New client, old worker** (a stale cached script, or a fixed worker URL during a deploy, finding M5): `hello` has no `features`, so `client.features` is empty. Subscribing sends nothing and never fires; in a development build the client prints one `console.warn` naming the missing feature (D10). An application that must follow changes checks `client.features.has('cacheChanged')` and polls otherwise.
- **Old client, new worker:** it never subscribes, and the worker sends `cacheChanged` only to subscribed connections, so it sees no new message; were one to arrive, its emitter would ignore the unknown name (`client/events.ts:12`).
- **The compatibility rule this proposes for M5 to adopt.** A change a peer from the other side of a deploy skew can ignore or detect is additive: it keeps `PROTOCOL_VERSION`, and a client learns of the worker's optional features from `hello.features` rather than by a failing request. `PROTOCOL_VERSION` changes only for a change an old peer would misread, and then, under N25, `createClient` rejects with `ProtocolMismatchError` until M5 designs recovery. M5 decides how a page learns that a newer worker exists; `features` gives it one more reason to want it.

### 3.9 Internal shape (for the implementer; not a public contract)

- `CacheStateHooks` gains a reader report beside `onChange`: written slot ranges (unclipped), withdrawn coverage (computed with `covered` before each subtraction, only while the owner says a subscriber exists), and cleared. The engine flushes a cache's collected report when its mutating call ends, after any `cacheCleared` of that call, through an internal observer like `observeCaches` (`engine/engine.ts:92-99`). `./engine`'s public surface does not change (D11), so N21's "the engine emits only cache-scoped `cacheCleared`" stays true of its public events.
- The RPC server keeps, per cache, the set of subscribed connections, plus the `all` set; tells the engine whether a cache has any; converts the report to ms; attaches the request id of the call or fetch that caused it; and posts to those connections only.
- The orchestrator's `#apply` reports the issuing `get`'s request id as it does for `mergeWarning`.

## 5. Contract tests for the later step

Engine-logic tests (Codex writes them first, from the approved text), at the level of `CacheState` and the engine's internal observer unless noted:

1. Each row of the §3.2 table: the event's `written`, `removed` and `cleared` for that cause, and no event where the table says none. For `put` with an empty batch and no range, each `meta` case separately: a differing `meta.version` clears (`cleared`, nothing written); a `meta.finalizedUntil` that sets the first watermark over covered slots reports them as `removed`; no `meta`, the cache's own version, a first version (N18) and a `meta.finalizedUntil` on a cache that already has a watermark (above, at or below it) send nothing.
2. A put wholly inside the volatile region reports its slots as `written` (D6), while the persistence hook still reports nothing for it (§4.10.4 unchanged).
3. `invalidate` over a range with no coverage sends nothing; over partly covered ranges, `removed` is exactly the covered part (D12).
4. `setFinalizedUntil` moved back reports the withdrawn coverage, finite and in ms; moved forward reports nothing.
5. A version-mismatch put: one event, `cleared: true` and the write's `written`, after `cacheCleared 'version-mismatch'`.
6. A put whose write fails part-way (an injected allocation failure, as `test/segment-atomic-alloc.test.ts` injects one) reports the touched slots as `written` and the withdrawn coverage as `removed`, with `cleared` when its version had cleared the cache, also when it withdrew no coverage; and it still rethrows the write's error. The same for a `hydrate` part whose write fails.
7. `hydrate`: `written` equals `applied` in ms; a skipped (`version-mismatch`) or idempotent second hydrate sends nothing.
8. `restore` sends nothing.
9. `clearAll`: one event per cache, each after that cache's `cacheCleared`.
10. With no subscriber, no report is built: the internal observer is not called, and `CoverageIndex.covered` is not called for an `invalidate` (a spy on the seam).
11. Property: for random sequences of puts, invalidations, watermark moves and clears, a reader that starts from a `cacheOnly` read and re-reads exactly the ranges each event names, and everything it holds after an event with `cleared` (fetching nothing), ends with the same `get` result as a fresh read, over any range.

RPC and client tests (written with the code, hybrid TDD):

12. Order for one put over the port: `cacheCleared` (when a version clears), `cacheChanged`, `mergeWarning`, then the response; for a manual `clear`, `cacheCleared` before `cacheChanged`.
13. Only subscribed connections receive the event; `subscribe { all: true }` receives every cache's; after `unsubscribe` nothing arrives (proved with a later barrier on the same port, never a sleep: `docs/testing.md`).
14. The last listener's unsubscribe sends `unsubscribe`; a second listener sends nothing new; `client.on` and `cache.on` listeners of the same cache combine correctly.
15. Subscribe, then read: a change applied by another connection after the subscription is either visible in the read or reported after it (no lost wake-up), for interleavings driven by gates.
16. An orchestrated fetch sends one event with the issuing `get`'s `requestId`, before that `get` resolves; a joined `get` adds none; a fetch dropped by the version fence, a failed fetch and an auth-pending miss send none.
17. A `cacheOnly` get and `updateAuth` send none.
18. An op deferred by `durably` (persistence chunk loading) still carries its `requestId`; a removal's event is sent before its durable answer.
19. Old worker: a `hello` without `features` gives an empty `client.features`, subscribing posts nothing, and a development build warns once. Old client: a worker never sends `cacheChanged` to an unsubscribed connection.
20. Dedicated and in-process hostings: the event reaches the tab's own client only.
21. A connection's subscriptions are dropped on dispose and on `bye`.

Browser (Playwright, one context, several pages):

22. Two tabs on a SharedWorker: a `put` in one tab reaches the other's `cache.on('cacheChanged')`, and its `cacheOnly` read shows the bar without a fetch (the backend's fetch count is unchanged).
23. The loop guard: two tabs show a cache with a volatile tail and follow §3.5. Each tab's first read fetches the tail, once or twice depending on whether they overlap in flight, so the test waits for both first reads to settle (a barrier on each page) and reads the backend's fetch count there; then the holder puts N feed bars, and the fetch count does not change.
24. Alternating versions (the rolling-deploy case of §3.5): a fetcher whose responses alternate between two dataset versions, two subscribed connections following §3.5, one `get`: the backend sees at most the two rounds N29 allows that `get`, and no fetch after it settles.

Bench: a messages-per-put budget with one subscriber, and the existing per-read message budget unchanged with none.
