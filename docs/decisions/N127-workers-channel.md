# N127: How workers of different generations find each other

Row N127 of the decision table in `docs/architecture.md` §8, whose introduction says how its rows were taken. Recorded in step 135 from the M5 design proposal (`docs/design/m5-deploy-skew.md`), which keeps the alternatives in full. Decisions are locked (`AGENTS.md`); the architecture section lists every decision with a one-line summary.

## Resolution

**A `BroadcastChannel`, `tscache-workers`, that every SharedWorker opens.** A worker subscribes before it answers any `init-ok`, so before any cache of it is opened or loaded. Once its first connection has completed `init`, and it so knows its fetcher, it posts one `announce`; a running worker answers another worker's `announce` with one `present`. The messages carry the worker's id, library version, script URL, resolved fetcher URL and start time, and a version of their own; a message with an unknown `t` or `v` is ignored. The channel is the origin's, the same partition as the database, so it reaches exactly the workers that write that database. It costs one message at a worker's start and nothing per operation, and it also carries `clearAll` (N135). Workers of 0.1.0 and 0.2.0 neither announce nor listen, and a realm without `BroadcastChannel` takes no part. Rejected: `navigator.locks.query()` at start (an old worker never learns of a newer one without polling, and renaming the lock amends N32); a record in the database (a layout change, read at every start); nothing beyond the name (two writers stay, unreported).
