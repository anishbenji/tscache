# N124: How slot starts in a zone are kept between conversions (G19)

Row N124 of the decision table in `docs/architecture.md` §8, whose introduction says how its rows were taken. Recorded in step 129 from the calendar grid design proposal (`docs/design/calendar-grid.md`, row G19), which keeps the alternatives in full. Decisions are locked (`AGENTS.md`); the architecture section lists every decision with a one-line summary.

## Resolution

**In tables of the starts of 512 consecutive slots, per resolved descriptor, in one least-recently-used order per engine with a fixed capacity of 256 tables (about 1 MB).** A table is computed whole only for a conversion that needs more than half of its slots at once (of the slots a table at an edge of the domain holds); every other start is computed alone, in at most six offset lookups, and not kept. A read converting the slots it returns and a put converting its timestamps count what they need of a block before they compute anything. So no conversion makes more than two resolutions for each start it needs, wherever its slots lie, and a load or a `hydrate`, which convert a record's anchors and nothing else, fill no table. The tables are a pure function of the descriptor and the runtime's zone rules: every cache of a descriptor shares them, and `clear`, `clearAll` and eviction have nothing to drop. They are object overhead, outside M3's count (N90). Rejected: a cache of starts per calendar cache (memory multiplies with the caches, and a long read misses on every point); one per descriptor without blocks (long reads still thrash it); the zone's transitions found by sampling (correct only if sampling never misses a pair of transitions closer than its step).
