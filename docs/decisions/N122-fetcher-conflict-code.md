# N122: How the refusal of a second fetcher module is identified

Row N122 of the decision table in `docs/architecture.md` §8, whose introduction says how its rows were taken. Recorded in step 135 from the M5 design proposal (`docs/design/m5-deploy-skew.md`), which keeps the alternatives in full. Decisions are locked (`AGENTS.md`); the architecture section lists every decision with a one-line summary.

## Resolution

**By a code: `ConfigError.code` is `'fetcher-conflict'`.** `ConfigError` gains an optional, read-only `code` of the exported type `ConfigErrorCode`, set on this refusal and unset on every other `ConfigError`. The error keeps its class, its `name` and its message, which still starts with `this worker already runs fetcher` and names both modules; an application recognises it by `error.code === 'fetcher-conflict'`, and the documentation no longer tells it to match the message. On the wire the error keeps the name `ConfigError` and travels with the existing `WireError.code`; the client's rebuilder restores a code it knows and leaves any other unset. A client from before the code rebuilds the same class with the same message. Rejected: a dedicated error class (it would reach an older client as a plain `TscacheError` with the name in front of the message, in exactly the stale-page case that still reaches the guard; and `errors.ts` already tells the variants of one class apart by a `code`, as `PutError` does). User decision 71 asked for a class or a code and left the choice open; the reconciled proposal (step 127) took the code and its value, and the brief of step 135 lists that identity with decision 71. 2026-11-16 (§2.6, §4.9, step 135)
