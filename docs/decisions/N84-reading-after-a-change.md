# N84: Reading after a change event

Row N84 of the decision table in `docs/architecture.md` §8, whose introduction says how its rows were taken. Recorded in step 114 from the M7 design proposal (`docs/design/m7-change-events.md`). Decisions are locked (`AGENTS.md`); the architecture section lists every decision with a one-line summary.

## Resolution

**When the event wrote something, re-read the shown range with `cacheOnly`; when it wrote nothing and cleared or removed overlapping coverage, re-read it with a fetching `get`; otherwise do nothing.** In full: when `written` is not empty, whatever else the event says, read what the view shows with `get(range, { cacheOnly: true })` if a written or removed range overlaps it or `cleared` is set; when `written` is empty and `cleared` is set or a `removed` range overlaps the view, read it with a fetching `get`. Why it cannot loop: every event an orchestrated fetch causes has a non-empty `written`, since a fetch's put carries its requested range as its authority, so it touches that range even when its response holds no point, when its version clears the cache first, or when its write fails part-way; such events lead only to `cacheOnly` reads, which fetch nothing. The fetches events cause are bounded by the application's own calls that write nothing (`invalidate`, `clear`, `clearAll`, `setFinalizedUntil`, and an empty put whose `meta` withdraws or clears), each leading to at most one fetching read per subscribed view. The sketch's rule (call `get` again on any overlap) loops wherever a cache has a volatile region: a fetching read always fetches the forming bar, the fetch's put writes it, and the write sends the next event. The accepted cost: after a fetch's response clears the cache for a new dataset version, other tabs re-read without fetching and show misses outside the fetched range until their next ordinary read. Without that, backends alternating between two versions during a rolling deploy would make every tab fetch on every clear, an unbounded loop driven only by events; with it, N29's bound of two rounds per `get` holds. User decision 65, the read rule of the proposal's §3.5 accepted as written, including its cost, 2026-11-16 (§2.7, step 114)

## Amendment, 2026-11-21

Decision concern DC1 of the M5 proposal (`docs/design/m5-deploy-skew.md` §8; step 135), built with its option (a) while the concern is with the user. Under N135 one `clearAll` is relayed across the SharedWorkers of an origin, and with k other workers running each worker clears about k + 1 times. Each of those clears sends `cacheChanged { cleared: true }` for every cache (N78), so one `clearAll` can lead to up to k + 1 fetching reads per subscribed view, where the resolution above counts at most one for each application call that writes nothing. For that count a `clearAll` relayed across k other workers is k + 1 calls. What a tab fetched between two of the clears is cleared and fetched again, and a `get` pending across two of them can come back `uncached` (N29's second round) until the read after the last event fills the view. Nothing loops: each worker relays a clear id once, so the count is fixed by k, and k is 0 unless workers of two generations or two keys run side by side. The rule itself is unchanged.
