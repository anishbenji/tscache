## Resolution

**Refetch once, then report**: a response dropped because the cache was cleared by a newer version mid-flight is re-requested once for what is still missing; a second drop returns the range as `'uncached'`. Bounded, and one version bump is invisible to the consumer. Rejected: report the miss immediately (one visible hiccup per bump). User-confirmed 2026-10-08. **Amended 2026-10-31 by user decision (#10, option B): the fence also re-plans once when the cache was cleared while a `get` waited, still at most two rounds.** A get's round that ends under another generation (clear count) than it was planned under triggers the one second round, for joined and own fetches alike, whether the clear dropped a response or wiped one already applied (§4.9.1 rule 5); a drop implies such a clear, so the original trigger is one case. The second round's result is final: what a clear during it drops or wipes comes back `'uncached'`. With in-flight subtraction (N31) a get awaits fetches other gets issued, which can land and then be wiped by another response's clear before the get reads (race A9, DC-1 in `docs/reviews/step-44.md`); as first written, that returned `'uncached'` with nothing dropped, against the rule's reason. Rejected: keeping the drop-only trigger (one visible hiccup per bump in that race). Cost: a manual `clear` during a get also causes one refetch of what it wiped
