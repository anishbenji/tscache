# N66: `clearAll` in the hostings that do not persist

Row N66 of the decision table in `docs/architecture.md` §8, whose introduction says how its rows were taken. The text below is that row, moved here unchanged in step 73. Decisions are locked (`AGENTS.md`); the architecture section lists every decision with a one-line summary.

## Resolution

**A dedicated-worker or in-process client's `clearAll` also empties the database, with one clear-only call** (§4.10.7): after clearing its engine (N22) it opens the database only if it exists (`ifExists`: a fresh browser gets none, except a browser without `IDBFactory.databases()`, such as Firefox before 126, where the opening creates an empty database; the clear is kept there, since such a browser has SharedWorker and can hold persisted records), runs `store.clearAll()` (every record, strict, N49), closes the connection, and answers after. The call is `clearDisk` in the lazy persistence chunk (§4.10.8), imported at the first `clearAll` and never at start; a realm without IndexedDB (Node) makes none. It is bounded as the persister's clear job (N61): retried after `debounceMs` until `timeoutMs` from the call, the import included; no disk call starts at or after that deadline, checked on the clock before the opening and each attempt (step 52, R1-1); the connection is closed by the time the call answers, a clear still pending then included (R1-2), which holds because the deadline has one owner at a time, an import timer until the chunk arrives and `clearDisk` after (pre-review PR-1); a database that fails to open fails it at once; it never rejects. **A failed clear changes nothing else.** D27 (N54's 2026-10-31 change) turns a SharedWorker's persistence off after a failed clear so that the same worker never serves back what the logout was to delete; a hosting that does not persist never reads the disk, so that already holds, there is no tracked cache to stop and no event to emit (N45), and its next `clearAll` tries again, as D27's does. As in the SharedWorker path, a SharedWorker started later can load what a failed clear left (§4.10.1). A SharedWorker alive at the call is another engine: the call does not reach its memory, and it writes back what it changes (as N52's overlap). User decision #11 (1), option (b), 2026-11-02, replacing D24 of step 38 (option (a), the disk left alone); the failure rule was designed at step 52 (`docs/reviews/step-52.md`) and confirmed by user decision #15, 2026-11-02 (option A: no event; documented). Rejected: a marker making a later SharedWorker distrust the store (a durable write to the storage that has just refused one, and a new record kind or layout version, N51); deleting the database instead (D12: the deletion waits for every other connection to close); a `persistStopped` per `persist: true` cache on failure (an event where N45 and D22 say none, for a persistence that never ran); joining concurrent calls as D28 does (nothing in this hosting writes between them, so a second clear costs one transaction and needs no rule).
