# N114: How snapshots, payloads, records and their JSON form name a calendar grid (G9)

Row N114 of the decision table in `docs/architecture.md` §8, whose introduction says how its rows were taken. Recorded in step 129 from the calendar grid design proposal (`docs/design/calendar-grid.md`, row G9), which keeps the alternatives in full. Decisions are locked (`AGENTS.md`); the architecture section lists every decision with a one-line summary.

## Resolution

**`format: 2`, for calendar caches only.** A calendar cache writes format 2 envelopes, payloads and cache records, in which one field, `grid`, the resolved calendar interval, replaces `interval` and `alignmentOffset`, with the slot indices of N113; the payload's rule becomes "slot i is the i-th slot after the slot of `start`". `encodeSnapshot` and `decodeSnapshot` carry both formats. A fixed cache keeps writing `format: 1` byte for byte, so nothing stored or rendered by a fixed cache changes; readers accept the format of their own grid and refuse the other, and a 0.2.0 engine or `decodeSnapshot` refuses format 2 as an unsupported format, never misreading it. This amends the locked payload invariant (§3.4), N34 (the envelope's fields), N38 (the JSON form) and N53 (the record format), with the user's explicit approval; the invariant itself, one structure for RPC, IndexedDB and server rendering, holds. The cost: readers handle two formats, and the public types `Snapshot`, `DenseSegmentPayload`, `EncodedSnapshot` and `EncodedSegmentPayload` become unions. Rejected: format 2 for every cache (a rolled-back fixed-grid deploy would refuse every record written since); format 1 with an extra `grid` field (an older reader would refuse only by accident, and the payload rule would be false under format 1).
