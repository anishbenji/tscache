# N126: What is in the generation key

Row N126 of the decision table in `docs/architecture.md` §8, whose introduction says how its rows were taken. Recorded in step 135 from the M5 design proposal (`docs/design/m5-deploy-skew.md`), which keeps the alternatives in full. Decisions are locked (`AGENTS.md`); the architecture section lists every decision with a one-line summary.

## Resolution

**`LIB_VERSION` and the fetcher module string: `tscache:<LIB_VERSION>:<module>`, with an empty module when the page passes no fetcher.** With the worker URL, which names the worker's build, the key names what the worker runs: the library, and the fetcher module, the only application code inside the worker (N44). The module is the string the page passes, as the worker compares it. The key sees the fetcher's URL, not its contents: a fetcher rebuilt behind an unchanged URL is not seen, and a new tab then joins the running worker, which keeps the module it loaded; a hashed, versioned or query-stamped fetcher URL avoids that. Application code, cache configs and the memory budget are not in the key: a changed cache structure is still refused within the worker (N20), and a changed budget waits for the worker to restart (N88). Rejected: `PROTOCOL_VERSION` in place of the library version (new tabs would run the old library's code); the fetcher only (a tscache upgrade at a fixed URL would be refused again); the library only (a fetcher-only deploy would still be refused with `ConfigError`, the commonest rejected shape). An application build id (`ClientOptions.build`) can be added later, by op, if asked for. User decision 71, row F2 option (a), 2026-11-16 (§2.7, §4.8, step 135)
