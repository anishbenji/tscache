# N106: How a SharedWorker's identity is chosen

Row N106 of the decision table in `docs/architecture.md` §8, whose introduction says how its rows were taken. Recorded in step 135 from the M5 design proposal (`docs/design/m5-deploy-skew.md`), which keeps the alternatives in full. Decisions are locked (`AGENTS.md`); the architecture section lists every decision with a one-line summary.

## Resolution

**A `name` from the page's generation key.** The shared hosting creates its worker with `new SharedWorker(url, { type: 'module', extendedLifetime: true, name })`. A SharedWorker is found by its URL and its name together, so pages whose keys differ never share a worker, at a fixed worker URL as at a hashed one: a deploy that changes what the worker runs starts a worker of its own instead of being refused by the running one with `ProtocolMismatchError` or `ConfigError`. Pages with the same URL and key share one worker, as before. Tabs of a release from before this decision pass no name, and the empty name equals no key, so a release with it never joins such a worker. The dedicated-worker and in-process hostings are per tab and take no name. This amends the approved text of §4.8 and §4.10.8 ("every tab of a deploy passes the same options"), which the user approved. Rejected: the URL alone, as before (new tabs are refused or run old code); an application-supplied `ClientOptions.workerName` (every application must get it right); a fixed URL and no name, so that every deploy shares one worker (new tabs run old code or are refused). User decision 71, row F1 option (a), 2026-11-16 (§2.7, §4.8, step 135)
