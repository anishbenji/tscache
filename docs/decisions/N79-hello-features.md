# N79: How the change events are versioned

Row N79 of the decision table in `docs/architecture.md` §8, whose introduction says how its rows were taken. Recorded in step 114 from the M7 design proposal (`docs/design/m7-change-events.md`). Decisions are locked (`AGENTS.md`); the architecture section lists every decision with a one-line summary.

## Resolution

**Additive: `PROTOCOL_VERSION` stays 1, and the hello gains an optional `features: string[]`, which lists `'cacheChanged'`.** The two ops and the event name are additive, as for `hydrate` (N37). A client learns the worker's optional features at connect time from `hello.features` and exposes them as `client.features`; an old worker sends no `features`, so the set is empty (N80). An old client never subscribes and ignores the extra hello field (it reads only `protocol`, `clientId` and `lock`), and a worker sends `cacheChanged` only to subscribed connections. The compatibility rule this sets for the deploy-skew design (finding M5): a change a peer from the other side of a skew can ignore or detect is additive and keeps `PROTOCOL_VERSION`; it changes only for a change an old peer would misread, and then `createClient` rejects with `ProtocolMismatchError` (N25). This amends the locked handshake of architecture §3.1 with one optional field. Rejected: no capability list (`on` is synchronous, so a subscription to an old worker would fail late, only as a rejected background request); bumping to 2 (every tab of an old deploy would reject `createClient`, harsher than the missing feature, as N37 found); a `features` op after `init-ok` (one more round trip on every connect, kept only if §3.1 were to stay as it was). User decision 65, row D9 option (a), including the amendment to the locked §3.1 handshake, 2026-11-16 (§3.1, step 114)
