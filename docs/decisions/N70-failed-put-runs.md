# N70: What a failed put may leave behind

Row N70 of the decision table in `docs/architecture.md` §8, whose introduction says how its rows were taken. Recorded in step 80. Decisions are locked (`AGENTS.md`); the architecture section lists every decision with a one-line summary.

## Resolution

**A put that fails part-way has applied an ascending prefix of its write runs, each run whole, and nothing of the rest.** `SegmentStore.put` works in steps, each of which either completes or changes nothing (§4.3): first, for a replace, the stored points inside its authority are removed; then the batch goes in one write run at a time, in ascending slot order. A write run (not the overlap warning's run of differing points, §4.3) is a maximal stretch of points that are consecutive in the batch, each on the same page as the one before it (N15) with at most K slots between them (N14); points already stored between two batch points are not counted, so a run is a function of the batch alone. It is not "the batch points that share a segment after the put", which stored points can join and a replace can split. The engine writes a put that carries `meta.finalizedUntil` as two `SegmentStore.put` calls (N19): first its points below `slotAtOrAfter(meta.finalizedUntil)`, with the authority clipped there, then the rest, merely upserted; a stretch that crosses that slot is therefore two runs, the lower one applied first. Each run is applied completely or not at all, because each run changes the stored segments in one atomic merge (§4.2); no run is ever half applied. After a failure the store is well formed as §4.3 states, and the engine withdraws any coverage it held for the put's range (§4.3, §4.5), so whatever prefix was applied is refetched before it is trusted. Why: §4.3 said a run "shares a segment" and did not give the order of the runs or say how a put's own watermark divides them, so the set of legal states after a failure could not be written down, and a test that injects failures (step 74) had no exact reference. A probe on step 74's branch injected 9,898 failures, each at a different point of the write after validation, and found the library always in this state; under "one run across the put's own watermark" 11 of those failures leave a run half applied, and under runs counted with the stored points between them 76 more do. The decision records what the library already does; no code changed. Rejected: runs in any order (admits states the library never produces, so a test cannot tell a defect from a legal outcome); a run counted with the stored points between its batch points (depends on the store, and the library does not write by it); one run across the put's own watermark (the two passes write it as two).
