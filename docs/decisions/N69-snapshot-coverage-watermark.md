# N69: A snapshot's coverage lies below its own watermark

Row N69 of the decision table in `docs/architecture.md` §8, whose introduction says how its rows were taken. The text below is that row, moved here unchanged in step 73. Decisions are locked (`AGENTS.md`); the architecture section lists every decision with a one-line summary.

## Resolution

**A snapshot whose `finalizedUntil` is set and whose `coverage` reaches a slot at or after `slotAtOrAfter(finalizedUntil)` is malformed:** snapshot validation rejects it, and `hydrate` throws `TscacheError` (`invalid snapshot: …`) before anything changes, the version and watermark included, as for every other malformation (N35). Its points at or after the watermark, outside its coverage, stay legal: they are its provisional tail, which `hydrate` does not apply. Why: `hydrate` clipped only by the receiving cache's volatile region, so such a snapshot made slots it itself called provisional authoritative (November 2026 review, finding F1, confirmed by a probe). Taking a snapshot never produces one, since a cache never covers a volatile slot (§4.5), so only a hand-built or corrupted snapshot reaches the check; snapshots cross a trust boundary (a server's HTML), which makes the cheap refusal worth having. Page snapshots in IndexedDB carry no watermark (§4.10.2), so the rule binds no stored record and no load changes. Rejected: clipping each part to the snapshot's own watermark, as N19 does for `put` (repairs a value the library never produces, against §2.8's rule that a malformed snapshot is refused, never repaired); leaving it and documenting a snapshot as trusted input.
