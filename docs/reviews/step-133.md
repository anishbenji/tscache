## (d) A tab joining while auth is invalid — CONFIRMED, fixed

**The report.** A newly opened tab with an object fetcher context may restore an invalid auth state to valid, so that fetches resume after `authInvalid` without anyone calling `updateAuth`.

**History on this branch.** My first triage read §4.9 Loading ("anything else is treated as new material") as settling the case, and committed tests pinning the restore (`0cf9fbc`). The director's independent fact-check at `6716b4d` confirmed the report as a defect, with the evidence below. I re-checked it, and the re-check showed that first reading was wrong: Loading's conservatism was chosen for the auth generation while auth is valid, and the other auth sentences decide the invalid case. The test that pinned the restore was replaced by the failing tests in `9f2501d`, before anything reached `main`.

**Where it breaks** (at `6716b4d`, confirmed). `RpcServer.#init` (`packages/tscache/src/rpc/server.ts:289-322`) calls `Orchestrator.load` for every joining tab. After the first load, `load` sends a joining context that is not `Object.is` the one in place to `updateAuth` (`orchestrator/orchestrator.ts:336-341` at `6716b4d`). `updateAuth` replaces the shared context, increments the auth generation and calls `restore()` (`:394-396`), which sets auth valid unconditionally (`orchestrator/auth.ts:62-64`). Through a SharedWorker every object context arrives as a structured clone, never the identical value, so a tab that joins carrying the credential already refused (for example an expired token read from storage at startup) restores auth. The next get fetches with the refused credential, and every tab hears `authInvalid` a second time. An identical primitive context (the same string) and a tab without a context do not trigger it. The test on `main` covered only a joining tab with fresh credentials while auth was valid.

**What the specification says a joining tab's context may do while auth is invalid.**

- §4.9.1 rule 4: "Auth stays invalid until the next `updateAuth`, which also switches the generation, so no get joins them again."
- §2.5: "while auth is invalid no fetch is issued … `updateAuth(context)` from any tab delivers new material and restores auth"; `site/guides/fetcher.md`: "no fetch runs until `updateAuth`"; the header of `orchestrator/auth.ts`: "nothing is fetched until updateAuth flips it back".
- §4.9 Loading (N30): "A tab that joins with a context that is not the identical value takes the `updateAuth` path once the module is loaded (structured-cloneable values have no cheap, cycle-safe equality, so anything else is treated as new material)."
- Its origin, `docs/reviews/step-11.md`: R4-2 routed a joining tab whose context differs through `updateAuth` so that the generation advances, and "one with the same context (the normal case) changes nothing"; R5-2 then narrowed "the same" to the identical value because the structural comparison of the time treated two `Map`s as equal and recursed forever on cycles.
- N8, N33 and N42 (the auth decision files) concern the failure signal, what `authInvalid` carries and the refresh snippet; none speaks of joining tabs.

**Reading.** Treating an unsure value as new material is conservative for the generation, which is all R4-2 and R5-2 were about, while auth is valid. While auth is invalid it is the unsafe direction: the context in place is the refused one, so a clone of it is not new material, and restoring auth with it breaks "auth stays invalid until the next `updateAuth`" as well as step 11's "the same context changes nothing". That case is provably wrong. Whether a _different_ context brought by a joining tab may restore auth is not settled: Loading says such a join takes "the `updateAuth` path", which restores, while rule 4 and the site can be read as meaning the client's `updateAuth` call. Following the director's instruction for that outcome, this step fixes only the equal-context case and puts the different-context question in DC-1.

**The fix** (`9f2501d`). While auth is invalid, `Orchestrator.load` gives a joining context that is not identical to the one in place to `sameMaterial` (`orchestrator/auth.ts`). If the two are certainly the same material, the join changes nothing. `sameMaterial` compares primitives by `Object.is` and plain arrays and plain objects member by member, in any key order. It answers false, so the join is new material as before, for anything it cannot be sure of: a `Map`, a `Date`, a typed array, a class instance, a cycle, nesting deeper than 32 levels, `0` against `-0`, a hole against `undefined`. It never answers true for two values that clone differently, so it cannot hide new material. It terminates on cycles, the failure R5-2 rejected, and it does not treat `Map`s as equal. While auth is valid nothing changed: a joining clone still takes the `updateAuth` path and advances the generation, as R4-2 requires (the test on `main`, "broadcasts authInvalid once …", still expects the joining tab's `{ token: "old" }` to reach the hook). The refused context is the one in place, because only a failure under the current generation flips the state, and the context and the generation switch together (§4.9 Auth), so comparing with `#context` compares with the refused credential.

**Tests** (`packages/tscache/test/orchestrator.test.ts`, "a tab joining while auth is invalid (step 133)", at the RPC-server level the existing auth tests use: one `RpcServer`, clients over `MessageChannel`, so contexts are structured-cloned as through a SharedWorker port):

1. A tab without a context leaves auth invalid; nothing is fetched and no second `authInvalid` is sent. Passed before the fix.
2. A tab with the identical primitive context leaves auth invalid. Passed before the fix.
3. A tab with other material restores auth through the hook, and the next fetches carry its context. Passed before the fix; it pins today's answer to DC-1.
4. **A clone of the refused context leaves auth invalid**: both tabs' gets answer `'auth-pending'`, one fetch in total, the hook is not called, no second `authInvalid`; a later `updateAuth` with new material still restores. Failed before the fix (`expected [ … ] to have a length of 1 but got 2`: the join restored auth and the get fetched again), passes after.
5. **A nested clone with keys in another order leaves auth invalid.** Failed before the fix the same way, passes after.
6. A context that differs deep inside is new material and restores auth. Passed before and after.
7. A cyclic context is new material and the join completes. Passed before and after.
8. `sameMaterial` unit tests: true only for plain values equal member by member; false for an extra `undefined` key, a different length, a hole against `undefined`, an array against an object, `0` against `-0`, `Map`, `Date`, `Uint8Array`, nesting past the limit and cycles.

**Is it a security problem?** No. The auth state decides only whether the worker asks the backend; the backend checks every credential, and cached data is served whatever the auth state. The defect cost one fetch with a refused credential per tab opened with it, and one more `authInvalid` to every tab (whose handler may refresh or prompt again). It could not loop: the refusal flips the state back at once.

**Hostings.** Only the SharedWorker hosting has joining tabs; a dedicated worker and the in-process hosting serve one client each (N27).

**Documentation.** §4.9 Loading now states that the conservatism is safe only while auth is valid, what a joining tab's context does while auth is invalid, how sameness is decided, the defect and its fix, and that the different-context case is DC-1. This replaces the sentence I added in `5c02c85`, which described the defect as specified.

## (e) `HostingError` is not exported

**Facts.**

- `HostingError extends TscacheError` is defined in `packages/tscache/src/client/hosting.ts:14-16` and keeps its name through minification (`nameFor`, step 69; `test/errors.test.ts:65`). The `.` entry (`src/entries/index.ts`) exports `TscacheError`, `ConfigError`, `InvalidRangeError`, `UnknownCacheError`, `PutError`, `ProtocolMismatchError`, `AuthInvalidError` and `isAuthInvalidError`, not `HostingError`.
- It is thrown at `hosting.ts:70` and `:77` (worker `error` before the handshake, no `hello` in time), `:114`, `:122` and `:155` (no `SharedWorker`, its constructor throwing, the lifetime lock granted before `init-ok`), `:186` and `:192` (no `Worker`, its constructor throwing) and `:230` (the in-process chunk failing to load).
- `connect` (`client/client.ts:167-182`) steps down on a `HostingError` and rethrows it when there is no next hosting (`:177`). The chain runs from the pin to the end of `shared → dedicated → in-process` (`client.ts:31`, `:105`), so the last hosting is always in-process. `createClient` therefore rejects with a `HostingError` only when the in-process chunk cannot be loaded (`hosting.ts:226-233`, message `the in-process hosting could not be loaded: …`), whatever the pin.
- What the documentation promises: architecture §4.8 Chain, "when the last one fails, `createClient` rejects with that error"; `site/how-it-works/startup.md:33-34`, "`createClient` rejects with its `HostingError`"; the 0.2.0 changelog, "the `HostingError` that ends the fallback chain, keep[s] their documented `name` through minification". Architecture §2.6 and `site/usage/errors.md` do not list it.
- How a user tells it apart today: `error instanceof TscacheError` is true, and `error.name === "HostingError"`. There is no class to test with `instanceof` and no exported type.

The options are in DC-2. Nothing changed: the exports are a Never path.

## (f) Listener errors

**Facts.**

- The emitter (`engine/emitter.ts:26-43`) runs every listener of an emit and rethrows the first error after all ran.
- Wire events (`authInvalid`, `cacheCleared`, `persistStopped`, `cacheChanged`, `mergeWarning`) are emitted from `ClientEmitter.receive` (`client/events.ts:12-49`) inside the client's port listener (`client/client.ts:205-208`, `rpc/port-client.ts` `#receive`, registered with `addEventListener('message')` in `rpc/protocol.ts:126-140`). The rethrown error propagates out of the port's `message` listener, and the host reports it as an uncaught exception. Checked under Node 26: a throw in a `MessagePort` `message` listener reaches `process.on('uncaughtException')`, and the next message is still delivered.
- `modeFallback` (`client/client.ts:210-228`): every step is emitted in one `setTimeout` callback; the first error across all the steps goes to `report()` (`client.ts:38-43`), which calls `globalThis.reportError` when there is one and throws otherwise. Errors of later steps are not reported. Pinned by `test/client.test.ts` ("delivers every fallback step even when a listener throws").
- `workerLost` (`client/client.ts:324-335`): one emit inside `#lose`, its first error through `report()`. Pinned by `test/client.test.ts` ("a throwing workerLost listener is reported; the others still hear it").
- In a browser both routes reach the window's `error` event: an exception in an event listener is reported the same way `reportError` reports it.

**The specification.** §4.8 Events: "`evt` messages re-emit as `ClientEvents` … and the client-made `modeFallback` and `workerLost`. Listeners run on the page; a throwing listener does not break the port (the emitter's rule)." §4.6 gives the emitter's rule. Both are explicit, and the code meets them on every path. Neither says by which route an error that nobody can catch is surfaced, nor whether `modeFallback` reports one error per step. That part is silent, so this step documents the behaviour as built (§2.7, "A listener that throws") and changes no code. The M7 proposal (`docs/design/m7-change-events.md` §3.7, "Listener errors") already described the wire route for `cacheChanged`.

## Decision concerns

For the user. Nothing here was acted on.

### DC-1 — may a joining tab's _different_ context restore auth while it is invalid?

The equal-context case is fixed (above). Still open: through a SharedWorker, a tab that joins while auth is invalid, with a context that is not the same material as the refused one, takes the `updateAuth` path and restores auth (§4.9 Loading). The spec does not settle whether only the client's `updateAuth` call may do that (§4.9.1 rule 4, §2.5). The case also covers values `sameMaterial` cannot compare (a `Map` holding the same stale token), which count as different.

| Option                                                                                                                                                               | Pros                                                                                                                                                                 | Cons                                                                                                                                                                                                                                                                     |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| (a) Keep: a different context on join restores auth, as built and as §4.9 Loading now states                                                                         | A tab opened after a fresh sign-in works at once; it joined after the `authInvalid` broadcast, so it never heard it and needs no special handling; no further change | A context that differs but is still stale (another expired token, a `Map` holding the refused one) costs one refused fetch and one more `authInvalid` to every tab, per tab opened with it                                                                               |
| (b) A join never restores auth: its material reaches the hook and switches the context and generation, but the state stays invalid until a client calls `updateAuth` | Only `updateAuth` restores, which reads §4.9.1 rule 4 and the site literally; no fetch with material nobody vouched for                                              | A tab with fresh credentials gets `'auth-pending'` for every uncached range until some tab calls `updateAuth`, and it never heard `authInvalid`, so the application must treat an `'auth-pending'` miss as the signal to call it; a rule change, new tests and site text |
| (c) As (b), but the worker also sends `authInvalid` to the joining port when it joins while auth is invalid                                                          | The new tab learns at once that it must call `updateAuth`, through the event it already handles                                                                      | Adds a delivery rule to the locked design b ("once per flip" would become "once per flip, and once to each tab that joins while invalid"), with its own tests and docs                                                                                                   |

**Recommendation: (a).** With the equal case fixed, what is left is a credential that is genuinely different; trying it once is what the joining-tab rule was written to do, the cost is bounded (one refused fetch per tab opened, no loop), and the backend checks every credential. (b) and (c) are the safer readings of rule 4 if the user prefers that only an explicit `updateAuth` restores auth; (c) is then the one that keeps a newly opened tab from waiting silently.

### DC-2 — `HostingError` is not exported, yet `createClient` can reject with it

| Option                                                                                    | Pros                                                                                                                                                                                                                           | Cons                                                                                                                                                                                                                                 |
| ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| (A) Export the class from `.` (and list it in §2.6 and `site/usage/errors.md`)            | `instanceof` works like every other error `createClient` can reject with; the type is importable; matches the changelog's "documented name"; no size cost (the client already bundles the class); additive, so a minor release | Commits to the class as public API; its meaning ("a hosting could not be established") must stay stable                                                                                                                              |
| (B) Keep it unexported; document `error.name === 'HostingError'` in §2.6 and the site     | No new export; the name is already kept through minification                                                                                                                                                                   | The one error a user cannot test with `instanceof`; a string comparison instead of a type                                                                                                                                            |
| (C) Fold it into an existing exported error: rethrow the last failure as a `TscacheError` | No new public name                                                                                                                                                                                                             | A behaviour change: `error.name` changes from `HostingError` to `TscacheError`, contradicting the changelog and `site/how-it-works/startup.md`; the user loses the only way to tell "no hosting started" from a fetcher-load failure |

**Recommendation: (A).** It closes the gap with one export line and two table rows, and it is additive.

### DC-3 — how a listener error that nobody can catch is surfaced

The emitter's rule (all listeners run, the first error is rethrown) holds everywhere. The route differs: wire events let the error escape the port's `message` listener; `modeFallback` and `workerLost` call `reportError`, or throw where it is missing; and `modeFallback` reports only the first error across all its steps.

| Option                                                                                      | Pros                                                                                                       | Cons                                                                                         |
| ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| (a) Keep, as documented in §2.7                                                             | No change; in a browser both routes reach the window's `error` event; in Node both are uncaught exceptions | Two routes to describe                                                                       |
| (b) Route wire-event listener errors through `report()` too                                 | One route in the code and the docs                                                                         | A code change with no effect a user can observe in a browser; one more wrapper on a hot path |
| (c) As (a), but `modeFallback` reports every step's first error, not only the first overall | No listener error is dropped                                                                               | Up to two reports for one chain; a small behaviour change                                    |

**Recommendation: (a).** The routes are equivalent where the library runs, and the behaviour is now written down.
