# Step 149 — a pre-push check for the commit address

Branch: `chore/149-push-email-check` · Reviewer: the director's review ladder · Rounds: 1 · Status: round 1 fixes in, awaiting the next round · Verdict after triage: —

## Scope

GitHub declines pushes of commits that carry the user's private address ("push declined due to email privacy restrictions", 2026-11-25). The repository's `user.email` is `anishbenji@users.noreply.github.com` (user decision #141 A). This step adds a pre-push check that refuses a push when an outgoing commit carries any other author or committer address, so the mistake is caught locally before GitHub rejects the push. `lefthook.yml` is a protected path; the edit is user-approved (2026-11-25).

## What changed

- `scripts/check-push-email.ts` reads git's pre-push stdin (`<local ref> <local sha> <remote ref> <remote sha>` per line) and lists the outgoing commits of each pushed ref: `<local sha> --not <remote sha> --remotes` for an existing remote ref (so commits merged in from another remote-tracking ref, such as `origin/main`, are not checked again); `<local sha> --not --remotes` for a new remote ref (remote sha all zeros), and also when the remote sha is not in this clone, where the range form would fail; nothing for a deleted ref (local sha all zeros). Each commit's `%ae` and `%ce` must pass `isAllowed`: an address ending in `@users.noreply.github.com`, or exactly `noreply@github.com`, compared case-insensitively (user decision #147 A; until then the one allowed address was the repository's own). On a mismatch it prints each offending commit (12-character hash, `author` or `committer`, the address) and how to re-author the unpushed commits, then exits 1. `Co-Authored-By:` trailers are message text and are not read. A non-empty line that is not four fields is an error (exit 1); with no non-empty line it prints "no pre-push input; nothing checked" and exits 0. A manual `bunx lefthook run pre-push --force` needs `</dev/null` (`docs/workflow.md`); see "Pre-review and security lane, before round 1".
- `lefthook.yml`: the `pre-push` hook is now `piped: true` with two jobs: `push-email` (a `script` job, `script: ../check-push-email.ts` under `source_dir: scripts/`, `runner: bun`, `use_stdin: true`) first, then a `checks` group with `parallel: true` holding the previous jobs unchanged. Lefthook's documentation says only one job receives stdin and that a job that reads it needs `use_stdin`; running the check first and alone gives it stdin, and the piped top level skips the heavy checks when it fails.
- `scripts/check-push-email.test.ts` builds a throwaway repository per test in a temporary directory, with remote-tracking refs written by `git update-ref` (no remote, no network), and calls the check with the stdin git would give. It strips the surrounding `GIT_*` variables (a hook's `GIT_DIR` would otherwise point the commands at this repository) and the global and system config. Covered: an existing branch with good commits passes; another author address, another committer address, and both are refused with the right field; commits before the remote sha are not checked; a new branch checks only commits on no remote-tracking ref, and every commit when there is none; an unknown remote sha falls back to the new-branch range; a deleted ref checks nothing; a `Co-Authored-By:` trailer with another address passes; several refs at once and empty stdin; the message format; and the script run as `bun scripts/check-push-email.ts` exits 1 naming the commit and 0 when clean. The describe block has a 30-second limit: each test spawns about ten git processes, which took up to 5.8 s for one test under a load average of 13; no assertion reads time.
- `AGENTS.md` (Toolchain hard rules, hook staging): the pre-push list names the check first, states its rule, and notes that it is the one hook `bun run ci` does not repeat (user decision #147 A).

Not changed: `scripts/ci.sh`, `.github/` and the root `package.json` scripts (outside this step's scope). CI does not run the check (user decision #147 A, below).

## User decision #147 A (2026-11-25)

The pre-review's decision concerns went to the user as #147: which identities the check allows (bot and GitHub commits, other people's addresses) and whether CI should run it. The user chose A.

- **Allowed identities.** Any author or committer address ending in `@users.noreply.github.com` (the user's, `49699333+dependabot[bot]@users.noreply.github.com`, a contributor's own), plus exactly `noreply@github.com` (GitHub's merge commits); everything else is refused. `isAllowed` lower-cases the address and tests the suffix with its leading `@`, so the match is exact and case-insensitive. The hard-coded `ALLOWED_EMAIL` export is gone; the script no longer names the user's address. The refusal message states the rule, and the fix advice tells the committer to set their own noreply address (`<you>@users.noreply.github.com`, from github.com/settings/emails) instead of the user's.
- **P1 #1 (PR-1).** Confirmed on e2dca7ac, unchanged here: an existing remote ref is checked as `<local sha> --not <remote sha> --remotes` and a new or unknown one as `<local sha> --not --remotes`, so every commit reachable from any remote-tracking ref is excluded. The fix is by reachability, not by an identity allow-list.
- **CI.** Not run in CI. `AGENTS.md` says the push-email check is the one hook `bun run ci` does not repeat, because it needs git's pre-push input (the refs being pushed), and GitHub refuses such pushes anyway.

Tests (written first; 19 failed before the change, all 37 pass after it): `isAllowed` allows the user's noreply address, Dependabot's, `noreply@github.com` and upper- and mixed-case variants of both forms, and refuses `x@users.noreply.github.com.evil`, a bare `users.noreply.github.com`, `x@xusers.noreply.github.com`, `x@users-noreply.github.com`, `noreply@github.com.evil`, `x@noreply.github.com`, an empty address, a Gmail address and `someone@example.com`; through `check`, a commit authored by Dependabot and committed by `noreply@github.com`, and one with upper-case addresses, pass. The format test asserted the user's address in the message; it now asserts the rule's two forms and the `<you>@users.noreply.github.com` advice instead, because the message no longer names one address. The other tests use the user's address as before, from a constant in the test file.

Not covered by the rule's wording and left as decided: an address that is only the suffix with an empty local part (`@users.noreply.github.com`) passes. It carries no private address, which is what the check guards.
