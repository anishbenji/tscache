# Step 149 — a pre-push check for the commit address

Branch: `chore/149-push-email-check` · Reviewer: the director's review ladder · Rounds: 3 · Status: settled after round 3 and the Neon lane (three P3: one confirmed and fixed with two tests, one rejected, one nit recorded); no round 4 · main merged 2026-11-27 (#176)

## Scope

GitHub declines pushes of commits that carry the user's private address ("push declined due to email privacy restrictions", 2026-11-25). The repository's `user.email` is `anishbenji@users.noreply.github.com` (user decision #141 A). This step adds a pre-push check that refuses a push when an outgoing commit carries any other author or committer address, so the mistake is caught locally before GitHub rejects the push. `lefthook.yml` is a protected path; the edit is user-approved (2026-11-25).

## Threat model

Grade every finding against this (part of user decision #147 A, stated 2026-11-26). The hook guards against the maintainer or an agent publishing a private address by accident. It is not a defence against someone hiding one on purpose: anyone with push access can skip hooks (the agents' guard blocks that for agents; the maintainer can). An escape that needs a deliberately built commit (an odd encoding, control bytes, a hand-made header) is a limit, graded P3 at most, not a blocker. A path that plain git can take by accident, such as a merge of one's own signed tag, is in scope.

## What changed

This section states the check as the branch has it after every round; the round tables below keep the history.

- `scripts/check-push-email.ts` reads git's pre-push stdin, one `<local ref> <local sha> <remote ref> <remote sha>` line per pushed ref. Each non-empty line is split at its last three spaces: the local ref before them may hold any character and is not used, and a line whose last three fields are not a full sha, a non-empty remote ref and a full sha is an error (exit 1). With no non-empty line it prints "no pre-push input; nothing checked" and exits 0. For each line it lists the outgoing commits with `git log -z --encoding=UTF-8 --no-show-signature --format=%H`: `<local sha> --not <remote sha> --remotes` for an existing remote ref (so commits merged in from another remote-tracking ref, such as `origin/main`, are not checked again); `<local sha> --not --remotes` for a new remote ref, and also when the remote sha is not in this clone; nothing for a deleted ref. The output is NUL-framed and each name must be a full sha.
- One `git cat-file --batch` reads the raw objects of those commits, each checked against its name and size. A header (everything before the first empty line) is decoded as strict UTF-8, not by its `encoding` field, so the bytes checked are the bytes pushed; a header that does not decode is refused as a `header` offence without its bytes being printed. Every `author` and `committer` line of a commit is checked, and every `tagger` line of each signed tag a `mergetag` field embeds (a `merged tagger` offence). When the pushed local sha is an annotated tag, every `tagger` line of that tag, and of each tag it names in turn, is checked; a tag object with no tagger line is refused. A lightweight tag is checked as the commits it names. Every git call runs with `--no-replace-objects`, so a replace ref cannot mask the objects pushed.
- `isAllowed` is the rule (user decisions #147 A and #154 A): a well-formed address ending in `@users.noreply.github.com` (a local part with no `@`, whitespace, `<`, `>` or control character), or exactly `noreply@github.com`, compared case-insensitively. `Co-Authored-By:` trailers are message text and are not read.
- On a refusal it prints the rule, one row per offence (12-character sha, field, address, and the tag's name for a tagger row, with control characters written as `\u{..}`), then fixed advice that names no ref and points to `docs/workflow.md`, "One-time setup", item 4; it exits 1. Any git failure or output of an unexpected shape is an error (exit 1). The script header states the threat model and three recorded limits: a commit already on another remote's tracking ref is not checked when pushed to a different remote (#147 A), a local source expression holding a newline is refused as malformed (R3-1), and an annotated tag on a blob reads the blob whole (R3-3).
- `lefthook.yml`: the `pre-push` hook is `piped: true` with two jobs: `push-email` (a `script` job, `script: ../check-push-email.ts` under `source_dir: scripts/`, `runner: bun`, `use_stdin: true`) first, then a `checks` group with `parallel: true` holding the previous jobs unchanged. Only one job receives stdin, and a `script` job is never skipped for want of push files (PR-2); the piped top level skips the heavy checks when the address check fails.
- `scripts/check-push-email.test.ts` builds a throwaway repository per test in a temporary directory, with remote-tracking refs written by `git update-ref` (no remote, no network), and calls `check` with the stdin git would give, or runs the script under Bun. `repoEnv()` drops the inherited `GIT_*` and `LEFTHOOK*` variables and the global and system config. 69 tests cover the ranges, the row parsing, the raw-header reads (encodings, `mergetag`, tags and nested tags, replace refs, signatures, a history past the 1 MiB output buffer), the refusal text and escaping, the `isAllowed` table and the `lefthook.yml` job form. The `check-push-email` describe block has a 30-second limit: each test spawns about ten git processes, which took up to 5.8 s for one test under a load average of 13; no assertion reads time.
- `docs/workflow.md`: item 3 names `ssh-keygen` with `-Y` signing support as a prerequisite of the tests; item 4 gives `bunx lefthook run pre-push --force </dev/null`, says what the check reads, and how to repair a refusal (the common branch case, a `header` row, a merged tag). `AGENTS.md` (Toolchain hard rules, hook staging) names the check first with its rule and threat model, and notes that it is the one hook `bun run ci` does not repeat (user decision #147 A). `knip.jsonc` lists `ssh-keygen` under `ignoreBinaries` (R1-3).

Not changed: `scripts/ci.sh`, `.github/` and the root `package.json` scripts (outside this step's scope). CI does not run the check (user decision #147 A, below).

Parked for the user (decision #170): the describe block's 30-second timeout predates step 154's rule in `docs/testing.md`, which limits such timeouts to three named tests and needs the user's OK for any other.

## User decision #147 A (2026-11-25)

The pre-review's decision concerns went to the user as #147: which identities the check allows (bot and GitHub commits, other people's addresses) and whether CI should run it. The user chose A.

- **Allowed identities.** Any author or committer address ending in `@users.noreply.github.com` (the user's, `49699333+dependabot[bot]@users.noreply.github.com`, a contributor's own), plus exactly `noreply@github.com` (GitHub's merge commits); everything else is refused. `isAllowed` lower-cases the address and tests the suffix with its leading `@`, so the match is exact and case-insensitive. The hard-coded `ALLOWED_EMAIL` export is gone; the script no longer names the user's address. The refusal message states the rule, and the fix advice tells the committer to set their own noreply address (`<you>@users.noreply.github.com`, from github.com/settings/emails) instead of the user's.
- **P1 #1 (PR-1).** Confirmed on e2dca7ac, unchanged here: an existing remote ref is checked as `<local sha> --not <remote sha> --remotes` and a new or unknown one as `<local sha> --not --remotes`, so every commit reachable from any remote-tracking ref is excluded. The fix is by reachability, not by an identity allow-list.
- **CI.** Not run in CI. `AGENTS.md` says the push-email check is the one hook `bun run ci` does not repeat, because it needs git's pre-push input (the refs being pushed), and GitHub refuses such pushes anyway.

Tests (written first; 19 failed before the change, all 37 pass after it): `isAllowed` allows the user's noreply address, Dependabot's, `noreply@github.com` and upper- and mixed-case variants of both forms, and refuses `x@users.noreply.github.com.evil`, a bare `users.noreply.github.com`, `x@xusers.noreply.github.com`, `x@users-noreply.github.com`, `noreply@github.com.evil`, `x@noreply.github.com`, an empty address, a Gmail address and `someone@example.com`; through `check`, a commit authored by Dependabot and committed by `noreply@github.com`, and one with upper-case addresses, pass. The format test asserted the user's address in the message; it now asserts the rule's two forms and the `<you>@users.noreply.github.com` advice instead, because the message no longer names one address. The other tests use the user's address as before, from a constant in the test file.

Not covered by the rule's wording and left as decided: an address that is only the suffix with an empty local part (`@users.noreply.github.com`) passes. It carries no private address, which is what the check guards.
