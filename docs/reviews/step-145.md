# Step 145 — a Playwright check that the built docs site draws every Mermaid diagram

Branch: `chore/145-mermaid-render-check` · Reviewer: the director's review ladder · Rounds: 0 · Status: pre-review and security lane triaged, before round 1 · Verdict after triage: pending

## Scope

User decision 139 C (2026-11-25): step 141's syntax check (`site/scripts/check-mermaid.ts`, in `docs:check`) is not a render, so a diagram that parses but fails to draw, or draws an error box, passes it. This step adds a check over the built site, in a real browser, that fails on any Mermaid error box. No dependency is added: Playwright and its Chromium are already installed for `e2e/`.

`playwright.config.ts` is a protected path. This is the user-approved tooling change of decision 139 C, and the pull request is for the user's merge. `scripts/ci.sh` and the root `package.json` are unchanged: `bun run ci` already builds the site (`bun run docs:build`) before it runs `bunx playwright test`, which runs every project.

## What changed

- **`e2e/docs/mermaid.spec.ts`**, in a new Playwright project, `docs` (Desktop Chrome, like the others). It opens every page of the built site that holds a `mermaid` fence, in the light and the dark colour scheme (the site draws its diagrams with Mermaid's dark theme while it is dark), and waits, on a condition and never a timer, until every diagram element holds an SVG and no render is under way, or Mermaid has drawn an error mark, or the page has logged an error. It then fails, naming the page and the scheme, when the page logged a console error or threw; when Mermaid's error marks (`.error-icon`, `.error-text`, from its error diagram and its error renderer) were added to the page at any point while it loaded, which an init script's `MutationObserver` counts, so an error box that a later render replaces still fails; when an error mark or Mermaid's error diagram is still shown; when a render left its temporary `dmermaid-*` element behind; when the page has a different number of diagram elements than its Markdown has fences; or when a diagram element holds no SVG. A further test fails when the built site has no page with a diagram, so the check cannot pass vacuously.
- **`e2e/docs/mermaid.spec.ts`** also fails when the dark run's page lacks VitePress's `dark` class on `html`, or the light run's has it.
- **`e2e/docs/pages.ts`** lists the pages: every HTML file of the built site (`site/.vitepress/dist`) except `404.html`, so the list follows the site's config (`srcExclude`, the generated `api/` pages) without repeating it. A page is listed when its built HTML has an element with the diagram class or its Markdown has a `mermaid` fence; the fences, counted in the Markdown the page was built from by `diagramReader` from `check-mermaid.ts` (includes expanded), are the number of diagrams it must draw, so a diagram element with no fence fails the count (the spec's wait ends as soon as a page has more diagram elements than fences). It throws when the site is not built, and when a built page has no Markdown page behind it (a rewrite or a dynamic route, which the site has neither of), rather than miss that page's diagrams. Today it finds 8 pages with 12 diagrams, the same as `docs:check`.
- **`playwright.config.ts`**: the `docs` project (`testMatch: docs/**/*.spec.ts`; the `chromium` project now ignores `docs/**`) and its server on port 5300 plus the checkout's offset, under the site's base (`/tscache/`). Both are defined when `E2E_EXAMPLES` names `docs`, or when it is unset and the site is built (`site/.vitepress/dist/index.html` exists), so a run of other specs in a checkout that never built the site still runs. `bun run ci` builds the site before Playwright, so it always runs the project.
- **`scripts/docs-server.ts`** (new) serves `site/.vitepress/dist` under `/tscache/` with `Bun.serve` on `127.0.0.1`, as `scripts/e2e-server.ts` does, answering as the published site does (`cleanUrls`: `guide/demo` is `guide/demo.html`, `how-it-works/` is its `index.html`; other paths get the site's 404 page with status 404; a path resolving outside the build is refused). It exits at once, naming the cause, when the site is not built.
- **`site/.vitepress/config.ts`** sets the plugin's `mermaidPlugin.class` to `mermaid-diagram` (`site/.vitepress/mermaid-class.ts`, shared with the spec and `pages.ts`), and `diagrams.css` styles that class. The new check found that every diagram page drew Mermaid's error box for a moment on every load: Mermaid registers a `load` handler that, while `startOnLoad` is on, renders every `.mermaid` element from its contents. `vitepress-plugin-mermaid` turns `startOnLoad` off only in its first `mermaid.initialize`, which comes after awaits in its `onMounted` hook and so after the window's `load` event. Mermaid's pass therefore rendered each plugin element while it was still empty and drew "Syntax error in text / No diagram type detected" into it, until the plugin's own render replaced it. In a probe of all 8 pages, three loads per page in each scheme, all 48 loads showed the box and none kept it. Mermaid's pass selects `.mermaid`, so under the plugin's other class it finds no element; the plugin still draws every diagram. (The first fix, `mermaid.startOnLoad = false` in the theme, worked but imported Mermaid into the theme chunk; see the triage below. The theme is unchanged from `main` again.)
- **`site/README.md`** and **`site/contributing.md`**: beside the syntax check's "not a render" limit, a line on the render check (in `site/README.md` also its server and when a run includes it); the theme bullet in `site/README.md` explains the diagram class.

## Decision concerns

- The spec fails on any console error or uncaught error on a diagram page, not only one that Mermaid logs: a console error the page logs for another reason fails it too, naming the page and quoting the error. Today the 8 pages log none.
- The class change is a fix to the site, not only a check: without it the new check fails on every diagram page. It is one plugin option and changes no diagram's look; the diagrams' wrapper class is now `mermaid-diagram` rather than `mermaid`, which only `diagrams.css` styled.
- The weekly `Flake hunt` workflow builds only the package, so its `--all` run no longer starts the docs project and does not hunt `e2e/docs/mermaid.spec.ts`; a manual hunt naming that file on GitHub finds no tests. Adding `bun run docs:build` to `.github/workflows/flake-hunt.yml` would include it; that is a workflow change, outside this step.
