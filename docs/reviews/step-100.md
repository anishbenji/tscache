**Where the design lives.** A proposal file beside M7's and M3's, for the reason they give: the architecture document records approved contracts, and this design has sixteen open rows, four of which would amend approved text (§4.8 and §4.10.8 by F1; §4.10.7 with N52 by F5; §4.10.7 with N54 and N66 by F11; the checklist's §12 item). The contract-test step moves the approved text into architecture §2.1, §2.7, §3.2, §4.8 and §4.10.6–§4.10.8.

**What it covers,** as the brief asked: how a deploy reaches open tabs today (the worker URL and the absent name, SharedWorker identity, `hello` and its unread `lib`, the protocol and fetcher checks, what an old and a new tab each see, per way of serving the worker); the failure shapes, rejected at connect (protocol mismatch, fetcher conflict) and silent (two workers side by side, with what each writes to IndexedDB when structure, dataset version, layout or record format differ; one worker serving two deploys); the options the brief listed (a build id in the hello or an op, a name stable across deploys, a broadcast to old tabs, a database lock or owner record, a read-only mode for the older engine, an event, an error or a flag); the interaction with M7 (the compatibility rule, D9's `features`, `cacheChanged`) and M3 (E3, E18, E20, two budgets during a skew); the cost when nothing is skewed (zero per operation and per port message); the public API change and its version; and the contract-test list, split into Codex-first persistence tests and tests written with the code.

**The design, in short.** The SharedWorker is named by a generation key, `tscache:<LIB_VERSION>:<fetcher module>`, so pages that would run different code in the worker never share one, at a fixed or a hashed URL; this removes the protocol mismatch and the fetcher conflict against a running worker. Workers announce themselves on a `BroadcastChannel`; a worker that hears a higher-ranked worker of another generation (higher library version, then later start) stops persisting for its life without a cleanup deletion (the path a failed `clearAll` already takes), keeps `clearAll`'s disk clear, and tells its tabs with a `superseded` event and a `client.superseded` property. A `clearAll` from any hosting reaches every SharedWorker over the same channel. The handshake is unchanged and `PROTOCOL_VERSION` stays 1.

**A finding the spec makes about current text.** The guides and architecture §4.10.7 say a hashed worker URL gives each deploy a SharedWorker of its own (`site/guides/workers.md:146-147`, `docs/architecture.md:1707`). A probe (two Vite builds of `examples/react-lwcharts`, the second with one constant added to the fetcher; both edits reverted) showed the worker file name unchanged in both the `es` and the `iife` worker formats while the fetcher's changed. A deploy that changes only the fetcher therefore keeps the worker URL, and every new tab is refused with `ConfigError` ("this worker already runs fetcher …") until the old tabs close. The known limit in the guides does not say so. The proposal's §7 records the correction, which is documentation alone; a separate step makes it (director, after the pre-review), so this step does not.

**Claims checked against the code.** Every statement about the current engine in the proposal's §2 and §3 cites a file and line on `main` at `2fc4308`; each was read at those lines with `cat -n`, `sed -n` or `grep -n`, not inferred. The statement that a SharedWorker is found by URL and name together is from the HTML Standard; the proposal's Playwright tests 18, 19 and 22 and the name test 13 pin the behaviour the design relies on.

## Decisions for the user

All sixteen rows, F1–F16, are open and listed with options, pros, cons and a recommendation in §5 of the proposal. None is decided here; the proposal's §4 assumes each recommendation. Rows whose recommended option needs the user's explicit approval because it amends a locked decision or approved text:

- **F5 (a)** (a superseded worker stops persisting for its life) narrows the two-writer overlap that N52 accepts and changes what N52 and architecture §4.10.7 describe. It adds no lock, no disk read and no persistence in another hosting, so N52's single-writer design stands.
- **F11 (b)** (the relay, recommended since round 3): `clearAll` reaches every SharedWorker over the channel, not awaited; each worker that runs a clear for another's clear id posts once when its own disk clear settles. It extends what N54 and N66 say `clearAll` reaches, and §4.10.7's last paragraph. Option (a), two posts without the relay, needs the same approval and leaves the logout gap of R2-1 after a successful clear; choosing it means accepting that gap.
- **F1 (a)** (the SharedWorker is named) amends the approved sentence of §4.8 and §4.10.8 that every tab of a deploy passes the same options; no locked decision.
- The review checklist's §12 item on two engines writing one database (a protected path the user owns) changes with F5 (a) and F11 (b).

Options that would change a locked decision and are not recommended: F2 (d) with a build id in `init` and M7's D9 (a) used for it (§3.1, the handshake); F3 (b) (renames N32's lock); F6 (b) (N59: a stopped cache would restart); F13 (b) (N25 and N30).

**F16** (pre-review, P1-2; new): pages of one deploy that pass different keys (a page without a fetcher beside pages with one, or two strings for one module) are one generation, with no event and a development warning, rather than ranked. It costs sharing between those pages, which today share one worker; F2 (e), the library alone in the key, would keep that sharing and keep the fetcher-only `ConfigError`.
