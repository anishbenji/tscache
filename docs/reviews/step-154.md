## Incident

On 2026-11-26 a pre-push Vitest run (`~/code/tscache-reports/run/push-145.log`, outside the repo) failed `packages/tscache/test/persist-hosted-event-orders.test.ts` > every order of up to 3 events > starting with clearAll: `Test timed out in 5000ms` at 5,006 ms, the file at 12,027 ms, with the 5-minute load average at about 7.5 (two directors' heavy jobs share the machine). The same day a step 135 child's full `bun run ci` failed the same test twice at 5,007 ms (load 8 to 9.5) and passed with `--testTimeout=60000`; run alone under load, the hosted tests took 1 to 4.4 s. Run alone on a quieter machine the file passed 3 of 3. A Codex child saw the same timeout earlier that day.

The two files are the order explorers added in step 132 (`persist-orders.ts` holds the harness; `persister-event-orders.test.ts` and `persist-hosted-event-orders.test.ts` each call `orderTests`). At bound 3 their `it.each` passed no timeout, so Vitest's 5 s default applied; at bound 5 (`TSCACHE_EVENT_ORDERS=5`) it already passed 900 s. The harness comment's "7,442 orders in about a second" dated from before step 132's round 5, which added a third loader outcome to the hosted harness.

## Change

`packages/tscache/test/persist-orders.ts`, `orderTests`: the `it.each` timeout at bound 3 is now 30,000 ms (it was Vitest's 5 s default); bound 5 keeps 900,000 ms. 30 s is twice the measured worst case, at a load far above the incidents' 7.5 to 9.5, and still catches a hang. The comment beside it gives the numbers. The timeout sits in the shared harness, the one place both files declare their tests, so each file gets it without its own setting; `vitest.config.ts` is unchanged. No test's assertions, bound or orders changed. The `BOUND` comment now gives today's counts and time.

`packages/tscache/test/cache-reader-ranges.test.ts` > includeRange > "reads O(log n) list entries per range when collecting ascending ranges" now passes a 30,000 ms timeout (it was Vitest's 5 s default), with a comment giving the numbers. Its durations: 2,267 ms in the full run alone at load 6 and 6,355 to 8,963 ms in the side-by-side pairs above (load 34 and 68); in the 2026-11-25 pre-push logs, where it failed the 5 s timeout, Vitest reported 6.4, 9.4 and 10.8 s (`push-146d.log`) and 16.4 s (`push-146.log`). 30 s is about twice that worst case, the same margin as the order tests. The test is synchronous, so Vitest reports a timeout when it returns rather than interrupting it. Its inputs (n = 4,096) and assertions are unchanged.

`vitest.config.ts` says a test that crosses 5 s again is "a slowdown to investigate, not to raise". These tests are not a slowdown of existing code: their cost is the work they check. The order tests enumerate every order up to the bound, their cost grows with the orders the harness explores (step 132 round 5 added hosted orders), and under load the hosted clearAll test, the largest, scales furthest. The reader-ranges test runs its control, the quadratic scan (n(n-1)/2, about 8.4 million list reads through a counting `Proxy`), to show the gap that the O(log n) claim rests on. The global 5 s stays.

After pre-review 1, neither test's own timeout undercuts the mutation run's: `vitest.mutation.config.ts` sets `TSCACHE_TEST_TIMEOUT` to its 60 s through Vitest's `test.env`, and both call sites pass `Math.max(30_000, TSCACHE_TEST_TIMEOUT)`, so they get 30 s under the root configuration (the variable is unset) and 60 s under Stryker. `vitest.config.ts` and `docs/testing.md` now name the exception and its criterion (Pre-review 1, finding 2).

After Codex round 1, the values no longer come from the shell: `vitest.config.ts` sets `TSCACHE_TEST_TIMEOUT` to 30000 in `test.env`, `vitest.mutation.config.ts` replaces it with its 60000, and both call sites pass the value as is. Vitest assigns `test.env` over the inherited environment in each worker, so a value exported in the caller's shell does not reach the tests (Round 1, R1-1).
