# Step 141 — a syntax check for the docs site's mermaid diagrams

Branch: `chore/141-mermaid-parse-check` · Reviewer: the director's review ladder · Rounds: 5 · Status: not settled: escalated under the convergence check after round 5 · Verdict after triage: the user decides at merge

## Scope

User decision 129 D (2026-11-21): `bun run ci` should parse every mermaid diagram on the docs site and fail on a syntax error. It would have caught the tabs diagram that rendered as "Syntax error in text" on the live site (a `;` in a sequence message ends the statement; fixed in step 140, #170). No dependency is added: the check uses the Mermaid and VitePress already installed for `site/`.

What the check promises (narrowed in round 3; the route guard goes by name since round 4; absolutes replaced by stated limits in round 5): it catches syntax errors in published Mermaid diagrams, outside a browser. Its limits:

- It is a syntax check, not a render. A diagram that parses but draws wrongly, or throws in Mermaid's renderer, passes.
- It reads the regular Markdown files Git lists under `site/` plus the generated `site/api/` pages; on this site today that is every published page, and also the files the site excludes. It does not load the site's config (`srcExclude`, rewrites, extra pages) or run route loaders. Rather than follow either, the no-argument run, which `docs:check` uses, fails naming the path on any name Git lists under `site/` that is a symbolic link (round 5), and on any Markdown file under `site/` with a bracket-named segment (VitePress's dynamic-route form), whatever it holds and excluded files included. The site has neither; a link or a dynamic route needs the check extended first.
- It reads `mermaid` fences only, not a hand-written `<Mermaid graph=…>` tag or raw HTML. A `mermaid` fence that a `::: code-group` shows as code is still parsed: a deliberately broken example goes in an `mmd` fence or a titled fence.
- It parses with Mermaid's default options, not the site's (`securityLevel: "strict"`, `sequence`), and does not apply the 50,000-character limit above which `mermaid.render` draws an error box instead of the diagram.
- A `details` statement, whose parsing reads an element of the page, is parsed without it.

This is narrower than the wording of decision 129 D ("every mermaid block"); the user decides it at merge (see Decision concerns).

## What changed

- `site/scripts/check-mermaid.ts` finds every `mermaid` fence with VitePress's Markdown renderer, as `check-doc-anchors.ts` reads pages, and runs `mermaid.parse` on each, then the parse step `mermaid.render` runs (`mermaidAPI.getDiagramFromText`; R3-1). Each page is first rendered as the site renders it, with its real path, so its `<!-- @include -->` directives are expanded (inside fences too), and the expanded text is searched (R1-1). A failure prints `file:line` (the fence's line) and Mermaid's own message, whose line numbers count within the diagram, then exits 1; a fence that an include brought in is named by its line on the expanded page. On success it prints `mermaid: N diagrams in M pages parse`. With no arguments it checks every page Git lists under `site/` (`git ls-files -z`, so a non-ASCII name is read as it is) and the generated `site/api/` pages, which Git ignores but the site publishes (R1-3); given files or directories, it checks those pages.
- Outside a browser, Mermaid's DOMPurify has no window and leaves out `sanitize`, `addHook` and `removeHook`. The script fills them in as no-ops on the instance Mermaid imports, then loads Mermaid. The sequence parser also reads `window?.CSS` to check a `box` colour, and a `details` statement reads `document.getElementById`, so each parse runs with a stand-in `window` and `document`, removed when the parse settles (R1-2, R3-2). Both packages are resolved with Node's resolver and their package `exports`, so no Mermaid version or path is hard-coded and the same code runs under Bun (`docs:check`) and under Node (Vitest). Step 140's throwaway script used `Bun.resolveSync`, which Node lacks.
- `docs:check` in the root `package.json` runs the script after `check-doc-anchors.ts`; nothing else in `scripts` changed.
- `site/scripts/check-mermaid.test.ts` covers: a sequence message holding a `;` fails naming the file and line, also when an include puts the `;` there; a valid flowchart and a valid sequence diagram pass, and so do sequence diagrams with a coloured and an uncoloured `box`, leaving no `window` behind; a page with no mermaid passes; fence lines after frontmatter, inside containers and lists, and around includes; other languages and a mermaid fence shown as code are ignored; the message formats; a listed page with a non-ASCII name and a broken diagram in the generated `site/api/` are checked; the git and no-page failures; a comment or a directive before a diagram's frontmatter fails, and frontmatter first passes (R3-1); a sequence diagram with `details` passes, leaving no `document` behind, and with a `;` message still fails (R3-2), also beside a caller's `window`, which is kept (R5-3); any bracket-named page fails, whatever it holds, naming the file and saying to rename it (R3-3, reversed in round 4); a bracket-named page with `<!--@content-->` and a CR-only one with frontmatter hiding a broken fence both fail (R4-1, R4-2); a symbolic link under `site/` fails naming it (R5-1); a fence holding only `error`, alone or after a comment, fails (R5-2). The real-parse cases run in process under Node and once as a `bun site/scripts/check-mermaid.ts <dir>` subprocess, since the DOMPurify patch depends on the runtime's module loader. Fixtures are written to temporary directories whose names hold a space and parentheses, and printed paths are compared as literal text (R5-5).
- `site/README.md` and `site/contributing.md` describe the new check and which pages it reads (the tracked pages and the generated `site/api/` pages, after includes); the `site/` row of `docs/INDEX.md` is re-measured (283.7 KB to 284.7 KB; still 42 tracked pages).
