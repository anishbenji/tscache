# Step 141 — a syntax check for the docs site's mermaid diagrams

Branch: `chore/141-mermaid-parse-check` · Reviewer: the director's review ladder · Rounds: 3 · Status: in review · Verdict after triage: pending

## Scope

User decision 129 D (2026-11-21): `bun run ci` should parse every mermaid diagram on the docs site and fail on a syntax error. It would have caught the tabs diagram that rendered as "Syntax error in text" on the live site (a `;` in a sequence message ends the statement; fixed in step 140, #170). No dependency is added: the check uses the Mermaid and VitePress already installed for `site/`.

What the check promises (narrowed in round 3): it catches syntax errors in published Mermaid diagrams, outside a browser. It has three limits:

- It is a syntax check, not a render. A diagram that parses but draws wrongly, or throws in Mermaid's renderer, passes.
- It reads the Markdown files Git lists under `site/` plus the generated `site/api/` pages, which is every published page and also the files the site excludes. It does not load the site's config (`srcExclude`, rewrites, extra pages) or run route loaders, and fails on a dynamic route that injects content.
- A `details` statement, whose parsing reads an element of the page, is parsed without it.

This is narrower than the wording of decision 129 D ("every mermaid block"); the user decides it at merge (see Decision concerns).

## What changed

- `site/scripts/check-mermaid.ts` finds every `mermaid` fence with VitePress's Markdown renderer, as `check-doc-anchors.ts` reads pages, and runs `mermaid.parse` on each, then the parse step `mermaid.render` runs (`mermaidAPI.getDiagramFromText`; R3-1). Each page is first rendered as the site renders it, with its real path, so its `<!-- @include -->` directives are expanded (inside fences too), and the expanded text is searched (R1-1). A failure prints `file:line` (the fence's line) and Mermaid's own message, whose line numbers count within the diagram, then exits 1; a fence that an include brought in is named by its line on the expanded page. On success it prints `mermaid: N diagrams in M pages parse`. With no arguments it checks every page Git lists under `site/` (`git ls-files -z`, so a non-ASCII name is read as it is) and the generated `site/api/` pages, which Git ignores but the site publishes (R1-3); given files or directories, it checks those pages.
- Outside a browser, Mermaid's DOMPurify has no window and leaves out `sanitize`, `addHook` and `removeHook`. The script fills them in as no-ops on the instance Mermaid imports, then loads Mermaid. The sequence parser also reads `window?.CSS` to check a `box` colour, and a `details` statement reads `document.getElementById`, so each parse runs with a stand-in `window` and `document`, removed when the parse settles (R1-2, R3-2). Both packages are resolved with Node's resolver and their package `exports`, so no Mermaid version or path is hard-coded and the same code runs under Bun (`docs:check`) and under Node (Vitest). Step 140's throwaway script used `Bun.resolveSync`, which Node lacks.
- `docs:check` in the root `package.json` runs the script after `check-doc-anchors.ts`; nothing else in `scripts` changed.
- `site/scripts/check-mermaid.test.ts` covers: a sequence message holding a `;` fails naming the file and line, also when an include puts the `;` there; a valid flowchart and a valid sequence diagram pass, and so do sequence diagrams with a coloured and an uncoloured `box`, leaving no `window` behind; a page with no mermaid passes; fence lines after frontmatter, inside containers and lists, and around includes; other languages and a mermaid fence shown as code are ignored; the message formats; a listed page with a non-ASCII name and a broken diagram in the generated `site/api/` are checked; the git and no-page failures; a comment or a directive before a diagram's frontmatter fails, and frontmatter first passes (R3-1); a sequence diagram with `details` passes, leaving no `document` behind, and with a `;` message still fails (R3-2); a bracket-named page without `<!-- @content -->` passes (R3-3). The real-parse cases run in process under Node and once as a `bun site/scripts/check-mermaid.ts <dir>` subprocess, since the DOMPurify patch depends on the runtime's module loader. Fixtures are written to temporary directories.
- `site/README.md` and `site/contributing.md` describe the new check and which pages it reads (the tracked pages and the generated `site/api/` pages, after includes); the `site/` row of `docs/INDEX.md` is re-measured (283.7 KB to 284.7 KB; still 42 tracked pages).

## Round 3 (Codex) — reviewer verdict: merge after fixes

The director's finding check (Fable 5.2) found all three findings valid; none triggers on the site's 12 diagrams or its current files. Rounds 1 to 3 each raised P1s because the step's stated promise was absolute ("every Mermaid diagram, as the site renders it") while the check models VitePress and the browser instead of observing them. This round fixes the two cheap gaps and narrows the stated promise (Scope) so later rounds judge the check against what it promises. All three are fixed in d075059a, each test written first and seen failing before the fix.
