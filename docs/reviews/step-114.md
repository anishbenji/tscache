# Step 114 — M7 change events

Branch: `feat/114-m7-change-events` · Reviewer: none yet (the director runs the pre-review, the security lane and the Codex gate) · Rounds: 0 · Status: implemented, awaiting review · Verdict after triage: pending

## Scope

Builds finding M7 of the review of 2026-11-10, as designed in `docs/design/m7-change-events.md` (step 92) and decided by the user on 2026-11-16 (decision 65): a cache-scoped `cacheChanged` event that tells a reader where what a `get` returns may have changed.

- **Architecture.** The approved text moved into `docs/architecture.md` §2.1 (`client.features`), §2.7 (the event, delivery, the read rule, cost), §2.8 (the amended "No events" bullet), §3.1 (`hello.features`), §3.2 (the two ops and the event envelope), §4.6–§4.8 (engine reader report, server subscriptions and request causes, client listener counting). Decision files N71–N84, indexed in §8; dated amendment notes on N35 and N36. The design proposal and the roadmap sketch are marked specified.
- **Engine.** `CacheState` collects a `ReaderChange` (`written`, `removed`, `cleared`, in slots) during each mutating call while its owner says a reader listens, and reports it once when the call ends, after the call's `onMutate` and `cacheCleared`. The engine fans it out through the internal `CacheObserver` seam (`hasReaders`, `onReaderChange`); its public events are unchanged.
- **RPC.** `hello.features: ['cacheChanged']`; additive ops `subscribe` and `unsubscribe` (`{ cacheId }` or `{ all: true }`); the server keeps per-cache and every-cache subscriber sets, answers `hasReaders` from them, converts the report to ms and posts one `evt scope:'cache'` per subscribed connection with the request id of the cause. Ops deferred by the persistence keep their id; `Persistence.clearAll` takes the memory clear as an optional argument for that; the orchestrator applies a fetch under the issuing `get`'s id.
- **Client.** `client.on` / `cache.on('cacheChanged')` count listeners per key and send `subscribe` for the first and `unsubscribe` for the last (`client/changes.ts`); `client.features`; against a worker without the feature nothing is posted and a development build warns once. Types: `ClientEvents['cacheChanged']`, `WorkerFeature`, `CacheEvent` gains `'cacheChanged'`.
- **Integrations.** `integrations/shared/changes.ts`: `reaction` (the read rule), `ChangeWatch` (one view, at most one read per animation frame, fetching only when an event of the frame wrote nothing and cleared or withdrew), `NextRead`. Vanilla, Solid, Vue, Svelte and Angular subscribe just before each read. React makes a view for each client, cache and range while rendering, which subscribes before its first read (see "React state model"); until pre-review 4 it subscribed in an effect and read the cache once more when the subscription started (`catchUp`).
- **Reference clients.** In the SharedWorker hosting, `liveFeed` redraws from `cacheChanged` (every tab, the holder's own included) instead of the holder's `BroadcastChannel` batch message; the channel still carries the bars for the dedicated and in-process hostings and every opening of a source.
- **Docs.** `site/concepts/events.md` (change events, the read rule, hostings, older workers, a snippet), `site/guides/live-feeds.md` (the known-limit box now states the remaining limit, one cache per tab outside a SharedWorker; "Many tabs, one feed"), `site/how-it-works/live-feeds.md`, `site/index.md` (limits qualified for 0.2.0), `docs/guides/patterns.md`, `docs/benchmarking.md`, `reference/README.md`, `integrations/README.md`, `docs/releases/0.2.0.md` (in preparation; the version is not bumped).

Choices made in this step without a decision row, each the simplest reading of the approved text:

- `subscribe` and `unsubscribe` run at once, never through the persistence's `durably`: they touch no data. Malformed params (`{}`, a non-string id, `all` other than `true`, both fields) are answered with `TscacheError`. Both are idempotent; a client counts its own listeners, so the server keeps sets, not counts.
- A subscription to a cache id that does not exist yet is accepted; it takes effect when the cache is created.
- `client.features` keeps only the feature names the client knows; a malformed `hello.features` counts as none.
- The integrations' frame scheduler is `requestAnimationFrame`, falling back to a zero timer where it is absent; a hidden tab therefore reads once when it shows again.
- In the reference clients, `onBatch` in the SharedWorker hosting receives the hull of every `cacheChanged` event's written ranges, whichever tab wrote (a feed bar or a fetch). Its existing guards (a span before the view is ignored, one meeting the view's end extends it with a cache-only read, one after a gap starts a catch-up) handle each; no loop is possible, since a fetch's event leads only to a cache-only read or to a catch-up whose own event meets the view.

### Redesign

The change re-read path drew findings in both pre-reviews, so its sequencing moved out of the adapters. `integrations/shared/changes.ts` now has `ViewReads`, which owns a view's reads end to end: it follows the client's handle before each read, decides fetch or cache-only from the changes and the view's inputs, holds a cache-only change while a fetching read is in flight, releases it only after that read's answer has resolved and only through the frame scheduler, and starts the cache-only read through `cacheOnlyAfter`, which waits for the previous answer and keeps its failure labels. The vanilla, Vue, Solid, Svelte and Angular adapters call `views.read(cache, range, inputs)` from their reactivity and apply latest-wins to the answer it returns; they no longer handle settling, holding or labels. `NextRead` is gone.

The order can no longer be broken per adapter. The release goes through the frame, a later task than the promise jobs in which every framework applies a resolved answer. And the cache-only read itself waits for the previous answer, so even a release at the wrong moment cannot overtake it. React cannot hold a per-view object across render retries (refs reset while a render suspends), so it keeps its render-time read cache and uses the same `cacheOnlyAfter` and frame release. `scripts/flake-hunt.sh -n 30 --load` over the four integration test files: 0 failures in 30 runs, 690 tests.

The shared hold (pre-review 3). React's re-read path drew findings four times (PR-2, PR-4, PR2-2, R1-2 and PR3-1) because it kept a hold of its own beside `ViewReads`, so the R1-3 fix reached only one of the two. The hold and its release are now one shared piece, `ChangeHold` in `integrations/shared/changes.ts`: it is told of each read a view starts, holds a cache-only change only while the latest one fetches and has not settled, ignores an overtaken read entirely, ends the hold when a cache-only read starts, and releases through a callback the owner points at the frame scheduler. `ViewReads` owns one; React keeps one per view in a ref and reports the newest read to it while rendering, which is idempotent per read, so a repeated render reports it once. React's `useChanges` now has no hold logic: it asks `hold.holds(how)` and otherwise records the change. A fix to the hold now lands once, for every adapter.

The React views (pre-review 4). The shared hold fixed how a change waits, but React still decided by itself which read a render gets: a read lived in a map under its client, cache and range for 30 s, the subscription started after a commit and made up for the gap with a cache-only read, and a change record travelling in React state said which reads were "after a change". Every finding since PR-2 was a path through those three that the others did not cover. They are gone. A React view is now one client, one cache and one range, which never change, with a `ViewReads` of its own: the class every other adapter uses, unchanged except that `reread` is told how the next read reads (PR4-2). It follows the client's handle before its first read, so there is no gap to make up for; its first read fetches and every later one is a change's, so "the same view" holds by construction and React has no hold, no change record and no key for reads after a change. What React keeps is in two short pieces of `integrations/react/series.tsx`: where a render finds its view (`viewFor`, and `View.show`, which takes a committed view out of the map), and when a view reads (a frame scheduler that waits until a mounted component shows the view). ### React state model

The model that the redesign of pre-review 4 follows; `integrations/test/react.test.ts` has a test for each row of the event table.

**The rule**, which `ViewReads` already follows: a view's read fetches, except when the same view (range by value, same client, same cache) reads again because of a change; that read is from the cache alone, starts after the previous answer and keeps its failure labels, unless the change wrote nothing and cleared or withdrew coverage, when it fetches (N84). No fetch is caused by a fetch's own event.

**A view** is one client (the promise the client is known by), one cache (the config by value, `keyOf`) and one range (by value). None of them ever changes. A view owns one `ViewReads` and `newest`, the promise of its newest read, which is what a render suspends on (`use`). Its first read is `ViewReads`' first, so it follows the client's handle and then fetches; every later read is asked by a change, so `ViewReads` decides it by the rule. One view never serves two ranges, clients or caches, so "the same view" cannot be judged wrongly: there is nothing to judge.

**Where a render finds its view.** A view must exist before anything commits, since the render suspends on it, so it is made while rendering.

| The render is                                                     | It finds its view                                                                |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| for the client, cache and range of the view the component shows   | in the component's ref, set when it commits                                      |
| a mounted component's, for another client, cache or range: a move | in the map, under client, cache, range and the identity of the view it shows now |
| a first mount's                                                   | in the map, under client, cache and range                                        |

A view is in the map only until a component commits with it; from then on it is that component's alone. A view no component shows leaves the map, and stops following its cache, `KEEP_MS` (30 s) after its newest read settled or, if later, after it was last shown.

**When a view reads.** At once when it is made (the first read). After that only while a mounted component shows it: a change is scheduled through a frame that waits for `show`, and coalesces as in every adapter (at most one read, a fetch winning over a cache-only read). So `newest` never changes under a suspended render, and a view that is never committed costs one read.

**Each event:**

| Event                                                        | Next read                                                                                                                                                                                          | Reads                                                 |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| First mount                                                  | A new view's first read, at render                                                                                                                                                                 | fetch                                                 |
| The view's first commit (a mount or a move)                  | One read, in place of any cache-only read that waited (see "kept for a test" below)                                                                                                                | cache                                                 |
| Range move to a new range                                    | A new view's first read; the view on screen goes on following until the move commits                                                                                                               | fetch                                                 |
| Range move back to a range shown before                      | A new view's first read: the earlier view was committed, so it is not in the map                                                                                                                   | fetch                                                 |
| Range move to a range still in the map                       | Only a view no component committed is in the map, under the view the component showed when it was made. A retry of the same move finds it; a move from any other view does not and makes a new one | none for a retry; else fetch                          |
| Cache change (another config value) or client change         | A new view's first read                                                                                                                                                                            | fetch                                                 |
| Lost worker                                                  | A new view on the next client; a read the lost client rejected is answered by that same view, so a first mount still suspended is answered too                                                     | fetch                                                 |
| Change event while the newest read fetches                   | A cache-only change waits for that read's answer, then reads after it, labels kept (`ChangeHold`, `cacheOnlyAfter`); one that wrote nothing reads at the next frame                                | cache; fetch for one that wrote nothing               |

| Remount                                                      | A new view's first read: the unmounted component's view was committed, so it is not in the map                                                                                                     | fetch                                                 |
| An `Activity` shown again                                    | Within `KEEP_MS`, what changed while hidden; later the view follows afresh and reads                                                                                                               | cache or fetch by what changed; fetch after `KEEP_MS` |

**N84.** A fetch's event has a non-empty `written`, so it asks for a cache-only read, and it reaches only views that exist: an event never makes a view. A fetching read is therefore caused only by a render with new inputs (a mount, a move, a new cache or client), by an application call that wrote nothing, or by showing again a view that had stopped following.

**Where React differs from the other adapters, and why:**

1. _Views are made while rendering and kept in a map._ A render needs its promise before it commits, React keeps no state for a first mount that suspends, and it reports no render it abandons. The other adapters make their `ViewReads` once per component.
2. _One `ViewReads` per client, cache and range, not per component._ A component's renders are speculative: a move may never commit, and the view on screen must go on following until it does. So a move does not go through the committed view's `ViewReads`; it gets its own.
3. _A first mount finds its view by client, cache and range alone._ It has no identity yet. Within `KEEP_MS` it therefore takes over a view that a mount React abandoned left in the map, instead of fetching. That view has followed its cache since before its read, so every change since is read when it is shown, a fetch included; what it does not get is the fresh fetching read a new mount would make (a provisional tail fetched again, a failed fetch retried). Two components that mount with equal inputs in one commit share a view; in separate commits the second makes its own.
4. _A view reads only while shown._ Otherwise every abandoned render's view would read on every change for 30 s. The frame is the hidden-tab case of `ChangeWatch`: it reads once when it shows again.
5. _Answers arrive through `useSyncExternalStore` and `useDeferredValue`._ A change's read replaces `newest`; the deferred value keeps the previous answer on screen while the new read suspends in a background render (PR-2).

**Kept for a test, not by the model.** When a component first commits with a view, the view reads the cache alone once. Until pre-review 4 that read made up for the subscription starting late (PR-4), and the existing test "a new range's commit reads it from the cache once more (PR-4)" pins it in a scenario where no change happens (the fixture's partial fetch fails, so no event follows). A view now misses no change without it. It is kept so that every existing React test passes unchanged, it costs nothing when a cache-only read was waiting anyway (the usual case: the first read's own fetch event), and it is for the director to drop together with that test's last wait.
