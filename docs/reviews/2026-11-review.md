# tscache review — November 2026

Reviewed 2026-11-10 (17:45–18:30 IST) at `main` = `0e45a85`. Read-only: no code or configuration was changed, and this file is the only file written in the repository. ## Summary

The library itself is in good shape. The 14-step plan is complete and merged. Every gate passes on `main` (build, type check, 2,142 tests, publint, attw, 163 Playwright tests, the full `ci.sh`). The storage core agrees with an independent model over about 1.4 million random operations. Of 113 decision rows compared with the code, 100 match, one is a real deviation (N25, already ruled on, fix waiting), and the rest are documents that lag approved changes.

The problems are around the core:

- **The path to a first publish is waiting on things nobody can see.** Five green pull requests and six questions are waiting for the user, while the file that should list them says "none" and the dashboard shows an empty queue.
- **Two defects would reach consumers of 0.1.0.** The in-process hosting cannot load a fetcher under webpack, Rspack or Next.js, and `null` or out-of-range field values are stored as wrong numbers without an error.
- **Several design gaps need a decision, not code**, before real applications depend on the behaviour: calendar intervals, memory bounds, deploy skew, change notifications.
- **A fresh director thread could not resume from files alone.** The state file is accurate about work in progress, but decisions, rules and status are spread over seven stores, and the always-loaded instructions ask every agent to read about 110,000 tokens first.

There is no Critical finding.

`pending-user-decisions.md` says "Open: none" and the dashboard shows "Open user decisions: none" and "Queue: empty". `director-state.md` (last written 2026-11-09 18:29 IST) records six items waiting on the user or the parent thread, among them approval for step 68 and the merge of #88–#92, and a queue of seven further steps. The director has logged nothing for 23 hours. Details: §6.1.

**H2. `main` cannot be published; the fixes sit in two unmerged pull requests.**
`packages/tscache/package.json:3` is version 0.0.0 (npm already has 0.0.1), the tarball has no README or LICENSE (`npm pack --dry-run`: 25 files, all under `dist/` plus the manifest), and there is no release workflow while the npm trusted publisher accepts nothing else. #90 and #91 fix all three and are green. Details: §5.2.

**H3. Locked decision N25 is not implemented: the handshake timeout also covers the fetcher import.**
The timer stops at `init-ok`, not at `hello` (`packages/tscache/src/client/hosting.ts:63-79`, `rpc/port-client.ts:146-149`, `rpc/server.ts:261-274`). A probe with a 400 ms fetcher import and a 100 ms timeout stepped down with "Worker did not answer within 100 ms". With defaults, a fetcher module that needs more than 5 s to load silently costs the page its SharedWorker. The user ruled "fix the code" on 2026-11-09; the fix (step 68, `a25de80`) is unpushed and waiting on H1. Details: §1.2, D1.

**H4. The in-process hosting cannot load a fetcher when the application is bundled by webpack, Rspack or Turbopack.**
The fetcher import is `import(/* @vite-ignore */ module)` (`packages/tscache/src/orchestrator/orchestrator.ts:334`). webpack 5.112.2 and Rspack 2.3.2 turn it into a context that always rejects; Next.js 16.4.6 (Turbopack) into a stub that throws, with no build warning. Result: `createClient` with a fetcher rejects on a Next.js server and at the last step of the browser fallback chain ("Cannot find module …"). Adding `/* webpackIgnore: true */` fixed every case in a scratch copy. No test in the repository builds with anything but Vite. Details: §3h.

**H5. `null` and out-of-range field values are stored as wrong numbers, with no error and no warning.**
Probe: a JSON batch with `close: [1.5, null, 3.5]` (`f64`) is stored as `[1.5, 0, 3.5]`; `300` and `-1` in a `u8` field become `44` and `255`; `put` returns `warnings: []`. Conversion is plain typed-array assignment (`packages/tscache/src/engine/batch.ts:195-197`). JSON has no `NaN`, so a JSON backend's missing value becomes a zero-price bar. The docs mention only that `1.5` becomes `1` in an `i32` field. This should be decided before 0.1.0, because tightening it later is a breaking change. Details: §3i.

### Medium

**M1. Public documentation and the starter prompt say Chrome on Android has no SharedWorker; that has been false since Chrome 148.**
Twelve statements, including `site/index.md:9` and `starter-prompt.md:54`. Live data: Chrome Platform Status ships it at 148 for Android and WebView; caniuse lists Chrome for Android 157 as supported and Samsung Internet 31 as not. No page gives a browser support table. Details: §4.4 and D4.

**M2. The scheduled flake hunt on `main` is red and tracked nowhere.**
Run 42621162595 (2026-11-09, head `0e45a85`): "2 failed / 4 did not run / 809 passed"; both failures are `e2e/examples/vanilla-uplot.spec.ts:45`. The dashboard says "Main CI: passing" and "Challenges: 0 open". Details: §5.2, §6.1.

**M3. Nothing bounds memory, and nothing reports it.**
No eviction, budget or size API exists in `packages/tscache/src` (grep: no match); the only design is a three-paragraph roadmap sketch. One year of one-minute OHLCV is about 21 MB per series, held by a SharedWorker that outlives its tabs. Details: §3c.

**M4. Calendar intervals are not supported, and the primary use case needs them.**
The grid is `alignmentOffset + k × interval` in fixed milliseconds. Daily bars stamped at a session open in a daylight-saving zone are rejected as `misaligned` for half the year; the docs acknowledge this in one sentence (`site/concepts/grid.md:28-29`) and give no recipe. Weekly and monthly bars are not mentioned anywhere. Details: §3b.

**M5. Version skew after a deploy is detected but has no recovery path, and with hashed worker URLs it is silent.**
A protocol mismatch rejects `createClient` with the advice "Close the old tabs and reload". With content-hashed worker URLs each deploy gets its own SharedWorker: old and new tabs stop sharing, nothing reports it, and both write one IndexedDB database on the premise that the overlap is brief (N52). `hello.lib` is never read. Details: §3d.

**M6. In the fallback hostings, auth events and persistence behave differently and the docs do not say so.**
`authInvalid` and `updateAuth` reach one tab only in a dedicated worker or in-process (`packages/tscache/src/rpc/server.ts:408-409`), while `site/guides/auth.md:14-15` promises "every tab". `persist: true` is "accepted and ignored, without an event" outside the shared hosting (`types.ts:75-78`). Details: §3e.

**M7. Readers get no notification when data changes.**
"tscache has no subscriptions" (`site/guides/live-feeds.md:3`). The engine already computes what each change touched for persistence (`engine/cache.ts:113-141`); the reference clients work around the gap with a `BroadcastChannel`. Details: §3f.

**M8. Snapshot embedding relies on the application for HTML safety, and on the host for byte order.**
`encodeSnapshot` leaves `<script>` escaping to the caller (`packages/tscache/src/snapshot.ts:54`) and the package exports no helper for it. Field bytes are documented as little-endian but copied in native order with no check (`snapshot.ts:46`). Details: §3g.

**M9. Every agent is told to read about 110,000 tokens before any work, and there is no index of documents.**
`AGENTS.md:5` requires `starter-prompt.md` (23.7 KB) and `docs/architecture.md` (420.5 KB). The decision table's rows are about 3 KB each on one line, so a single grep into it cost the director 21,941 characters. Details: §6.2.

**M10. There is no append-only decision log.**
Decisions live in seven places; architecture rows are amended in place; the auto-approved log is in the memory folder and has no entry after 2026-11-02. Details: §6.1.

**M11. Rules that bind every agent live outside the always-loaded files, and three documents disagree on who merges.**
The one-heavy-job lock, lowercase commit subjects, the release hard rules ("no npm token ever; no v* tag; no publish") and the budgeted review entry point are in the director's brief, its state file or memory. This review's own gate run went without the lock for that reason. Details: §6.3.

**M12. The director thread has taken in about 390,000 tokens of tool output, most of it delegable.**
Measured from its transcript: 1,571,711 characters over 1,990 tool results, 12 compactions, one thread of 4,284 items. The largest shares are review files and Codex output (290 K characters), its own control files (240 K), `git diff`/`show`/`log` (196 K) and 53 identical `orchestrator_capabilities` calls (135 K). Details: §6.5.

**M13. The dashboard's curated sections are a week old and contradict the state file.**
`direction.json` and `entries.json` were last written 2026-11-03. "Now and next", the parked list and the challenge list no longer match reality. Details: §6.1.

**M14. The review checklist and two normative documents require a behaviour the code deliberately lacks.**
"`updateAuth` … retries paused fetches" (`docs/review-checklist.md:69`, `docs/architecture.md:271`, `starter-prompt.md:65`). Nothing is paused or retried, by an approved step-11 decision (`docs/architecture.md:1107`). Every review is told to check for it. Details: D3.

**M15. The engine rules added last have example tests only, written by their implementer.**
N17, N18, N19, the overlap warning and the failed-write guarantees have no property test; the property tests run three fixed seeds with K = 2 and cap = 8, never pass `meta`, and use no shrinking. No bug was found there; the gap is regression protection. Details: §2.3, §2.4.

### 2.1 Finding

**F1 (Low, confirmed by probe): `hydrate` accepts a snapshot whose coverage reaches past the snapshot's own `finalizedUntil`.**

- Validation never compares a snapshot's coverage with its own watermark, and `hydrate` clips only by the target cache's volatile region: `packages/tscache/src/engine/snapshot.ts:204`, `:257`; `packages/tscache/src/engine/cache.ts:437`.
- Input: a target cache with `finalizedUntil: 1000` (interval 10) and a snapshot with `finalizedUntil: 30` and `coverage: [{ start: 0, end: 90 }]`.
- Output (`bun p2/probe-hydrate.ts`, re-run by me): `applied: [{"start":0,"end":90}]  target coverage: [{"start":0,"end":90}]  target finalizedUntil: 1000`. Slots 30–90 become authoritative although the snapshot itself calls them provisional.
- This is the snapshot analogue of what N19 closed for `put`. It is Low because the library's own `takeSnapshot` cannot produce such a snapshot (no cache held a covered slot at or after its watermark in any modelled operation), and §4.5 does not list the check, so the code follows the document. Only a hand-built or corrupted snapshot reaches it. Since snapshots cross a trust boundary (HTML from a server), rejecting it in validation is the cheap option; that is a decision for the user.

## Part 3 — Design gaps

Each item says what the code on `main` (`0e45a85`) does today. "Not addressed" means no code, test or decision covers it; a roadmap sketch is noted where one exists.

### 3a. Non-aligned timestamps (jittered metrics, sparse events) — rejected by design, no help offered

- A `put` rejects the whole batch at the first timestamp that is off the grid: `packages/tscache/src/engine/batch.ts:106-110` (`code: "misaligned"`), using `isAligned` in `packages/tscache/src/grid.ts:42-46`. This is locked (starter §3.1).
- Read and invalidate ranges may be unaligned; they snap outward (`grid.ts:100-125`). A `put` range snaps inward (N13).
- Sparse series are supported only as aligned points with gaps (the K-split, N14). An irregular-timestamp layout is deferred: `docs/roadmap.md:130-135` (`ColumnarSegment` and "a third segment layout for irregular timestamps").
- Not addressed: there is no bucketing or snapping helper in `src/`, and no guide recipe for it (`grep -i "jitter|bucket|irregular"` over `site/` and `docs/guides/` returns nothing). A consumer with jittered metrics has to floor timestamps and resolve collisions in the fetcher, and nothing says so.

### 3b. Calendar intervals — fixed-millisecond grid only; DST is acknowledged in one sentence, weekly and monthly are not addressed

- `interval` is one positive safe integer in milliseconds (`packages/tscache/src/engine/validate.ts:118`), and `alignmentOffset` is an integer normalised into `[0, interval)` (`validate.ts:37-46`). The grid is `alignmentOffset + k × interval` and nothing else (`grid.ts:1-5`).
- Daily bars at a fixed UTC time work, and the docs show it: `site/concepts/grid.md:22-24`.
- A session that moves with daylight saving time does not fit, and the docs say only that: "The grid is fixed: a session that moves with daylight saving time does not fit one offset all year" (`site/concepts/grid.md:28-29`). No workaround is given.
- Weekly bars work only as a fixed 604,800,000 ms step with an offset; that is not documented. Monthly, quarterly and yearly bars cannot be represented (variable length). `grep -i "monthly|weekly|calendar"` over `packages/tscache/src`, `docs/roadmap.md`, `docs/guides` and `site/` finds nothing, and `docs/architecture.md` has no hit for "calendar", "monthly" or "DST".
- Why it matters here: the stated primary use is OHLC charts. Daily bars from an exchange in a DST zone are the common case, and a batch stamped at the session open is rejected with `misaligned` for half the year.
- The design leaves room: every ms↔slot conversion lives in `grid.ts` (N9), so a calendar grid is a change to one module plus the config, not to coverage or segments. That is a new decision for the user. Until then the docs need a recipe (stamp daily bars at 00:00 UTC of the trading date; stamp weekly bars at a fixed weekday; map monthly bars to a synthetic ordinal grid in the fetcher).

### 3c. Memory budget and eviction — not addressed

- No eviction, LRU, byte budget or memory limit exists in the package: `grep -rni "evict|lru|maxBytes|byteBudget|memoryLimit"` over `packages/tscache/src` returns nothing. Neither per cache nor global.
- No API reports memory use. `CacheHandle` exposes `get`, `put`, `invalidate`, `clear`, `coverage`, `hydrate`, `setFinalizedUntil` (`packages/tscache/src/client/cache.ts`), and the client `cache`, `clearAll`, `updateAuth`, `on`, `off`, `dispose` (`client/client.ts:43-71`).
- What exists: a per-point memory measurement in the performance suite (`packages/tscache/test/perf/memory.test.ts`), a disk-quota stop for persistence (N47), and a three-paragraph sketch, "A byte budget per worker, enforced by evicting least-recently-read pages", with the invariant that eviction must subtract coverage (`docs/roadmap.md:123-128`).
- Scale: a dense page stores no timestamps, so one year of one-minute OHLCV in `f64` is 525,600 × 5 × 8 B ≈ 21 MB per series (the bench suite's own "read-year" case). A SharedWorker serves every tab and, since #86, outlives its last tab by about 30 s (`client/hosting.ts:104-107`). Fifty symbols of scroll-back is about 1 GB that only `clear` or `clearAll` releases.

### 3d. SharedWorker version skew between tabs after a deploy — detected and documented; recovery and sharing across the skew are not addressed

What the code does:

- Handshake: the worker's `hello` carries `protocol`, the client compares it with `PROTOCOL_VERSION = 1` (`packages/tscache/src/rpc/protocol.ts:21`, `rpc/port-client.ts:103-113`) and the worker checks the client's `init` (`rpc/server.ts:247-253`). A mismatch is a `ProtocolMismatchError`, and `createClient` rejects without stepping down the chain (`client/client.ts:131-146`).
- `PROTOCOL_VERSION` has never changed. Additive operations rely on an older worker answering `unknown op` (N37).
- `hello.lib` is a hand-written constant, `LIB_VERSION = "0.0.0"` (`packages/tscache/src/entries/worker.ts:21`). The client never reads it (no reference to `.lib` in `rpc/port-client.ts` or `client/`), and nothing ties it to `package.json`.
- Worker identity: `new SharedWorker(url, { type: "module", extendedLifetime: true })` with no `name` (`client/hosting.ts:107`), so identity is the URL.
  - Hashed worker URL (the Vite default): each deploy gets its own SharedWorker. Old and new tabs stop sharing the cache, fetch dedup, `authInvalid` and `clear` until the old tabs close. No event reports it. Both workers write the same IndexedDB database with no lock; N52 accepts this on the premise that "Two SharedWorkers overlap only briefly (a deploy skew…)" (`docs/architecture.md:1817`). A tab left open for days keeps the old worker alive for days, so "briefly" is an assumption, not a property.
  - Fixed worker URL: a new tab connects to the old worker's old code until every old tab has closed (plus about 30 s). A changed protocol rejects `createClient`; changed creation options step down to a dedicated worker (`site/guides/workers.md:80-90`).
- Documentation: `site/guides/workers.md:80-90`, `site/troubleshooting.md:15-18` ("Close the old tabs and reload"), `site/guides/persistence.md:76`, `docs/guides/patterns.md:139`.
- Tests: unit tests only (`packages/tscache/test/rpc.test.ts`, `client.test.ts`, `errors.test.ts`). No Playwright spec loads two builds of the worker.

Not addressed:

1. Recovery. The only advice is to close the old tabs. An application cannot close a user's other tabs, so the first release that bumps `PROTOCOL_VERSION` breaks every new tab of a fixed-URL deployment until then. A documented retry pinned to `mode: 'dedicated'`, or a "newer worker available" event to old tabs, would cover it.
2. Visibility. With hashed URLs the split is silent: `client.mode` is `'shared'` in both generations.
3. Two-generation persistence beyond the accepted cost in N52 (one worker can write back a range the other removed).

### 3e. Cross-tab auth broadcast and mode visibility in the fallbacks — per-tab only in the fallbacks; the docs do not say so

- The broadcast is a loop over one server's connections (`packages/tscache/src/rpc/server.ts:408-409`). A dedicated worker and the in-process hosting have one server per tab (`client/hosting.ts:148`; N27), so `authInvalid` reaches only the tab whose fetch was refused, and `updateAuth` (`client/client.ts:56`) reaches only that tab's worker. There is no `BroadcastChannel` or storage-event bridge in `src/` (grep: no match).
- The refresh snippet (`examples/react-lwcharts/src/auth-refresh.ts`) still converges: each tab that later gets its own refusal takes the Web Lock, sees a newer stored token and adopts it. Recovery is lazy and per tab; propagation is not addressed.
- The auth guide states the SharedWorker behaviour without qualification: "The worker marks credentials invalid and **broadcasts `authInvalid` to every tab**" (`site/guides/auth.md:14-15`). `docs/guides/patterns.md:34-35` and `:61-62` describe the dedicated-mode difference for timers and `clear`, not for auth.
- Mode visibility: `client.mode` (`client/client.ts:45`, `:162`) and `modeFallback { from, to, reason }`, replayed once on the macrotask after `createClient` resolves (`client/client.ts:168-185`). A listener attached later misses the event; `client.mode` remains. There is no development-console warning for a fallback (`client/dev.ts` prints merge warnings only).
- `persist: true` in a hosting that cannot persist is "accepted and ignored, without an event" (`packages/tscache/src/types.ts:75-78`). A page that silently fell back to a dedicated worker loses persistence with no signal other than `client.mode`.

### 3f. Push or stream writes and change notifications — writes are supported; notifications are not addressed

- Writes: a `put` without a range adds or overwrites and claims coverage only for its own span below the watermark (N3, N11; `site/guides/live-feeds.md:13-16`). In shared mode any tab's `put` lands in the one cache.
- Notifications: none. "tscache has no subscriptions" (`site/guides/live-feeds.md:3`). The event set is `authInvalid`, `modeFallback`, `workerLost`, `cacheCleared`, `mergeWarning`, `persistStopped` (`packages/tscache/src/types.ts:275-320`); nothing reports changed data.
- The mechanism exists internally: the engine calls a synchronous `onChange` hook with the slots each write, removal, watermark move or clear touched (`packages/tscache/src/engine/cache.ts:113-141`, call sites `:328-470`). Only persistence consumes it.
- Sketch: `cacheChanged { cacheId, range }`, notify-only, coalesced per macrotask (`docs/roadmap.md:115-121`).
- Workaround shipped as reference code, not as library API: one tab elected by a Web Lock holds the feed, puts each bar and tells the others over a `BroadcastChannel`; they re-read with `cacheOnly` (`reference/shared/src/live.ts`; `site/guides/live-feeds.md:29-36`).

### 3g. Version field, byte order and SSR text encoding of the segment transfer payload

- Version field: present and checked at all three uses. Segment payload `format: 1` (`packages/tscache/src/segment/payload.ts:27`), snapshot envelope (`engine/snapshot.ts:135`; decode `snapshot.ts:89`, `:131`), persisted record (`persist/records.ts:20`, `:53`). An unknown format is rejected. No migration path is defined for a format 2.
- Byte order: specified, not recorded and not enforced. The types and docs say little-endian (`packages/tscache/src/types.ts:149`, `:199`; `site/concepts/segments.md:58-64`; `site/guides/fetcher.md:85`). The encoder copies native bytes (`toBase64(new Uint8Array(data))`, `snapshot.ts:46`); there is no `DataView`, endianness probe or flag anywhere in `src/` (grep: no match). A snapshot produced on a big-endian server would carry big-endian bytes under a little-endian contract. The practical risk is low; the assumption is unstated in the format that is meant to become the interchange and persistence format.
- SSR text encoding: `encodeSnapshot` returns a JSON-safe object with each mask and field buffer as standard padded base64 (`snapshot.ts:52-56`, `base64.ts:44-53`, native `Uint8Array.prototype.toBase64` where it exists). `NaN` survives because bytes are encoded, not numbers. Cost: +33 % size, no compression.
- HTML safety is left to the application: "Escaping for a `<script>` element stays with the app" (`snapshot.ts:54`). The docs snippet and the integration helper escape `<` as `<` (`site/snippets/snapshots-server.ts:42-47`, `integrations/shared/hydration.ts:169-170`). The package exports no helper that does it, so every consumer has to remember a step whose omission is an injection bug when a field name or `version` string comes from data.

Cause: webpack and Rspack replace an `import()` of a bare expression with an empty context that always rejects; Turbopack replaces it with a stub that throws. The copy-dist recipe protects the worker files, but the in-process hosting is reached through `dist/index.js`, which the application's bundler always processes.

Consequences:

1. Server-side use of `createClient` with a fetcher (the in-process hosting is the only one on a server) fails under Next.js and any webpack or Rspack server build.
2. The last step of the fallback chain is dead in those builds: a browser that reaches in-process with a fetcher configured gets a rejected `createClient` (N30) instead of a working client. Turbopack gives no build-time signal.

Fix, verified on a scratch copy of `dist/`: adding `/* webpackIgnore: true */` beside the existing hint makes every failing case pass (webpack and Rspack on Node print `{"mode":"in-process","points":3,…}`; the Next.js server paths return `ok: true` and the browser hydrates the snapshot). For Next.js server code alone, `serverExternalPackages: ["@anishbenji/tscache"]` also works.

Side observation from the same probe: error names do not survive minification. `TscacheError` sets `this.name = new.target.name` (`packages/tscache/src/errors.ts:23`), and under the Next.js builds the name arrived as `r`, `b`, `e`, `t` or `o`. Anything that matches on `error.name` breaks in a minified consumer build.

Not probed: a fetcher that has its own imports or is written in TypeScript under webpack or Rspack, `next dev`, the edge runtime, other meta-frameworks, Firefox and Safari.

### 3i. Field-level missing values within a present point — float `NaN` only; `null` and out-of-range integers are stored as wrong numbers without an error

- Presence is one bit per point (`packages/tscache/src/types.ts:50-54`). A float field marks a missing value with `NaN`, which is legal and survives transfer, snapshots and persistence. An integer field cannot (`docs/guides/patterns.md:44-53`, `site/concepts/segments.md:18-23`). Per-field masks are deferred (`docs/roadmap.md:137-138`).
- Values are converted by typed-array assignment (`packages/tscache/src/engine/batch.ts:195-197`). The docs give one consequence, "`1.5` given for an `i32` field is stored as `1`" (`site/concepts/grid.md:66-68`).
- Probe (run for this review, `bun` against `src/engine/engine.ts`; a batch parsed from JSON with `close: [1.5, null, 3.5, undefined]` as `f64`, `volume: [10, null, 30, 40]` as `i32`, `flags: [1, 2, 300, -1]` as `u8`):

  ```
  put ok, warnings: []
  close : [ 1.5, 0, 3.5, NaN ]
  volume: [ 10, 0, 30, 40 ]
  flags : [ 1, 2, 44, 255 ]
  ```

  JSON has no `NaN`, so a JSON backend sends `null` for a missing value. The cache stores `0`: a zero-price bar on a chart, indistinguishable from data. `300` wraps to `44` and `-1` to `255` in a `u8` field. None of this raises `PutError` or a warning, and none of it is documented.
- This is inside the locked rule "NaN is a legal field value", not against it. Rejecting `null` and non-finite-by-coercion values in `number[]` input, or mapping `null` to `NaN` for float fields, is a new decision (it adds a pass over the put path).
