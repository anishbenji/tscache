**Where the design lives.** A proposal file beside the M7, M3 and M5 proposals, with the same shape: the gap, what the engine has today (with file and line), the design with each recommendation taken, the decision rows, the contract tests and what changes when it is built. The architecture document records approved contracts, and this design would amend locked text (below), so the approved parts move into the architecture in the contract-test step.

**What it covers,** as the brief asked: today's grid (`grid.ts`, N9, `alignmentOffset`, the step 71 recipes in `site/concepts/grid.md:31-85` and `site/snippets/grid.ts`); the target cases (daily at a session open in a DST zone, trading-day calendars with holidays, weekly, monthly, 24/7, and two intraday cases the brief did not list but that bound the scope); the four options of the brief, each with its public API, its cost on every engine path that assumes fixed slots (snaps, coverage, segment caps, pages, gaps of K, persistence keys and records), its bundle size against the budgets and its behaviour when records written under one grid are read under another; the interactions with M3, M7 (including the integrations' `snappedOut` on `feat/114-m7-change-events`) and M5; migration; and twenty-two contract tests for the build step.

**Two findings the spec makes about the current engine.** (1) Everything inside the engine except `grid.ts` already runs on slot indices, and the payload decoder already reads a payload slot-relative (`segment/payload.ts:51-57`), so a calendar grid changes the two primitives of `grid.ts` and the places where the grid is _named_ (config, N20 comparison, payload, snapshot envelope and its JSON form, cache record, fetch request, the safe-integer domain checks), not coverage or segments. (2) A cache config crosses the port as a structured clone (`client/client.ts:208-215`), so a pluggable grid function cannot travel in the config; it would have to be code the worker loads, which today is only the fetcher module (N44). That is the main reason the proposal recommends data descriptors (option c) over functions (option b).

**Claims checked against the code.** Every statement about the current engine in the proposal's §2 tables and in §4–§6 cites a file and line on `main` at `362870f` (and `integrations/shared/changes.ts` on `feat/114-m7-change-events` at `7388283`); each was read at those lines, not inferred. The architecture sections cited (§2.2, §2.8, §3.1, §3.4, §4.1, §4.10.2 at lines 1387-1395) and the decision files (02, 03, 04, N1, N9, N12, N13, N14, N15, N17, N20, N34, N38, N39, N44, N55) were read in full. Bundle sizes come from `packages/tscache/bench/budgets.json`; the calendar code's own size (1–2 KB brotli) is labelled as an estimate in the proposal, to be measured by `scripts/size.ts` in the build step. The New York daylight-saving dates of 2026 (8 March, 1 November) used in the examples and tests were computed from the calendar, and match `site/snippets/grid.ts:40-42`. The skipped dates of Pacific/Apia and Pacific/Kwajalein and the `Intl` behaviour beyond `Date`'s range were reproduced with Node 26.13's `Intl` (pre-review, below).

**Redesign: the zone-data compatibility rule (G8, with G18).** This is the area's fourth finding in a row (PR-2, R1-1, PR3-2, R2-1) and the second from the gate in consecutive rounds, so by the convergence rule of `docs/workflow.md` (step 7) it was redesigned again, this time from the problem instead of from the last counterexample. Each earlier rule checked some places of a record and described the rest in words such as "every" and "exact"; each finding was a difference at a place the rule did not look. The proposal now states the problem in terms that leave no such place. A record's _named slots_ are every slot it says anything about (the ends of its range, its coverage, its payloads' slots). A record means the same to a reader exactly when each named slot starts at the same instant under the reader's zone data as under the writer's; a slot that does not is a difference of class 1 (within the slot) or class 2 (to another slot), wherever it lies. Every option is then stated as the condition under which it applies a record, a condition on the starts of specific slots, so what it leaves open is by definition the differences at the other named slots: for (a), anything that keeps the anchors aligned; for (c), anything at a slot that is not an anchor's, which is R2-1; for (d), nothing inside the record. Zone data can differ at one slot and no other, so no rule that inspects fewer slots than (d) can be complete, whatever its wording. Option (d) cannot be defeated the way (a) and (c) were, because its statement is an equivalence and not a list of cases: a further counterexample would have to change what a record means without changing the start of any slot the record names. What lies outside a record is listed in §5.6 as five points (differences elsewhere, the watermark, which data is right, zone data changing under a running engine, forged records), each either harmless by the same argument or stated as an assumption. G18 (b) is likewise stated on starts instead of on skipped dates, which makes `startOf` strictly increasing for any zone data, and its "the slot stays empty" now says exactly when: a point is there only if a put stamps one at the synthetic instant, and a record from other zone data cannot bring one under G8 (d), and can under (a), (b) and (c).

**What was checked for the redesign** (scratch programs outside the repository; nothing under `packages/` or the test suites changed):

- _The options, in a model with injected zone rules._ Cases a to k of §9.1 have the outcomes the table gives (case l follows from case g and the page arithmetic). ## Decisions for the user

All twenty rows, G1–G20, are open and listed with options, pros, cons and a recommendation in §8 of the proposal. None is decided here; the proposal's §5 assumes each recommendation. Rows that need the user's explicit approval because they amend locked or approved text, if taken as recommended:

- **G4 (a)** (`interval: number | CalendarInterval`) changes the meaning of decision 2's `interval` from always milliseconds to milliseconds or a calendar unit, keeping its words ("required, no default"), and narrows decision 3 (`alignmentOffset` must be absent or 0 with a calendar interval). N20's structural list is unchanged; `interval` is compared by value.
- **G9 (a)** (a `format: 2` snapshot, payload, cache record and JSON form, written by calendar caches only) amends the locked payload invariant of architecture §3.4 (its field set and "t_i = start + i × interval"), N34 (the envelope's fields), N38 (the JSON form, which carries format 1 only today) and N53 (the record format). Fixed caches keep `format: 1` byte for byte.
- **G1 (c)** carries the above; **G1 (b)** would also add a second kind of application code in the worker (N44).

**G8** now recommends (d), after round 2: a format 2 envelope stores the start of every slot it names (`starts`, as runs), and a reader applies a record exactly when each of those slots starts at the same instant under its own zone data (§5.6). It amends nothing beyond what G9 (a) already amends, since `starts` is part of the format 2 shape. Two things for the user to weigh. First, (d) also refuses a record when a daylight-saving date differs inside it, which earlier drafts applied and read at the reader's instants; the record is fetched again instead. Second, its cost: one slot start per named slot on write and on read (145 ms cold for a full daily page of 89 years, once per descriptor), and a difference at one slot refuses the whole snapshot or page. (c) is the alternative with a smaller cost and a stated residual; (a) leaves the most open; (e) and (f) are listed with the reasons against them.

**G20** (new, from PR4-4) is asked only if G8 (d) is taken: which named slots the check covers, and how a load stays inside N46's 5 s. Recommended (c), the slots that hold data and the two ends of every gap, which amends nothing and leaves one narrow case open (a differing slot strictly inside a gap). G20 (b), every named slot checked in chunks, leaves nothing open inside a record but adds a checking phase before `restore` and a rule at the load's deadline, an amendment of the approved text of architecture §4.10.5 and §4.10.6 that needs the user's explicit approval, and limits what a snapshot may name. G20 (a), the design as it stood after round 2, does not keep N46's bound for a cache with a long gap.

**G18** (new, from PR-2) touches no locked decision but decides the one case where a calendar day slot has no wall-clock start; recommended (b), which since round 2 is stated on starts (a slot whose G6 start is not before the next slot's start), so that `startOf` is strictly increasing for any zone data; in today's zone data that is exactly the slot of a skipped date. **G19** (new, from PR2-3) touches no locked decision either; it decides how slot starts in a zone are kept, recommended (c), shared tables per descriptor.

N9 needs no amendment with G13 (a) (the calendar code stays in `grid.ts`). G4 (a), G9 (a) and G10 (a) bring compile-time breaks for TypeScript code that does arithmetic on `interval` from `CacheConfig`, `ResolvedCacheConfig` or `FetchRequest`, or reads it from `Snapshot`, `DenseSegmentPayload`, `EncodedSnapshot` or `EncodedSegmentPayload`, fixed-grid code included, and a silent `[object Object]` where a fetcher stringifies `interval` (PR2-2); all allowed in a 0.x minor release and named for the release notes. G14 (a) depends on M7's N79 (`hello.features`), which the order of decision 62 builds first.
