Benchmark: tscache and three baselines

One workload, the same for every mode: a chart of one-minute candles opens on the newest screen (240 bars), scrolls back five screens, zooms out to four screens and back in, and returns to the newest screen. Then the market moves on by five bars and three tabs do the same at once. The tabs are same-origin iframes of this page, so tscache's tabs share one SharedWorker, as real tabs of one origin do.

  • No cache: every view fetches its range.
  • Per-tab memo: a Map per tab, keyed by the exact range.
  • TanStack Query (@tanstack/query-core): one QueryClient per tab, key [series, start, end], staleTime: Infinity.
  • tscache: one client per tab, all on one shared cache, which fetches only what it does not hold.

Every mode fetches through the same fetcher code and the same mock backend, with the same latency per page, and draws with the same uPlot chart. Each mode of each run starts empty (new tabs, a new tscache cache id), and the backend's counters are read as deltas. Time to chart runs from the read's start to the frame after setData returned. tscache's first connect, which starts the worker, is its own column and is inside the workload time.

Limits of this comparison
  • TanStack Query and the memo cache per tab and by exact key: they are not range-aware, so an overlapping or shifted range is a new fetch. That is the point of the comparison, not a misconfiguration.
  • The workload reads final history only. tscache refetches provisional (still-forming) bars on every read, which exact-key caches would serve stale; a live workload would add those fetches to tscache.
  • The three tabs are iframes on one main thread, so their timings share a thread that real tabs would not. Request, bar and byte counts do not depend on it.
  • The backend is a mock on the same machine: latency is simulated per page, and bandwidth is not limited.
